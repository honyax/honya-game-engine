# Day作成スキル

Day番号 XX(2桁ゼロ埋め)に対して、計画書 `docs/plans/DayXX.html` とリファレンスコード `reference/DayXX/` を作成する。
計画書は HTML で書く(下記「計画書の HTML の書き方」)。図と、理論を動かして確かめる実験台をページの中に置くため。

## 手順

1. `docs/roadmap.html` から該当Dayの内容(ゴール、Phase、事前に読む資料)を確認する。「次のDay」と言われた場合は `reference/` の最新Dayの次を対象にする
2. 前Dayの `reference/DayXX` を確認する(Day 1は新規作成)。前Dayが存在しない・ビルドが通らない場合は作業を止めてユーザーに報告する
3. 計画書を書く(手順 4〜7 のリファレンスを先に作り、数値を実測してから書いてもよい)。
   既存の計画書が `docs/plans/DayXX.md` として先行作成されている場合は、その内容を HTML に移して md は削除する。
   `docs/plans/DayXX.html` の構成:
   - **今日のゴール**(動くもの1行)
   - **事前に読む資料**(ロードマップ記載のもの。URL付き)
   - **理論の要点**(その日の実装に必要な理論を3〜7項目で解説。数式は必要最小限+直感的説明)
   - **前Dayからの差分概要**(新規/変更ファイルと役割)
   - **写経する順番**(下記「写経する順番の書き方」に従う)
   - **設計書**(Day 25 以降。下記「設計書の書き方」に従う)
   - **完成条件**(動作確認の手順と期待される見た目)
   - **改造課題**(2〜3個、難易度順。理解確認が目的)
4. `reference/DayXX/` を作成する。前Dayの完全コピーをベースに、その日の実装を追加。csprojは `DayXX.csproj` にリネーム
   - **名前空間は書き換えない**(Phase単位で固定。Day 1〜10 は `SoftwareRasterizer`)。Phaseをまたぐ最初のDay(11, 14)でだけ切り替える
   - csprojに `<AssemblyName>` は追加しない(ファイル名から決まる)
5. `dotnet format whitespace reference/DayXX/DayXX.csproj` で整形する。
   VSCodeが保存時に同じRoslynフォーマッタを走らせるので、先に通しておかないと
   ユーザーがファイルを開いて保存しただけで差分が出て写経の差分確認が濁る。
   `--verify-no-changes` を付けて差分ゼロになることまで確認する
6. `dotnet build reference/DayXX` でビルド確認。実行可能なら軽く動作確認もする。失敗したら修正してから完了とする
7. **計画書の「写経する順番」に漏れが無いか機械的に検算する**(下記参照)
8. **計画書の HTML を検証する**(下記「検証」)
9. `docs/roadmap.html` の該当Dayの Day セルを `<a href="plans/DayXX.html">XX</a>` にする(「状態」セルには触れない。「済」はユーザーの写経完了時に付ける)
10. 最後にユーザーへ報告: 実装内容の要約 / 写経時に読む順番(新規・変更ファイルの一覧) / 実験台の一覧 / 改造課題

## 写経する順番の書き方

写経は `git diff --no-index` ベースでユーザーが自力で進めるので、
**この一覧がユーザーの作業リストそのもの**になる。1ファイルでも漏れると、
そのファイルだけ写経されずビルドが通らない(あるいは差分が残る)。

- **前Dayから新規・変更になったファイルを1つ残らず載せる**。
  `Program.cs` や新規クラスのような主役だけでなく、
  **数行だけ足した既存ファイル**(例: Day 15 の `Shader.cs` に `SetVector2` を追加)や
  **csproj**(パッケージ追加時)、**シェーダ**、**コメントだけの変更**も対象
- 並べる順は**依存順**にする。あるファイルが使うメソッドは、そのファイルより前に足しておく
  (`Material.Apply()` が `Shader.SetVector4` を呼ぶなら `Shader.cs` を先に置く)。
  そうしないと写経の途中でビルドが通らない状態が生まれる
- コメントだけの変更は「コメントのみ。差分0にしたいなら合わせておく」と断り書きを添えて末尾に置く
- 素材(`assets/`)や、実行時に生成されるファイルは写経の対象外なので載せない

### 検算の手順

計画書を書き終えたら、思い出しで確認せず必ずコマンドで突き合わせる。

```
diff -rq -x bin -x obj reference/DayNN reference/DayXX
```

出力に並ぶファイル(csproj のリネーム分を除く)が、
すべて「写経する順番」に登場していることを確認する。
登場していないものがあれば、上のルールに従って追加する。

## 設計書の書き方

**Day 25 以降の計画書には「設計書」の章を置く**(場所は「前Dayからの差分概要」の直後、
「完成条件」の直前)。書くのは**その日の設計判断**だけにする。

- その日に足した層やクラスが、何に依存し何を知らないか(例: Day 43「`Physics/` が今日も何も知らないままであること」)
- 処理の順番そのものが設計になっている箇所と、**入れ替えると何が壊れるか**(例: Day 43「5段の順番」)
- **今日わざと残した歪み**と、直す時期の見当(例: Day 43「`B = -1` という分岐」→ Day 44 で `Collider` に切り出す)
- 試して分かったこと(例: Day 43「位置の補正を反復にしたこと」)

**エンジン全体の構成図・全フォルダのクラス図・1フレームの流れを、前Dayから引き継いで載せることはしない**
(Day 42 までの md の計画書ではやっていたが、毎回数千行になり、その日の話が埋もれた)。
`Program.cs` の行数のような、その日の主題と関係の薄い歪みの記録も載せない。

- **図だけ置かない**。図の下に「なぜその形なのか」「入れ替えると何が壊れるか」を必ず添える
- 過去Dayの要点を参照するときは `Day 42 の要点5` のように**どこを見ればよいかを書く**
- クラスや依存の話は**必ずコードから確かめて**書く。層をまたぐ依存はコメントに書かれた型名を拾って
  しまいやすいので、コメントを落としてから調べる

```
cd reference/DayXX
cat Physics/*.cs | sed -E 's#//.*$##' | grep -oE '\b(型名1|型名2|...)\b' | sort -u
```

## 計画書の HTML の書き方

**直近の Day の HTML(最初は `docs/plans/Day43.html`)をひな形にする**。見た目と部品の使い方を揃えるため。

### ページの骨組み

- `<link rel="stylesheet" href="../site/doc.css">` を読む。色・文字・表・コード・実験台の枠はすべてここにある。
  ページ側に `<style>` を書くのは、そのページにしかない部品だけ
- 左に目次(`aside.side`)、本文は `main.doc`。章は `<section class="part">` + `<h2 id="sN">`、節は `<h3 id="sN">`。
  目次は h2 と h3 から作る(幅が狭いときは `nav.toc-inline` が出る)
- ヘッダの `.meta` に `<a href="../roadmap.html">ロードマップへ戻る</a>` を置く
- 表・コード・引用は doc.css の既定のスタイルで書く(`div.table-wrap > table`、`div.code > pre > code`、`blockquote`)
- コード中の強調は `<strong>` で書く(md の `**` は使わない)

### 図

- **外部ライブラリ(mermaid 等)を使わない**。ブラウザでファイルを直接開いて、オフラインでも完結させる
- 構造の図はインライン SVG で描く。色は `var(--ink)` などのトークンで指定し、ダークテーマでも読めるようにする
- 処理の段の並び(例: 1ステップの5段)は、SVG より `ol.pipeline` のカード(番号・読む/書くもの・入れ替えると)のほうが読みやすい

### 実験台

**理論の要点のうち、パラメータを動かしたときの変化が主題のものには実験台を置く**
(例: Day 43 の積分法・撃力・クォータニオン・インパルス・反発係数・積み上げ)。
静止画や文章では「変化」そのものが伝わらないため。

- 枠は `<figure class="lab">`(`.lab-head` / `.stage` に canvas / `.controls` / `.readout`)。部品は `../site/lab.js` の `Lab`
  (`fit` `seg` `stat` `arrow` `animate` など)を使う
- **数値は reference と一致させる**。その日のアルゴリズムを JS に移すときは、式・順番・つまみ・既定値を C# と同じにし、
  計画書に書く数値(自己チェックの値など)が JS でも出ることを Node で確かめる
- その Day でしか使わない JS(物理の移植など)はページの `<script>` に書く。**2つ目の Day で同じものが要るようになったら**
  `docs/site/` へ移して両方から読む
- 実験台で見た現象を実機で再現できるよう、**実験台の操作と実機のキーの対応表**を完成条件の最後に置く
- `prefers-reduced-motion` のときは動かさず、結果の状態を描いておく

### 検証

- 本文の `<script>` を取り出して `node --check` で構文を確かめる
- `python -m http.server`(`docs/` で起動)経由でブラウザで開き、コンソールエラーが無いこと、
  実験台が動くこと、ロードマップからのリンクで開けることを確かめる。終わったらサーバとタブを閉じる
- ファイル出力に絵文字を使わない

## 注意

- コードには学習用の日本語コメントを丁寧に入れる(「何をしているか」より「なぜそうするか」)
- 1Dayの差分は写経1〜3時間程度(数百行以内)に収める。超えそうなら報告して分割(DayXXa/DayXXb等)を提案
- `work/` には触れない
- 共有素材が必要な場合は `assets/` に置き、入手元URLを計画書に記載する
