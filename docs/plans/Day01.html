Phase 0 / ロードマップ該当行: 「環境構築、ピクセルバッファを60fpsで画面表示」

今日のゴール

640x480のピクセル配列を毎フレームCPUで書き換え、それが60fpsでウィンドウに表示される。

これ以降のDay 2〜10でやること(線分、三角形、Zバッファ、テクスチャ、シェーディング)は、すべて「このピクセル配列の中身をどう決めるか」という話に還元される。今日はその器と、器を毎秒60回画面へ流し込む配管だけを作る。

理論の要点

1. フレームバッファ — すべての描画の出口

ソフトウェアラスタライザの出力先は Framebuffer.Pixels ただ1つしかない。GPUで言えばバックバッファに相当する。今後どんな高度な処理を書いても、最後は必ず「この配列の何番目に、どの色を入れるか」に落ちる。

配列は2次元 [y, x] ではなく1次元 [y * Width + x] にしている。メモリが連続していてキャッシュに乗りやすく、境界チェックも1回で済むため。以降のDayでも一貫してこの形を使う。

2. ピクセルのメモリ配置 — なぜ 0xAARRGGBB なのか

1ピクセルを int(32bit)1個で表し、値の並びを 0xAARRGGBB にしている。これをリトルエンディアンのメモリに置くと、バイト列は B, G, R, A の順に並ぶ。そしてこれは GDI+ の 32bpp フォーマットのメモリ配置とちょうど一致する。

つまり「見た目の16進表記(RRGGBB、人間に読みやすい)」と「GDI+が要求するバイト順(BGRA)」が、エンディアンのおかげで自動的に噛み合っている。この一致のおかげで、画面への転送は単なるメモリコピーだけで済み、ピクセルごとの並べ替え処理が一切要らない。

byte[] ではなく int[] にした理由も同じ流れで、インデックス計算に * 4 が要らず、1ピクセルの読み書きが1命令で済み、転送に使う Marshal.Copy が int[] を直接受け取れる。

3. LockBits と stride — マネージド配列を画面へ渡す

Bitmap の中身は GDI+ が管理するアンマネージドメモリで、C#の配列とは別世界にある。Bitmap.LockBits は「今からこのメモリを直接触るので動かさないでくれ」と宣言するAPIで、返ってくる BitmapData.Scan0 が生ポインタ、BitmapData.Stride が1行あたりの実バイト数。

Stride は 幅×4 とは限らない。 GDI+ は各行の先頭を4バイト境界に揃えるためパディングを入れることがある。32bppかつ幅640なら実際には Stride == 640*4 になるが、行単位でコピーして毎行 Stride ぶん進める書き方にしておけば、どんな幅でも壊れない。

LockBits したら必ず UnlockBits する。忘れるとビットマップが固定されたままになるため、途中で例外が出ても解放されるよう finally に置く。

4. ゲームループ — なぜ Application.Run を使わないのか

WinForms の標準である Application.Run(form) は「メッセージが来るまで待つ」イベント駆動のループ。ボタンを押したら反応するアプリならこれでよいが、ゲームは入力が無くても毎フレーム絵を更新したい。そこで自前の while ループを持ち、その中で Application.DoEvents() を呼んでメッセージ処理だけを借りる形にする。DoEvents を呼ばないとウィンドウが「応答なし」になる。

ちらつき(フリッカ)対策も必要になる。既定ではOSが「背景を塗る → こちらが描く」の2段階で描画するため、一瞬背景色が見えてチラつく。画面全体を毎フレーム自前で埋めるので背景塗りは完全に無駄であり、ControlStyles.Opaque | UserPaint | AllPaintingInWmPaint を立てて背景塗りを止める。

5. フレームレート制限 — VSyncが無い世界の話

GPUを使わないのでVSync(垂直同期)による自動的なフレーム制御が存在しない。放っておくと出せるだけフレームを出してCPUを100%使い切るので、自分で待つ必要がある。

ここには2つの罠がある。

罠1: 誤差の累積。 「今の時刻 + 16.67ms」を毎回計算すると、1フレームごとの微小な待ち誤差がそのまま積み上がり、平均フレームレートが目標より下がる。「前回の目標時刻 + 16.67ms」を積む(絶対時刻でスケジュールする)ことで誤差が累積しなくなる。

罠2: Thread.Sleep は当てにならない。 Windowsのタイマ分解能は既定で粗く、本Dayの実測では Thread.Sleep(1) が平均約4ms、最悪14ms眠っていた。目標時刻を飛び越してしまう。そこで「残りが十分あるうちだけ Sleep して CPU を他へ譲り、最後の数msはスピンウェイトで自分で数える」というハイブリッドにする。しきい値を 2ms → 5ms に変えるだけで実測 58.8fps → 59.9fps に改善した。

これは「正確さのためにCPUを燃やす」という割り切りで、ゲームループでは定番の判断。より真面目なタイムステップ設計は Day 19(固定タイムステップ+補間)で改めて扱う。

6. 高DPIと「1ピクセル = 1ピクセル」

Windowsのディスプレイスケーリングが125%や150%だと、DPI非対応アプリはOSに画面を引き伸ばされ、フレームバッファの1ピクセルが画面の1ピクセルに対応しなくなる(絵がぼやける)。ソフトウェアラスタライザでこれが起きると、そもそも何を描いたのか確認できない。

対策は3点セット。

  • csproj で <ApplicationHighDpiMode>PerMonitorV2</ApplicationHighDpiMode> を宣言し、スケーリングを自前の責任にする
  • AutoScaleMode = AutoScaleMode.None でWinFormsの自動スケーリングを止める
  • Graphics.DrawImage には転送先の矩形を明示的に渡す。DrawImage(bitmap, 0, 0) のオーバーロードはビットマップのDPIと描画先のDPIの比で勝手に拡大縮小してしまう(有名な罠)

7. 60fpsの時間予算 — 実測値

1フレームの持ち時間は 1/60秒 = 約16.67ms。640x480 = 307,200ピクセルを毎フレーム埋めるので、単純計算で1ピクセルあたり約54ns。この予算感がPhase 1全体の前提になる。

本Dayのリファレンスを Release ビルドで実測した内訳(平均):

処理時間備考
Render(全ピクセル書き込み)約0.8ms307,200ピクセル。まだ十分軽い
フレームバッファ → Bitmap のコピー約0.13ms1.2MBのメモリコピー。要点2の設計が効いている
Graphics.DrawImage(画面へ転送)約6.0msここが最大のコスト
空き約9.7msDay 2以降の描画処理に使える予算

つまり一番重いのは自分の描画ではなくGDI+の画面転送で、これはPhase 1の間ずっと固定費として乗る。GDI+の品質設定(CompositingMode.SourceCopy 等)を変えても改善しないことは実測で確認済み。この固定費が消えるのは Phase 2 でGPUに移ってからになる。

完成条件

dotnet run --project reference/Day01

以下がすべて満たされていれば完成。

  1. 640x480 のウィンドウが画面中央に出る(リサイズ不可)
  2. 背景が 左→右で赤が濃くなり、上→下で緑が濃くなるグラデーションで、さらに青成分が約3.1秒周期で明滅する
  3. 48x48 の白い四角が画面内を斜めに動き、四辺で跳ね返る。カクつきや飛びが無い
  4. タイトルバーに Day01 - Framebuffer 59.x fps のようなFPSが表示され、59〜61の範囲にいる
  5. Esc キーまたは閉じるボタンで終了する
  6. ウィンドウの中身がちらつかない(背景色が一瞬見える現象が起きない)

うまくいかないときの確認ポイント:

  • 絵の色がおかしい(赤と青が逆) → Framebuffer.Rgb のビットシフト位置。要点2を読み直す
  • 絵が斜めにずれる/縞になる → Stride を使わず 幅*4 で進めている。要点3
  • 絵がぼやける、ウィンドウが640x480でない → 高DPI設定の3点セット。要点6
  • FPSが55前後までしか出ない → WaitUntil のスピンしきい値。要点5の罠2
  • FPSが安定しない、だんだん遅れる → 「今の時刻+16.67ms」で待っている。要点5の罠1
  • ちらつく → SetStyle の3フラグ。要点4
  • ウィンドウが応答なしになる → ループ内で Application.DoEvents() を呼んでいない

改造課題

課題1(易): 解像度を変えて負荷の正体を掴む

Program.cs の Width / Height を 320x240 と 1280x720 に変えて、それぞれのFPSを測る。

  • ピクセル数は 320x240 で約1/4、1280x720 で約3倍になる。FPSはその比率どおりに変化するか?
  • しなかったとしたら、時間を食っているのはどの処理か? 要点7の表を見て考える
  • Framebuffer と GameWindow を解像度べた書きせずに書けているか、この機会に確認する

課題2(中): SetPixel だけで図形を描く

FillRect を使わずに、Framebuffer.SetPixel の呼び出しだけで以下を描く。

  • 画面の外周1ピクセルを赤い枠で囲む
  • 画面中央に、縦横それぞれ画面いっぱいの白い十字線を引く

さらに余力があれば、任意の2点を結ぶ斜めの線を自分なりのやり方で引いてみる。おそらく素直に書くと点が飛び飛びになるか、遅くなるはず。「なぜ素直に書くとうまくいかないのか」を体感しておくと、Day 2 の Bresenham のありがたみが桁違いに分かる(この体感がこの課題の目的)。

課題3(難): フレームループを計測して壊す

GameWindow.Run に Stopwatch を仕込み、1フレームの内訳(Render / Present / 待ち時間)を計測してタイトルバーかファイルに出す。そのうえで:

  1. SpinThresholdSeconds を 0.002 に戻すとFPSがいくつになるか。要点5の実測を再現できるか
  2. WaitUntil の呼び出し自体をやめると何fps出るか(= この構成の上限値)
  3. 「今の時刻 + 16.67ms」で待つ実装に書き換えると、FPSがどうずれるか

3つとも「壊してみて初めて、元の実装がなぜその形なのかが分かる」タイプの確認。測り終わったら元に戻しておくこと。
