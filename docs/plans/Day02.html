Phase 1 / ロードマップ該当行: 「線分描画(Bresenham)」

今日のゴール

任意の2点を結ぶ線分をピクセル単位で描けるようにして、方眼・放射線・星型・リサージュ曲線が60fpsで動くのを見る。

Day 1 で作ったのは「ピクセル配列を画面に出す配管」だった。今日からは中身、つまり「何色をどこに置くか」を決めるアルゴリズムの話に入る。その最初の一歩が線分で、ここで出てくる「連続的な図形を離散的なピクセルに落とす」という考え方が、Day 3 の三角形、Day 7 のZバッファ、Day 8 のテクスチャまでずっと同じ形で効いてくる。

事前に読む資料

  • ゲームグラフィックス特論 A-1 レンダリングパイプライン — 今日の必読。Phase 1 全体の見取り図。「頂点をどう画面座標にするか」と「画面座標をどうピクセルに塗るか」が分かれていることを掴んでおくと、Day 2〜10 の各回が全体のどこにいるのか迷わなくなる
  • tinyrenderer Lesson 1: Bresenham の線分描画 —素朴な実装から順に改良してBresenhamへ辿り着く流れが丁寧。C++だが読み替えは容易
  • 西川善司「ゲーム制作者になるための3Dグラフィックス技術 改訂3版」Ch2(概念とレンダリングパイプライン) — 特論A-1と併読
  • (任意)Alois Zingl: A Rasterizing Algorithm for Drawing Curves —本Dayで使う「8方向を1つのループで書く一般形」の出典。円・楕円・ベジエへの拡張も同じ枠組みで載っている

理論の要点

1. ラスタライズ = 連続的な図形を、格子の上の点に決め直す作業

数学の線分は太さがなく、どこまでも細かい実数の座標を持つ。一方フレームバッファは整数座標の格子でしかない。だから線を描くというのは、実際には「格子のどのマス目を塗れば、その線に一番近く見えるか」を決める問題になる。

ここで決めることは2つある。

  • どのピクセルを塗るか(今日の主題)
  • 塗るピクセルをどんな色にするか(Day 4 の属性補間、Day 8 のテクスチャ、Day 9 のシェーディング)

この2つが分かれている構造は、この先ずっと変わらない。三角形の塗りつぶしも「どのピクセルが三角形の内側か」+「そのピクセルの色は何か」の2段構えになる。

2. 素直な発想 = DDA。ただし「長い方の軸」を主軸にする

線分 (x0,y0)-(x1,y1) の傾きは dy/dx。x を1進めるたびに y を dy/dx だけ足すのが一番素直な実装で、DDA(Digital Differential Analyzer)と呼ばれる。

ただしこれには注意が要る。傾きが急な線(|dy| > |dx|)で x を主軸にすると、x が1進むあいだに y が2以上飛んでしまい、線に穴が空く。

text
x を主軸にした急な線       長い方(y)を主軸にした同じ線
  . o .                      . o .
  . . .   <- 穴              . o .
  o . .                      o . .
  . . .   <- 穴              o . .

なので原則は「長い方の軸を1ずつ進め、短い方は進むか留まるかを選ぶ」。この原則は Bresenham でもまったく同じで、両者の違いは「短い方を進めるかどうかの判定を、浮動小数でやるか整数でやるか」だけとも言える。

3. Bresenham = 誤差を整数で持ち回る

DDA が毎ピクセル浮動小数の加算と丸めをするのに対して、Bresenham は「理想の直線から今どれだけ縦にズレているか」を誤差として持ち回り、そのズレが半ピクセルを超えたら短い軸を1進める。

素直に書くと誤差は dy/dx という分数になるが、全体を dx 倍しておけば分母が消えて整数だけで済む。さらに「0.5 と比べる」判定も、両辺を2倍すれば小数が消える。だから実装に出てくるのは err * 2 という一見唐突な式で、これは分数と小数を消すために全体をスケールした結果でしかない。

この「割りたくないので全体に分母を掛けておく」「0.5と比べたくないので2倍する」という手口は、ラスタライザ全体で何度も出てくる定石。Day 3 のエッジ関数でも同じことをする。

4. 8オクタント問題と、それを消す一般形

線の向きは「右/左」×「上/下」×「緩い/急」で8通り(8オクタント)あり、素朴に書くと場合分けだらけになる。本Dayの実装はこれを次の2手で消している。

  • dx を正、dy を負の絶対値にそろえ、進む向きは sx / sy(±1)に追い出す
  • x 方向と y 方向の判定を同じ err 1つで見る(両方成立したら斜めに1歩進む = 45度に近い線)
csharp
int dx =  Math.Abs(x1 - x0);
int dy = -Math.Abs(y1 - y0);   // 符号を反転させておくのが定石
int sx = x0 < x1 ? 1 : -1;
int sy = y0 < y1 ? 1 : -1;
int err = dx + dy;

while (true)
{
    SetPixel(x0, y0, color);
    if (x0 == x1 && y0 == y1) break;   // 終点も塗ってから抜ける

    int e2 = err * 2;
    if (e2 >= dy) { err += dy; x0 += sx; }
    if (e2 <= dx) { err += dx; y0 += sy; }
}

これで8方向すべてが1つのループで描けるのが一般形のありがたみ。水平線(dy = 0)と垂直線(dx = 0)も特別扱いなしにそのまま通る。本Dayのデモで方眼を描いているのは見た目のためだけでなく、この退化ケースの動作確認を兼ねている。

5. 実測1: DDA と Bresenham は、完全には一致しない

「どちらも同じ線を描くのだから結果は同じはず」と思いたくなるが、実際は違う。本Dayの実装で 23,600本(全方向 + ランダム)を描いて1ピクセルずつ比べた結果:

比較結果が違う線違うピクセル数
Bresenham vs DDA4,094本(17.3%)29,030 px(総描画 6,120,075 px の 0.474%)

線の17%で差が出るが、ずれるのは1本あたり数ピクセル。目で見て分かる差ではない。

ずれの原因は DDA 側にある。 例えば (320,240)-(620,241) は x=470 のちょうど中間でy が 240.5 になる引き分けのケースだが、DDA は stepY = 1/300 を150回足し込むため累積誤差で 240.49999… に着地し、四捨五入で 240 に落ちる。整数だけで進む Bresenham は誤差が積もらないので、厳密計算どおり 241 を選ぶ。

「誤差が累積する」という言葉の意味が、そのまま絵の1ピクセルとして出てくる場所で、Bresenham を使う理由の本命はここ。速度ではなく、同じ入力なら必ず同じ結果になることにある。

6. 実測2: 速度差は、測る場所によって「30%」にも「1%」にもなる

同じ23,600本を20回ずつ描いた実測(Release / .NET 10):

測り方BresenhamDDA差
座標計算のみ(SetPixelを呼ばない)0.40〜0.44 us/本0.53〜0.65 us/本Bresenhamが25〜30%速い
実際に描く(SetPixelあり)0.552 us/本 (2.13 ns/px)0.560 us/本 (2.16 ns/px)ほぼ差なし(1〜2%)

アルゴリズム単体では確かに Bresenham が速い。しかし実際に描くと差がほとんど消える。理由は、支配的なコストが座標計算ではなく SetPixel(範囲チェック + メモリ書き込み)側にあるから。1ピクセル約2.1nsのうち大半をそちらが食っているので、計算を3割速くしても全体は動かない。

これは「ボトルネックでない場所を最適化しても全体は速くならない」という、プロファイリングの一番基本的な教訓そのもの。Bresenham を採用する理由は現代では速度ではなく、整数演算の決定性と、この考え方が後々まで応用が効くことだと理解しておくとよい。

なお、この「主軸を1ずつ進め、従軸を誤差で選ぶ」構造は、この先三角形のスキャンライン走査、ボクセルのレイ走査(DDA traversal)、ミップマップの選択などに姿を変えて何度も再登場する。

7. 画面外は描かないほうがいい(が、今日はまだやらない)

SetPixel が範囲外を黙って捨てるので、画面外に伸びる線を渡しても落ちはしない。ただしループ自体は画面外でも回り続けるので、長さ5000ピクセルの線を渡せば1ピクセルも見えないのに5000回ループする。

正しい対処は、描く前に線分を画面の矩形で切り詰めること(Cohen–Sutherland クリッピング)。本Dayのデモは放射線の3本に1本をわざと画面外まで伸ばして、この無駄を実演している。実装は改造課題2に回した。Day 10 でやる「視錐台クリッピング」は次元が上がるだけで発想は同じなので、ここで2Dの形を手で書いておくと後が楽になる。

改造課題

課題1(易): 線の本数と時間の関係を測る

FanSpokes を 36 → 360 に、LissajousSegments を 160 → 1600 に増やして、タイトルバーの render 時間がどう変わるか測る。

  • 線の本数を10倍にしたら、時間も10倍になったか?
  • ならなかったとしたら、増えているのは「線の本数」ではなく何か(ヒント: 総ピクセル数)
  • Space で DDA に切り替えると時間はどれだけ増えるか。 ほとんど変わらないはず。なぜ変わらないのかを要点6の表を見て自分の言葉で説明できれば、この課題は達成

課題2(中): Cohen–Sutherland で線分をクリッピングする

画面外へ伸びる線を、描く前に画面矩形で切り詰める。

  1. 点の位置を画面に対して4bitのコード(上/下/左/右)で表す ComputeOutCode を書く
  2. 両端のコードが両方0なら完全に画面内(そのまま描く)、AND が0でなければ完全に画面外(何も描かない)、それ以外は交点を求めて端点を詰める、を繰り返す
  3. DrawFan の radius を 340 → 5000 に変えても render 時間が変わらないことを確認する

クリッピングを入れると SetPixel の範囲チェックが不要になる場面が増える(= 速くなる)。ただしチェックを外すのはクリッピングが完璧に正しいときだけで、1つでも漏れがあると配列外アクセスで即クラッシュする。この緊張感も含めて体験しておくとよい。Day 10 の視錐台クリッピングは、これの次元が上がっただけのもの。

課題3(難): 始点と終点を入れ替えると、絵が変わることを確かめる

同じ線分を DrawLine(A, B) と DrawLine(B, A) で描き、結果を1ピクセルずつ比較する小さな検証コードを書く。

実測では 23,600本のうち 7,905本(33.5%)で結果が変わる(差分は合計 60,606 px)。つまり Bresenham の一般形は始終点の入れ替えに対して対称ではない。

  1. なぜ対称でないのか。誤差の初期値 err = dx + dy と、理想の直線がピクセル中心のちょうど中間を通る「引き分け」のケースを考える
  2. どうすれば対称にできるか。一番安直な手は「常に x が小さい方を始点にする」正規化だが、これで本当に全部のケースが対称になるか?(垂直線はどうする?)
  3. そもそも対称であるべきか。三角形を3辺の線で描くとき、隣り合う三角形が共有する辺を互いに逆向きに描くと、辺が1ピクセルずれて隙間が見えることがある。Day 3 以降の「隙間なく敷き詰める」話に直結する問題なので、ここで一度考えておく価値がある

余力があれば、太さのある線(平行に数本引く / 円を掃く)か、アンチエイリアスされた線(Xiaolin Wu のアルゴリズム。カバー率で色を薄める)にも挑戦してみるとよい。後者は「1ピクセルを塗る/塗らないの2値ではなく、どれだけ覆っているかで濃さを決める」という、Day 8 のバイリニア補間や後のMSAAに繋がる発想の入口になる。
