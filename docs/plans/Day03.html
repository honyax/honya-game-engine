Phase 1 / ロードマップ該当行: 「三角形の塗りつぶし(エッジ関数)」

今日のゴール

任意の3点で指定した三角形を塗りつぶせるようにして、隣り合う三角形の継ぎ目が二重に塗られないこと(top-left rule)を目で確かめる。

線から面に進む日。三角形はこの先すべての3D描画の唯一の単位になる。モデルも地形もキャラクターも、最後は全部三角形に分解されてこの関数を通る。だからここで書く数十行は、Day 10 まで(そしてGPUに移った後も概念として)ずっと効き続ける。

事前に読む資料

  • ゲームグラフィックス特論 A-1 レンダリングパイプライン —Day 2 に続いて再度。今日は特に「ラスタライズ」の段が何をする工程なのかを意識して読む
  • Fabian Giesen: Optimizing the basic rasterizer —本Dayの実装(エッジ関数 + バウンディングボックス + top-left rule)の元ネタ。シリーズ全体(A trip through the Graphics Pipeline)はGPUの中身の解説として今後も何度も戻ってくる
  • Scratchapixel: Rasterization - a Practical Implementation —エッジ関数とバリセントリック座標の関係(Day 4 の予習にもなる)
  • 西川善司「ゲーム制作者になるための3Dグラフィックス技術 改訂3版」Ch2

理論の要点

1. 三角形だけが特別扱いされる理由

多角形一般ではなく三角形なのは、都合のよい性質が揃っているから。

  • 必ず平面上にある。4点以上だとねじれる可能性があり、「面の向き」が一意に決まらない
  • 必ず凸。凹んだ形は内外判定が面倒(交差回数を数える等)になるが、三角形なら「3本の辺すべてに対して内側」で済む
  • 3頂点の値から内部の任意の点の値を一意に決められる(Day 4 のバリセントリック座標)

だからモデリングツールが四角形ポリゴンで作られていても、描画の直前には必ず三角形に分割される。ソフトウェアラスタライザでもGPUでも事情は同じ。

2. エッジ関数 = 2次元の外積。符号で内外、大きさで面積

線分 a→b と点 p に対して次を計算する。

E(a, b, p) = (b.x - a.x) * (p.y - a.y) - (b.y - a.y) * (p.x - a.x)

これは2次元の外積 (b - a) × (p - a) で、2つの意味を同時に持つ。

  • 符号 … p が辺 a→b のどちら側にあるか(今日使う)
  • 大きさ … a, b, p が張る平行四辺形の符号付き面積 = 三角形の面積の2倍(Day 4 で使う)

三角形の3辺それぞれについてこれを計算し、3つとも同じ符号なら点は内側。今日は内外判定にしか使わないが、内外判定のために計算した値が、明日そのまま補間の重みになる。無駄な計算を1つもしていない、という点でこの方法は美しい。

なお画面座標は y が下向きなので、紙の上の数学とは符号の向きが逆になる。a=(0,0), b=(1,0), p=(0,1) で E = +1、つまり「辺 a→b より画面の下側が正」。

3. 巻き方向(ワインディング)をそろえる

3頂点を渡す順序が時計回りか反時計回りかで、3つのエッジ関数の符号が一斉に反転する。判定を「3つとも非負」の一択にするため、本Dayでは

csharp
int area = EdgeFunction(x0, y0, x1, y1, x2, y2);
if (area == 0) return;                              // 面積0(3点が一直線)
if (area < 0) (x1, y1, x2, y2) = (x2, y2, x1, y1);  // 負なら頂点を入れ替える

として、負なら頂点を2つ入れ替えてしまう。

ここで捨てている符号は、Day 10 で意味を持つ。 三角形を裏から見ると巻き方向が反転するので、この符号は「今その面を表から見ているか裏から見ているか」の情報そのもの。Day 10 の背面カリングは、入れ替える代わりに「負なら描かない」と判断するだけで実装できる。

4. top-left rule — 継ぎ目を二重に塗らないための取り決め

辺の真上に乗ったピクセル(エッジ関数がちょうど0)を塗るべきか。隣り合う2つの三角形は辺を共有しているので、両方が「自分の内側だ」と答えるとそのピクセルは2回塗られる。逆に両方が「外側だ」と答えると隙間が空く。

解決は「辺の種類で機械的に決める」こと。上の辺と左の辺なら塗る、下の辺と右の辺なら塗らない。どの辺も必ずどちらか一方の三角形にとってだけ「上または左」になるので、共有ピクセルはちょうど1回だけ塗られる。

本Dayの座標系(巻き方向を正に正規化済み、y下向き)では次の形になる。

csharp
private static bool IsTopLeft(int ax, int ay, int bx, int by)
    => (ay == by && bx > ax) || by < ay;

実装はバイアスとして効かせる。top-left な辺は 0、そうでない辺は -1 を足してから「非負なら内側」と判定すれば、ちょうど0のピクセルが後者では弾かれる。

実測(本Dayの実装で検証):

図形ルールONルールOFF
正方形を三角形2枚に分割6,400 px すべて1回6,561 px 中 81 px が2回
円盤(ファン32枚)9,512 px すべて1回416 px が2回、1 px が3回
格子8x8(三角形128枚)10,816 px すべて1回2,114 px が2回、77 px が3回以上

ONのとき正方形がぴったり 6,400 = 80×80 になっている点に注目。重なりも隙間もなく平面を敷き詰められているということで、これがラスタライザに求められる性質。

不透明な単色で塗っている限り二重描画は見えない。しかし半透明合成では色が濃くなり、Day 7 のZバッファでは深度の書き込み回数が変わり、加算合成のエフェクトでは境界線が光る。Day 2 の課題3で考えた「共有辺が1ピクセルずれると隙間が見える」問題の、正式な解答がこれ。

5. バウンディングボックス走査と、その原理的な無駄

画面全体(307,200 px)を走査するのは論外なので、3頂点を囲む矩形の中だけを見る。ただし矩形の中で実際に三角形の内側なのは一部だけで、残りは判定して捨てるだけの無駄になる。

実測(本Dayのデモ1フレーム):

図形判定したピクセル塗ったピクセル無駄
単体の三角形23,54210,94053.5%
継ぎ目テスト(50枚)54,45025,60053.0%
円盤(64枚・細長い)284,70836,62687.1%
1フレーム合計362,70073,16679.8%

約50%の無駄は原理的なもので、三角形の面積はどうやっても外接矩形の半分を超えられない。問題は細長い三角形で、円盤の細い扇形では87%が捨てられている。「三角形が細長いほどラスタライザは効率が落ちる」というのは実機でも同じ傾向で、モデルの三角形はなるべく正三角形に近い方がよい、と言われる理由の一つ。

Day 3 の render 時間 1.31 ms を判定ピクセル数で割ると 1判定あたり約3.6ns。Day 2 の線分が1ピクセル約2.1nsだったので、エッジ関数3本ぶんの上乗せが見えている。

6. 面を塗ることは、線を引くこととコストの桁が違う

Day 2 は236本の線で 0.17 ms、Day 3 は115枚の三角形で 1.31 ms。枚数は半分以下なのに時間は約8倍になっている。

線のコストは長さ(周囲長)に比例するが、面のコストは面積に比例するため。半径 r の円を線で描けば 2πr ピクセルだが、塗れば πr² ピクセルになる。r = 108 の円盤なら 679 px 対 36,600 px で、54倍の差になる。

この「塗るピクセル数がすべてを決める」という感覚は、この先ずっと効いてくる。Day 7 のZバッファで「見えない部分を塗る無駄(オーバードロー)」を潰したくなるのも、現代のGPUがピクセルシェーダのコストを気にするのも、根っこは同じ話。

改造課題

課題1(易): 三角形の性質を壊してみる

  1. FillTriangle の巻き方向の正規化(if (area < 0) の行)をコメントアウトして実行する。回転する三角形と円盤がどうなるか。なぜそうなるかを説明できるか
  2. area == 0 の早期リターンを消すとどうなるか。3点が一直線に並ぶ瞬間(DrawSingleTriangle は回転するので必ず通る)に何が起きるか
  3. DrawDisc の DiscTriangles を 64 → 512 にする。render 時間はどれだけ増えるか。塗るピクセル数はほぼ変わらないのに時間が増えるはず。その差は何のコストか

課題2(中): エッジ関数を差分で計算する(インクリメンタル化)

現在は1ピクセルごとにエッジ関数を3本フルに計算しているが、これは無駄が多い。エッジ関数は x, y の1次式なので、隣のピクセルへ移るときの増分は定数になる。

E(x + 1, y) - E(x, y) = -(by - ay)     // x方向の増分
E(x, y + 1) - E(x, y) =  (bx - ax)     // y方向の増分

つまり行の先頭で1回だけ計算し、あとは加算だけで進める書き換えができる。

  1. 上の性質を式で確かめる(エッジ関数の定義に代入するだけ)
  2. 走査ループを「行頭で初期値を計算、内側は w0 += dw0dx だけ」に書き換える
  3. render 時間がどれだけ改善するか測る。期待するほど速くならない可能性が高いので、そのときは Day 2 の要点6(支配的なコストはどこか)を思い出して考える

これはGPUのラスタライザが実際にやっていることでもある(さらに複数ピクセルを同時に判定する)。

課題3(難): 塗り残しと重なりを自分で検証する

「重なりも隙間もなく敷き詰められる」ことを、目視ではなくコードで確かめる。

  1. 画面と同じ大きさの int[] カウンタを用意し、FillTriangle が塗るたびに +1 する(AdditiveBlend を参考にするか、専用のデバッグモードを足す)
  2. 適当なポリゴン(格子、円盤、ランダムな三角形分割)を描いたあと、カウンタが2以上のピクセルが0個であることを確認する
  3. UseTopLeftRule = false にすると何ピクセルが2以上になるか数える。本Dayの実測値(格子8x8で2,114 px)と近い数字になるか

さらに余力があれば: 頂点が整数でなくなったらどうなるかを考えてみる。今日の実装は頂点も走査点も整数だが、Day 6 で変換行列を通すと頂点は実数になる。そのとき「ピクセルの中心」をどこにするか(整数位置か、+0.5 か)で、top-left rule の判定も変わってくる。Day 5〜6 でこの問題に正面から向き合うことになる。
