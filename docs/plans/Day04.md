# Day 04: バリセントリック座標と属性補間

Phase 1 / ロードマップ該当行: 「バリセントリック座標と属性補間」

## 今日のゴール

3頂点に別々の色を持たせると、三角形の内部がその3色で滑らかに混ざる。
さらに、補間した値を色以外(テクスチャ座標)として使えることを確かめる。

Day 3 で「どのピクセルを塗るか」は解けた。今日は残りの半分、
**「そのピクセルの値をいくつにするか」**を解く。しかも Day 3 で内外判定のために
計算した数値をそのまま使い回すだけで解ける、というのが今日の気持ちのよいところ。

## 理論の要点

### 1. バリセントリック座標 = 「3頂点をどの割合で混ぜたか」

三角形の内部の任意の点 P は、3頂点 V0, V1, V2 の**重み付き平均**として必ず書ける。

```
P = λ0 * V0 + λ1 * V1 + λ2 * V2      ただし λ0 + λ1 + λ2 = 1、すべて 0 以上
```

この (λ0, λ1, λ2) がバリセントリック座標(重心座標)。名前の由来は物理の重心で、
「3頂点にそれぞれ λ の重さの錘を置いたとき、釣り合う点が P」という意味になる。

重要なのは、**この重みが位置だけでなく、あらゆる属性に使える**こと。

```
Pの色 = λ0 * V0の色 + λ1 * V1の色 + λ2 * V2の色
PのUV = λ0 * V0のUV + λ1 * V1のUV + λ2 * V2のUV
Pの法線 = λ0 * V0の法線 + λ1 * V1の法線 + λ2 * V2の法線
```

式の形は完全に同じ。だからラスタライザは属性の中身を知る必要がなく、
「頂点が持っている数値を、重みで混ぜて配る」だけの機械になれる。
Day 8 でUVが、Day 9 で法線が増えても、このコードは1行も変わらない。

### 2. 重みの正体は面積比 — つまりエッジ関数そのもの

λ0 は「頂点0の向かい側の辺と点Pが作る三角形の面積 ÷ 全体の面積」に等しい。

```
        V0
       / | \
      /  |  \          λ0 = (P,V1,V2 の面積) / (V0,V1,V2 の面積)
     /   P   \         P が V0 に近いほど、この面積は大きくなる
    /  /   \  \
   V1---------V2
```

そして Day 3 で書いたエッジ関数は、まさにこの面積の2倍を返していた。
**内外判定のために計算した w0, w1, w2 を、全体の面積で割るだけで重みになる。**

```csharp
float invArea = 1.0f / area;   // 三角形につき1回だけ割り算する
...
float l0 = w0 * invArea;       // ピクセルごとは掛け算だけ
float l1 = w1 * invArea;
float l2 = w2 * invArea;
```

Day 3 の実装が最初からこの形だったのは、この日のためだった。
スキャンライン方式(辺に沿って左右の端点を追う古典的な手法)だと、
内外判定と属性補間を別々に管理する必要があって、こう素直にはいかない。

**実測での検算**: 三角形の全ピクセルで λ0 + λ1 + λ2 を計算したところ、
1.0 との誤差は**厳密に0**(整数で計算してから1回だけ割っているため)。
3頂点に赤・緑・青を置いたときの重心の色は **(85, 85, 85)** = 255/3 ちょうどになる。

### 3. 内外判定にはバイアス、補間には生の値

top-left rule のバイアス(Day 3)は、辺の上のピクセルを塗るかどうかを決めるための ±1 でしかない。
これを重みの計算に混ぜてはいけない。

```csharp
int w0 = EdgeFunction(...);   // 生の値
...
if (((w0 + bias0) | (w1 + bias1) | (w2 + bias2)) < 0) continue;  // 判定はバイアス付き
float l0 = w0 * invArea;                                          // 補間は生の値
```

混ぜると三角形の縁で色がわずかにずれる。1/area 程度の微小な誤差なので画面では気づきにくいが、
Day 8 でUVに使うとテクスチャの端が1テクセルずれる形で表面化する。
**「同じ数字でも用途によって使い分ける」**必要がある例。

### 4. 色は float で持つ

`Vertex` の色を byte(0〜255)ではなく float(0.0〜1.0)にしている。

- 補間の途中で丸めが入らない
- Day 9 で「明るさを掛ける」計算が自然に書ける(0.5倍 = 0.5を掛けるだけ)
- 1.0 を超える値を一時的に持てる。光を足し合わせると簡単に超える

**byte に落とすのは画面へ書き込む最後の1回だけ**、というのが原則。
GPUのシェーダーが色を float で扱うのも同じ理由で、
「1.0 を超えた分をどうするか」がトーンマッピング(Day 31)の話になる。

### 5. 補間した値を「色以外」に使う — シェーダーの発想

今日のデモの2つ目は、頂点1と頂点2に (1,0) と (0,1) を持たせて補間し、
その値を整数化して偶奇で色を変えている。結果は市松模様になる。

つまり補間された値を**色として使わず、模様を引く鍵として使っている**。
これが Day 8 のテクスチャマッピングそのもので、違いは
「模様を計算で作るか、画像から読むか」しかない。

この分離をコードにするため、`PixelShader` デリゲートを用意した。

```csharp
internal delegate int PixelShader(float a0, float a1, float a2);
```

ラスタライザの責任は「どのピクセルか」と「そこでの属性値はいくつか」まで。
**色をどう決めるかは呼び出し側に委ねる。** GPUがシェーダーをプログラマブルにしたのは、
まさにこの境界に「差し替え可能な穴」を開けたということだった。

### 6. 実測 — デリゲート呼び出しより、float→byte 変換のほうが高かった

640x480に収まる大きな三角形1枚を200回描いた実測(Release / 最良値):

| 描き方 | 時間 |
|---|---|
| 頂点カラー補間(`Framebuffer.Rgb(float,float,float)` で色を作る) | 1.439 ms/枚 |
| シェーダ経由(デリゲート呼び出し + 市松判定) | **1.148 ms/枚** |

**デリゲートを挟んだほうが速い。** 直感に反するが、理由は単純で、
`Rgb(float,float,float)` が3チャンネル分のクランプと丸めをしているのに対し、
市松シェーダは2つの整数化と1回のビット判定で色を返しているから。
**デリゲート1回の呼び出しコストより、float→byte 変換3回のほうが重かった**ということ。

Day 2 の「速度差は測る場所で変わる」に続き、
**思い込みで最適化の当たりをつけない**という教訓がまた出てきた形になる。

なお1フレーム全体の render 時間は Day 3 の 1.31 ms(115枚)から
Day 4 は 1.63 ms(66枚)に増えている。枚数はほぼ半分なのに時間は増えた。
1ピクセルあたりの仕事が「単色を書く」から「重み3つ + 属性3つ + 変換」に増えたため。

### 7. 頂点を共有すると継ぎ目が消える

3つ目のデモの円盤は、Day 3 とまったく同じ三角形64枚。違いは
**隣り合う扇形が縁の頂点色を共有している**ことだけ。

Day 3 では扇形1枚が単色だったので色の段差が見えたが、今日は境界で色が連続するので
継ぎ目が完全に消え、なめらかな円盤に見える。三角形の枚数は1枚も増えていない。

これは Day 9 のグーローシェーディングと原理的にまったく同じこと。
「頂点でだけ計算して、内部は補間で誤魔化す」という手抜きが、
なぜあれほど効果的なのかがここで体感できる。

うまくいかないときの確認ポイント:

- **色が頂点と対応していない/回転で色が入れ替わる** → 巻き方向の正規化のとき、
  位置だけ入れ替えて色を入れ替えていない。`Vertex` ごと交換すること
- **三角形の縁だけ色がおかしい** → 補間にバイアス付きの w を使っている。要点3
- **重心が灰色にならない** → `invArea` の計算。`area` を正に正規化した後の値を使っているか
- **色が飛び飛び(バンディング)になる** → 色を byte で補間している。float で持つこと
- **市松模様が出ない/全面が単色** → シェーダに渡る属性の順序。
  `Vertex` の R を U、G を V として使っている点に注意
- **円盤に継ぎ目が見える** → 隣り合う三角形で縁の頂点色が一致していない。
  `i / DiscTriangles` と `(i+1) / DiscTriangles` が次の三角形の値と揃うか確認

## 改造課題

### 課題1(易): バリセントリック座標を直接見る

`DrawGradientTriangle` の頂点色を (1,0,0), (0,1,0), (0,0,1) にしたまま、
シェーダを渡して次を表示してみる。

1. `λ0` だけをグレースケールで表示する(頂点0で白、向かいの辺で黒)
2. `λ0, λ1, λ2` のうち**最小のもの**をグレースケールで表示する。
   何が見えるか(ヒント: 辺からの距離)。これは輪郭線を描く安直な方法になる
3. `λ` のどれかが 0.5 に近いピクセルだけ色を変える。三角形の中に何が現れるか

### 課題2(中): 属性を増やす

`Vertex` に4つ目の属性(例えば `A`)を足し、ラスタライザで一緒に補間する。

1. `Vertex` にフィールドを追加し、`FillTriangle` の補間を1行増やす
2. `PixelShader` を4引数に変更する
3. 使い道の例: 4つ目を「透明度」として使い、背景と混ぜる(アルファブレンド)

**補間のコードが機械的にしか増えないこと**を確認するのが目的。
Day 8 でUV、Day 9 で法線を足すときも、やることは完全に同じになる。
逆に言えば、属性が増えるたびに引数が増えるこの設計は限界があり、
Day 5 でベクトル型を導入するとかなり整理される。

### 課題3(難): 補間の精度を壊してみる

1. `float` を `Half`(16bit浮動小数)に変えると、どこから絵が崩れるか
2. 重みを `int` の固定小数点(例えば 1.0 を 65536 とする)で持つとどうなるか。
   速くなるか? 精度は足りるか?
3. **今日の実装は、三角形が画面外に大きくはみ出すと破綻する。**
   頂点座標が数万ピクセルになると、エッジ関数の `(bx-ax)*(py-ay)` が
   `int` の範囲(約21億)を超えてオーバーフローする。
   どのくらいの座標値から壊れるか計算し、実際に大きな三角形を描いて確かめる。
   この問題への正しい対処が Day 10 のクリッピングになる(画面外の部分を先に切り落とす)
