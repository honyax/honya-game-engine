Phase 1 / ロードマップ該当行: 「ベクトル・行列数学の自作(と System.Numerics 比較)」

今日のゴール

Vec2 / Vec3 / Vec4 / Mat4 を自作し、図形の「形」と「置き場所」を分離する。図形は原点まわりの単純な形として書き、配置は行列に任せる。

今日は絵の派手さより土台の日。ただし土台の作り方を間違えるとDay 6 以降のすべてが崩れるので、規約(要点2)だけは絶対に押さえること。そして今日の実装は Day 6 でそのまま3Dのモデル行列になる。

事前に読む資料

  • ゲームグラフィックス特論 A-3 変換(1) 同次座標による座標変換 —今日と Day 6 の必読。同次座標がなぜ必要かの理論そのもの。ただし資料は列ベクトル規約なので、本リポジトリのコード(行ベクトル規約)とは行列が転置になる。要点2を読んでから資料に当たると混乱しない
  • Scratchapixel: Geometry —点・ベクトル・法線の違い(W=1 と W=0 の話)を丁寧に扱っている
  • System.Numerics.Matrix4x4 のドキュメント —比較対象。本Dayの実装はこれと同じ規約・同じメモリ配置にそろえてある

理論の要点

1. なぜ 3x3 ではなく 4x4 なのか — 平行移動が入らないから

3x3 行列は平行移動を表せない。行列は必ず原点を原点へ写すので、どんな 3x3 行列を掛けても (0,0,0) は動かない。

そこで次元を1つ増やし、点を (x, y, z, 1) の4成分で表す(同次座標)。すると 4x4 行列の4行目に平行移動量を置けて、回転・拡大・平行移動をすべて「行列を掛ける」1つの操作に統一できる。

統一できると何が嬉しいか: 変換をいくつ重ねても、事前に行列を掛け合わせて1つの行列にまとめられる。頂点が10万個あっても、行列の合成は1回で済む。これが Day 6 で「モデル行列 x ビュー行列 x 投影行列」を1つにまとめられる理由。

W の使い分けも重要。

W意味平行移動の影響
1位置(点)受ける
0方向(ベクトル)受けない

法線や光の向きを W=1 で変換すると、平行移動のぶんだけ向きが狂う。グラフィックスで頻出のバグで、Day 9 で実際に気をつけることになる。

2. 規約 — ここを間違えると一日溶ける

本リポジトリは行ベクトル規約を採用する。

変換後の点 = 点 * 行列        (v' = v * M)

点は「横に寝た 1x4 の行」として扱い、平行移動量は4行目(M41〜M43)に入る。これは System.Numerics / XNA / MonoGame / DirectX と同じで、Day 14 で Silk.NET へ移るときそのまま繋がる。

一方 OpenGL / GLSL と多くの教科書(特論も)は列ベクトル規約で、v' = M * v と書き、平行移動量は4列目に入る。

行ベクトル(本リポジトリ)列ベクトル(OpenGL / 特論)
書き方v * MM * v
平行移動の位置4行目4列目
合成の順序Model * View * Proj(左から適用)Proj * View * Model(右から適用)

2つは互いに転置の関係にあり、どちらが正しいということはない。ただし混ぜると壊れる。教科書やネットのコードを写すときは、まずどちらの規約かを確認すること。Phase 2 で生 OpenGL に行列を渡すときは、転置するか glUniformMatrix のtranspose 引数を true にする必要がある。

3. 合成の順序 = 変換の順序

行ベクトル規約では、左に書いた変換から順に適用される。

csharp
Mat4.Scale(pulse) * Mat4.RotationZ(angle) * Mat4.Translation(position)
// 拡大 → 回転 → 移動 の順

行列の積には交換法則が無いので、順序を変えると別物になる。

  • 「原点で回してから移動」… その場で自転する(普通に欲しいのはこちら)
  • 「移動してから原点で回す」… 遠くの点を軸にぐるっと公転する

デモの DrawOrbitSystem はこの性質を逆手に取って、公転と自転を作り分けている。

csharp
// 子がぶら下がる座標系: 公転半径ぶん移動 → 公転 → 親の変換
Mat4 childFrame = Translation(半径) * RotationZ(公転角) * parent;

// 子の見た目: 縮小 → 自転 → 上の座標系へ
DrawTransformed(child, Scale(26) * RotationZ(自転角) * childFrame, null);

親の行列に自分の行列を掛けるだけで階層ができる。 これがそのままDay 22 の Transform コンポーネント(シーングラフ)になる。太陽 - 惑星 - 衛星を2Dでやっているだけで、3Dでも構造は完全に同じ。

4. 内積と外積 — 使い道を先に知っておく

演算式の意味この先どこで使うか
内積 a・b|a||b|cosθ。単位ベクトル同士なら cosθ そのものDay 9 のランバート反射(面の向きと光の向きの内積 = 明るさ)、Day 10 の背面カリング
外積 a×b両方に垂直なベクトル。長さは平行四辺形の面積Day 10 の法線計算(三角形の2辺の外積 = 面の向き)

Day 3 のエッジ関数は、この外積のZ成分だけを取り出したものだった。 2次元では「両方に垂直な方向」が画面の手前/奥の1方向しかないので、向きは符号1つで表せて、値は面積そのものになる。Vec2.Cross として今日ちゃんと名前が付いたことになる。

外積は順序を入れ替えると符号が反転する(a×b = -(b×a))。これが「頂点の巻き方向が面の表裏を決める」ことの数学的な理由。

5. 頂点座標が int から float になった

Day 4 まで画面座標を int で持っていたのを Vec2(float)に変えた。理由は2つ。

  1. Day 6 で変換行列を通すと、画面座標は当然のように小数になる
  2. 小数のまま扱えば、三角形の辺をピクセルより細かい精度で置ける(サブピクセル精度)

これに伴い、ラスタライザの判定点をピクセルの中心に変えた。ピクセル (x, y) が覆っているのは [x, x+1) x [y, y+1) の正方形なので、その代表点は中心の (x + 0.5, y + 0.5) になる。Day 4 まで整数位置で判定していたのは頂点も整数だったからできた手抜きで、頂点が小数になった今は中心で測らないと絵が半ピクセルずれる。

top-left rule のバイアスも整数の -1 が使えなくなった。代わりに float.Epsilon (float で表せる最小の正の数、約 1.4e-45)を引いている。ちょうど0だった値だけが負になり、通常の大きさの値は1ビットも変わらないため、「0のときだけ効く補正」を分岐を増やさずに書ける。

実測での検証(本Dayの実装):

検証結果
正方形を対角線で2枚に分割(整数座標)25,600 px すべて1回、重なり0・隙間0
同じものを +0.5 ずらす(サブピクセル)25,281 px すべて1回、重なり0・隙間0
四角形をどちらの対角線で割っても同じピクセル集合か片方だけのピクセル 0(= 継ぎ目の割れ無し)
三角形を 0.1 px ずつ横へずらしたときの塗りピクセル数4,950 → 5,050 と変化する(int 実装なら全部同じ)

最後の項目が、サブピクセル精度が本当に効いていることの証拠になる。

6. struct にする理由、readonly にしない理由

Vec3 も Mat4 も class ではなく struct にしている。毎フレーム数万個を扱う値なので、class にすると1個ごとにヒープ確保とポインタ参照が発生してGCが暴れる。

Mat4 を float[16] の配列にしていないのも同じ理由。配列だとヒープ確保と境界チェックが入るが、16個のフィールドならレジスタに乗る。行列の積を三重ループではなく16行に展開しているのも、インデックス計算とループのオーバーヘッドを消すため。

readonly struct にしていないのは、写経中に v.X = 1 と書いて試せるようにするため。実務では readonly struct + with 式にするのが定石。

7. 実測 — System.Numerics との比較

正しさ: 自作の実装と System.Numerics の結果を比べたところ、Translation / Scale / RotationX,Y,Z / 合成 / 点の変換 / 方向の変換 / Dot / Cross / Normalizeのすべてで差が厳密に 0(ビット単位で一致)。規約もメモリ配置も同じにそろえてあるので、当然そうなるべきではある。

速度(1回あたり / 最良値 / Release / SIMD有効):

演算自作System.Numerics自作は
Vec3 内積7.69 ns6.23 ns1.23倍の時間
Vec3 外積17.53 ns7.46 ns2.35倍
Vec3 正規化8.63 ns3.03 ns2.85倍

System.Numerics は SIMD(1命令で4個のfloatをまとめて処理する)で実装されているので、成分が多い演算ほど差が開く。行列の積(64回の積和)で2.2倍というのは妥当な差。

それでも今日は自作する。中身が分からないまま使うと「なぜ正規化が要るのか」「内積の符号は何を意味するのか」が身につかないため。Day 14 で Silk.NET へ移るとき System.Numerics に乗り換える段取りにしてある。

なお絶対値には配列アクセスのコストも含まれているので、数字そのものより比を見ること(測り方の注意は Day 2 の要点6と同じ)。

JIT に消された測定: 最初に書いたベンチマークは行列の積が 1.74 ns というあり得ない値を出した。(A * B).M11 としか書いていなかったので、JIT が残り15成分の計算を「使われない」と判断して丸ごと削除していた。16成分すべてを足し込むように直したら 24.57 ns になった。マイクロベンチマークは結果を使わないと測定にならない、という定番の罠。

改造課題

課題1(易): 規約を体で確かめる

  1. Mat4.Translation の平行移動量を4行目ではなく4列目(M14, M24, M34)に置いてみる。絵はどうなるか。なぜそうなるかを説明できるか
  2. DrawGradientTriangle の合成順序を Translation * RotationZ * Scale に変える。何が起きるか。「移動してから回す」の意味を絵で確認する
  3. Mat4.RotationZ の sin の符号を両方反転させる。回転の向きはどうなるか

課題2(中): System.Numerics と比べる

計画書の要点7の実測を自分で再現する。

  1. Vec3 / Mat4 と System.Numerics.Vector3 / Matrix4x4 で同じ計算をして、結果が一致することを確認する
  2. 速度を測る。結果を必ず使うこと(要点7の最後に書いたJITの罠を踏まないように)
  3. System.Numerics.Vector.IsHardwareAccelerated を表示して、SIMDが有効か確認する
  4. 余力があれば: Vec3 を System.Runtime.Intrinsics で SIMD 化してみる。ただし Vec3 は12バイトで SIMD レジスタ(16バイト)に半端に収まるため、素直にやると速くならない。なぜ System.Numerics.Vector3 が速いのかを考える手がかりになる

課題3(難): 逆行列を実装する

Mat4.Inverted() を実装する。

  1. まず回転だけの行列は転置が逆行列になることを確かめる(直交行列の性質)。Mat4.RotationY(0.7f) * Mat4.RotationY(0.7f).Transposed() が単位行列になるか
  2. 平行移動を含む場合はどうか。Translation(t) の逆行列は Translation(-t) でよいか
  3. 一般の 4x4 逆行列(余因子展開)を実装し、M * M.Inverted() が単位行列に十分近くなるか確認する

逆行列は Day 6 のビュー行列(カメラの逆変換)と、Day 9 の法線変換(逆転置行列)で必要になる。ただし本リポジトリでは、どちらも「逆行列を計算せずに済ませる」方法を採る予定なので、この課題は「なぜ逆行列を避けられるのか」を理解するための準備でもある。
