Phase 1 / ロードマップ該当行: 「モデル→ビュー→透視投影のパイプライン」

今日のゴール

回転する立方体が、遠近感のついた3Dとして画面に出る。

Day 5 までは全部2Dだった。今日 3D になる。しかも新しく書く計算は「行列を2つ追加」と「W で割る」だけで、他はすべて Day 1〜5 の積み上げがそのまま動く。

事前に読む資料

  • ゲームグラフィックス特論 A-3 変換(1) 同次座標による座標変換 —今日の必読。透視投影行列の導出そのもの。資料は列ベクトル規約なので、行列は本リポジトリの転置になる(Day 5 の要点2)
  • Scratchapixel: The Perspective and Orthographic Projection Matrix —投影行列の各要素がどこから来るかを段階的に導く
  • LearnOpenGL: Coordinate Systems —座標系が何段階あるかの全体像。図が分かりやすい
  • 西川善司「ゲーム制作者になるための3Dグラフィックス技術 改訂3版」Ch2

理論の要点

1. 座標系は5段階ある

頂点は、画面に出るまでに次の座標系を通る。

座標系何を基準にした位置か変換するもの
モデル座標物体そのもの(立方体の中心が原点)← ここが Vertex.Position の初期値
ワールド座標世界の原点モデル行列(配置・回転・拡大)
ビュー座標カメラ(カメラが原点、視線が -Z)ビュー行列
クリップ座標4次元。W に奥行きが入っている投影行列
NDC-1〜1 の立方体透視除算(W で割る)
画面座標ピクセルビューポート変換

行列は3つだが、掛け合わせて1つの MVP 行列にできる。頂点が10万個あっても行列の合成は物体ごとに1回で済む。これが Day 5 で「変換を行列に統一した」ことの実利。

csharp
Mat4 mvp = model * view * projection;   // 行ベクトル規約なので左から順

2. ビュー行列 = カメラを動かす代わりに、世界を動かす

カメラという実体はレンダラの中に存在しない。カメラが右に3進んだ景色は、世界が左に3ずれた景色と同じ。だからビュー行列は「カメラの姿勢の逆変換」になる。

逆行列を真面目に計算する必要はない。カメラの姿勢は「回転 + 平行移動」だけなので、

  • 回転の逆 … 直交行列なので転置でよい
  • 平行移動の逆 … 回転後の各軸との内積の符号を反転したもの

で済む。Mat4.LookAt の中身がまさにこの形になっている(Day 5 の課題3で「逆行列を避けられる」と書いたのはこのこと)。

csharp
Vec3 zAxis = (eye - target).Normalized();      // カメラの後ろ向きが Z(-Z を見る約束)
Vec3 xAxis = Vec3.Cross(up, zAxis).Normalized();
Vec3 yAxis = Vec3.Cross(zAxis, xAxis);          // up を作り直して直交させる

up を外積で作り直しているのは、呼び出し側が渡す up が視線と直交している保証がないため。

3. 透視投影行列がしているのは「Z を W にコピーする」だけ

ここが今日一番の勘所。投影行列は遠近感を作っていない。

csharp
M11 = xScale;                       // 視野角による倍率
M22 = yScale;
M33 = far / (near - far);
M34 = -1.0f;                        // ← Z を W へコピーする係数。これが本体
M43 = near * far / (near - far);
M44 = 0.0f;                         // ← ここが 0 なのが透視投影の目印

M34 = -1 により、変換後の W にはカメラからの奥行きが入る。そして遠近感は次の段階の割り算で生まれる。

csharp
float invW = 1.0f / clip.W;
float ndcX = clip.X * invW;   // 奥のものほど W が大きい → 小さくなる
float ndcY = clip.Y * invW;

実測での検算(カメラ (0,0,5)、視野角90度、near=1, far=11):

点の zカメラからの距離W画面上の高さ NDC.Y深度 NDC.Z
4.01.01.001.0000.0000
3.02.02.000.5000.5500
0.05.05.000.2000.8800
-3.08.08.000.1250.9625
-6.011.011.000.0911.0000

W はカメラからの距離そのものになっており、画面上の高さは距離にきれいに反比例している(1.0, 0.5, 0.2, 0.125, 0.091 = 1/距離)。これが「遠くのものが小さく見える」の全て。同次座標の W は、この割り算のために用意された仕組みだったということになる。

4. 深度は距離に比例しない — near は大きいほどよい

上の表の一番右の列に注目してほしい。near から far までを 0〜1 に写す深度が、距離に対して激しく非線形になっている。

  • 距離 1 → 2(全体の10%)で深度は 0 → 0.55。半分以上を使い切る
  • 距離 8 → 11(全体の30%)では 0.96 → 1.0。わずか4%しかない

つまり深度の精度は手前に集中し、奥はスカスカ。M43 = near * far / (near - far) の形からくる性質で、near を小さくするほど極端になる。

その結果、near を 0.01 のような小さい値にすると、遠くの物体の前後関係を深度値で区別できなくなり、面がチラチラと入れ替わる(Zファイティング)。near はできるだけ大きくが鉄則。

なお near = 0 は不可能。数式が破綻するだけでなく、「カメラの位置にある点の投影先」が定義できないため。

5. カメラの後ろの頂点は、素直には投影できない

W はカメラからの奥行きなので、カメラの後ろにある点は W が負になる。そのまま割ると符号が反転し、三角形が画面の反対側へ裏返って飛んでいく。

正しい対処は「三角形を近クリップ面で切って、手前の部分だけ描く」ことで、それが Day 10 のクリッピング。今日は W が正でない頂点を1つでも含む三角形は丸ごと捨てるという手抜きで済ませている。

csharp
if (clip.W <= MinClipW) { screen = default; return false; }

そのためカメラが物体に近づきすぎると面が丸ごと消える。これは今日の時点では正常な挙動(Day 10 で直る)。

6. 画家のアルゴリズムと、その限界

3Dになった途端、新しい問題が出る。どの面が手前にあるか。何も考えずに描くと、後から描いた面が前の面を上書きしてしまう。

今日は古典的な画家のアルゴリズムを使う。三角形を奥から順に並べ替えて、奥から描く。絵の具を重ねる画家のやり方に似ているのでこの名前。

csharp
triangles.Sort(static (a, b) => b.Depth.CompareTo(a.Depth));   // 遠い順

S キーで並べ替えを切ると、立方体が崩壊して奥の面が手前に見える。

しかしこの方法には原理的な限界がある。

  1. 三角形1枚につき深度が1つしかない。 実際には三角形は奥行きを持った面なので、「三角形Aのほうが手前」と一言では言えない場合がある
  2. 交差する三角形は絶対に解けない。 十字に交わる2枚は、どちらを先に描いても間違いになる(互いに相手を貫いているため)
  3. 循環する場合がある。 AはBより手前、BはCより手前、CはAより手前、という3枚の配置が作れてしまう
  4. 並べ替えのコストが乗る。 三角形が10万枚なら毎フレーム10万個のソート

Day 7 のZバッファは、これをピクセル単位で判定することで全部まとめて解決する。今日のソートの仕組みは Day 7 でまるごと消える。

7. 実測 — 3Dになっても中身は Day 3〜5 のまま

Day 6 の render 時間は 1.9〜2.0 ms(立方体4個 = 48枚)。Day 5 の 0.6 ms(10枚)から増えているが、これは枚数と塗る面積が増えたからで、1枚あたりのコストの構造は変わっていない。

今日追加した計算は頂点あたりのもの(行列の掛け算1回 + 割り算1回)で、ピクセルあたりの仕事は Day 4 から1つも増えていない。頂点は三角形1枚につき3個、ピクセルは数百〜数千個あるので、3D化のコストは実質ゼロと言ってよい。

これは「頂点処理とピクセル処理を分ける」というパイプラインの設計が効いている証拠で、GPUが頂点シェーダとピクセルシェーダを別々に持っている理由でもある。

改造課題

課題1(易): 投影行列を壊して仕組みを見る

  1. Mat4.Perspective の M34 を -1 から 0 に、M44 を 0 から 1 に変える。何が起きるか。これは何という投影法か(ヒント: 設計図やアイソメトリックなゲームの見え方)
  2. M34 を -2 にすると何が変わるか。-0.5 では?
  3. Camera.FieldOfView を 20度と 150度にして比べる。同じ位置から同じ物を見ているのに、形が違って見えるのはなぜか(実写でも起きる現象で、広角レンズで顔を撮ると鼻が大きくなるのと同じ理屈)

課題2(中): 深度の非線形性を自分で確かめる

要点4の表を自分で再現し、near の影響を測る。

  1. カメラの前に等間隔(距離 1, 2, 3, ... 10)で点を置き、それぞれの NDC.Z を出力する
  2. near を 0.1 / 1.0 / 4.0 と変えて、値の分布がどう変わるか比べる
  3. 深度を float ではなく 16bit 整数(0〜65535)で持つと仮定して、距離 50 と距離 51 の点が区別できるかを near ごとに計算する。near = 0.01 だとどうなるか

Zファイティングは実際のゲーム開発で頻繁に遭遇する問題なので、「なぜ near を大きくしろと言われるのか」を数字で納得しておくと後々効く。

課題3(難): 画家のアルゴリズムを破る

要点6で挙げた限界を、実際に絵として再現する。

  1. 交差する2枚: 十字に交わる大きな三角形2枚を描く。どちらを先に描いても正しくならないことを確認する
  2. 循環: A→B→C→A と互いに重なり合う3枚を配置する(細長い三角形を少しずつずらして重ねると作れる)
  3. 三角形をソートする基準を「平均」から「最も手前の頂点」「最も奥の頂点」に変えると、結果はどう変わるか。どの基準でも壊れるケースが作れることを確認する

ここで壊れた絵を見ておくと、Day 7 のZバッファが「なぜピクセル単位でなければならないのか」が腹に落ちる。
