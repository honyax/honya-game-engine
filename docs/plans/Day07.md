# Day 07: Zバッファ(深度テスト)

Phase 1 / ロードマップ該当行: 「Zバッファ」

## 今日のゴール

立方体を貫通する板が、正しく前後関係を保って描かれる。
**描く順番を一切気にしなくてよくなる。**

Day 6 の画家のアルゴリズムでは原理的に描けなかった絵が、
配列を1枚増やすだけで描けるようになる。しかも**コードは短くなる**。

## 理論の要点

### 1. アイデア: ピクセルごとに「今の勝者の深さ」を覚えておく

画面と同じ解像度の float 配列をもう1枚用意し、
**そのピクセルに現在描かれているものの深度**を記録しておく。

新しいピクセルを描こうとするたびに、

1. そのピクセルの深度を求める
2. 既に記録されている深度と比べる
3. **手前なら**描いて深度を更新する。奥なら捨てる

これだけ。三角形単位ではなく**ピクセル単位**で判定するのが Day 6 との決定的な違いで、
これによって Day 6 で挙げた限界がすべて消える。

| Day 6 の問題 | Zバッファでどうなるか |
|---|---|
| 交差する三角形が解けない | 交差線を境に自然に切り替わる。特別な処理は不要 |
| 前後関係が循環する配置 | そもそも三角形同士を比較しないので起こり得ない |
| 三角形1枚に深度が1つしかない | ピクセルごとに深度を持つので問題にならない |
| 毎フレームのソートが重い | ソートが要らなくなる |

そして描画順序が完全に自由になる。**これが実用上いちばん効く。**
物体を追加するのに「どこに挿入するか」を考えなくてよくなり、
マルチスレッドやGPUでの並列描画も可能になる。

### 2. コードは短くなる

Day 6 → Day 7 の差分で、**増えた行より消えた行のほうが多い**。

消えたもの: 三角形を溜める配列、深度の計算、ソート、二段構えの描画メソッド。
増えたもの: `DepthBuffer` クラス(実質10行)、走査ループの中の6行、毎フレームのクリア1行。

```csharp
float z = v0.Position.Z * l0 + v1.Position.Z * l1 + v2.Position.Z * l2;

if (depthTest)
{
    if (z >= depth[index]) continue;   // 奥なら捨てる
    depth[index] = z;
}
```

**正しくなったのに簡単になった**。こういう解法は滅多にないので味わっておくとよい。

### 3. なぜ深度は「補間するだけ」で正しいのか

深度バッファに入れているのは、カメラからの距離ではなく **NDC の Z**
(透視除算を済ませた後の値、0 = 近クリップ面、1 = 遠クリップ面)。

これには理由がある。**透視除算後の Z は、画面上で線形に変化する**。
つまり画面座標 x, y の1次式になっているので、
Day 4 のバリセントリック補間をそのまま使えば、内部の任意のピクセルの正しい深度が求まる。

一方、**カメラからの距離そのものを補間すると間違う**。
遠近感によって「画面上で等間隔でも、実空間では等間隔でない」ためで、
奥に行くほど1ピクセルが担当する実距離が伸びていく。

そして**色やUVなどの属性は、まさにこの「間違う」側**。
Day 4 から今日までずっと属性を単純補間してきたが、実は3Dでは正しくない。
今は面が単色なので誤差が見えていないだけで、
**Day 8 でテクスチャを貼った瞬間に破綻が目に見える**ようになる。
その修正(透視補正補間)が Day 8 の主題になる。

「Z だけは単純補間でよい」というのは、Zバッファがうまくいく理由の核心でもある。

### 4. 深度テストは色を計算する前に行う

```csharp
float z = ...;
if (z >= depth[index]) continue;   // ここで捨てる
depth[index] = z;

Vec3 attribute = ...;              // 通ったピクセルだけが色を計算する
pixels[index] = ...;
```

順序が大事。落ちるピクセルのために色やテクスチャを計算するのは丸損なので、
**判定は可能な限り早く**行う。Day 9 でシェーディングが重くなるほど効いてくる。

GPUもまったく同じ考えで、本来ならピクセルシェーダの後にあるはずの深度テストを
条件が許すときは前倒しする(**アーリーZ**)。
シェーダの中で深度を書き換えたり、ピクセルを捨てたりすると
この最適化が無効になって激重になる、というのはGPUプログラミングの常識になっている。

### 5. 等号を含めない(z >= なら捨てる)

同じ深度のピクセルが来たときは、**先に描いたほうを残す**。
後勝ちにすると、描画順を変えただけで絵が変わってしまい、
「順序を気にしなくてよい」というZバッファの利点が壊れる。

とはいえ、深度がぴったり同じになる状況は本来おかしい。
2つの面が同じ場所にある(同一平面)ということで、この状態では
浮動小数の誤差でどちらが勝つかがピクセルごとにばらつき、
**ちらつく斑点**(Zファイティング)になる。

本Dayの制作中に実際にこれを踏んだ。2枚の板を `RotationZ` で90度回して
「直交させたつもり」だったが、`RotationZ` は板を**自分の平面の中で**回すだけなので、
2枚が同一平面に重なってしまい、画面が斑点だらけになった。
`RotationY` に直して解決している(コード中にコメントを残した)。

現実の対処法は、
- そもそも同一平面に2つの面を置かない(地面と地面のデカールなど)
- 深度に微小なオフセットを足す(**ポリゴンオフセット**)
- near を大きくして深度の精度を稼ぐ(Day 6 の要点4)

### 6. 深度バッファを覗く

D キーで深度バッファの中身を白黒表示できる。手前が白、奥が黒。

そのまま NDC の Z を明るさにすると**ほぼ真っ白**になって何も見えない。
Day 6 の要点4で見たとおり深度値が手前に極端に偏っているためで、
near=0.1 / far=100 では距離5の点でも深度は 0.99 を超えている。

そこで**カメラからの距離に逆算してから**表示している。

```csharp
// 投影行列は ndcZ = far/(far-near) * (1 - near/distance) を作っていたので、
// これを distance について解く
float distance = near / (1.0f - ndcZ * (far - near) / far);
```

この式は「深度値がどう作られたか」を理解していないと書けないので、
Day 6 の復習にちょうどよい。

深度バッファの可視化はデバッグの基本技でもある。絵がおかしいときに
「形は合っているのか」「深度が壊れているのか」を切り分けられる。

### 7. 実測 — コストは正直に増える

| Day | 内容 | 三角形 | render |
|---|---|---|---|
| 6 | 画家のアルゴリズム | 48 | 1.9〜2.0 ms |
| 7 | Zバッファ | 52 | **4.1〜4.6 ms** |

増えた理由は2つあり、片方は本質的ではない。

- **本質的**: ピクセルごとに深度の補間・比較・書き込みが増えた
- **本質的でない**: 今日のシーンは大きな板2枚を追加したので、
  塗るピクセル数そのものが Day 6 より大幅に多い

Zバッファには「奥のピクセルはシェーディングを省ける」という節約効果もあるが、
今日はシェーディングが単なる色のコピーなので恩恵がほぼない。
**Day 9 で光の計算が乗ると、この節約が効き始める**。

なおメモリは 640x480 x float = 1.2MB 増える。
1970年代にはこれが現実的でなかったので画家のアルゴリズムが使われていた。
**メモリが安くなったからZバッファが標準になった**、という側面がある。

   もう一度押すと直る
5. **D** キーで深度バッファが白黒表示になる。**手前が白く、奥ほど黒い**。
   板が奥に向かってなめらかなグラデーションになっている
6. **W** キーでワイヤーフレーム
7. タイトルバーが `58.x fps | 52 tri | render 4.x ms | 深度テスト:ON` のようになっている

うまくいかないときの確認ポイント:

- **物体が虫食いに抜ける / 前フレームの残像が出る** → 毎フレームの `Depth.Clear()` を忘れている。
  症状が独特なので、見たらまずここを疑う
- **何も描かれない** → `Clear()` の値。0.0 で埋めると全部が「既に最前面」になって全滅する
- **奥のものが手前に出る** → 比較の向きが逆。小さいほど手前(`z >= depth` なら捨てる)
- **ちらつく斑点が出る** → Zファイティング。同一平面に2つの面が乗っている。要点5
- **深度表示が真っ白 / 真っ黒** → 距離への逆算をしていない、または表示範囲が合っていない。要点6
- **深度テストは効いているのに、面の縁がギザギザに欠ける** → 深度を
  「画面座標の Z」ではなく「カメラからの距離」で補間している。要点3

## 改造課題

### 課題1(易): 画家のアルゴリズムを、この絵で試して壊す

Day 6 のソート機構(`_triangleBuffer` と `DrawSubmitted`)を Day 7 のシーンに移植する。

1. 深度テストを切り、三角形を奥から順にソートして描く
2. **貫通している板と立方体が正しく描けないこと**を確認する。
   板の全体が立方体の手前に来るか、逆に全部奥に行くかのどちらかになるはず
3. ソートの基準を「平均」「最も手前の頂点」「最も奥の頂点」に変えても、
   どれも正解にならないことを確認する

Day 6 で理屈として説明したことを、実際の絵として見るのが目的。

### 課題2(中): Zファイティングを再現し、対策を試す

1. 板を2枚、**まったく同じ位置**に置く(色だけ変える)。斑点が出るはず
2. カメラを近づけたり遠ざけたりすると、斑点の出方がどう変わるか
3. `Camera.NearPlane` を 0.01 と 1.0 で比べる。どちらが斑点が減るか。
   Day 6 の要点4で計算したことと一致するか
4. 片方の板の深度に小さなオフセットを足して解決する(ポリゴンオフセット)。
   **オフセットはいくつなら足りるか**。近くと遠くで必要な量が変わることに気づけるか

### 課題3(難): 深度バッファを 16bit 整数にする

`float[]`(32bit)ではなく `ushort[]`(16bit)で深度バッファを実装する。

1. NDC の Z(0〜1)を 0〜65535 に写して格納する
2. メモリは半分になる。速度はどう変わるか(**キャッシュに乗りやすくなるので速くなる可能性がある**)
3. どんなシーンで破綻するか。near と far の比を大きくしていくと、
   どのあたりから前後関係が壊れ始めるか

さらに余力があれば **逆Z(reversed-Z)** を調べて実装してみるとよい。
「near を 1、far を 0 に割り当てて、深度テストの向きを逆にする」だけで
浮動小数の精度分布と深度の非線形性が打ち消し合い、精度が劇的に改善する技法で、
現代のゲームエンジンではほぼ標準になっている。
Day 6 の要点4で見た「深度が手前に偏る」問題への、最もエレガントな解答。
