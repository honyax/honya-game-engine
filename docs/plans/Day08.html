Phase 1 / ロードマップ該当行: 「テクスチャマッピング(ニアレスト→バイリニア)」

今日のゴール

立方体と床に画像が貼られる。しかも遠近感に沿って正しく歪む。

今日は2つの山がある。テクスチャを引くこと自体は簡単だが、Day 4 からずっと間違っていた属性補間(Day 7 の要点3で予告したもの)がテクスチャを貼った瞬間に目に見えるようになる。その修正が今日の本題。

事前に読む資料

  • ゲームグラフィックス特論 B-9 テクスチャマッピング(1) 座標生成とサンプリング —今日の必読。UV座標とサンプリングの理論。資料PDFのファイル番号は1つずれる(B-9の資料は ggnote08)点に注意
  • Scratchapixel: Perspective-Correct Interpolation —透視補正補間の導出。今日の要点2の数学的な裏付け
  • 西川善司「ゲーム制作者になるための3Dグラフィックス技術 改訂3版」Ch2

理論の要点

1. テクスチャは「UV で読む画像」

テクスチャの実体は Framebuffer と同じ「int の1次元配列 + 幅と高さ」。違うのは読み方だけで、整数のピクセル座標ではなく 0.0〜1.0 の実数座標(UV)で読む。

UV が 0〜1 に正規化されているのは、テクスチャの解像度と切り離すため。モデル側は「この頂点は画像の右上」とだけ言えばよく、その画像が 64x64 でも 4096x4096 でも同じデータが使える。解像度を差し替えられる(LOD、モバイル向けの縮小版)のはこの設計のおかげ。

そしてUVはモデルの形とは独立に決められる。同じ立方体でも、6面に同じ絵を貼ることも、1枚の絵を切り分けて貼ることもできる。この割り当てを決める作業がUV展開で、モデラーが手間をかけている部分でもある。

実装としては、Day 4 で作った属性補間の仕組みに Vec2 TexCoord を1つ足しただけ。補間のコードは1行増えただけで済んでいる。Day 4 の要点1で書いた「属性が増えても式の形は変わらない」がそのとおりになった。

2. 透視補正補間 — Day 4 からずっと間違っていたもの

画面上で属性を素直に線形補間するのは、3Dでは間違い。

理由は Day 7 の要点3の裏返し。透視除算のあと、画面上で線形に変化するのはZ だけで、色やUVは線形に変化しない。遠近感によって「画面上で等間隔でも、実空間では等間隔でない」ためで、奥に行くほど1ピクセルが担当する実距離が伸びていく。

正しい補間はこうなる。

補間したい属性を A、クリップ座標の W とすると
  (A/W) を画面上で線形補間したもの ÷ (1/W) を画面上で線形補間したもの = 正しい A

つまり A/W と 1/W なら画面上で線形に変化するので、その2つを補間してから割る。

csharp
// 三角形ごとに1回: 属性を W で割っておく
Vec2 uv0 = v0.TexCoord * v0.InvW;  // 以下 v1, v2 も

// ピクセルごと: 補間して、補間した 1/W で割り戻す
float interpolatedInvW = iw0 * l0 + iw1 * l1 + iw2 * l2;
float w = 1.0f / interpolatedInvW;
Vec2 uv = (uv0 * l0 + uv1 * l1 + uv2 * l2) * w;

P キーで補正を切ると、床のタイルが三角形の対角線を境にぐにゃりと折れ曲がる。初代プレイステーションのテクスチャが揺れて見えたのはまさにこれで、当時のハードにはピクセルごとに除算器を回す余裕がなかった。

なぜ今まで見えなかったのか: Day 6〜7 は面が単色だったので、補間が間違っていても結果が同じだった。色を頂点ごとに変えていればDay 6 の時点で(よく見れば)歪んでいたことになる。

3. ニアレストとバイリニア

方式読むテクセル数拡大したとき
ニアレスト1ブロック状(ドット絵の拡大)
バイリニア4なめらか(ぼやける)

バイリニアは周囲4テクセルを距離で重み付けして混ぜる。混ぜ方は Day 4 の線形補間を横方向に2回、縦方向に1回やるだけ。「バイ(2つの)リニア(線形)」という名前どおり。

実装の要点は -0.5 のずらし。テクセルの色が定義されている場所はテクセルの左上の角ではなく中心なので、テクセル座標に直したあと 0.5 引く。

csharp
float x = u * Width - 0.5f;   // この -0.5 を忘れると絵が半テクセルずれる

拡大率が大きいほどずれが目立つので、忘れるとすぐ分かる……はずだが、「なんとなくぼやけている」だけに見えて見逃しやすい罠でもある。

4. 範囲外のUVをどう扱うか(ラップモード)

床は UV を 0〜4 にしてテクスチャを4回繰り返している。1 を超えたUVをどう扱うかは選べて、本Dayはリピート(折り返し)を実装した。

csharp
private static int WrapIndex(int value, int size) => ((value % size) + size) % size;

% を2回使っているのは、C# の % が負の数に対して負を返すため。UV が 0 未満のとき、素直に書くと配列外アクセスになる。

他にクランプ(端の色を引き伸ばす)、ミラー(鏡像で折り返す)があり、実機ではテクスチャごとに設定できる。地面のタイルはリピート、空のパノラマはクランプ、といった使い分けをする。

5. 実測 — 正しさはタダ、品質は高い

1フレームを設定違いで測った実測(Release / 38枚 / 640x480):

設定1フレーム
ニアレスト / 透視補正OFF7.23 ms
ニアレスト / 透視補正ON7.23 ms
バイリニア / 透視補正OFF9.57 ms
バイリニア / 透視補正ON9.63 ms

読み取れることが2つある。

透視補正のコストは実質ゼロ。 ピクセルごとに除算1回と乗算数回が増えるはずなのに、測定できるほどの差が出ていない。他の処理(特にテクスチャの読み込み)がメモリ待ちで詰まっている間に、ついでに終わってしまうため。PS1 が透視補正を諦めた理由は「当時のハードには除算器が無かった」からで、現代のCPUでは絵が正しくなる代わりに払うものが何も無い。

バイリニアは 33% 高い(7.23 → 9.63 ms)。テクセルを1個ではなく4個読むためで、純粋にメモリアクセスが4倍になる。Day 2 から繰り返し出ている「支配的なコストはメモリ」というテーマがここでも出てくる。

6. 縮小方向の問題(今日は解決しない)

床の奥のほうを見ると、タイルがちらついたりモアレ模様が出たりする。1ピクセルが何テクセルもの範囲を覆っているのに、そのうち1点(または4点)しか読んでいないので、本来平均すべき情報を取りこぼしているため。

これは拡大(マグニフィケーション)ではなく縮小(ミニフィケーション)の問題で、フィルタを変えても直らない。正しい解決策はミップマップ——あらかじめ縮小した画像を何段階か用意しておき、そのピクセルが覆う範囲に合った解像度から読む方法。

本ロードマップでは Phase 3 以降(GPU に移ってから)扱う。ソフトウェアでも実装できるが、「そのピクセルがテクスチャ上でどれだけの範囲を覆っているか」の計算(UVの微分)が必要で、Day 8 の分量を超えるため。

7. 大きな三角形は、カメラの後ろに回ると丸ごと消える

本Dayの床は一辺 6.4 の正方形1枚(三角形2枚)にしてある。もっと大きくしたいところだが、大きくするとカメラが回ったときに床が丸ごと消える。

Day 6 の要点5のとおり、今の実装は「頂点が1つでもカメラの後ろにある三角形」をまるごと捨てている。床は大きな三角形2枚なので、隅がカメラの後ろに回った瞬間に床全体が消えてしまう。

制作中に実際にこれを踏んで、床が完全に見えなくなった。カメラの周回半径(6.5)を床の対角の長さ(4.5)より大きく取ることで回避している。Day 10 のクリッピングを入れるとこの制約から解放される。

改造課題

課題1(易): 補正とフィルタの効果を数字で見る

  1. P と F を切り替えながら render 時間を記録し、要点5の表を再現する
  2. 透視補正のコストがほぼゼロであることを確認する。なぜそうなるのか説明できるか
  3. テクスチャの解像度を 32 → 512 に変える(Texture.CreateTestPattern(512, 128))。バイリニアのコストはどう変わるか。遅くなるはずだが、その理由は計算量ではない(ヒント: 512x512x4バイト = 1MB は L2 キャッシュに乗るか?)

課題2(中): ラップモードを増やす

Texture に折り返し方の選択肢を足す。

  1. クランプ: 0未満は0に、1以上は1に切り詰める。床の端がどうなるか
  2. ミラー: 1を超えたら鏡像で折り返す。市松模様のつなぎ目がどう変わるか
  3. 床の UV を 0〜4 ではなく 0.25〜0.75(テクスチャの中央だけを引き伸ばす)にするとどう見えるか

さらに、バイリニアとリピートの相性問題にも触れておくとよい。テクスチャの右端のテクセルは、リピートなら左端と混ぜるべきだが、クランプなら右端の色をそのまま使うべき。SampleBilinear の中で WrapIndex を使っているのはリピート前提の実装になっている。

課題3(難): ミップマップを実装する

要点6の縮小方向の問題に取り組む。

  1. テクスチャを半分ずつ縮小した画像を、1x1 になるまで作る(ミップチェーン)
  2. そのピクセルがテクスチャ上でどれだけの範囲を覆うかを求める。隣のピクセルとのUVの差(UVの微分)から計算できる。ラスタライザの走査ループで、x方向に1つ進んだときのUVの変化を出せばよい
  3. 覆う範囲の大きさから適切なミップレベルを選び、そこから読む
  4. さらに、隣り合う2つのミップレベルを混ぜる(トライリニア)と段差が消える

床の奥のちらつきが消えることを確認する。GPUがミップマップを標準機能として持っているのは、この計算(特に2)をピクセルシェーダの外で自動的にやってくれるからで、自分で書いてみるとその親切さが分かる。
