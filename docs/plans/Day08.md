## 理論の要点

### 1. テクスチャは「UV で読む画像」

テクスチャの実体は <see cref="Framebuffer"/> と同じ「int の1次元配列 + 幅と高さ」。
違うのは**読み方**だけで、整数のピクセル座標ではなく 0.0〜1.0 の実数座標(UV)で読む。

UV が 0〜1 に正規化されているのは、**テクスチャの解像度と切り離すため**。
モデル側は「この頂点は画像の右上」とだけ言えばよく、
その画像が 64x64 でも 4096x4096 でも同じデータが使える。
解像度を差し替えられる(LOD、モバイル向けの縮小版)のはこの設計のおかげ。

そしてUVは**モデルの形とは独立**に決められる。同じ立方体でも、
6面に同じ絵を貼ることも、1枚の絵を切り分けて貼ることもできる。
この割り当てを決める作業がUV展開で、モデラーが手間をかけている部分でもある。

実装としては、Day 4 で作った属性補間の仕組みに `Vec2 TexCoord` を1つ足しただけ。
**補間のコードは1行増えただけ**で済んでいる。Day 4 の要点1で書いた
「属性が増えても式の形は変わらない」がそのとおりになった。

### 2. 透視補正補間 — Day 4 からずっと間違っていたもの

**画面上で属性を素直に線形補間するのは、3Dでは間違い。**

理由は Day 7 の要点3の裏返し。透視除算のあと、画面上で線形に変化するのは
Z だけで、色やUVは線形に変化しない。
遠近感によって「画面上で等間隔でも、実空間では等間隔でない」ためで、
奥に行くほど1ピクセルが担当する実距離が伸びていく。

正しい補間はこうなる。

```
補間したい属性を A、クリップ座標の W とすると
  (A/W) を画面上で線形補間したもの ÷ (1/W) を画面上で線形補間したもの = 正しい A
```

つまり **A/W と 1/W なら画面上で線形に変化する**ので、その2つを補間してから割る。

```csharp
// 三角形ごとに1回: 属性を W で割っておく
Vec2 uv0 = v0.TexCoord * v0.InvW;  // 以下 v1, v2 も

// ピクセルごと: 補間して、補間した 1/W で割り戻す
float interpolatedInvW = iw0 * l0 + iw1 * l1 + iw2 * l2;
float w = 1.0f / interpolatedInvW;
Vec2 uv = (uv0 * l0 + uv1 * l1 + uv2 * l2) * w;
```

**P キーで補正を切ると、床のタイルが三角形の対角線を境にぐにゃりと折れ曲がる。**
初代プレイステーションのテクスチャが揺れて見えたのはまさにこれで、
当時のハードにはピクセルごとに除算器を回す余裕がなかった。

なぜ今まで見えなかったのか: Day 6〜7 は面が単色だったので、
補間が間違っていても結果が同じだった。色を頂点ごとに変えていれば
Day 6 の時点で(よく見れば)歪んでいたことになる。

### 3. ニアレストとバイリニア

| 方式 | 読むテクセル数 | 拡大したとき |
|---|---|---|
| ニアレスト | 1 | ブロック状(ドット絵の拡大) |
| バイリニア | 4 | なめらか(ぼやける) |

バイリニアは周囲4テクセルを距離で重み付けして混ぜる。
混ぜ方は Day 4 の線形補間を横方向に2回、縦方向に1回やるだけ。
「バイ(2つの)リニア(線形)」という名前どおり。

**実装の要点は -0.5 のずらし**。テクセルの色が定義されている場所は
テクセルの左上の角ではなく**中心**なので、テクセル座標に直したあと 0.5 引く。

```csharp
float x = u * Width - 0.5f;   // この -0.5 を忘れると絵が半テクセルずれる
```

拡大率が大きいほどずれが目立つので、忘れるとすぐ分かる……はずだが、
「なんとなくぼやけている」だけに見えて見逃しやすい罠でもある。

### 4. 範囲外のUVをどう扱うか(ラップモード)

床は UV を 0〜4 にしてテクスチャを4回繰り返している。
1 を超えたUVをどう扱うかは選べて、本Dayは**リピート**(折り返し)を実装した。

```csharp
private static int WrapIndex(int value, int size) => ((value % size) + size) % size;
```

`%` を2回使っているのは、C# の `%` が負の数に対して負を返すため。
UV が 0 未満のとき、素直に書くと配列外アクセスになる。

他にクランプ(端の色を引き伸ばす)、ミラー(鏡像で折り返す)があり、
実機ではテクスチャごとに設定できる。地面のタイルはリピート、
空のパノラマはクランプ、といった使い分けをする。

### 5. 実測 — 正しさはタダ、品質は高い

1フレームを設定違いで測った実測(Release / 38枚 / 640x480):

| 設定 | 1フレーム |
|---|---|
| ニアレスト / 透視補正OFF | 7.23 ms |
| ニアレスト / 透視補正**ON** | **7.23 ms** |
| バイリニア / 透視補正OFF | 9.57 ms |
| バイリニア / 透視補正ON | 9.63 ms |

読み取れることが2つある。

**透視補正のコストは実質ゼロ。** ピクセルごとに除算1回と乗算数回が増えるはずなのに、
測定できるほどの差が出ていない。他の処理(特にテクスチャの読み込み)が
メモリ待ちで詰まっている間に、ついでに終わってしまうため。
**PS1 が透視補正を諦めた理由は「当時のハードには除算器が無かった」からで、
現代のCPUでは絵が正しくなる代わりに払うものが何も無い。**

**バイリニアは 33% 高い**(7.23 → 9.63 ms)。テクセルを1個ではなく4個読むためで、
純粋にメモリアクセスが4倍になる。Day 2 から繰り返し出ている
「支配的なコストはメモリ」というテーマがここでも出てくる。

### 6. 縮小方向の問題(今日は解決しない)

床の奥のほうを見ると、タイルがちらついたりモアレ模様が出たりする。
1ピクセルが何テクセルもの範囲を覆っているのに、そのうち1点(または4点)しか
読んでいないので、**本来平均すべき情報を取りこぼしている**ため。

これは拡大(マグニフィケーション)ではなく**縮小(ミニフィケーション)**の問題で、
フィルタを変えても直らない。正しい解決策は**ミップマップ**——
あらかじめ縮小した画像を何段階か用意しておき、
そのピクセルが覆う範囲に合った解像度から読む方法。

本ロードマップでは Phase 3 以降(GPU に移ってから)扱う。
ソフトウェアでも実装できるが、「そのピクセルがテクスチャ上でどれだけの範囲を
覆っているか」の計算(UVの微分)が必要で、Day 8 の分量を超えるため。

### 7. 大きな三角形は、カメラの後ろに回ると丸ごと消える

本Dayの床は一辺 6.4 の正方形1枚(三角形2枚)にしてある。
もっと大きくしたいところだが、大きくすると**カメラが回ったときに床が丸ごと消える**。

Day 6 の要点5のとおり、今の実装は「頂点が1つでもカメラの後ろにある三角形」を
まるごと捨てている。床は大きな三角形2枚なので、隅がカメラの後ろに回った瞬間に
床全体が消えてしまう。

制作中に実際にこれを踏んで、床が完全に見えなくなった。
カメラの周回半径(6.5)を床の対角の長さ(4.5)より大きく取ることで回避している。
**Day 10 のクリッピングを入れるとこの制約から解放される。**

`Vertex.InvW` は**投影を通した後だけ意味を持つ**フィールド。
モデル座標の頂点を作る時点では値が入っておらず、`DrawTriangle` が投影の途中で埋める。
きれいな設計ではないが、頂点の型を2つに分けるほどの複雑さでもないので同居させている。

## 完成条件

```
dotnet run --project reference/Day08 -c Release
```

1. **市松模様とオレンジの円**が描かれたテクスチャが、床と立方体に貼られている
2. 床のタイルが**奥へ行くほど小さく**なり、遠近感に沿って正しく縮んでいる
3. 立方体が回転し、6面すべてにテクスチャが貼られている
4. **P** キーで透視補正を切ると、**床のタイルが三角形の対角線で折れ曲がる**。
   正方形だったタイルがひし形に歪む。もう一度押すと直る
5. **F** キーでニアレストに切り替わると、立方体の模様が**ブロック状**になる。
   特に円の縁が階段状になる
6. **D** キーで深度表示、**W** キーでワイヤーフレーム
7. タイトルバーが `58.x fps | 38 tri | render 10.x ms | バイリニア | 透視補正:ON` のように

うまくいかないときの確認ポイント:

- **テクスチャが真っ黒 / 単色** → UV が頂点に設定されていない、または
  シェーダに渡す引数の順序が違う
- **床のタイルが対角線で折れる(Pキーを押していないのに)** → 透視補正が効いていない。
  `InvW` が投影時に埋められているか確認する
- **絵が少しぼやけて半テクセルずれる** → `SampleBilinear` の -0.5。要点3
- **UV が 1 を超えると落ちる / 変な色になる** → `WrapIndex` の負数対応。要点4
- **床が消える** → カメラが床の外側を回れていない。要点7
- **模様が上下反転する** → V の向き。画像の原点を左上とするか左下とするかの流儀の違い
  (OpenGL は左下、DirectX は左上。本リポジトリは左上)

## 改造課題

### 課題1(易): 補正とフィルタの効果を数字で見る

1. `P` と `F` を切り替えながら render 時間を記録し、要点5の表を再現する
2. **透視補正のコストがほぼゼロ**であることを確認する。なぜそうなるのか説明できるか
3. テクスチャの解像度を 32 → 512 に変える(`Texture.CreateTestPattern(512, 128)`)。
   バイリニアのコストはどう変わるか。**遅くなるはず**だが、その理由は
   計算量ではない(ヒント: 512x512x4バイト = 1MB は L2 キャッシュに乗るか?)

### 課題2(中): ラップモードを増やす

`Texture` に折り返し方の選択肢を足す。

1. **クランプ**: 0未満は0に、1以上は1に切り詰める。床の端がどうなるか
2. **ミラー**: 1を超えたら鏡像で折り返す。市松模様のつなぎ目がどう変わるか
3. 床の UV を 0〜4 ではなく **0.25〜0.75**(テクスチャの中央だけを引き伸ばす)にすると
   どう見えるか

さらに、**バイリニアとリピートの相性問題**にも触れておくとよい。
テクスチャの右端のテクセルは、リピートなら左端と混ぜるべきだが、
クランプなら右端の色をそのまま使うべき。
`SampleBilinear` の中で `WrapIndex` を使っているのはリピート前提の実装になっている。

### 課題3(難): ミップマップを実装する

要点6の縮小方向の問題に取り組む。

1. テクスチャを半分ずつ縮小した画像を、1x1 になるまで作る(ミップチェーン)
2. そのピクセルがテクスチャ上でどれだけの範囲を覆うかを求める。
   隣のピクセルとのUVの差(**UVの微分**)から計算できる。
   ラスタライザの走査ループで、x方向に1つ進んだときのUVの変化を出せばよい
3. 覆う範囲の大きさから適切なミップレベルを選び、そこから読む
4. さらに、**隣り合う2つのミップレベルを混ぜる**(トライリニア)と段差が消える

床の奥のちらつきが消えることを確認する。
GPUがミップマップを標準機能として持っているのは、この計算(特に2)を
ピクセルシェーダの外で自動的にやってくれるからで、
自分で書いてみるとその親切さが分かる。
