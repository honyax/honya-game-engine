## 理論の要点

### 1. OBJ は「頂点の一覧と面の一覧」でしかない

```
v  1.4  0.0  0.0      # 位置
vt 0.0  0.0           # テクスチャ座標
vn 1.0  0.0  0.0      # 法線
f  1/1/1  3/3/3  2/2/2   # 面(位置/UV/法線 の索引を3つ)
```

これだけ。索引は**1始まり**で、負の値は末尾からの相対を意味する。

テキスト形式でありサイズも速度も不利だが、**中身をエディタで開いて読める**のが学習には大きい。
「モデルファイルとは要するに頂点と面の一覧である」と腑に落ちる。
実用ではバイナリの glTF が主流で、そちらはパーサだけで数千行になる。

本Dayのローダが対応するのは実際に使う範囲だけ。マテリアル(mtl)、グループ、
スムージンググループは無視する。ただし次の3点は実際のファイルでよく出るので対応した。

- **多角形の面**(四角形以上)→ トライアングルファンで分割
- **負の索引**
- **法線が無いファイル** → 面法線を頂点で平均して自動生成

### 2. OBJ の頂点と、レンダラの頂点は別物

OBJ は位置・UV・法線を**別々の配列**で持ち、面がそれぞれを独立に参照する。
一方こちらの `Mesh` は「1つの頂点が位置もUVも法線も持つ」形(Day 9)。

そこで **(位置索引, UV索引, 法線索引) の組み合わせごとに頂点を1つ作る**。
同じ組み合わせが再登場したら使い回さないと、索引を使う意味(Day 9 の要点5)が消える。

```csharp
var vertexCache = new Dictionary<(int Position, int TexCoord, int Normal), int>();
```

**実測**: 本Dayのトーラス(561頂点 / 1024三角形のOBJ)を読み込むと、
できあがる `Mesh` も**ちょうど 561頂点 / 1024三角形**になった。
重複排除が正しく効いている証拠(効いていなければ 3072 頂点になる)。

### 3. V座標の反転 — 最も頻繁に踏むバグ

OBJ(と OpenGL)は**画像の左下**を原点とし、V が上に向かって増える。
本リポジトリのテクスチャは配列の先頭が左上なので、V は下に向かって増える。

```csharp
texCoords.Add(flipV ? new Vec2(uv.X, 1.0f - uv.Y) : uv);
```

**「テクスチャが上下逆さまになる」はグラフィックスで最頻出のバグ**で、原因はたいていここ。
どちらが正しいということはなく、単に流儀が2つあるだけなので、
どこかで必ず吸収する必要がある。

### 4. 背面カリング — Day 3 で捨てた符号を拾い直す

閉じた立体では、裏を向いた面は必ず表の面に隠れて見えない。
**見えないと分かっているものを、描く前に捨てる**のがカリング。

判定材料はすでに手元にある。Day 3 でエッジ関数から面積を求めたとき、
「負なら頂点を入れ替えて向きをそろえる」と書いて**符号を捨てていた**。
その符号こそが「表から見ているか裏から見ているか」の情報だった。

```csharp
bool frontFacing = area < 0.0f;
if (Culling == CullMode.Back && !frontFacing) { CulledTriangles++; return; }
```

符号がどちら向きになるかは、モデルの巻き方向・Y軸の向き・ビューポート変換のY反転が
積み重なって決まる。**覚えるより「片方を試して裏返っていたら逆にする」と割り切るのが早い。**
だからこそ Day 9 で全メッシュの巻き方向をそろえておくことが前提になる。

**実測**: 本Dayのシーンでは 2,202枚のうち **1,165枚(53%)がカリングされる**。
閉じた面の約半分は裏を向いている、という直感どおりの数字。

ただし**速度の改善は 6% にとどまった**(17.7 ms → 18.9 ms の差)。理由は2つ。

- シーンで最も広い面積を占める**床は片面なのでカリングできない**(`CullMode.None` で描いている)
- Day 7 の深度テストが**色を計算する前に**裏面を捨てているので、
  一番高い処理(テクスチャ + フォン)はもともと走っていなかった

つまり**Day 7 の時点ですでに大半の恩恵を得ていた**ということ。
それでもカリングを入れる価値はあり、頂点数が多くラスタライズ負荷が高いシーンでは効くし、
何より「片面しかない板」を正しく扱うための設定として必要になる。

### 5. クリッピングは近クリップ面だけでよい

Day 6 から引きずっていた制約——**頂点が1つでもカメラの後ろにあると三角形を丸ごと捨てる**——を、
今日ようやく解消する。

なぜ近クリップ面だけを切ればよいのか。

- **左右上下と遠クリップ面**は、はみ出しても壊れない。
  バウンディングボックスの画面内への切り詰め(Day 3)と深度テスト(Day 7)が面倒を見る。
  無駄な走査は増えるが、正しい絵は出る
- **近クリップ面だけは違う**。ここを跨ぐと透視除算で符号が反転し、
  三角形が画面の反対側へ裏返って飛んでいく。**除算の前に切るしかない**

切る条件は驚くほど単純で、**クリップ座標の Z が 0 以上か**。
本リポジトリの投影行列は近クリップ面を Z = 0 に写す(Day 6 の要点3)ので、
この不等式1つで判定できる。カメラの後ろの点も Z が負になるので、まとめて処理できる。

### 6. サザーランド・ホジマン — 多角形を平面で切る

多角形の辺を順に見て、次の4通りに振り分けるだけ。

| 辺の状態 | 出力するもの |
|---|---|
| 内 → 内 | 終点 |
| 内 → 外 | 交点 |
| 外 → 内 | 交点と終点 |
| 外 → 外 | 何も出さない |

三角形1枚を平面1つで切ると、結果は**頂点が最大4つの多角形**になる
(三角形の1頂点だけが外に出た場合)。それをファンで三角形に分割し直す。

**クリップ座標のまま補間してよいのがこの方法の美点。**
透視除算の前なのですべてが線形に扱え、位置も色もUVも法線も同じ比率で混ぜるだけで済む。
除算の後に切ろうとすると、Day 8 の透視補正と同じ問題に悩まされることになる。

これで床を**1枚の大きな四角形**にできるようになった。
Day 8 と Day 9 では、カメラの後ろに回ると床が丸ごと消えるのを避けるために
床を細かく分割したり小さくしたりしていたが、その必要がなくなった。

### 7. 実測 — Phase 1 の到達点と限界

Day 10 のシーン(トーラス1024枚 + 床 + 球 + 立方体、合計2,202枚)の実測:

| 設定 | render | 概算 fps |
|---|---|---|
| フォン + バイリニア(既定) | 17.8 ms | **約 41 fps** |   <!-- 固定フレームでの計測 -->
| フォン + ニアレスト | 14.6 ms | 約 47 fps |
| グーロー + バイリニア | 11.8 ms | 約 56 fps |
| グーロー + テクスチャ無 | 7.0 ms | 60 fps |

(上の表は同一フレームでの計測。実際に動かすとカメラの上下で床の占める面積が変わり、
16.8〜21.6 ms = **32〜41 fps** の範囲で変動する)

**Day 1 から守ってきた60fpsは、最高品質の設定では出せなくなった。**
これは実装の不備ではなく、CPUソフトウェアラスタライザの素直な限界と考えてよい。
内訳を見ると分かりやすい。

- **バイリニアフィルタ … 約 +7 ms**。テクセルを4個読むので、
  ほぼメモリアクセスのコストそのもの(ニアレストはほぼタダ)
- **ピクセル単位のフォン計算 … 約 +7 ms**。正規化(平方根)と `Pow` が毎ピクセル

640x480 = 307,200 ピクセルを、1ピクセルあたり数十ナノ秒で処理して、
ようやくこの数字になる。**Phase 2 でGPUに移る理由がここにある**——
GPUは同じ処理を数千の演算器で並列にこなす。

なおこれは「もう手が無い」という意味ではない。本ロードマップで扱わなかった
最適化がいくつも残っている(改造課題を参照)。

### 素材について

ライセンスの心配もネットワークも不要。生成に使った式は次のとおり。

```
位置 = ((R + r cos v) cos u,  r sin v,  (R + r cos v) sin u)
法線 = (cos v cos u,  sin v,  cos v sin u)     ※ 主半径 R=1.0 / 管半径 r=0.4
```

別のモデルを試したい場合は、同じ場所に置いて `ObjLoader.Load` のパスを変えればよい。

   `38.x fps | 1016 描画 / 1186 カリング | render 18.x ms | フォン | 背面カリング:ON` のように

床が画面を占める面積(= 塗るピクセル数)がフレームごとに変わるため。

うまくいかないときの確認ポイント:

- **モデルが表示されない / 内側から見たようになる** → カリングの符号が逆。
  `frontFacing` の条件を反転してみる(要点4)
- **モデルの表面がまだらに欠ける** → メッシュの巻き方向が不揃い(Day 9 の要点6)
- **テクスチャが上下逆** → `flipV`。要点3
- **床の一部が消える / 画面全体に巨大な三角形が走る** → クリッピングが効いていない。
  `ClipNearPlane` の内外判定の向きを確認する
- **カメラが物体を通り抜けるときにちらつく** → 正常。近クリップ面で切られている
- **素材が見つからない例外** → `assets/models/torus.obj` の場所。
  `ResolveAssetPath` は実行ファイルと作業ディレクトリの両方から上へ辿る
- **OBJ の読み込みで例外** → 小数点の解析。`CultureInfo.InvariantCulture` を指定しているか
  (地域設定によっては 1.5 が読めない)

## 改造課題

### 課題1(易): 別のモデルを読み込む

1. [tinyrenderer の african_head.obj](https://github.com/ssloy/tinyrenderer/tree/master/obj) など、
   外部のモデルを `assets/models/` に置いて読み込む
2. 法線が無いモデルなら、自動計算(`ComputeNormals`)が効くことを確認する。
   立方体のような角のある形だと、角が丸まって見えるはず。**なぜそうなるか**を説明できるか
3. モデルの三角形数と render 時間を記録する。三角形が1万枚を超えるとどうなるか

### 課題2(中): クリッピングを6面すべてに広げる

今日は近クリップ面だけを切った。左右上下と遠クリップ面も切ってみる。

1. クリップ座標での判定条件を書き出す
   (右: `x <= w`、左: `-w <= x`、上下も同様、遠: `z <= w`)
2. 平面を順に適用する(1つ切るたびに多角形の頂点が増えうる。最大で何頂点になるか?)
3. **速くなるか、遅くなるか測る。** 画面外に大きくはみ出す三角形がある場面では
   走査の無駄が減るが、そうでなければクリッピング自体のコストが乗るだけになる。
   要点5で「近クリップ面以外は切らなくてよい」と書いた判断が妥当だったか、数字で確かめる

### 課題3(難): 60fps を取り戻す

要点7の限界に正面から挑む。効果が大きい順に。

1. **エッジ関数のインクリメンタル化**(Day 3 の課題2)。
   走査ループから乗算を追い出す
2. **タイル分割**。画面を 32x32 などのタイルに分け、タイルごとに三角形を仕分けてから塗る。
   フレームバッファと深度バッファのアクセスがキャッシュに収まるようになる。
   現代のGPU(特にモバイル)はまさにこの方式
3. **SIMD 化**。`System.Runtime.Intrinsics` で4〜8ピクセルを同時に処理する。
   エッジ関数の判定も属性の補間も、ピクセル間に依存が無いので並列化しやすい
4. **マルチスレッド化**。タイル分割ができていれば、タイルを別スレッドに割り振るだけで済む。
   Zバッファのおかげで**描画順序が自由**(Day 7 の要点1)なのが効いてくる
5. テクスチャを**モートン順**(Zオーダー)に並べ替えて、バイリニアの4テクセルが
   キャッシュに乗りやすくする

1 と 2 だけでも大きく変わるはず。どこまで速くできるか、そして
**どこで頭打ちになるか**を体験しておくと、Phase 2 でGPUの速さを見たときの驚きが違ってくる。
