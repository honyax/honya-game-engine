2. シェーダは「1個につき1回」走る小さなプログラム

GPU のシェーダが CPU の関数と決定的に違うのは、呼び出し回数と並列性。

実行される単位今日の実行回数
頂点シェーダ頂点1個につき1回3回
フラグメントシェーダ塗るピクセル1個につき1回十数万回

Day 9 でフォンシェーディングが重かったのは、まさにこの「十数万回」をCPU が1コアで順番に回していたから(実測 +7ms)。GPU は同じ処理を数千の演算器に配って同時に走らせる。

もう1つの違いがコンパイルのタイミング。GLSL のコンパイルは実行時で、GPU ごとに命令セットが違うためドライバがその場で機械語に落とす。つまりシェーダの文法エラーは実行時にしか出ない。Day 12 で AllocConsole を仕込んでおいたのは、このログを読むため。

実際にセミコロンを1つ忘れると、こう出る(本Dayの環境で確認):

フラグメントシェーダのコンパイルに失敗した:
0(7) : error C0000: syntax error, unexpected identifier, expecting ',' or ';' at token "undefinedFunction"

0(7) は「0番目のソースの7行目」。行番号が出るので、ログさえ読めればデバッグは C# と大差ない。逆に、ログを捨てる実装にしてしまうと「何も出ない」だけが手掛かりという地獄になる。

3. VBO と VAO — 「データ」と「読み方」を分ける

初見でいちばん混乱するところなので、先に役割を分けておく。

  • VBO(Vertex Buffer Object)= GPU 上のただのバイト列。意味を持たない
  • VAO(Vertex Array Object)= そのバイト列をどう解釈するかの記録

今日の頂点データはこう並んでいる。1頂点が5つの float で、交互に詰めてある。

[ x, y, r, g, b ][ x, y, r, g, b ][ x, y, r, g, b ]
  └─位置─┘└─色──┘
  ← stride = 20バイト →

これを「位置は先頭から2個」「色は8バイト目から3個」と教えるのが glVertexAttribPointer。

csharp
GL.glVertexAttribPointer(0, 2, GL_FLOAT, GL_FALSE, stride, IntPtr.Zero);          // 位置
GL.glVertexAttribPointer(1, 3, GL_FLOAT, GL_FALSE, stride, new IntPtr(8));        // 色

第1引数の番号が、GLSL の layout (location = 0) と対応する。ここが食い違ってもコンパイルは通り、実行時に絵が壊れるだけなので気を付ける。

位置と色を別々の配列にする持ち方(SoA)もあるが、交互(AoS)にすると1頂点ぶんが連続するので GPU のキャッシュに乗りやすい。実際のモデルデータもほぼこの形で、Phase 1 の Vertex 構造体の配列と同じ発想。

VAO のおかげで、描画時は glBindVertexArray 1回で全部の設定が復元される。VAO が無かった OpenGL 2.x の時代は、描画のたびに全属性の設定を呼び直していた。コアプロファイルでは VAO は省略できない(0番のままだと描画がエラーになる)。

細かいが引っかかりやすい点を1つ。GL_ARRAY_BUFFER のバインドは VAO の状態に含まれないが、インデックスバッファ(GL_ELEMENT_ARRAY_BUFFER)は含まれる。改造課題2でインデックス描画をやると、ここを踏む。

4. 頂点属性・uniform・補間 — 3種類のデータの流れ

シェーダにデータが入る経路は2つ、出る経路は1つ。

種類変わる単位今日の例
頂点属性(in)頂点ごと位置、色
uniformドローコールごと(全頂点で同じ)変換行列
out → inラスタライザが補間して渡す色

3つ目が Day 4 の回収になる。頂点シェーダで

glsl
out vec3 vColor;   // 頂点ごとの色を出す

と書き、フラグメントシェーダで

glsl
in vec3 vColor;    // 補間済みの色が届く

と受けるだけで、間の補間は GPU がやる。Day 4 で自分で書いたバリセントリック座標の計算が、out と in の名前を揃えるだけになったのが今日の一番の実感どころ。しかも Day 8 で苦労した透視補正まで既定で入っている。

uniform について1つ注意。glGetUniformLocation が -1 を返してもエラーとは限らない。「そんな名前は無い」(タイプミス)のほかに、「宣言はしたが結果に影響しないので最適化で削除された」場合も -1 になる。シェーダを書き換えている最中によく出るので、警告を出すようにしてある。

5. 列優先(column-major)— 行列で最初に踏む地雷

glUniformMatrix4fv に渡す float[16] は、列優先で並んでいることが期待される。

行列                    配列の並び(列優先)
| m0  m4  m8  m12 |     [m0, m1, m2, m3,  m4, m5, m6, m7,  ...]
| m1  m5  m9  m13 |      └── 第0列 ──┘  └── 第1列 ──┘
| m2  m6  m10 m14 |
| m3  m7  m11 m15 |

つまり配列の最初の4要素が1行目ではなく1列目。m[列 * 4 + 行] の順で詰める。

行優先で持っている場合は第3引数の transpose を GL_TRUE にすればドライバが転置してくれるので、どちらでもよい。ただし片方に決めて一貫させること。 混ざると、「回転しているように見えるが向きが逆」「平行移動が効かない」といった原因の分かりにくい症状になる。

なお平行移動成分が m12, m13, m14 に入るのは列優先での話。Phase 1 の自作 Mat4 がどちらだったかを確認しておくと、Phase 3 で移植するときに困らない。

6. GLboolean は1バイト — マーシャリングの罠

glVertexAttribPointer の normalized と glUniformMatrix4fv の transpose はGLboolean 型で、これは C の unsigned char、つまり1バイト。

ところが C# の bool を P/Invoke でマーシャリングすると、既定では4バイトの Win32 BOOL になる(Win32 API の BOOL 引数ならこの既定で正しいが、GLboolean とはサイズが違う)。引数として渡すぶんには、32ビットでも64ビットでも1引数ずつ4・8バイトの枠に入るので、たいていずれずに動いてしまう。壊れるのは構造体のフィールドや配列の要素を bool で宣言した場合で、そこではバイト数の違いで後ろのデータがずれる。

このバインディングでは GLboolean を取る引数をすべて byte にして、GL_FALSE = 0 / GL_TRUE = 1 を定数で用意した。型が同じ名前でもサイズが違う——P/Invoke で最も静かに壊れる類の問題で、GLsizeiptr を int で受けてしまう事故(64bit でずれる)も同じ系統。

7. ドローコール1行の向こう側

csharp
GL.glDrawArrays(GL.GL_TRIANGLES, 0, 3);

CPU が送るのはこの1行だけ。この向こうで、頂点シェーダが3回、クリッピングと透視除算とビューポート変換、ラスタライズ、そしてフラグメントシェーダが十数万回走る。

うまくいかないときの確認ポイント:

  • 何も出ない(クリア色だけ) → 原因が多いので順に潰す。
    1. glBindVertexArray を描画前に呼んでいるか
    2. glEnableVertexAttribArray を忘れていないか(属性は既定で無効)
    3. shader.Use() を呼んでいるか
    4. uTransform が全部0の行列になっていないか(初期化忘れ)
  • 真っ白 / 真っ黒な三角形が出る → 色の属性が届いていない。glVertexAttribPointer の第1引数(1番)と GLSL の layout(location = 1) の対応、およびオフセット(8バイト)を確認

  • 横に間延びした二等辺三角形になる → アスペクト補正が入っていない。これはバグではなく NDC の仕様で、Phase 1 の投影行列と同じ話(要点5)
  • シェーダのコンパイルに失敗した → ログの行番号を読む。よくあるのは #version 330 core の書き忘れと、コアプロファイルで廃止された gl_FragColor の使用
  • GLSL のコメントの日本語が原因で落ちる → ソースの渡し方。自動マーシャリング(ANSI)ではなく UTF-8 で渡しているか(Shader.CompileShader)
  • uniform 'uTransform' が見つからない の警告 → シェーダ内で実際に使われていないと最適化で消える。gl_Position の計算に使っているか確認(要点4)
  • 描画が1フレーム目だけおかしい → glViewport を呼ぶ前に描いている

改造課題

課題1(易): シェーダを書き換えて遊ぶ

シェーダは実行時コンパイルなので、書き換え→実行のサイクルが速い。 まずは慣れる。

  1. フラグメントシェーダで色を反転する(FragColor = vec4(1.0 - vColor, 1.0))
  2. 頂点シェーダで、頂点を法線方向ではなく中心から外へ膨らませる (gl_Position に渡す前に aPosition * 1.5 など)
  3. わざと壊す。 セミコロンを消す、存在しない関数を呼ぶ、out の名前を片方だけ変える。それぞれどんなエラーメッセージになるか。リンクエラーとコンパイルエラーの違いは出るか
  4. W キーでワイヤーフレームにしたとき、なぜ色の混ざりが見えなくなるのかを説明できるか(ヒント: フラグメントシェーダが走るピクセルがどこか)

課題2(中): インデックスバッファで四角形を描く

三角形2枚で四角形を作る。素直にやると頂点が6個必要だが、実際には4個で足りる。

  1. 頂点を4個(四隅)にして、[0,1,2, 2,3,0] というインデックス配列を用意する
  2. GL_ELEMENT_ARRAY_BUFFER に EBO を作り、glDrawElements で描く(glDrawElements(GLenum mode, GLsizei count, GLenum type, const void *indices)。type は GL_UNSIGNED_INT)
  3. VAO のバインドを外す順序を変えて、壊してみる。要点3で触れたとおり EBO のバインドは VAO に含まれるので、VAO をバインドしたまま glBindBuffer(GL_ELEMENT_ARRAY_BUFFER, 0) を呼ぶと描画されなくなる。実際に踏んで、なぜかを説明できるか
  4. 頂点数とインデックス数を比べる。立方体(8頂点・36インデックス)ならどうか。Day 9 で索引付きメッシュにしたときの理屈がそのまま GPU 側に来ている

課題3(難): シェーダのホットリロード

実務で最も効く仕組み。 シェーダを書き換えるたびにアプリを再起動するのは、1日に何十回もやると効率が段違いに落ちる。

  1. シェーダのソースを C# の定数から .vert / .frag のファイルへ出す (パス解決は Phase 1 の ResolveAssetPath が参考になる)
  2. F5 キーで再読み込みして、シェーダプログラムを作り直す
  3. コンパイルに失敗しても落ちないようにする。 これが肝で、失敗したらエラーをコンソールに出して古いシェーダを使い続ける。落ちると結局再起動になってしまい、意味が半減する
  4. 発展: FileSystemWatcher でファイルの更新を検知し、保存した瞬間に反映されるようにする。ただし変更通知は複数回飛ぶことと、保存途中の不完全なファイルを読むことがあるので、少し待ってから読むなどの対策が要る
  5. 古いシェーダプログラムの glDeleteProgram を忘れないこと。何十回もリロードすると GPU リソースが積み上がる
