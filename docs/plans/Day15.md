## 理論の要点

### 1. 3つの責務に分ける

Day 14 の `CreateTriangle()` は、次の3つを一緒くたにやっていた。

| 責務 | 具体的には | 今日の担当 |
|---|---|---|
| **形** | 頂点の座標、面の張り方 | `Mesh<TVertex>` |
| **素材** | 画像データ、読み方の設定 | `Texture` |
| **見た目** | どのシェーダに、どの値を渡すか | `Material` |

分ける動機は「きれいだから」ではなく、**組み合わせが掛け算で増えるから**。
メッシュ10種 × マテリアル10種を直書きすると100通り書くことになるが、
分ければ 10 + 10 で済む。

**シェーダとマテリアルの違い**が最初は分かりにくいので、対比しておく。

- **シェーダ** … 処理そのもの(GPU で動くプログラム)。コンパイルが要る。**重い。使い回す**
- **マテリアル** … その処理に渡す値の組。ただのデータ。**軽い。いくつも作る**

「木箱」「石壁」「金属板」はマテリアルが3つあれば足り、シェーダは1本でよい。
**シェーダの本数を増やさずに見た目の種類を増やす**のがこの分離の目的。

今日のデモはそれをそのまま形にしてある。**メッシュ1枚・テクスチャ1枚・シェーダ1本**から、
マテリアルを2つ作るだけで違う見た目の四角形が2つ出る。

### 2. 誰がリソースを所有するか

抽象化すると必ず出てくるのが**寿命の問題**。GPU リソースは GC の管轄外なので、
「誰が `Dispose` するか」を決めておかないとリークか二重解放になる。

今日の方針はこう。

| クラス | 所有するもの | 所有しないもの |
|---|---|---|
| `Mesh` | VAO / VBO / EBO | — |
| `Texture` | テクスチャオブジェクト | — |
| `Material` | **何も所有しない** | シェーダ、テクスチャ(参照するだけ) |

`Material` が何も持たないのが肝。マテリアル2つが同じテクスチャを指しているとき、
片方を捨てたらテクスチャが消える、では困る。
**共有されるものは、共有される側が寿命を管理しない**。

今日は `Program` が全部の寿命を握っている。これは規模が小さいから成立する形で、
**ハンドルベースの正式な仕組みは Day 21(リソース管理)で作る**。

### 3. uniform には3つの階層がある

マテリアルを作ると「どの値をマテリアルに持たせるか」を決める必要が出てくる。
判断の基準は**何ごとに変わる値か**。

| 階層 | 変わる頻度 | 例 | 今日の担当 |
|---|---|---|---|
| **フレームごと** | 1フレームに1回 | ビュー行列、投影行列、時間 | `Program`(Day 16 でカメラへ) |
| **オブジェクトごと** | 描画1回ごと | モデル行列 | `Program` |
| **マテリアルごと** | マテリアル1つごと | 色、テクスチャ、UV倍率 | **`Material`** |

`Material.Apply()` に3階層すべてを詰め込みたくなるが、そうすると
「同じマテリアルで100個描く」ときに毎回ビュー行列を送り直すことになる。
**変わらない値を毎回送らない**ための線引きで、Day 17〜18 の
スプライトバッチ(1万枚を最小のドローコールで)で決定的に効いてくる。

だから今日のコードは、こう分かれている。

```csharp
material.Apply();                                   // マテリアルごと
material.Shader.SetMatrix4("uTransform", transform); // オブジェクトごと
mesh.Draw();
```

### 4. テクスチャの上下反転 — Day 10 の V 座標問題、再び

画像ファイルは「1行目 = 画像の一番上」で保存されている。
一方 OpenGL のテクスチャは「最初のテクセル = UV(0,0)」で、**UV の原点は左下**。
素直に流し込むと上下が逆さまになる。

```csharp
StbImage.stbi_set_flip_vertically_on_load(1);
```

Day 10 の要点3で「テクスチャが上下逆さまになるのはグラフィックスで最頻出のバグ」と書いた話が、
そっくりそのまま GPU 側でも起きる。**どちらが正しいということはなく、流儀が2つあるだけ**なので、
どこかで必ず吸収する必要がある。

今日は「読み込み時に反転する」を選んだ。こうしておくと、
四角形の左下の頂点に UV(0,0) を割り当てたときに
**画像ファイルで見たとおりの向き**で表示される。

本Dayのテスト用テクスチャには、これを一目で判定できるよう
**UV原点に白い四角**を入れてある。実際に描いた結果、白い四角は
左の四角形の**左上**に出た——元の PNG でも白は左上なので、向きは正しい。

### 5. フィルタとラップ — 自作したものが設定1つになる

Day 8 で「バイリニアはテクセルを4個読むのでメモリアクセスのコストそのもの、実測 +7ms」
と書いた処理は、GPU では**設定1つ**になる。

```csharp
_gl.TexParameter(TextureTarget.Texture2D, TextureParameterName.TextureMinFilter, ...);
```

やっていることは同じで、**専用回路が受け持つようになっただけ**。

ここで Phase 1 に無かったものが1つ増える。**ミップマップ**。
縮小版をあらかじめ作っておき、遠くの物体には縮小済みのものを使う。
原寸から間引くとテクセルを飛ばし飛ばし読むことになり、模様がちらつく(エイリアシング)。
「遠くのテクスチャがチカチカする」の答えがこれで、`GenerateMipmap` 1行で用意できる。

フィルタの指定に**非対称性**がある点に注意。

| | ミップマップ指定 | 理由 |
|---|---|---|
| MinFilter(縮小時) | **できる** | 縮小するのだから縮小版を使う |
| MagFilter(拡大時) | **できない** | 拡大するのに縮小版は要らない |

MagFilter に `LinearMipmapLinear` を指定すると `GL_INVALID_ENUM` になる。
Day 13 の要点で書いたとおり OpenGL は黙って続行するので、
「なぜか拡大時だけ効かない」という形で現れる。

**ラップモード**は UV が 0〜1 の外に出たときの扱い。実測で確認した違い:

| モード | UV倍率2 のときの見え方 |
|---|---|
| `Repeat` | 模様が**縦横2回ずつ、計4枚**繰り返される |
| `ClampToEdge` | 左下に1枚だけ出て、**残りは端の色が引き伸ばされる** |

### 6. テクスチャユニットという段

Phase 1 では `Texture` オブジェクトを直接サンプリング関数に渡していた。
GPU では**間に「ユニット」という段が挟まる**。

```
シェーダ: 「0番のユニットを見ろ」   ← sampler2D uTexture に int の 0 を渡す
C#側:    「0番にこのテクスチャを刺す」 ← ActiveTexture(Texture0) + BindTexture
```

回りくどく見えるが、これがあるおかげで**1回の描画で複数のテクスチャを使える**。
Day 34 の法線マップ(色テクスチャ + 法線テクスチャ)で本領を発揮する。

**間違えやすいのは `sampler` に何を渡すか。** 渡すのはテクスチャのハンドルではなく
**ユニットの番号(int)**。ハンドルを渡してしまっても、それが小さい整数だと
偶然動いてしまうことがあるぶん厄介。

### 7. 頂点を構造体にする

Day 14 は `float[]` に `[x, y, r, g, b]` を手で並べていた。構造体にすると:

- **意味のある名前**で書ける
- コンパイラが**サイズとオフセットを計算**する
- 用途の違う頂点(Day 17 のスプライト用)を別の型として区別できる

```csharp
[StructLayout(LayoutKind.Sequential)]
internal struct Vertex
{
    public Vector3 Position;
    public Vector2 TexCoord;
    public Vector4 Color;

    public static ReadOnlySpan<int> AttributeSizes => [3, 2, 4];
}
```

`StructLayout(Sequential)` が要るのは Day 11 で Win32 の構造体に付けたのと同じ理由。
**これが無いと CLR がフィールドを詰め替えてよい**ことになっており、
教えたオフセットと食い違う可能性がある。

`Mesh` 側は `Unsafe.SizeOf<TVertex>()` でストライドを取り、
`AttributeSizes` を順に足してオフセットを組み立てる。
そして**合計がサイズと一致するか検算する**。

```csharp
if (offset != stride) throw new InvalidOperationException(...);
```

属性の記述を間違えると、GL は何も言わずに壊れた絵を出す。
自分で検算しておけば、**絵を見る前に例外で気付ける**。

なお今日の実装は**全属性が float 前提**の簡易版。色を byte 4個に詰めて
頂点を小さくしたくなるのは Day 17 で、そこで拡張することになる(改造課題3)。

## 改造課題

### 課題1(易): マテリアルとテクスチャ設定で遊ぶ

**マテリアルを増やすのがどれくらい安いか**を体感する。

1. 3つ目・4つ目のマテリアルを作って四角形を増やす。
   **メッシュもテクスチャもシェーダも増やさずに**見た目を変えられることを確認する
2. `Tint` のアルファを 0.5 にしてみる。**半透明にならない**はず。
   なぜか(ヒント: ブレンドは既定で無効。`gl.Enable(EnableCap.Blend)` と
   `gl.BlendFunc(...)` が要る)。有効にして半透明を出す
3. `UvScale` に 0.5 や負の値を入れる。何が起きるか
4. `Texture.FromFile` の `stbi_set_flip_vertically_on_load(1)` を `0` にする。
   **白い四角がどこへ移動するか**を予想してから実行する(要点4)

### 課題2(中): テクスチャを2枚使う

要点6のテクスチャユニットを実際に2つ使う。

1. 2枚目のテクスチャ(市松でない別のもの。単色グラデーションなどを自作してもよい)を
   ユニット1にバインドする
2. フラグメントシェーダに `uniform sampler2D uTexture2;` を足し、
   `SetInt("uTexture2", 1)` で番号を教える
3. 2枚を混ぜる。まずは単純な乗算、次に
   `mix(texel1, texel2, uBlend)` で `uBlend` をマテリアルのパラメータにする
4. `Material` に `Texture? SecondTexture` を足す。
   **テクスチャが N 枚になったときにどう持つべきか**を考える
   (配列? 名前付きの辞書? Day 32 で glTF の PBR マテリアルを読むと
   ベースカラー・法線・メタリックラフネス・オクルージョンで4枚以上になる)

### 課題3(難): 頂点属性の型に対応する

要点7で書いた「全属性 float 前提」の制約を外す。**Day 17 への直接の布石**。

1. `AttributeSizes`(`int[]`)を、型情報を持つ記述に置き換える。
   最低限「要素数・型・正規化するか」の3つが要る
2. 色を `Vector4`(16バイト)から **`byte` 4個(4バイト)** に変える。
   1頂点が 36バイト → 24バイト になる
3. `glVertexAttribPointer` の **`normalized` を true** にする。
   これで 0〜255 の byte が、シェーダ側では 0.0〜1.0 の float として読まれる。
   **Day 13 の要点6で「GLboolean は1バイト」と書いた引数がこれ**
4. 頂点数を1万に増やして、24バイト版と 36バイト版で fps を比べる。
   **差が出るか。出ないなら、その理由は何か**
   (ヒント: 今のシーンは頂点数ではなくピクセル数で決まっている)
5. 発展: 位置を `float` から半精度(`half`)にできるか。
   どこまで削ると絵が壊れ始めるか

4 は特に大事で、**「小さくすれば速い」は測るまで分からない**。
Day 2 と Day 9 で繰り返し踏んだのと同じ話が、GPU 側でも起きる。
