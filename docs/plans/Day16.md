## 理論の要点

### 1. カメラの正体は行列2本しかない

「カメラ」という実体はレンダラの中に存在しない。あるのは次の2つだけで、
これは Phase 1 でも今日でも変わらない。

- **ビュー行列** … カメラを動かす代わりに、世界のほうを逆向きに動かす。
  カメラが右に3進んだ景色は、世界が左に3ずれた景色と同じ
- **投影行列** … 奥行き(ビュー座標の z)を W にコピーする。
  遠近感そのものはこの行列ではなく、**そのあとの透視除算**(x, y, z を W で割る)で生まれる

`Camera` クラスがやっているのは、人間に扱いやすい言葉(位置・注視点・視野角)から
この2本を組み立てることだけ。Day 6 で自作した `Camera` とほぼ同じ形にしてあるので、
`git diff --no-index reference/Day10/Camera.cs reference/Day16/Camera.cs` で見比べるとよい。

`Matrix4x4.CreateLookAt` は Phase 1 の `Mat4.LookAt` と**まったく同じもの**を作る。
右手系・カメラは -Z 方向を見る・行ベクトル規約、と3つとも一致しているのでそのまま使える。
「そのまま使えると判断できる」ために自作したのが Day 5〜6 だった。

### 2. System.Numerics の投影行列は、OpenGL にそのまま渡せない

今日いちばん引っかかりやすいところ。

`Matrix4x4.CreatePerspectiveFieldOfView(fov, aspect, near, far)` は名前も引数も
ぴったりだが、**深度を 0〜1 に写す DirectX の規約**で作られている。
OpenGL の NDC は z が **-1〜1**。Phase 1 の `Mat4.Perspective` も DirectX 側に
合わせてあった(自前の Z バッファがその範囲を前提にしていたため)。

行列の違いは Z に関わる2成分だけ。

| | M33 | M43 |
|---|---|---|
| DirectX(`System.Numerics`) | `f/(n-f)` | `nf/(n-f)` |
| OpenGL(`Camera.CreatePerspective`) | `(f+n)/(n-f)` | `2fn/(n-f)` |

遠近感を作る仕掛け(`M34 = -1` で z を W にコピーし、透視除算で割る)は共通で、
**違うのは「割ったあとの z をどの範囲に収めるか」だけ**。

厄介なのは、間違えても**絵が出てしまう**こと。深度の大小関係は保たれるので
前後関係は正しく描かれ、一見なんともない。壊れるのは次の2点で、
`near = 0.1 / far = 100` で実測すると次のようになる
(板を1枚置いて深度バッファを読み出した値。`1.00000` は「描かれなかった」)。

| ビュー座標 z | 自作(OpenGL規約) | `System.Numerics` |
|---|---|---|
| -0.0499 | クリップ | クリップ |
| -0.0501 | クリップ | **描画** 深度 0.00150 |
| -0.0700 | クリップ | **描画** 深度 0.28550 |
| -0.0999 | クリップ | **描画** 深度 0.49950 |
| -0.1001 | 描画 深度 0.00100 | 描画 深度 0.50050 |
| -1.0 | 0.90090 | 0.95045 |
| -10.0 | 0.99099 | 0.99550 |

読み取れることは2つ。

1. **近クリップ面が near/2 まで手前にずれる**。`near = 0.1` と指定したのに
   0.0501 の板が描かれている。正確には `nf/(2f-n)`(この条件で 0.050025)
2. **深度バッファの半分(0〜0.5)が、本来クリップされるはずの隙間に食われる**。
   指定した near の位置で深度が 0.5 になってしまっている

どちらも「なんとなく変」で済んでしまい、遠くで Z ファイティングが出て初めて疑うことになる。
だから今日は `Camera.CreatePerspective` / `CreateOrthographic` を自前で持つ。

補足: OpenGL 4.5 以降なら `glClipControl(GL_LOWER_LEFT, GL_ZERO_TO_ONE)` で
GPU 側を 0〜1 に切り替えられる(むしろ精度的にはそちらが有利)。
今日は 3.3 コアプロファイルなので使えない。

### 3. 深度テスト — Day 7 のZバッファが設定2行になる

Phase 1 では `float[,]` を確保し、毎フレーム `float.MaxValue` で埋め、
ピクセルを書く前に比較していた。GPU では次で終わる。

```csharp
gl.Enable(EnableCap.DepthTest);
gl.DepthFunc(DepthFunction.Less);   // 既定値。「小さい = 手前」
```

そして毎フレーム、**色と一緒に深度も消す**。

```csharp
gl.Clear(ClearBufferMask.ColorBufferBit | ClearBufferMask.DepthBufferBit);
```

注意点は2つ。

- **深度テストは既定で無効**。有効化を忘れると「あとから描いたものが手前に来る」
  という、Day 7 以前の絵になる。3D で最初に踏むバグの筆頭
- 深度バッファは**ウィンドウ生成時に要求**しておく必要がある。
  Silk.NET の既定でも 24bit が付いてくるが、
  `PreferredDepthBufferBits = 24` と書いておくと意図が残る

Z キーで切り替えられるようにしてあるので、切ってからカメラを回すとよい。
描いた順で前後が固定されるので、**回すたびに前後関係が破綻する**のが見える。
これが Day 7 で「描く順で解決するのは無理」と書いたことの実演になっている。

なお、`glGetIntegerv(GL_DEPTH_BITS)` で深度のビット数を問い合わせる方法は
**コアプロファイルでは使えない**(`GL_INVALID_ENUM` になる)。
デフォルトフレームバッファの属性は
`glGetFramebufferAttachmentParameteriv` で引く決まりになっている。

### 4. 背面カリング — Day 10 の判定が設定3行になる

閉じた立体では、裏を向いた面は必ず表の面に隠れる。だから描く前に捨ててよい。

```csharp
gl.Enable(EnableCap.CullFace);
gl.CullFace(TriangleFace.Back);
gl.FrontFace(FrontFaceDirection.Ccw);   // 既定値。反時計回りが表
```

判定の中身は Day 10 とまったく同じ。**スクリーン上での三角形の回り方**、
つまり Day 3 のエッジ関数が返す符号付き面積の符号を見ているだけで、
Day 10 で `bool frontFacing = area < 0.0f;` と書いた1行が
`gl.FrontFace(...)` の設定に置き換わっている。

Day 10 では「符号の向きは規約の積み重ねで決まるので、片方を試して
裏返っていたら逆にする」と割り切ったが、OpenGL はそこを
**CCW が表**と決めてくれている(Y の向きも含めて規約が固定されている)ぶん、
迷わなくてよい。

このため、**頂点を並べる順が意味を持つ**。`Primitives.CreateCube` は
6面すべて「外から見て反時計回り」にそろえてある。1面でも間違えると、
その面だけ**内側から覗いたときに見える**という分かりやすい壊れ方をする。

C キーで切り替えられる。塗りつぶしのままだと見た目はほとんど変わらない
(そもそも隠れている面なので当然)が、W キーでワイヤーフレームにすると
裏側の線が出るので違いが分かる。**描画結果を変えずに仕事量を半分にする**、
という最適化の典型例。

### 5. uniform の3階層が完成する

Day 15 で書いた「uniform には3つの階層がある」が、今日そろう。

| 階層 | 中身 | 誰が、いつ送るか |
|---|---|---|
| フレームごと | ビュー射影行列、時間 | `Program` がフレーム頭で**1回** |
| オブジェクトごと | モデル行列 | 描画のたびに `Draw` が |
| マテリアルごと | 色、UV倍率、テクスチャ | `Material.Apply()` が |

Day 15 は3つを `uTransform` 1本に混ぜていた。今日それを
`uViewProjection`(フレーム)と `uModel`(オブジェクト)に分ける。

分けられる根拠は、**uniform がプログラムに紐づく状態**であること。
`glUseProgram` を呼び直しても値は消えないので、フレーム頭で1回入れれば
そのフレームの全ドローコールで有効なままになる。
オブジェクトが100個あっても、ビュー射影行列を送るのは1回でよい。

```csharp
// フレーム頭。1回だけ
_shader.Use();
_shader.SetMatrix4("uViewProjection", _camera.ViewProjection);

// オブジェクトごと
material.Apply();                              // マテリアル階層
material.Shader.SetMatrix4("uModel", model);   // オブジェクト階層
mesh.Draw();
```

GLSL 側の掛ける順にも注意。C# は行ベクトル規約なので `model * view * projection`
だが、GLSL は列ベクトル規約なので**逆に左から書く**。

```glsl
gl_Position = uViewProjection * uModel * vec4(aPosition, 1.0);
```

Day 14 の要点4で見たとおり、この2つは同じ変換を表している。

### 6. カメラと、カメラの操作方法を分ける

`Camera` は「どこから、どこを、どんなレンズで見るか」しか知らない。
マウスもキーボードも知らない。入力から `Camera` の値を作るのは
`OrbitCameraController` の仕事にしてある。

分ける理由は、**同じ Camera を別の操作方法で使い回したいから**。
一人称視点、三人称追従(Day 50)、シネマティックの固定カメラ、
どれも「Camera が要る」のであって「マウスが要る」わけではない。
ここを混ぜると、カメラを使いたいだけなのにマウスへの依存が付いてくる。

位置は**球面座標**で持つ。半径 d・水平角 yaw・仰角 pitch から:

```
x = d * cos(pitch) * sin(yaw)
y = d * sin(pitch)
z = d * cos(pitch) * cos(yaw)
```

`cos(pitch)` が x と z の両方に掛かるのは、**上を向くほど水平方向の半径が縮む**から
(地球儀の緯線が極に近いほど短くなるのと同じ)。
直交座標で持つと「距離を保ったまま回す」のが面倒なのに対し、
球面座標なら回転は角度の足し算、ズームは距離の掛け算で済む。

仰角は ±86度あたりで止めてある。真上・真下に来ると視線と `Up` が平行になり、
`LookAt` が軸を作れずに絵が壊れる。この破綻を根本的に避けるには
クォータニオンが要る(特論 A-4。Phase 4 の Transform で扱う)。今日は角度制限で回避する。

ズームは**加算ではなく乗算**にしてある。加算だと近くでは動きすぎ、
遠くでは動かなすぎる。「今の距離に対する割合」で動かすと、どの距離でも同じ操作感になる。

### 7. アスペクト比はカメラの持ち物になった

Day 15 は `Matrix4x4.CreateScale(1.0f / aspect, 1, 1)` を毎フレーム
モデル行列に混ぜ込んでいた。これは本来カメラの仕事なので、今日は
`Camera.AspectRatio` に移した。移した結果、**ウィンドウのリサイズに対応できる**。

リサイズ時にやることは2つで、どちらを忘れても絵が歪む。

1. `gl.Viewport(size)` … クリップ座標 → ピクセルの対応。古いと描画範囲がずれる
2. `camera.AspectRatio = w / h` … 古いと絵が縦長・横長に潰れる

イベントは `Resize` ではなく **`FramebufferResize`** を使う。
高DPI環境では**ウィンドウのサイズ(論理ピクセル)と描画先のサイズ(物理ピクセル)が
一致しない**ためで、ビューポートは物理ピクセルで指定する必要がある。
Day 11 で `SetProcessDpiAwarenessContext` を叩いたときと同じ話が、
Silk.NET 側では「どちらのイベントを使うか」という形で出てくる。

## 改造課題

### 課題1(易): 投影行列を壊して、症状を観察する

要点2を体で確認する。**症状から原因を逆算できるようになる**のが目的。

1. `Camera.CreatePerspective` の中身を
   `Matrix4x4.CreatePerspectiveFieldOfView(fieldOfViewY, aspectRatio, near, far)` に
   差し替える。**絵はほとんど変わらない**ことを確認する
2. `NearPlane` を `0.1` のまま、カメラを立方体にめり込むまで寄せる
   (`MinDistance` を `0.05` くらいまで下げる)。
   自作版と差し替え版で、**面が消え始める距離が違う**ことを見る
3. `FarPlane` を `100` から `10000` に上げ、遠くに小さな立方体を2つ、
   ほぼ同じ深さに重ねて置く。**どちらの版が先に Z ファイティングを起こすか**
4. `NearPlane` を `0.001` にする。3 の Z ファイティングがどうなるか。
   「near はできるだけ大きく」の意味を確認する

### 課題2(中): カメラの操作方法をもう1つ作る

要点6の分離が効いていることを確かめる。**`Camera.cs` に一切手を入れずに**やる。

1. `FlyCameraController` を作る。WASD で前後左右、Q/E で上下、
   右ドラッグで視線の向き(いわゆるFPS操作)
2. `Camera.Position` と「向き」から `Target` を作る必要がある。
   `Target = Position + forward` でよい。`forward` は yaw/pitch から作る
3. Tab キーで `OrbitCameraController` と切り替えられるようにする
4. 移動速度を**フレーム時間に比例**させる。していないと、
   VSync を切った(V キー)ときに操作が速くなりすぎる。
   これは Day 19 の固定タイムステップにつながる問題

余力があれば、視野角(`FieldOfView`)をホイールに割り当ててみる。
**距離で寄るのと視野角で寄るのは別物**で、後者は遠近感そのものが変わる
(映画のドリーズーム)。両方を試すと `FieldOfView` の意味がはっきりする。

### 課題3(難): 視錐台カリングを入れる

背面カリング(要点4)は「面」を捨てる仕組みだった。
今度は**オブジェクトごと捨てる**。Day 26 の空間分割、Day 46 のブロードフェーズ、
そしてアセットが増える Day 39〜40 のデモ組み上げに直接つながる。

1. `Primitives.CreateCube` に、そのメッシュを包む球(中心と半径)を持たせる。
   立方体なら中心は原点、半径は `sqrt(3)/2 * scale`
2. ビュー射影行列から**視錐台の6平面**を取り出す(Gribb-Hartmann 法)。
   行ベクトル規約(`System.Numerics`)では `clip = v * M` なので、
   `clip.x` は **M の第1列**との内積になる。だから使うのは行ではなく**列**:

   ```
   c1 = (M11, M21, M31, M41)   c2 = (M12, M22, M32, M42)
   c3 = (M13, M23, M33, M43)   c4 = (M14, M24, M34, M44)

   左 = c4 + c1   右 = c4 - c1
   下 = c4 + c2   上 = c4 - c2
   近 = c4 + c3   遠 = c4 - c3
   ```

   各平面は `(a,b,c)` の長さで割って正規化してから使う。
   近平面が `c4 + c3` になるのは NDC の z が **-1〜1** だから。
   要点2で 0〜1 の行列を使っていたら、ここも `c3` 単体に変わる
3. 各オブジェクトについて、包む球が6平面すべての内側にあるかを調べ、
   外なら `Draw` を丸ごと飛ばす
4. 立方体を 10000 個に増やし、カリングの ON/OFF で fps を比べる。
   **カメラを回すと fps が変動する**はず。何を見ているときが一番速いか
5. 発展: この判定は「見えないものを捨てる」だけで、**見えているものは全部描く**。
   手前の壁に完全に隠れた 1000 個は捨てられない。
   これを扱うのがオクルージョンカリングで、
   Day 51 のディファードレンダリングと問題意識を共有している

4 で fps が上がらなかったら、それも収穫。**ボトルネックが CPU 側の
ドローコール発行なのか、GPU 側のピクセル処理なのか**が分かる。
Day 17〜18 のスプライトバッチは前者を潰す話なので、その前提を測っておく意味がある。

## 動作確認済み環境

- .NET SDK 10.0.102 / Windows 11 / NVIDIA GeForce RTX 3070(ドライバ 596.49)
- Silk.NET 2.23.0 / StbImageSharp 2.30.16 / OpenGL 3.3 コアプロファイル
- 960x640 / VSync ON で 60.0 fps
- フレームバッファを読み出して画像化し、次を確認:
  - 透視投影で床が地平線に収束し、6個の立方体が正しい前後関係で描かれる
  - 深度テスト OFF で、奥の立方体が手前の立方体を上書きする
  - 平行投影で床のマス目が均一になり、遠近による大小差が消える
  - ワイヤーフレーム + カリング OFF で、立方体の裏側の稜線と面の対角線が見える
  - 背面カリング ON のまま面が欠けない(6面の CCW がそろっている)
- 深度規約の差は板を1枚置いて深度バッファを読み出して実測(要点2の表)。
  `System.Numerics` 版は z = -0.0501 の板を描いてしまい、
  指定した near(-0.1)で深度が 0.5005 になることを確認
- `dotnet build` 警告 0 / `dotnet format whitespace --verify-no-changes` 差分 0
