Phase 3 / ロードマップ該当行: 「2Dスプライトバッチ(動的頂点バッファ)」

今日のゴール

Day 16 の3Dシーンの上を、1万枚のスプライトが飛び回っても 60fps を割らない。

ここまでの Mesh<TVertex> は「1つの形 = 1回の glDrawElements」だった。その調子でスプライトを1万枚描くと、1万回のドローコールになる。実測すると、それだけで1フレーム 38.6ms かかる(60fps の予算は 16.6ms)。

今日は同じ1万枚を4回のドローコールで描く。0.6ms になる。GPU の仕事量は変わっていない。減らしたのは「描けと命じる回数」だけ。

事前に読む資料

ロードマップの指定は「-」(特論に対応する回が無い)。実装寄りの回なので、次を読んでおくと引っかかりが減る。

  • Buffer Object Streaming — OpenGL Wiki —毎フレーム書き換えるバッファの扱い。オーファニングもここ
  • Blending — LearnOpenGL —アルファブレンドと、半透明を描く順の話
  • Vertex Specification Best Practices — OpenGL Wiki —頂点フォーマットをどう決めるか
  • 復習として Day13.md の要点3(VAO/VBO/EBO) と Day15.md の要点7(頂点構造体)。今日はそこに「毎フレーム作り直す」が加わるだけ

理論の要点

1. ドローコールは1回いくらか

「ドローコールは高い」とよく言われるが、いくらなのかを測っておくと判断が早くなる。このリポジトリのスプライト(テクスチャ1枚、uniform 変更なし)で測ると:

条件ドローコールfpsms/frame
1000枚 バッチあり216280.614
1000枚 バッチなし10002583.879
10000枚 バッチあり416530.605
10000枚 バッチなし1000025.938.629
20000枚 バッチあり69481.055

バッチなしの2行から、ドローコール1回あたり約 3.9 マイクロ秒と読める(3.879ms / 1000 も 38.629ms / 10000 も同じ 3.9µs になる。きれいに線形)。

この数字が分かると、予算が計算できる。60fps の 16.6ms を全部ドローコールに費やしても 4200回 が上限。実際には他の処理もあるので、現実的な目安は1フレーム 1000〜2000 回。「1万個のオブジェクトを個別に描く」は最初から成立しない。

そして高いのは CPU 側であることに注意。GPU は 10000 回でも 4 回でも同じ量の三角形を塗っているだけで、暇をしている。GPU を遊ばせないために CPU の口数を減らすのがバッチング。

2. バッチの原理 — 「1万個の絵」を「1個の巨大な絵」にする

やることは単純で、1万枚ぶんの頂点(4万頂点)を1本のバッファに詰めて、1回で描かせる。GPU から見れば4万頂点の三角形リストでしかなく、それが1万個の別々の絵だとは知らない。

これを成立させるには条件がある。オブジェクトごとの uniform を持てないこと。

Day 16 の 3D 描画は、オブジェクトごとに uModel を送っていた。これをスプライトでやると、1万回 glUniformMatrix4fv を呼ぶことになり、ドローコールを減らした意味が消える。

だからスプライトバッチは、位置・回転・大きさを CPU 側で頂点に焼き込む。SpriteBatch.Draw が回転行列を掛けた4隅の座標を計算して配列に書く。シェーダに渡る uniform は、フレームに1本の投影行列だけになる。

3D  : 頂点は固定、行列で動かす        → オブジェクトごとに uniform が要る
2D  : 頂点そのものを毎フレーム作り直す → uniform はフレームに1本

「毎フレーム4万頂点ぶんの座標を CPU で計算するのは無駄では?」と思うところだが、そのコストは実測 0.6ms の中に収まっている。3.9µs × 1万回のほうが桁違いに高い。

3. 動的頂点バッファ

Mesh<TVertex> を使い回せないのは、あちらが StaticDraw で「1回アップロードして、あとは読むだけ」を前提にしているから。

スプライトバッチのバッファの扱いは3点で違う。

(a) 確保と書き込みを分ける

csharp
// 生成時: サイズだけ確保。中身は未定義(第3引数が null)
gl.BufferData(ArrayBuffer, capacity * 4 * sizeof(SpriteVertex), null, BufferUsageARB.StreamDraw);

// 毎フレーム: 使ったぶんだけ上書き
gl.BufferSubData(ArrayBuffer, 0, vertexCount * sizeof(SpriteVertex), data);

StreamDraw は「毎フレーム書き換えて、数回描いて捨てる」という使い方の申告。StaticDraw / DynamicDraw / StreamDraw はドライバへのヒントでしかなく、間違えても動く。ただしドライバはこれを見てメモリの置き場所を決めるので、嘘をつくと遅くなることがある。

(b) インデックスバッファは静的でよい

四角形 i の頂点は必ず 4i, 4i+1, 4i+2, 4i+3 に並ぶので、インデックスの中身はスプライトの内容に一切依存しない。だから生成時に capacity * 6 個を1回作れば、あとは触らない。動的なのは頂点だけ、というのが見落としやすいところ。

(c) オーファニング — 定番と言われているが、測ったら効かなかった

同じバッファに BufferSubData で上書きするとき、GPU がまだ前フレームの描画でそのバッファを読んでいると、ドライバは読み終わるのを待つ(CPU が止まる)。そこで同じサイズ・同じ用途で BufferData を呼び直すと、「前の中身はもう要らない」という宣言になり、ドライバは古い領域を GPU に使わせたまま新しい領域をこちらに渡す。古い領域は描き終わったら回収される(= 孤児 orphan にする)。動的バッファの定番テクニックとされている。

このデモで測った結果:

条件ドローコールfpsms/frame
20000枚 オーファニング ON6944.51.059
20000枚 オーファニング OFF6947.71.055

差は 0.3% 以内。1000枚では ON のほうがむしろ遅かった。理由は単純で、待つほど GPU が遅れていないから。オーファニングは「待ちを消す」技であって、待ちが無いところではBufferData の呼び出しぶんだけ損をする。効くのは GPU 律速のとき。

なので既定は OFF にして、O キーで切り替えられるようにしてある。Day 2(Bresenham)・Day 9(シェーディング)で繰り返し踏んだのと同じ話で、定番と呼ばれる手法でも、自分の負荷で測るまでは分からない。

4. フラッシュの条件 — バッチが「効かなくなる」のはいつか

SpriteBatch が溜めたぶんを吐き出す(= ドローコールを1回発行する)のは2つの場合。

  1. テクスチャが変わる … シェーダに刺さっているテクスチャは1つだけなので、違う絵を同じドローコールに混ぜられない
  2. バッファが満杯 … 物理的に入らない

1 が今日いちばん大事なところ。バッチは「連続する描画が同じ状態を使っている」ときにしか効かない。テクスチャを交互に使うと、こうなる:

条件ドローコールfps
1000枚 テクスチャごとにまとめる21628
1000枚 交互に描く1000255

バッチは有効なのに、バッチなし(258 fps)とほぼ同じ。まとめる仕組みがあるだけでは足りず、まとめられる順に描く必要がある。

今日のデモは呼び出し側が手で分けている(偶数番 → 奇数番)が、本来これはバッチの中でやるべき仕事。それが Day 18 のソートで、そもそもテクスチャを1枚にまとめてしまうのがアトラス。今日はこの問題を T キーで体感するところまで。

2 のほうは容量とのトレードオフ。容量 4000 なら 2万枚で 6 回のドローコール(円 1万枚で3回 + リング 1万枚で3回)。容量を上げればドローコールは減るが、頂点バッファのメモリが増える(4000枚 = 4000 × 4頂点 × 32バイト = 512KB)。ドローコール 3.9µs は、数回の差なら誤差なので、無理に上げる意味は薄い。

5. 2D を描くための状態

同じフレームの中で 3D の次に 2D を描くと、GL の状態を切り替える必要がある。Day 16 のままでは3つとも壊れる。

状態3D では2D では忘れるとどうなるか
深度テストONOFFあとから描いた手前のスプライトが弾かれる
背面カリングONOFFY 下向きの座標系で巻きが裏返り、全部消える
ブレンドOFFONα が 0 の部分も塗り潰され、四角い板になる

カリングを切る理由は、スクリーン座標が Y 下向きなこと。投影行列で Y を反転している(要点6)ので、素直に「左上 → 右上 → 右下 → 左下」と並べた四角形は NDC 上で時計回りになり、裏面と判定される。回転で符号が変わる可能性もあるので、2D では巻きを気にせずカリングを切るのが普通。

SpriteBatch.Begin がこの3つを設定し、End で元に戻している。ただし BlendFunc は戻していない。「何を保存して何を保存しないか」をクラスごとに決め打ちするのは長期的に破綻するので、本来はレンダーステートをまとめて持つ仕組みが要る。今日は「Begin が必ず設定し直す」ことで辻褄を合わせてある。

アルファブレンドの式は:

結果 = 描く色 × α + すでにある色 × (1 - α)

glBlendFunc(GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA) がこれ。第2引数を GL_ONE にすると加算ブレンドになり、重なるほど明るくなる(炎や魔法エフェクトの定番。改造課題1で試す)。

6. スクリーン座標をそのまま使う投影行列

2D では「左上が (0,0)、右下が (幅, 高さ)」でスプライトを置けたほうが圧倒的に楽。そのための行列を Camera.CreateScreen に足した。呼び方は:

csharp
Camera.CreateScreen(left: 0, right: width, bottom: height, top: 0, near: -1, far: 1);

bottom に height、top に 0 を渡すのがポイントで、これで Y 軸が下向きになる。上下の入れ替えは M22 の符号1つで済むので、専用の反転行列は要らない。

そして V 座標の反転が今日で3回目になる。

Day場面対応
10OBJ の V が下から上読み込み時に 1 - v
15画像は上から、テクスチャは下からstbi_set_flip_vertically_on_load
17スクリーンは Y 下向き、テクスチャは V 上向き四隅への UV 割り当てで入れ替え

3回とも「原点の取り方が違う2つの世界をつなぐ」という同じ問題で、直し方も毎回1か所。どこで1回だけ反転させるかを決めておくのが肝で、2か所で反転すると元に戻ってしまい、しかも動いてしまうので気付きにくい。

7. 今日やっていないこと(= Day 18 でやること)

今日の SpriteBatch には、まだ次の穴がある。全部 Day 18 で埋める。

  • テクスチャを混ぜられない … 呼び出し側が順番を工夫するしかない → アトラス
  • 描画順を制御できない … 積んだ順にそのまま描く。半透明の前後関係を自分で解決できない → ソート
  • 頂点が 32 バイトある … 色を byte 4個にすれば 20 バイト。2万枚 = 8万頂点なので、毎フレーム 2.5MB → 1.6MB の差になる
  • テクスチャの一部を切り出す指定が UV … スプライトシートはピクセルで指定したい

改造課題

課題1(易): ブレンドで遊ぶ

要点5のブレンド式を実際にいじる。状態を戻し忘れるバグも踏んでおく。

  1. SpriteBatch.Begin の BlendFunc を(BlendingFactor.SrcAlpha, BlendingFactor.One) に変える。加算ブレンドになり、重なるほど明るくなる。炎・魔法・パーティクルの定番
  2. 加算ブレンドのまま、スプライトの色のアルファを下げる(0.85 → 0.2)。「濃さ」の意味が通常ブレンドとどう違うか
  3. SpriteBatch.End から SetCap(EnableCap.Blend, _savedBlend) を消してみる。次のフレームの3D描画がどうなるか。原因に辿り着けるか
  4. 3 の状態で、さらに Begin の _gl.Enable(EnableCap.Blend) も消す。1フレーム目だけ正しく、2フレーム目から壊れる…といった挙動になるはず。状態を持つ API のいやらしさを1回体験しておくと、Day 18 以降で助かる

課題2(中): 容量とドローコールのトレードオフを測る

要点4の後半を数字にする。

  1. SpriteBatch の capacity を 100 / 500 / 4000 / 20000 に変え、スプライト2万枚でのドローコール数と fps を記録する
  2. ドローコール数は予想どおりに変わるはず。fps はどうか。3.9µs × 何回ぶんの差になっているか
  3. 頂点バッファのメモリ量も計算して並べる(capacity × 4頂点 × 32バイト)。どこが妥当か
  4. インデックスを uint から ushort に変える。インデックスバッファが半分になるが、capacity の上限が 16384 になる。なぜか(ヒント: 頂点番号は capacity × 4)
  5. 発展: capacity を超える枚数を1つのテクスチャで描いたとき、フラッシュがフレームの途中で起きる。半透明の描画順に影響が出ないのはなぜか(ヒント: 今日は深度テストを切っている)

課題3(難): インスタンシングで書き直して比べる

バッチングとは別の解き方がある。同じ形を何度も描くなら、頂点を複製せずに「この頂点データを N 回描け」と1回で命じればよい。

  1. 四角形1枚ぶん(4頂点・6インデックス)の静的なバッファを作る
  2. スプライトごとの情報(位置・大きさ・回転・色)を別の VBO に入れ、glVertexAttribDivisor(location, 1) を指定する。divisor が 1 の属性は、頂点ごとではなくインスタンスごとに1回進む
  3. glDrawElementsInstanced(GL_TRIANGLES, 6, GL_UNSIGNED_INT, 0, spriteCount) で描く
  4. 頂点シェーダで、四角形のローカル座標にインスタンスの回転・拡大・平行移動を適用する。CPU でやっていた4隅の計算が GPU に移る
  5. 転送量を比べる。バッチングは1枚 128 バイト(4頂点 × 32)、インスタンシングは1枚 24 バイト(位置8 + サイズ8 + 回転4 + 色4[byte×4])。5分の1以下になる
  6. 両方で2万枚を測る。どちらが速いか。予想と合ったか

6 が本題。転送量が4分の1になっても速くならない可能性が高い(要点1で見たとおり、この規模ではもう転送がボトルネックではない)。インスタンシングが本当に効いてくるのは、1インスタンスあたりの頂点数が多いとき(草・木・瓦礫を数万本)で、それは Day 32 以降の話。「同じ問題に2つの解き方があり、どちらが良いかは規模で決まる」を体験しておく。
