Phase 3 / ロードマップ該当行: 「スプライトバッチ最適化(アトラス、ソート) — レンダラ完成」

今日のゴール

スプライト1万枚を、ドローコール1回で描く。 Phase 3 のマイルストーン。

Day 17 のバッチは、呼び出し側が「テクスチャごとにまとめて渡す」ことに依存していた。まとめずに渡すと、1万枚が1万回のドローコールに戻る(実測 25.2 fps)。

今日はその依存を潰す。どんな順に Draw を呼んでも 1 ドローコールにする。やることは2つで、片方だけでは足りない。

  • アトラス … 絵の種類が増えてもテクスチャは1枚のまま
  • ソート … 呼び出し順に関係なく、まとめられる順に並べ替える

ついでに Day 15 の課題3から持ち越していた「頂点を小さくする」も片付ける(1頂点 32 → 20 バイト)。こちらは Day 17 のオーファニングと違い、測ったら効いた。

事前に読む資料

ロードマップの指定は「-」。実装寄りの回なので、次を読んでおくとよい。

  • Array Texture — OpenGL Wiki —アトラスの「現代的な代替」。今日は使わないが、アトラスの弱点を知るのに読む価値がある
  • Vertex Specification — OpenGL Wiki —normalized の意味。整数を 0.0〜1.0 として読ませる仕組み
  • A Thousand Ways to Pack the Bin(矩形パッキングの調査) —棚詰めより良い詰め方はいくつもある。論文 PDF がリポジトリに入っている
  • 復習として Day15.md の課題3(頂点属性の型) と Day17.md の要点4(フラッシュの条件)。今日はこの2つの続き

理論の要点

1. アトラス — 「絵が違う」と「テクスチャが違う」を切り離す

Day 17 で見たとおり、バッチはテクスチャが変わるたびにフラッシュする。絵の種類が10個あれば、どう並べ替えても最低10回のドローコールになる。

アトラスはこれを構造から潰す。複数の画像を1枚のテクスチャに詰め込み、それぞれの位置を UV の矩形として覚えておく。絵の種類が増えてもテクスチャは1枚のままなので、フラッシュの理由が消える。

AtlasRegion が「どのテクスチャの、どこを、元は何ピクセルだったか」を持つ。SpriteBatch から見れば、テクスチャを渡されようが領域を渡されようが同じ経路を通る。

詰め方は「棚(shelf)詰め」。高い画像から順に横一列(棚)に並べ、入らなくなったら次の段へ移る。最適な矩形パッキングは NP 困難だが、高さでソートしてから棚に並べるだけで実用上は十分埋まる。正解を求めるより、十分よい答えを安く出すの典型例。

今日詰めるのは4枚だけなので、256x256 のアトラスに対して充填率は 17.6% (使用 11,520 / 全体 65,536 px)しかない。これは棚詰めが悪いのではなく、2の累乗に切り上げているぶん。枚数が増えるほど効率は上がる。

パディング(すき間)を空けるのはブリーディング対策。バイリニア補間は指定した点の周囲2x2テクセルを読むので、すき間が無いと端のピクセルに隣のリージョンの色が混ざる。さらに UV を半テクセル内側に寄せて、境界を踏まないようにしてある。

2. アトラスとミップマップは相性が悪い

今日のアトラスはミップマップを作らない。理由は原理的なもの。

ミップマップは縮小版を作る仕組みだが、その過程で隣のリージョンの色が混ざる。レベルが上がるほど広範囲から混ざり、最後は全体が1テクセルに潰れるので、パディングをどれだけ空けても防げない。

対策は3つある。

対策内容評価
ミップマップを使わない今日これ縮小率が小さければ十分。手軽
リージョンごとにミップマップを自前で作って詰め直す各レベルを別のアトラスに正しいが手間
テクスチャ配列(GL_TEXTURE_2D_ARRAY)同じ大きさの絵を層に積む現代的な答え。混ざりようがない

テクスチャ配列は「全部の絵が同じ大きさでなければならない」という制約と引き換えに、ミップマップ・Repeat・フィルタのすべてが素直に効く。改造課題3で扱う。

実装上、この話は Texture にミップマップを持っているかどうかの記録を足す必要を生んだ。ミップマップが無いテクスチャの MinFilter にLinearMipmapLinear を指定すると、そのテクスチャは「不完全(incomplete)」になり、描画結果が真っ黒になる。エラーは出ない(合法な組み合わせで、単に条件を満たしていないだけ)ので、「なぜか黒い」の原因として上位に来る。

3. ソート — キーを1本の long に畳む

SpriteBatch.Begin にモードを渡せるようにした。

モード並べ替え使いどころ
Immediateしない呼んだ順を保証したいとき(Day 17 の挙動)
Textureテクスチャでドローコール最小。不透明・重ならないもの
BackToFrontレイヤー → テクスチャ半透明の前後関係が要るとき

実装のポイントは、比較関数を書かずに数値1本に畳むこと。

上位32bit … レイヤー(奥ほど小さい。0.0〜1.0 を 0〜65535 に量子化)
下位32bit … テクスチャのハンドル

Comparison<T> を渡すとデリゲート呼び出しが比較のたびに起きる。数値に畳めば単純な整数比較になり、優先度の順にビットを並べるだけで多段ソートになる。レイヤーを量子化するのは、float をそのままビット比較できないため(負数の扱いが素直でない)。65536 段あれば 2D の重ね順には十分すぎる。

Array.Sort(_keys, _order, 0, _pending) はキーの配列と番号の配列を対で受け取り、キーで並べ替えつつ番号も同じ順に動かす。(key, index) のペアを自分で作るより割り当てが少ない。

注意: Array.Sort は安定ソートではない。同じキーのスプライトの順序は保証されない。Texture モードで同じテクスチャの2枚を重ねると、どちらが上になるかは不定になる。順序が要るなら BackToFront でレイヤーを明示するか、キーに通し番号を混ぜる。

4. アトラスとソートは、どちらか片方では足りない

今日いちばんの発見。1万枚での実測:

ソートモードアトラスドローコールfps
Immediateなし1000125.2
Immediateあり11258.9
Textureなし4771.2
Textureあり1959.6
BackToFrontなし7482270.9
BackToFrontあり1661.1

読みどころは BackToFront × アトラスなしの 7482 回。

ソートを入れたのに、Day 17 の最悪ケース(1万回)とほとんど変わらない。レイヤーを優先して並べ替えるので、テクスチャの並びが完全に崩れるからで、これは実装の不備ではなくそういうものである。

数も予想できる。レイヤーがばらばらなら、隣り合う2枚が同じテクスチャになる確率はテクスチャ4枚に対して 1/4。だから期待されるドローコール数は

10000 × (1 - 1/4) = 7500

実測 7482。ほぼ一致する。

半透明を正しく描こうとした瞬間に、ソートだけでは無力になる。だから 2D エンジンはアトラスを使う。逆に、アトラスがあればImmediate でもドローコールは1回になる(テクスチャが変わらないので)。

もう一つ細かい観察。Texture × アトラスなしは4回のドローコールで済んでいるのに、アトラスあり(1回)より 0.26ms 遅い。ドローコール3回ぶん(約 12µs)では説明がつかない差なので、テクスチャの切り替えはドローコールそのものより高いと読める。

5. 転送は1回、ドローコールは切れ目の数だけ

Day 17 のフラッシュは「溜まったぶんを送って描く」を繰り返していた。つまりテクスチャが変わるたびに転送が起きていた。

今日は分ける。

  1. 並べ替えた頂点を1回で全部送る(glBufferSubData 1回)
  2. テクスチャの切れ目ごとに glDrawElements をオフセットをずらして呼ぶ

これができるのは、インデックスバッファが「先頭から順に四角形」の形で固定だから(Day 17 の要点3b)。頂点のほうを並べ替えて詰め直せば、四角形 runStart 個ぶん先から n 個、という指定がバイトオフセットだけで書ける。

csharp
_gl.DrawElements(
    PrimitiveType.Triangles,
    (uint)((i - runStart) * 6),
    DrawElementsType.UnsignedInt,
    (void*)(runStart * 6 * sizeof(uint)));   // ここがオフセット

6. 頂点を小さくする — 今度は効いた

色を Vector4(16バイト)から byte 4個(4バイト) に詰め、1頂点 32 → 20バイトにした。1万枚 = 4万頂点で 1.28MB → 0.80MB。

そのために頂点属性の記述を一般化した。Day 15 から使ってきたReadOnlySpan<int>(float が何個か)では、型も正規化の有無も表せない。

csharp
VertexAttribute.Float(2)      // float 2個
VertexAttribute.UNormByte4()  // unsigned byte 4個を 0.0〜1.0 として読む

normalized = true が肝で、これで 0〜255 の byte がシェーダ側では 0.0〜1.0 の vec4 として届く。GLSL は1文字も変わらない (sprite.vert / sprite.frag は Day 17 と完全に同一)。GPU 側から見れば、頂点属性の型はバッファの読み方の指定でしかない。

Day 15 の課題3で「小さくすれば速い、は測るまで分からない」と書いたので、測った。20バイト版と32バイト版を交互に2往復させた結果(ms/frame、小さいほうが速い):

条件20バイト32バイト差
10000枚 Texture0.9891.389-0.40ms
10000枚 Immediate0.7801.154-0.37ms
19997枚 Texture2.332.54-0.21ms

1万枚で 29% 短縮。Day 17 のオーファニング(効果なし)とは逆に、こちらは効いた。節約できたのは転送量だけではなく、頂点を書き込む処理と、並べ替え後のコピーも1枚あたり 128 → 80 バイトに減っている。

面白いのは 2万枚のほうが差が小さいこと。転送量は倍なので単純には倍の差が出そうなものだが、逆になっている。2万枚では GPU 側(重なりの塗り)が律速になっていて、CPU 側で節約した時間が GPU の待ち時間に隠れる、というのが素直な解釈になる。Day 17 でオーファニングが効かなかったのと同じ構図で、ボトルネックがどちら側にあるかで、同じ最適化の価値が変わる。

色を 8bit にして精度は落ちないのかという点は、画面に出す色が最終的に 8bit なので問題ない。中間計算で精度が要るのは HDR を扱い始める Day 31 から。

7. 容量を超えるとソートが分断される

SpriteBatch は容量が満杯になると、そこまでのぶんを吐き出す。並べ替えモードではこれが起きるとソートが分断される——前半だけで並べ替え → 描画 → 後半だけで並べ替え、になるので、前半の手前のスプライトが後半の奥のスプライトに隠される。

だから容量は「1フレームで積む最大枚数」以上にしておくのが素直。今日は 20000 に取ってある(20000 × 4頂点 × 20バイト = 1.6MB。積んだ配列と並べ替え後で2本ぶん必要なので 3.2MB)。

Day 17 では容量 4000 でドローコールを分けていたが、アトラスとソートが入った今は容量がそのままドローコール数を決めるようになった。1万枚で 1 回にできるのは、容量が1万を超えているから。

改造課題

課題1(易): アトラスを壊して、症状を覚える

要点1・2の落とし穴を実際に踏む。症状から原因を逆算できるようになるのが目的。

  1. TextureAtlas.FromFiles の padding を 0 にする。スプライトを大きく描いて(Size を 200 くらいに)縁を見る。今日の4枚では、にじみは見えないはず。どの画像も縁の2ピクセルが完全に透明で、バイリニアが読む隣の1テクセルも透明だから。縁まで色のある画像(ベタ塗りの四角など)を1枚足して、どの方向ににじむかをアトラスの並び順と照らして確かめる
  2. 半テクセル内側寄せ(float half = 0.5f)を 0.0f にする。padding が 0 のときにどう変わるか
  3. Texture.FromPixels の generateMipmaps を true にしてアトラスを作る。スプライトを小さく(Size を 4〜8)描いて、リージョンの色が混ざるのを見る
  4. Texture.SetFilter の振り分けを消して、常に LinearMipmapLinear にする。アトラス(ミップマップなし)が真っ黒になることを確認する。これが要点2の「エラーが出ないのに黒い」

課題2(中): ソートキーを設計し直す

要点3の「1本の long に畳む」を自分で組み替える。

  1. 安定ソートにする。キーの下位に通し番号を混ぜて、同じレイヤー・同じテクスチャなら積んだ順が保たれるようにする。32bit をどう配分するか(レイヤー / テクスチャ / 通し番号)を決めるのが本題
  2. レイヤーの量子化を 16bit から 8bit に落とす。何段まで減らすと重なりがおかしく見え始めるか
  3. マテリアル(シェーダ)を切り替えられるようにして、キーに足す。シェーダの切り替えはテクスチャより高いので、優先度はシェーダ > テクスチャ > レイヤー……にしたくなるが、BackToFront ではレイヤーが最優先でなければ絵が壊れる。この矛盾をどう扱うかを考える(ヒント: 実際のエンジンは不透明と半透明でパスを分け、前者はシェーダ優先、後者はレイヤー優先にする)
  4. Array.Sort を基数ソート(radix sort)に置き換えて、2万枚で測る。キーが整数なので O(n) にできる。効くかどうかは測るまで分からない

課題3(難): テクスチャ配列に置き換える

要点2で挙げたアトラスの弱点を、根本から解決する。

  1. 4枚を GL_TEXTURE_2D_ARRAY の4層として読み込む。全層が同じ大きさでなければならないので、64x64 にそろえる(小さい画像は中央に配置してパディングするか、拡大する)
  2. SpriteVertex に層番号を足す。UV は毎回 0〜1 でよくなるので、AtlasRegion の UV 矩形が要らなくなる
  3. フラグメントシェーダを sampler2DArray にして、texture(uTexture, vec3(vTexCoord, vLayer)) で読む
  4. ミップマップを有効にする。混ざらないことを確認する
  5. アトラス版と比べる。ドローコール数、fps、頂点サイズ、そして素材の準備しやすさ。どちらを採るか

5 が本題。テクスチャ配列は技術的に上位互換に見えるが、「全部同じ大きさ」の制約は素材側の負担が大きい。16x16 のアイコンと 512x512 の背景を同じ配列に入れると、前者のために 512x512 の層を1つ使うことになる。制約と自由度の取り引きであって、新しいほうが常に良いわけではない。
