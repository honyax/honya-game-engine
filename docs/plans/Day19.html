今日のゴール

シミュレーションを 5Hz まで落としても、絵が滑らかなまま動く。

Day 18 までの更新はこう書いていた。

csharp
sprite.Position += sprite.Velocity * (float)deltaSeconds;   // 可変タイムステップ

短くて分かりやすいが、これは同じ操作をしても環境によって結果が変わる書き方になっている。今日それを「シミュレーションは固定間隔、描画は好きなだけ」に組み替える。

Phase 3 が「絵をどう出すか」だったのに対し、Phase 4 はエンジンコア——描画以外の土台を作る。ゲームループはその最初の1本で、このあとの入力(Day 20)・コンポーネント(Day 22)・ECS(Day 23)はすべて「毎ステップ何が呼ばれるか」の上に載る。

事前に読む資料

  • Fix Your Timestep! (Gaffer On Games) —ロードマップ指定。今日の内容はほぼこの記事。可変 → 固定 → アキュムレータ → 補間、と段階的に組み上げていく構成なので、写経の前に一度通しで読んでおくとよい
  • deWiTTERS Game Loop —同じ話を別の切り口で。図が多い
  • Game Programming Patterns: Game Loop —Robert Nystrom。パターンとしての整理と、各方式の向き不向き
  • 復習として Day17.md の要点1(ドローコールの実測)。今日も「予算 16.6ms をどう配るか」の話が出てくる

理論の要点

1. 可変タイムステップの何が問題か

「経過時間を掛ければ、fps が変わっても同じ速さで動く」——これは半分正しい。等速直線運動なら確かに合う。合わなくなるのは次の3つ。

(a) 再現しない

同じ操作をしても、fps が違えば結果が変わる。浮動小数の足し算は結合則を満たさないので、0.016 を60回 と 0.008 を120回 は別の値になる。1回の誤差は無視できても、数千ステップ積み上がると軌道が変わる。

これが困るのは、リプレイ、タイムアタックの記録検証、ロールバック方式のネットワーク対戦——同じ入力から同じ結果を再現したい場面すべて。

(b) 壊れる

フレームが長引くと1ステップの移動量が大きくなる。弾が壁を「すり抜ける」典型的なバグはこれ。物理を入れると、積分の刻みが粗くなって発散する(バネがどんどん振幅を増して吹き飛ぶ、など。Day 43 で本格的に扱う)。

(c) 調整が効かない

「1秒で何回更新されるか」が環境任せなので、ゲームバランスの数値が確定しない。「毎ステップ 0.5 ダメージ」は 60Hz なら毎秒 30、144Hz なら毎秒 72 になる。

2. アキュムレータ — 溜めて、固定間隔で吐き出す

対策はひとつで、シミュレーションを固定間隔で回す。ただし描画のタイミングは固定間隔とは一致しないので、経過時間をいったん溜めて、溜まったぶんだけ進める。

csharp
_accumulator += frameSeconds;

while (_accumulator >= FixedDeltaTime)
{
    fixedUpdate(FixedDeltaTime);   // ← 常に同じ値
    _accumulator -= FixedDeltaTime;
}

1フレームでの呼び出し回数は 0 回のことも複数回のこともある。描画が速ければ 0 が続き、遅ければまとめて回る。描画レートとシミュレーションレートが完全に分離するのがこの数行の成果。

fixedUpdate に渡る値が毎回同じ、というのが決定性の実体になる。今日の Program.UpdateSprites は「引数だけで結果が決まる」形(グローバルな状態も乱数も時刻も読まない)に切り出してある。

3. 補間 — 5Hz のシミュレーションを 4000fps で滑らかに見せる

固定間隔にすると、そのままではシミュレーションのレートでしか絵が動かない。60Hz なら気付きにくいが、20Hz や 5Hz にすると一目でカクつく。

描画のタイミングは必ず「あるステップと次のステップの間」にある。どのくらい進んでいるかが Alpha = accumulator / FixedDeltaTime(0.0〜1.0)なので、前のステップと今のステップを混ぜれば「間」の絵が作れる。

csharp
Vector2 drawn = Vector2.Lerp(sprite.PreviousPosition, sprite.Position, alpha);

代償は状態を2つ持つこと。動かす前に前の値を保存する必要があり、これを忘れると前と後が同じ値になるので補間が効かない(症状は「補間を入れたのにカクついたまま」)。

実測すると効果がはっきり出る。5Hz でスプライト1枚の「1フレームあたりの画面上の移動量」を2秒間集計した結果:

動かなかったフレームの割合1フレーム最大移動平均移動
補間 OFF99.9%33.38 px0.039 px
補間 ON0.0%0.20 px0.042 px

平均移動がほぼ同じなのがポイント(差は計測窓の違いによる誤差)。総移動量は変わっておらず、変わったのは分配のしかただけ。補間 OFF は「200ms 止まって 33px 跳ぶ」、補間 ON は「毎フレーム 0.04px ずつ動く」。同じ距離を進んでいる。

補間で気を付けるのは瞬間移動。ワープ、リスポーン、画面切り替えのときに前と後を直線で結ぶと、画面を横切る線になってしまう。そういう場面では前の状態を現在値で上書きして、補間を1フレーム無効にする。

4. 何を FixedUpdate に書き、何を描画に書くか

今日いちばん大事な設計判断。

置き場所例
FixedUpdate移動、当たり判定、AI、タイマー、ダメージ、入力の反映
描画補間、カメラの追従、パーティクルの見た目、UI のアニメーション

境界は「ゲームの状態を変えるか」。状態を変える処理が描画側に紛れ込むと、その瞬間に決定性が壊れる。「描画のついでにちょっと座標を直す」が最も入り込みやすい。

逆に、見た目だけのものを FixedUpdate に入れると、シミュレーションレートを下げたときにそれまでカクつく。

5. 死のスパイラルと、遅れの扱い方

固定ステップには落とし穴がある。

フレームが重い → 溜まった時間が増える → 次フレームでステップ数が増える
→ もっと重い → もっと溜まる → …

これが死のスパイラル(spiral of death)で、一度入ると復帰できない。1フレームで回すステップ数に上限(MaxStepsPerFrame)を付けるのが非常ブレーキ。

上限を付けると、遅い環境ではシミュレーションが実時間より遅れる。その遅れをどう扱うかが設計判断になる。

方針挙動使いどころ
捨てる(既定)シミュレーションがスローモーションになる。遅れは溜まらないほとんどのゲーム
捨てない遅れが永久に増え続け、二度と追いつかないほぼ選ばない

1ステップに 20ms かかる負荷をかけて実測した(60Hz なので1ステップの予算は 16.67ms。つまり原理的に追いつけない):

設定fps遅れ捨てた時間(2秒間)
捨てる41.04.6 ms0.20 s
捨てない6.2354.9 ms0.00 s

捨てる場合、シミュレーションは実時間の約 90% の速さで進む(2秒で 0.2 秒ぶん落とした)。遅いが動き続ける。捨てない場合は毎フレームが上限いっぱいのステップ数になり、fps が 6 まで落ちたうえで遅れが増え続ける。非常ブレーキが無ければ完全に固まる。

「捨てる」を選ぶのは、重い環境ではゲーム内時間が実時間よりゆっくり進むのを許すという判断でもある。オンライン対戦のように実時間と同期しなければならない場合は、捨てるのではなく描画やシミュレーションの質を落とすほうを選ぶ。

6. Silk.NET の固定レート機能をあえて使わない

WindowOptions.UpdatesPerSecond に値を入れると、Silk.NET がUpdate イベントを固定レートで呼んでくれる。今日はこれを 0(上限なし)にして、素のフレーム時間を自分の GameLoop に渡す。

出来合いを使わないのは、Phase 2 で wgl を自分で叩いたのと同じ理由——中で何が起きているかを一度見ておくため。それに、出来合いのものには補間の仕組みが無い。Alpha を自分で持っていないと要点3ができないので、どのみち書くことになる。

7. 決定性は測れる(Y キー)

「同じ入力なら同じ結果」は口で言うだけでは確かめられないので、自己チェックを組み込んである。同じ初期状態から3通りに進めて突き合わせる。

  • A: 固定ステップを 600 回、まとめて回す
  • B: 同じ 600 回を、2〜32ms のばらばらなフレーム時間に分けて GameLoop 経由で回す
  • C: 可変タイムステップで、同じ実時間ぶん進める

結果(状態の FNV-1a ハッシュ):

A 固定・まとめて      : 7F43863E1E5DFDB8
B 固定・フレーム分割  : 7F43863E1E5DFDB8  一致
C 可変・同じ実時間    : 7444383E9D7F0545  不一致

A == B ≠ C。フレームの刻み方が違っても、ステップ数が同じなら結果は同じ。可変だと同じ実時間でも結果が変わる。

比較にビット単位のハッシュを使っているのは意図的で、「誤差の範囲で合っている」では意味がないから。1ビット違えば数千ステップ後には全く別の結果になる。

改造課題

課題1(易): 補間を壊して、症状を覚える

要点3の落とし穴を実際に踏む。

  1. UpdateSprites の PreviousPosition の保存を、移動したあとに移す。5Hz + 補間 ON でどうなるか。原因が分かるか(前と後が同じ値になるので、補間しても常に最新の状態が出る)
  2. GameLoop.Advance の末尾にある Math.Clamp(..., 0.0, 1.0) を外し、余剰破棄を OFF にして負荷をかける。α が 1 を超えると補間ではなく外挿になり、スプライトが先へ飛び出す
  3. スプライトを「ワープ」させてみる。たとえば 5 秒ごとに1枚をランダムな位置へ飛ばす。補間が画面を横切る線を引くのを確認し、前の状態を現在値で上書きして直す
  4. SetSimulationRate から _loop.Reset() を消して、5Hz から 120Hz へ切り替える。一瞬だけ早送りになるのを確認する

課題2(中): 入力を固定ステップに載せる

Day 20 の入力システムへの布石。入力は描画レートで来るが、シミュレーションは固定レートという食い違いを扱う。

  1. 矢印キーで動かせるスプライトを1枚足す。まず素直に OnKeyDown の中で座標を変えてみる。シミュレーションレートを 5Hz に落としたとき、補間がどう壊れるか
  2. 直す。キーの状態を「押されているか」のフラグとして持ち、FixedUpdate の中で読んで座標を変える
  3. 「押した瞬間」(ジャンプなど)はフラグでは表せない。OnKeyDown でフラグを立て、FixedUpdate で消費する形にする。1ステップの間に2回押されたらどうするか
  4. Y キーの決定性チェックが、入力を入れたあとも通るようにする。通らないなら、入力のどこかが FixedUpdate の外で状態を変えている

課題3(難): 可変ステップとの誤差を定量化する

要点1(a)の「浮動小数の足し算は結合則を満たさない」を数字で見る。

  1. スプライト1枚を等速直線運動させ(壁の反射を切る)、固定 60Hz で 10 秒ぶん進めた座標と、可変(2〜32ms のばらばら)で同じ 10 秒ぶん進めた座標の差を測る
  2. 差はどのくらいか。10秒でどれだけずれるか、100秒では
  3. 反射を戻すと差はどうなるか。分岐(if)が入ると誤差が非線形に拡大する——わずかな座標差が「壁に当たったか当たらなかったか」を分ける
  4. 速度に重力を足して(velocity.Y += 9.8f * dt)、同じ比較をする。等速のときより差が大きくなるはず。なぜか
  5. 発展: float を double に変えると差はどうなるか。精度を上げれば決定性が手に入るのか (ヒント: 手に入らない。CPU が違えば double でも結果が変わりうる。本気でやるなら固定小数点にする。格闘ゲームのロールバック実装がそうしている)

5 が本題。「精度を上げる」と「決定的にする」は別の問題で、後者が欲しいなら浮動小数から離れる必要がある、という話につながる。
