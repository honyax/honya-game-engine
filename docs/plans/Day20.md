# Day 20: 入力システム(ポーリング+イベント)

Phase 4 / ロードマップ該当行: 「入力システム(ポーリング+イベント)」

## 今日のゴール

**矢印キーで動かした操作を記録して、再生すると寸分たがわず同じ動きが再現される。**

Day 19 で「同じ入力なら同じ結果」を確かめた。今日はそこに**実際の入力**を載せる。
入力が決定的な形で扱えれば、記録した入力列を流し直すだけでリプレイになる——
これが今日の到達点で、Day 19 の設計が配当を返す場面でもある。

デバッグ用のキー(Day 16〜19 で足してきたもの)はイベントで直接処理していた。
それはそれで正しいが、**ゲームの入力を同じやり方で書くと壊れる**。
なぜ壊れるのか、どう分けるのかが今日の主題。

## 理論の要点

### 1. 時間の粒度が3つある

入力まわりで踏む罠は、突き詰めるとこれに尽きる。

| 粒度 | 誰が決めるか | どのくらいか |
|---|---|---|
| 1. デバイスのイベント | OS。不定 | 1フレームに何回でも来る |
| 2. 描画フレーム | 可変 | 数千fps 出ることもある |
| 3. シミュレーションのステップ | **こちらが固定** | 60Hz など |

ゲームのロジックが見たいのは **3 だけ**。だから 1 を溜めておいて、
3 の境界で1枚の値に畳む。それが `InputSnapshot` で、
畳む役が `InputSystem.BeginStep()`。

畳んでしまえば、ゲームのロジックから見た入力は
「毎ステップ渡ってくる、変わらない1個の値」になる。おかげで

- ステップの途中で入力が変わらない(判定が安定する)
- **そのまま記録できる**(要点5)
- テストで好きな値を差し込める

が全部手に入る。今日の `UpdatePlayer` は入力を**引数で受け取る**形にしてあり、
グローバルなキーボードの状態を直接見に行かない。これが後半のリプレイを可能にしている。

### 2. 「押されている」と「押した瞬間」は別物

`Held` / `Pressed` / `Released` の3つを持つ。

| | 意味 | 例 |
|---|---|---|
| `Held` | このステップの間、押されていた | 移動、チャージ、ガード |
| `Pressed` | このステップで**新たに**押された | ジャンプ、発射、決定 |
| `Released` | このステップで離された | 溜め攻撃の発動、長押しの終わり |

ジャンプを `Held` で書くと、押しっぱなしで毎ステップ発動する。
逆に移動を `Pressed` で書くと、1ステップしか動かない。
**この2つの取り違えは、入力バグの過半数を占める**。

「押した瞬間」の実装で気をつける点が2つある。

**(a) オートリピートを弾く**

キーを押しっぱなしにすると、OS が `KeyDown` を繰り返し送ってくる。
これは Day 14 でシェーダのホットリロードを検証したときに踏んだのと同じ挙動で、
そのまま `Pressed` に流すと毎秒何十回も「押した瞬間」が発生する。
すでに押されているぶんを除いてから立てる。

```csharp
GameAction newlyPressed = action & ~_heldNow;
```

**(b) 1ステップぶんで消費して捨てる**

`Pressed` は `BeginStep()` で空にする。これを忘れると、
1フレームで複数ステップ回ったとき(Day 19 要点2)に
**同じ「押した瞬間」を何度も消費**する。ジャンプが2回発動する形で表面化する。

実測で確かめた(偽のキーボードで `InputSystem` を直接駆動):

| 検証 | 結果 |
|---|---|
| `KeyDown` を6回連続で送っても `Pressed` は1回だけ | OK |
| 押しっぱなしで8ステップ回しても `Pressed` は1回だけ | OK |
| 押しっぱなしの間 `Held` は5ステップとも立つ | OK |

### 3. ステップの間に押して離したら?

1ステップ(60Hz なら 16.7ms)の間に、フレームは何回も回る。
その間に「押して離した」場合、ステップ境界の時点では**もう離れている**。
素直に書くと `Held` が立たず、タップがまったく効かない。

対策は、`Held` に「このステップで押された」を足すこと。

```csharp
Held = _heldNow | _pendingPressed;
```

こうすると、素早いタップでも**そのステップの間は押されていた**ことになる。
実測すると `Pressed` / `Released` / `Held` の3つが同時に立ち、
次のステップで全部消える。取りこぼしも持ち越しも起きない。

これは設計判断であって唯一の正解ではない。
「タップは移動に含めない」仕様なら足さないほうがよい。
**どちらを選んだかを決めて、1箇所に書いておく**のが大事。

### 4. キーではなくアクションを見る

ゲームのコードが `Key.Left` を直接見ると、次が全部できなくなる。

- キーコンフィグ(ユーザーがキーを変えられない)
- ゲームパッド対応(スティックは `Key` ではない)
- 複数割り当て(矢印キーと WASD の両方)
- **リプレイ**(記録したいのは「左に動きたかった」であって「左キー」ではない)

だから間に1枚挟む。**デバイス → アクション → ゲームのロジック**。
`InputMap` が前半、`InputSnapshot` が後半の境界になる。

`GameAction` を `[Flags]` の列挙型にしてあるのは、
「今どのアクションが有効か」を `uint` 1個で表せるようにするため。
集合演算(AND / OR)で判定でき、そのまま記録もできる。
**32個までしか作れない**が、それを超えるならカテゴリごとに分けるべき合図。

「どちらへ動きたいか」への翻訳も `InputSnapshot` の担当にしてある。

```csharp
public Vector2 MoveAxis { get; }   // -1〜1、斜めは正規化済み
```

斜めを正規化しないと**斜め移動が √2 倍速くなる**。2D ゲームの古典的なバグ。
また `Vector2.Normalize` は長さ0で NaN を返すので、無入力を弾いておく必要がある
(**入力が無い状態が最も頻繁**なので、ここを踏むと毎フレーム NaN が撒かれる)。

### 5. リプレイは「入力を溜めて順に返す」だけ

大がかりな機能に見えるが、Day 19 の固定タイムステップと
今日の `InputSnapshot` がそろっていれば**ほとんど何もしていない**。

```
ゲームの状態(t+1) = f(ゲームの状態(t), 入力(t))
```

f が決定的(Day 19 要点7)で、入力が全部記録されているなら、
初期状態から同じ入力を流せば必ず同じ結果になる。
だから**画面を録画する必要が無い**——入力列だけあれば再現できる。
1時間のプレイでも 60Hz × 3600秒 × 20バイト ≒ 4MB。

実測(擬似的な操作列を 300 ステップぶん記録して再生):

```
[記録停止] 300 ステップ (5.00 秒ぶん) / 終了時ハッシュ D35E4CB90A9CF6C8
  記録終了時点の座標: <50.516518, 130.90172> 速度: <15.81633, -288.16577>
[再生開始] 300 ステップ
  再生終了時点の座標: <50.516518, 130.90172> 速度: <15.81633, -288.16577>
[再生終了] ハッシュ D35E4CB90A9CF6C8 / 記録時 D35E4CB90A9CF6C8  一致
```

座標も速度も**ビット単位で一致**する。

記録データには「前提条件」を一緒に入れておく必要がある。
今日は `FixedDeltaTime` だけだが、**これが違うと入力列が同じでも結果が変わる**
(1ステップの重みが変わるので別のシミュレーションになる)。
実際のリプレイ形式には、さらにゲームのバージョンと乱数の種が入る。

この性質はリプレイだけでなく、

- ロールバック方式のネットワーク対戦(過去に戻って入力を差し替え、やり直す)
- タイムアタックの記録検証(サーバで再生して不正を検出する)
- バグの再現(「この入力列で落ちる」を添付できる)

の土台になる。**エンジンを決定的に作っておいたことの配当**がここで返ってくる。

### 6. フォーカスを失うと KeyUp が来ない

押しっぱなしのまま Alt+Tab で別のウィンドウへ移ると、`KeyUp` が届かない。
戻ってきたときに**ずっと右へ走り続ける**のはこれが原因。

対策は「フォーカスを失ったら押しっぱなしを全部解除する」。

```csharp
_window.FocusChanged += focused => { if (!focused) _inputSystem.Clear(); };
```

同じ `Clear()` をリプレイの開始時にも呼んでいる。
そうしないと、`N` を押した瞬間に押していたキーが再生に混ざる。

### 7. デバッグキーとゲームキーは分けたほうがよい

今日、矢印キーをプレイヤーに使うために、スプライト数の増減を
`Up`/`Down` から `PageUp`/`PageDown` へ移した。
WASD も使いたいところだが、`W`(ワイヤーフレーム)・`A`(アトラス)・
`S`(ソート)がデバッグ用に埋まっていて割り当てられない。

これは**実際によく起きる問題**で、本来はデバッグ用の入力を別のマップに分け、
「デバッグモードのときだけ有効」にするのが筋。
今日はそこまでやらないが、`InputMap` を複数持てる形にはなっている
(改造課題1で扱う)。

### 記録と再生(今日の見せ場)

1. **`M`** を押す → コンソールに `[記録開始]`
2. 矢印キーと `X` で 5〜10 秒ほど動かす。タイトルバーの `記録中 N` が増えていく
3. **`M`** をもう一度 → `[記録停止] N ステップ ... 終了時ハッシュ XXXX`
4. さらに適当に動かして、プレイヤーを別の場所へ持っていく
5. **`N`** を押す → プレイヤーが記録開始時の位置へ飛び、**同じ動きをなぞる**
6. 再生が終わると `[再生終了] ハッシュ ... 一致` と出る

**4 が大事**。再生前にプレイヤーがどこにいても、記録時と同じ結果になる。
記録しているのは座標ではなく**入力だけ**で、初期状態は巻き戻されている。

### 固定レートを変えても入力が効くこと

1. **`4`** でシミュレーションを 5Hz に落とす
2. 矢印キーで動かす。**動きは 5Hz のままだが、補間で滑らかに見える**(Day 19 要点3)
3. `X` を素早く連打する。5Hz でも**押した瞬間が取りこぼされない**(要点3)
4. **`2`** で 60Hz に戻す

5Hz のときに `N` で再生すると「ステップ間隔を記録時の 60Hz に戻します」と出る。
入力列が同じでも 1 ステップの重みが違えば別の結果になるため(要点5)。

## 改造課題

### 課題1(易): 入力の分離を進める

要点7の「デバッグキーとゲームキーが衝突する」を実際に直す。

1. `InputMap` をもう1つ作り、デバッグ用のアクション
   (`ToggleWireframe`、`ToggleAtlas` など)を定義する
2. `InputSystem` を2つ持ち、`F1` でデバッグ用の有効/無効を切り替える。
   **無効のときは W / A / S がゲーム側に流れる**ようにする
3. WASD をプレイヤーの移動に割り当て、矢印キーと併用できることを確認する
4. `InputMap.Resolve` の線形探索を `Dictionary` に置き換えて、
   1万件の割り当てで速度を比べる。**そもそも何件で意味が出るか**
   (ヒント: 実際に引かれるのは1フレームに数回。Day 17 の
   「ドローコールを数える」と同じで、まず回数を数える)

### 課題2(中): 記録をファイルに保存する

要点5の「入力列だけあれば再現できる」を、プロセスをまたいで確かめる。

1. `InputSnapshot` をバイナリで書き出す。
   `Held` / `Pressed` / `Released` は `uint` 3個、マウスは省略してよい
2. ヘッダに前提条件を入れる。最低限 `FixedDeltaTime` と初期状態、
   できればフォーマットのバージョン番号
3. 起動時にファイルを読んで自動再生するモードを付ける
   (コマンドライン引数か、環境変数で)
4. **わざと壊す**。ヘッダの `FixedDeltaTime` を書き換えて再生し、
   ハッシュが合わなくなることを確認する
5. 圧縮を試す。**同じ入力が続く区間**が多いので、
   ランレングス符号化(何ステップ同じか)がよく効くはず。
   1分間の記録が何バイトになるか

### 課題3(難): 入力遅延と先行入力(バッファリング)

「押したのに反応しない」の正体を掘る。**ゲームの手触りに直結する話**。

1. 今の実装で、キーを押してから画面に出るまでの遅延を数える。
   最悪ケースは何ステップぶんか
   (ヒント: 入力 → 次のステップ境界 → シミュレーション → 描画 → 表示。
   VSync も入る)
2. **先行入力(input buffering)** を入れる。
   `Pressed` を1ステップで捨てず、数ステップ保持しておき、
   「まだ着地していないがジャンプを押した」を拾えるようにする。
   何ステップ保持するのが妥当か
3. 保持すると副作用が出る。**古い入力が意図せず発動する**ことがあるので、
   消費したら明示的に捨てる仕組みが要る
4. 逆方向の実験: `InputSystem.BeginStep` をステップの**後**に呼ぶように変えて、
   遅延が1ステップ増えることを確認する。16.7ms の差が体感できるか
5. 発展: 記録・再生で遅延を測る。同じ入力列を
   「先行入力あり/なし」で再生して、結果が変わることを確認する

2 は格闘ゲームやアクションゲームで必ず入っている仕組みで、
**入力を1ステップで捨てる素朴な実装は、実は手触りが悪い**。
「正しく実装する」と「気持ちよく遊べる」が別物である例として押さえておく。

### 検証の途中で直したこと

`InputSnapshot.MouseDelta` のコメントに
「差分で取ると途中の往復が消える」と書いていたが、**これは誤り**だった。
絶対座標だけを見ている限り、イベントごとの差分の合計は
「今の位置 − 前のステップの位置」と必ず一致する(途中が打ち消し合う)。
検証で往復させたときに合計がゼロになって気付いた。

合計の形で持つ本当の理由は、カーソルを画面中央へ戻すマウスルックを入れたときに
**戻した瞬間の座標の飛びを除外できる**こと。コメントを書き直してある。
