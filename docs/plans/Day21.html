今日のゴール

テクスチャもシェーダも ResourceManager を通してしか出入りしなくなり、1024x1024 のテクスチャ6枚を 1フレームも止めずに 読み込める。

Day 15 で書いた「ハンドルベースの正式な仕組みは Day 21 で作る」という宿題の回収でもある。

  • E キー(同期ロード): その場で全部読む。実測で 69ms 画面が固まる
  • Q キー(非同期ロード): 即座にハンドルが返る。紫の市松模様(仮の絵)が出て、読めたものから1枚ずつ差し替わる。最悪フレームは 7ms 前後で、止まったようには見えない

事前に読む資料

ロードマップでは資料の指定が無い日なので、この設計の出所にあたるものを挙げておく。

  • Handles are the better pointers(Andre Weissflog)今日の設計はほぼこの記事のとおり。「なぜポインタ(参照)ではなくハンドルなのか」がC++ の文脈で丁寧に書かれている。C# には GC があるので事情が少し違うが、GPU リソースの寿命は GC の管轄外なので話はそのまま通じる
  • Using Rust For Game Development(Catherine West, RustConf 2018)世代付き添字(generational index)が「オブジェクトの参照」の代わりになる、という話。後半は Day 23 の ECS に直結する。今日は前半だけでよい
  • OpenGL and multithreading(Khronos wiki)コンテキストがスレッドに紐づくこと。要点5の根拠

理論の要点

1. 参照を配ると、寿命の持ち主が決まらない

Day 15 の Material にはこう書いてあった。

/// 貼るテクスチャ。共有されるので、こちらも破棄の責任は持たない。
/// 誰が寿命を持つかを曖昧にするとリークか二重解放になる。

「破棄の責任は持たない」と書けるうちはよいが、これは規約であってコードではない。マテリアルが100個あって、どれも同じことを守ってくれる保証はどこにも無い。実際 Day 20 の OnClosing は、こう並べるしかなかった。

csharp
_atlas.Dispose();
foreach (Texture texture in _looseTextures) { texture.Dispose(); }
_spriteShader.Dispose();
_texture.Dispose();
_shader.Dispose();

ここに1行足し忘れれば、そのぶんだけ静かにリークする。気づくきっかけは無い(GL のリソースは GC が回収しない)。

C# なら参照が宙に浮くことは無いのでは、と思うかもしれないが、壊れるのは C# のオブジェクトではなく GPU 側の実体のほう。Dispose すると glDeleteTextures が走り、C# のオブジェクトだけが残る。その状態で Bind すると、削除済みの番号を指すので描画が真っ黒になるか、番号が再利用されていればまったく別の絵が出る。原因(Dispose)と症状(描画)が離れるので、追跡はかなり難しい。

2. ハンドル = 添字 + 世代

解決策は、参照の代わりに整数1個を配ること。実体は配列の中にあり、持ち主はその配列(ResourcePool<T>)ただ1つになる。

  31            24 23                            0
  +---------------+------------------------------+
  |   世代 (8bit) |         添字 (24bit)          |
  +---------------+------------------------------+

添字だけでは足りない。スロットが再利用されると、古いハンドルが別人を指したまま生き続けるからで、これでは 1 の問題が戻ってくる。そこでスロットに世代番号を持たせ、解放のたびに +1 する。

csharp
removed = slot.Value;
slot.Value = null;
slot.Generation = NextGeneration(slot.Generation);   // この1行で古いハンドルが全部死ぬ

引くときは世代も一緒に照合するので、古いハンドルはその場で「無効」と分かる。実測でも確認できる(T キー)。

[OK] 空いたスロットが再利用される  新 #5.g2 / 旧 #5.g1
[OK] それでも古いハンドルは無効のまま

細かいが効く工夫が2つ。

  • 世代 0 を「無効」に予約する。default(Handle<T>) はビットが全部 0 なので、初期化し忘れたハンドルが自動的に無効になる。添字 0 は正当なスロットなので、「添字が 0 なら無効」という判定にはできない
  • 進めるのは解放時。再利用時に進める実装だと、解放してから次に使われるまでの隙間で古いハンドルが通ってしまう

世代は 8 ビットなので 255 回の再利用で一周する。その時点で 255 代前のハンドルを握った相手がいれば蘇るが、起きたら発見はほぼ不可能な種類のバグなので、気になるならビット配分を変える(世代 16 / 添字 16 など)。「同時に持てる個数」と「安全に再利用できる回数」の綱引きで、どちらが厳しいかはリソースの種類によって違う。

3. 共有は参照カウントで扱う

同じテクスチャを複数のマテリアルが使うのは普通のことなので、1人が要らなくなっただけで消えては困る。Retain で +1、Release で -1 し、0 になった瞬間だけスロットを空ける。

これで Day 15 の但し書きが要らなくなる。マテリアルは「持てないものは壊せない」。

重複排除も同じ表で成立する。同じパスを頼まれたら、読まずに Retain して同じハンドルを返す。

同じパスを 1000 回: 10.85ms / 増えたテクスチャ 1 件 / キャッシュヒット 999 回
参照カウント: 1000
全部返したあと: テクスチャ 5 件(開始時 5 件)

1000 回で 10.85ms、つまり1回あたり 10 マイクロ秒かかっている。中身はほぼ Path.GetFullPath(パスの正規化)で、決して安くはない。毎フレームパスで問い合わせるのではなく、ハンドルを持ち回るのが正しい使い方。

なお参照カウントは循環参照に弱い(A が B を、B が A を持つと永遠に 0 にならない)。リソースは他のリソースを持たないので今回は問題にならないが、ゲームオブジェクトの寿命に同じ手を使うと詰まる。Day 22 では別の手を使う。

4. 間接参照のコストは実質ゼロ

「毎回配列を引くなら遅いのでは」という懸念は当然出る。実測すると、

1回あたり
参照を直接使う0.78ns
ハンドルを解いてから使う1.31ns
差0.53ns

差は 0.5ns 程度。スプライト2万枚ぶん解決しても +0.011ms で、1フレームの予算 16.6ms に対して誤差の範囲。やっているのは境界チェックと世代の比較だけなので、当然といえば当然。

だから Submit では素直にその場で解いている。

csharp
_spriteBatch.Draw(_resources.GetTexture(_looseTextures[kind]), center, size, rotation, color, layer);

キャッシュミスの心配があるのは、解いた先(テクスチャ本体)を触るときであって解決そのものではない。プールの配列は連続していて、しかも小さい。

5. 非同期化の境目は「GL を呼ぶかどうか」

OpenGL のコンテキストはスレッドに紐づいている。別スレッドから glTexImage2D を呼んでも、そのスレッドではカレントになっていないので何も起きないか落ちる(共有コンテキストを作れば可能だが、話が一気に面倒になる)。

つまり、テクスチャの読み込みは2つに割れる。

段階中身スレッド実測(1024x1024)
復号ファイル読み + PNG 展開どこでもよい6.0ms
アップロードglTexImage2D + glGenerateMipmap描画スレッド限定1.5ms(ミップマップ無)/ 4.0ms(有)

重いほうが自由に動かせるので、割った甲斐がある。Texture.FromFile を DecodeFile(CPU)と FromPixels(GPU)に分けたのはこのため。

呼び出し側から見た違いはこうなる。

同期    : 呼び出しが返るまで 68.2ms  ← この間ウィンドウは無反応
非同期  : 呼び出しが返るまで  0.1ms  ← 仮の絵を指すハンドルが即座に返る

そしてハンドルだから差し替えられる。読み終わったらプールの1スロットを書き換えるだけで、そのハンドルを持っている全員が新しいほうを見る。呼び出し側に「読み終わったか」を問い合わせるコードすら要らない。

csharp
// 毎フレームこう書くだけ。何が入っているかは知らなくてよい
_spriteBatch.Draw(_resources.GetTexture(handle), ...);

参照を配る設計だと、配った先を全部探して書き換えることになる。これが間接参照を1段はさんだ最大の見返り。

6. アップロードも絞らないと、結局カクつく

復号を裏に回しても、アップロードは描画スレッドに残る。6枚を一度に上げれば、そのフレームで 24ms 止まる——せっかく裏で読んだのに、という間抜けな結果になる。実測がそのとおりになる。

呼び出し全部そろうまで最悪フレーム
基準(ロードなし、1500 フレーム)--0.78ms
同期68.2ms70ms69.7ms
非同期・MaxUploadsPerFrame = 990.1ms35ms27.7ms
非同期・MaxUploadsPerFrame = 10.1ms43ms6.6ms

絞ると「全部そろうまで」は 35ms から 43ms に伸びるが、最悪フレームは 27.7ms から 6.6ms に下がる。遅くなったほうが体感はよい、という典型例。

1フレームずつ追うと、内訳がはっきり見える。

frame   1:   3.21ms  upload  0.00ms  待ち 6   ← 復号中。ワーカーが CPU を食う
frame   5:   2.74ms  upload  0.00ms  待ち 6
frame  33:   5.34ms  upload  4.16ms  待ち 4   ← ここから1フレーム1枚ずつ
frame  34:   4.63ms  upload  2.74ms  待ち 3
frame  37:   3.56ms  upload  4.14ms  待ち 0

止まらないとはいえ、平常時の 0.78ms に対して 3〜5ms は乗る。内訳は「ワーカースレッドが CPU を使うぶん」と「1枚ぶんのアップロード」で、どちらも避けられない。非同期は仕事を消すのではなく、均すもの。

ちなみに 6 枚ぶんの復号バッファは 4MB x 6 = 24MB あり、この間に GC が1回走る。本気でやるなら ArrayPool<byte> で使い回すが、今日はそこまでしない。

7. キャッシュのキーは「同じ結果になる条件」を全部含める

同じ PNG でも、ミップマップ有りと無しは別のテクスチャになる。パスだけをキーにすると、先に読まれたほうが返ってしまう。

Day 18 で見たとおり、ミップマップが無いのに LinearMipmapLinear を指定したテクスチャはエラーも出さずに真っ黒になる。キャッシュのキーをけちると、この形で表面化する。

csharp
private static string MakeTextureKey(string path, bool generateMipmaps) =>
    generateMipmaps ? Path.GetFullPath(path) : Path.GetFullPath(path) + "|nomip";

Path.GetFullPath を通すのは、./assets/x.png と assets/x.png を同じものと見なすため。Windows は大文字小文字を区別しないので、比較も OrdinalIgnoreCase にしてある(Linux へ持っていくならここは変えることになる)。

[ロード完了] 非同期 / 呼び出し 0.1ms / 全部そろうまで 43ms / 最悪フレーム 6.6ms
  → 1フレームの予算に収まっている。読み込んでいることに気づかせない

差し替わる様子を目で追いたいときは V(VSync)を先に押す。上限を外した状態だと 1000fps 近く出るので、43ms は 40 フレーム程度——一瞬で終わってしまって見えない。

[ロード開始] 非同期 6 枚 / 呼び出しが返るまで 0.0ms

裏の復号は完走するが、出来上がったものは Update の生存確認で捨てられる。テクスチャの数が増えていないことがその証拠。参照を配る設計だと、ここで解放済みのオブジェクトに書き込むことになる。

実験台は reference/Day21 の Handle.cs、ResourcePool.cs、ResourceManager.cs(いずれも docs/site/enginecore.js)と、Program.cs の LoadDemoTextures、UnloadDemoTextures、UpdateLoadWatch、RunResourceCheck を JS に移したもの。テクスチャは名前だけの値で、復号とアップロードの時間は本文の実測をもとに置いたモデル。ms の数字はこのページの時計の値で、本文の表(手元の RTX 3070 環境の値)とは一致しない。

改造課題

課題1(易): 仮の絵を変えてみる

ResourceManager.CreatePlaceholder の色を、たとえば黒や透明に変えてみる。

そのうえで Q を押し、「読み込み中であること」に気づけるかどうかを見る。紫の市松が業界の定番になっている理由が体感できる(自然界にほぼ無い色なので、絵として成立してしまわない)。

余裕があれば ResourceManager.MaxUploadsPerFrame を 1 と 99 で切り替えて、タイトルバーの fps がどう変わるかを見る。

課題2(中): メッシュもプールに載せる

Mesh<TVertex> は今も Program が直接 Dispose している。これを ResourcePool<Mesh<Vertex>> に載せて、OnClosing から_cube.Dispose() / _quad.Dispose() を消す。

Handle<Mesh<Vertex>> と書けること(幽霊型がジェネリック型でも動くこと)、ResourcePool<T> がリソースの種類を一切知らずに再利用できることが確認できる。

ただし Mesh はファイルから読むものではないので、ResourceManager の「パス→ハンドル」の表には載らない。プールに載せることと、キャッシュのキーを持つことは別。どこで線を引くかを考えるのがこの課題の主題。

課題3(難): ロードを打ち切れるようにする

今の LoadTextureAsync は、投げた Task を止める手段が無い。ResourceManager.Dispose のコメントにも「本物のエンジンではCancellationToken を渡して止められるようにする」と書いてある。

CancellationTokenSource を持たせて、

  • Release で参照カウントが 0 になったら、対応するロードを取り消す
  • Dispose で全部取り消して、飛んでいる Task の完了を待ってから破棄する

を実装する。シーンを切り替えた瞬間に前のシーンのロードを全部捨てられるようになる。

難しいのは取り消しと完了の競合で、「取り消した直後に完了した」場合に_pending が合わなくなったり、二重に破棄したりしやすい。世代番号があるおかげで最悪でも「捨てられる」だけで済んでいる、という今の作りのありがたみが分かるはず。

重複排除

同じパスを 1000 回要求 → テクスチャは1件、キャッシュヒット 999 回、所要 10.85ms。1回 10 マイクロ秒はほぼ Path.GetFullPath の費用。

検証の途中で分かったこと

  • Handle<T> を辞書のキーにするなら GetHashCode / Equals が要る。readonly struct の既定実装はリフレクション経由で遅いうえ、== を定義しないと参照比較のような書き味にならない
  • 非同期ロード中の最悪フレーム 6.6ms は、内訳を追うと「ワーカースレッドが CPU を食うぶん(3ms)」と「1枚ぶんのアップロード(4ms)」だった。アップロードを絞っても平常時の 0.78ms には戻らない。非同期は仕事を消すのではなく均すもの、という理解でよい
  • 同期ロードでは ResourceManager.Update を通らないので、LastUploadMilliseconds は 0 のまま。GPU 側の費用も同じだけかかっているが、この指標には出てこない
