理論の要点

1. 継承の木は、組み合わせが増えると必ず破綻する

Entity → MovingEntity → Enemy → FlyingEnemy と伸ばしていって、あるとき「飛ばないが爆発する敵」が要る、となる。

  • ExplodingEnemy を作る → 爆発の処理が FlyingEnemy と重複する
  • Enemy に上げる → 爆発しない敵まで爆発の処理を持つ

機能の組み合わせが増えるほど、木のどこに置いても間違いになる。「飛ぶ」「爆発する」「毒を撒く」が独立に付いたり付かなかったりするなら、継承の木は 2^3 通りの葉を要求してくる。

合成なら「爆発する」を1個のコンポーネントにして、必要なものに足すだけ。組み合わせは掛け算で増えるが、部品は足し算でしか増えない。

代わりに払うものが3つある。今日はそれも全部測る。

  • 部品どうしが話すには GetComponent<T>() が要る(要点6)
  • 実行順が決まらない(要点7)
  • オブジェクト1個がヒープ上の何個ものオブジェクトになる(要点5)

2. Transform だけ特別扱いする

Transform は AddComponent しなくても最初から生えている。「そこに無いオブジェクト」が考えにくいからで、Unity も Unreal もここは同じ。

そして親子関係は Transform が持つ。これが今日いちばん効く部分で、

ワールド行列 = 自分のローカル行列 * 親のワールド行列

を根まで再帰するだけで、砲塔が戦車についてくる。掛ける順番が「ローカル * 親」なのは System.Numerics が行ベクトル規約(v' = v * M)だから。Day 16 で見たのと同じ約束で、先に適用したいものを左に置く。

実演として、根 → 子3つ → それぞれの孫1つ、の3段の木を置いてある(画面右上の黄色い丸と、そのまわりを回る水色のリング、さらにそのまわりのピンク)。子も孫も「原点から半径 R の円周上を回る」としか書いていない。どこに出るかは親が決める。

計算し直すのは「変わったときだけ」にしてある(遅延評価)。値を書き換えたら MarkDirty が子孫まで印を付けて回り、LocalToWorld を読まれたときに初めて計算する。すでに印が付いていたら子をたどらないのがコツで、そうしないと深い木で何度も動かしたときに同じ枝を何度も歩く。

3. 回転はクォータニオンで持つ

オイラー角(X回転・Y回転・Z回転の3つの数)で持つと2つ困る。

  • ジンバルロック … 特定の姿勢で軸が重なり、回転の自由度が1つ消える
  • 補間できない … 2つの姿勢の間を角度ごとに線形補間すると、途中で変な方向を向く(最短の回り方にならない)

クォータニオンは4つの数で回転を表し、どちらも起きない。System.Numerics.Quaternion があるので自作はしない。

合成の順番に罠がある。実際に行列と突き合わせて確かめると、

書き方行列の M(local) * M(parent) と一致するか
Quaternion.Concatenate(local, parent)一致する
parent * local(演算子)一致する
local * parent(演算子)一致しない

つまり演算子 * は行列と順序が逆。行列の掛け算と並べて書くと必ず間違えるので、Concatenate を使うほうが安全。

なお 2D(Z 軸まわりだけ)なら、合成は単なる角度の足し算になる(0.7 と 0.4 を合成すると 1.1 になることを確認済み)。Transform.GetInterpolatedWorldRotationZ はこれを使っている。

4. Awake と Start はなぜ分かれているのか

呼ばれるとき何を書くか
AwakeAddComponent の中で即座に自分の初期化だけ
OnEnable有効になったとき購読の開始など
Start最初の FixedUpdate の直前他のコンポーネントを探す
FixedUpdate毎ステップゲームの状態を変える
OnDisable / OnDestroy無効化・破棄のとき後始末

Start が遅れるのには理由がある。Start が走る時点ではそのステップで作られたオブジェクトの Awake が全部終わっているので、「相手を探す」処理を安心して書ける。A が B を、B が A を探しても、どちらの順で作っても動く。Awake でやると、先に作られたほうが相手を見つけられない。

もう1つ、Awake は AddComponent の中で走るので、プロパティを設定する前に呼ばれる。H キーの実演で確かめられる。

  CreateGameObject + AddComponent
    [obj] Awake       (AddComponent した直後)   ← ラベルがまだ既定値
    [obj] OnEnable
  ↑ ラベルはまだ obj。Awake は AddComponent の中で走るので、
     プロパティを入れる前に呼ばれている

「Awake の中で、外から設定した値をあてにしてはいけない」がここから出てくる。

5. 更新中に消してはいけない

Destroy はその場では消さず、予約するだけにしてある。更新中に List から要素を消すと、そこで例外になるか、運が悪いと1個飛ばして更新される。

  Destroy を予約 → まだ生きている
    IsDestroyed = True / シーンにはまだ 9 個
  次のステップの終わりで実際に消える
    [demo] OnDisable
    [demo] OnDestroy   (合計 4 ステップ動いた)
    シーンは 8 個になった

この「予約して後で」はゲームエンジンのあちこちに出てくる形で、Day 21 の非同期ロード(復号を予約して、描画スレッドで消化する)も同じ骨格。

まとめて消すときは RemoveAll を1回だけ呼ぶ。1個ずつ Remove すると、そのたびに後ろ全部がずれて O(n^2) になる(ウェーブが全滅する瞬間のような、大量に消える場面で効く)。

6. GetComponent は「遅い」のか

「GetComponent は遅いから Start でキャッシュしろ」とよく言われる。実測すると、

1回あたり
フィールドを読む0.88ns
GetComponent<T>() 1個目1.03ns
GetComponent<T>() 2個目2.01ns

ほとんど差が無い。型の判定はせいぜい数個ぶんで、しかも同じオブジェクトを続けて触るからキャッシュに乗る。

効いてくるのは別々のオブジェクトを順に引くとき。描画パスと同じ形で2万個を1周すると、

1周あたり
あらかじめ配列に集めておく0.039ms
毎回 GetComponent で引く0.201ms

0.16ms の差。60fps の予算 16.6ms に対して 1% なので致命的ではないが、無視もできない。そしてこの差は探索そのものより「オブジェクトを渡り歩くこと」から来ている——配列版でも中身は散らばったオブジェクトへの参照で、そこはどちらも同じだからだ。

つまり結論は「GetComponent を速くする」ではなく、「オブジェクトを渡り歩かない形に変える」。それが Day 23 の ECS。

7. 実行順は決めていない

Scene は _gameObjects に入っている順(= 生成した順)に更新するだけ。「敵より先にプレイヤーを動かしたい」という要求が出てきたら、優先度を持たせるか、フェーズ(入力 → 移動 → 当たり判定)に分けることになる。

順序が要るのに順序を決めていない設計は、必ずどこかで1フレーム遅れのバグを生む。「なぜかカメラが1フレーム遅れてついてくる」の正体はたいていこれ。

Day 23 の ECS では、この点が「システムを順に並べる」という形で最初から明示的になる。GameObject 方式の弱点が、ECS では設計の前提に変わる。

8. 代償はメモリの置き方で払う

同じ動きを2通りで回した実測(1ステップあたり)。

個数構造体の配列GameObject比うち枠組みうち部品の中身
1,0000.020ms0.089ms4.5x0.039ms0.050ms
5,0000.032ms0.318ms9.9x0.095ms0.223ms
19,9810.082ms1.370ms16.8x0.614ms0.755ms

倍率が個数とともに大きくなるのが肝心なところ。定数倍の差(仮想呼び出し、null チェック)なら倍率は一定のはず。増えていくのはキャッシュに乗り切らなくなるからで、これがデータ配置の問題である証拠。

「枠組み」は部品の中身を止めて測ったもの(Transform の控え + 走査 + 有効判定)で、だいたい半分を占める。部品を軽くしても半分しか減らない。

置き場所を変えただけで計算は変えていないので、当然そうなる。リプレイ(Day 20)は GameObject 化しても壊れない。

改造課題

課題1(易): 部品を1個足す

画面の端に着いたときに色が変わる FlashOnBounce を書いて、EnsureSceneSprites の中で AddComponent する。

  • Start で SpriteRenderer を1回引いて持つ
  • BouncingMover の速度の符号が変わったフレームで色を差す

BouncingMover にも SpriteRenderer にも手を入れずに機能が増えることを確認する。これが合成の見返りそのもの。

課題2(中): 描画リストを登録制にする

RenderScene は毎フレーム全オブジェクトに GetComponent<SpriteRenderer>() を呼んでいる。これを Scene 側に List<SpriteRenderer> を持たせ、RegisterComponent のときに登録する形に変える(破棄のときに外すのを忘れないこと)。

要点6の 0.16ms が消えるはず。タイトルバーの fps で確かめる。

そのうえで考えてほしいのが、この「型ごとのリスト」を全種類ぶん作ったらどうなるか。それが Day 23 の ECS の入口になる。

課題3(難): 実行順を決められるようにする

Component に ExecutionOrder(既定 0)を足して、Scene.FixedUpdate がその順に呼ぶようにする。要点7の「順序が決まっていない」を解消する。

素直にやると毎ステップ全コンポーネントをソートすることになって遅い。

  • コンポーネントが増減したときだけ並べ直す
  • そのために Scene が全コンポーネントの平坦なリストを持つ(今は GameObject ごとの入れ子になっている)

まで来ると、シーンの持ち方が「オブジェクトの木」から「コンポーネントの列」へ寄っていくのが分かる。Day 23 はその先にある。

検証の途中で分かったこと

  • GetComponent は思ったより速い。「遅いからキャッシュしろ」という定説をそのまま書こうとしたが、測ると 1.03ns でフィールド読みと大差なかった。遅いのは探索ではなく、散らばったオブジェクトを渡り歩くことのほう。コメントは測定に合わせて書き直した
  • クォータニオンの合成は演算子 * と行列の * で順序が逆。Quaternion.Concatenate(local, parent) が行列の M(local) * M(parent) に対応する。行列と並べて書くコードでは事故のもとなので、実際に突き合わせて確認した
  • GameObject 版の遅さのうち、SetLocalRotationZ(sin/cos とクォータニオン生成)がそれなりの割合を占める。汎用の Transform を持つこと自体のコストで、コンポーネント方式そのものの費用ではない。比の 16.8 倍を全部「合成のせい」と読むのは正しくない
