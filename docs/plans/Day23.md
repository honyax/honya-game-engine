## 理論の要点

### 1. ECS は「持ち方の裏返し」

Day 22 の `GameObject` は、名前と `Transform` とコンポーネントのリストを抱えた
ヒープ上のオブジェクトだった。ECS ではそれが**32 ビットの整数1個**になる。

```
GameObject : GameObject[] → それぞれが Component[] を持つ   (1個ぶんがまとまる)
ECS        : ComponentStore ごとに配列                       (同じ種類がまとまる)
```

「位置」も「絵」も「速度」も、エンティティが**持っている**のではなく、
`ComponentStore<T>` の側が「この番号のぶん」として持つ。

この裏返しが ECS の全部と言ってよい。
そして名前のとおり3つに分かれる。

| | 中身 | 今日のファイル |
|---|---|---|
| **E**ntity | ただの番号。データもふるまいも持たない | `Entity.cs` |
| **C**omponent | データだけの構造体。ふるまいを持たない | `EcsComponents.cs` |
| **S**ystem | 配列を舐めるだけの手続き。状態を持たない | `EcsSystems.cs` |

`Entity` の中身は Day 21 の `Handle<T>` とまったく同じ
——世代 8 ビット + 添字 24 ビットで、世代 0 を無効に予約している。
**「使い回される配列の枠を安全に指す」という問題は同じ**なので、答えも同じになる。

### 2. sparse set — 3本の配列で「隙間なく詰める」

`ComponentStore<T>` の中身。

```
_dense         [ Pos0 ][ Pos1 ][ Pos2 ] ...   ← 実体。隙間なし。ここを舐める
_denseToEntity [  7   ][  3   ][  12  ] ...   ← 密な添字 → エンティティ番号
_entityToDense [ .. ][ .. ][  1  ][ .. ]      ← エンティティ番号 → 密な添字(-1 で無し)
```

肝は `_dense` に隙間が無いこと。システムはここを頭から順に舐めるだけなので、
CPU のプリフェッチが効き、キャッシュラインを無駄なく使える。

取り除くときは**末尾と入れ替えて縮める**ので O(1)。
代わりに並び順が変わるので、密な添字を覚えておいてはいけない。

`Values` を `Span<T>` で返しているのも意味がある。
`List<T>` の添字アクセスは構造体だと**コピーが返る**ので、その場で書き換えられない。
`Span<T>` なら `ref` で触れる。同じ理由で `Get` も `ref T` を返している。

### 3. なぜ速いのか — 触るバイト数が減る

移動のシステムが読み書きするのは `Transform2D`(12 バイト)と
`Velocity2D`(16 バイト)だけ。合計 28 バイト。

Day 17 からの `Sprite` 構造体は **64 バイト**あって、
色(16)も種類(4)もレイヤー(4)も**移動には要らないのに一緒に運ばれていた**。
64 バイトのキャッシュラインに 1 体しか入らない計算になる。
ECS では 28 バイトなので、同じ 1 ライン に 2 体強が乗る。

だから ECS は「GameObject より速い」だけでなく、
**手書きの構造体配列にも並ぶ**(実測 1.01 倍)。
1,000 体では 0.96 倍とわずかに速いことすらある。

もう1つ、ECS では**表現を用途ごとに選べる**。
Day 22 の `Transform` はクォータニオン・スケール・親子・ダーティフラグを
全員に配っていたが、`Transform2D` は `Vector2` + `float` しか持たない。
3D が要るところには 3D 用のコンポーネントを別に作ればよい。
Day 22 で「16.8 倍のうちいくらかは汎用 Transform のコスト」と書いたが、
ECS はその汎用性を**捨てる自由**を与える。

### 4. 結合(join)のコストと、アーキタイプ方式

いいことばかりではない。移動には `Transform2D` と `Velocity2D` の**両方**が要る。
2本の配列を突き合わせる(結合する)には、
エンティティ番号 → 密な添字 → 実体、と1段余計にたどることになる。

```csharp
// 一般の場合: 片方を舐めて、もう片方は番号で引く
int dense = velocities.DenseIndexOf(entities[i]);
Step(ref t[i], ref velocities.AtDense(dense), ...);
```

実測すると、これが効く。

| 体数 | 添字をそのまま使う | 番号で引く | 比 |
|---|---|---|---|
| 1,000 | 0.018ms | 0.063ms | 3.45x |
| 19,981 | 0.087ms | 0.137ms | 1.57x |

**全員が同じコンポーネントを同じ順で持っていれば、添字をそのまま使える**。
このデモは全員を同じ手順で作っているのでその状態になっており、
`EcsSystems.AreAligned` で確かめてから速い経路に入る。

問題は、その前提が**いつ崩れるか**が直感に反すること。`D` キーで確かめられる。

```
[OK] 同じ順で付ければ並びは一致する
[OK] 破棄しても並びの一致は保たれる      ← 全ストアが同じ入れ替えをするから
[OK] 片方にしか無ければ件数が合わない
[OK] 件数がそろっても順番は戻らない      ← 後から足すと崩れる
```

「破棄では崩れないが、後から足すと崩れる」。
崩れたまま速い経路を使えば**静かに間違う**——例外も出ず、別人の速度で動く。

そこで出てくるのが**アーキタイプ方式**(Unity DOTS、flecs、Bevy などが採る)。
「同じコンポーネント構成のエンティティを、同じ塊にまとめて置く」ことで、
上の `aligned` な状態を**人間の注意力ではなく構造で保証する**。
代わりにコンポーネントを足し引きすると塊の間で引っ越しが起きる。

今日は sparse set を書いて**結合のコストを実際に払ってみる**ところまで。
「なぜアーキタイプという面倒な仕組みがあるのか」が、
1.57〜3.45 倍という数字で腹に落ちるはず。

### 5. システムの順番は「書く」もの

Day 22 の要点7で、`Scene` の実行順は「リストに入っている順」でしかなく
誰も決めていない、と書いた。ECS では逆で、**書かないと動かない**。

```csharp
EcsSystems.Snapshot(_world, _ecsAligned);   // 控えてから
EcsSystems.Move(_world, dt, bounds, _ecsAligned);   // 動かす
```

逆にすると補間が1ステップぶんずれる。
「入力 → 移動 → 当たり判定 → 描画」を呼び出し側に並べさせるのが ECS の作法で、
**Day 22 の弱点が設計の前提に変わる**。

システムを静的メソッドにしてあるのも同じ狙い。
システムが状態を持ち始めると、それは結局オブジェクトになる。
状態はコンポーネント(= `World` の中)にしか置かない。

### 6. ECS は全部を置き換えるものではない

このデモでも、**プレイヤーと階層の実演は3つのどのモードでも GameObject のまま**。
意図的にそうしてある。

ECS が苦手なのは、

- **親子関係** … 「親のワールド行列」を引くには結局ポインタを辿ることになる。
  ECS で階層をやるなら、親のエンティティ番号を持たせて
  「親が先に更新されている順」に並べ替える(トポロジカルソート)ことになり、
  Day 22 の `Transform` より確実に面倒
- **少数で、それぞれ違うふるまいをするもの** … プレイヤー1体のために
  コンポーネントとシステムを作る旨みは無い。`PlayerController` 1クラスのほうが読める
- **オブジェクト間の1対1のやりとり** … 「この敵がこの弾に当たった」のような
  個別の関係は、配列を舐める形に馴染まない

逆に得意なのは**同じ処理を大量にかけるもの**。
Phase 5 の卒業制作(敵が数百体押し寄せる見下ろし型アクション)は
まさにそれで、敵と弾は ECS、プレイヤーと UI は GameObject、
という**混ぜた作り**が現実的な答えになる。

「どちらが正しいか」ではなく「どこに何を使うか」。
ロードマップが**同じものを2回書かせた**のは、この判断ができるようになるため。

### 7. 設計を変えても計算は変わっていない

3つの経路を同じ初期状態から 400 ステップ回して、位置をハッシュで突き合わせる。

```
500 体 x 400 ステップ後の位置のハッシュ
  構造体の配列: 46918C8954922A4A
  ECS         : 46918C8954922A4A  一致
  GameObject  : 46918C8954922A4A  一致
```

**ビット単位で一致する**。浮動小数点の足し算は順序を変えると結果が変わる
(Day 19 要点7)ので、これは「同じ演算を同じ順でやっている」ことの証明になる。

つまり今日やったのは最適化であって、仕様変更ではない。
Day 20 のリプレイも、Day 19 の決定性も、そのまま生きている。
**性能の話をするときは、まずこれを確かめてから**でないと、
速くなったのか壊れたのか区別がつかない。

## 改造課題

### 課題1(易): コンポーネントとシステムを1つ足す

`Fade2D { public float Life; }` を作り、時間で `Sprite2D.Color.W` を下げる
`FadeSystem` を書いて、`EcsSystems` に足す。

- `EnsureEcsSprites` で一部のエンティティにだけ `Fade2D` を付ける
- 付いていないエンティティは**そもそもストアに入っていない**ので、
  `if (has fade)` のような判定が1つも要らないことを確認する

**「持っていないものは配列に無い」**が ECS のいちばん気持ちのよいところ。
Day 22 では全オブジェクトを回って `GetComponent` の結果を null チェックしていた。

なお `Fade2D` を一部にだけ付けると、そのストアだけ並びが崩れる。
`FadeSystem` は番号で引く経路を通ることになるので、そこも確かめる。

### 課題2(中): `Store<T>()` の辞書引きをなくす

`World.Store<T>()` は毎回 `Dictionary<Type, ...>` を引いている。
2万体を作るのに `Add` が 8 万回走り、そのたびに辞書を引くので、
構築の 20ms のかなりの部分がこれになっている。

定石は**静的ジェネリッククラスに型ごとの番号を焼く**こと。

```csharp
private static class TypeId<T> where T : struct
{
    public static readonly int Id = Interlocked.Increment(ref _nextTypeId) - 1;
}
```

`Id` は型ごとに1回だけ計算され、以降は定数を読むのと同じ速さになる。
ストアを `IComponentStore[]` に持ち替えて、この番号で引く。

構築時間がどこまで下がるか測ってみること
(更新時間のほうは、ループの外で1回引いているので変わらないはず)。

### 課題3(難): アーキタイプ方式に一歩寄せる

要点4の「並びが崩れると静かに間違う」を、構造で防げるようにする。

いきなり本物のアーキタイプは重いので、まずは**崩れたら分かる**ところから。

- `ComponentStore` に「構造が変わった世代番号」を持たせる
- `Snapshot` / `Move` は、渡された `aligned` が現在の世代と食い違ったら例外にする

そのうえで、余裕があれば本物に近づける。

- 「このコンポーネント構成のエンティティ群」をアーキタイプとして持つ
- コンポーネントを足し引きしたら、アーキタイプ間で引っ越す
- システムは「この構成を含むアーキタイプ」だけを舐める

引っ越しのコストと、結合が消える利得のどちらが勝つか。
**エンティティの構成が頻繁に変わるゲームでは負けることもある**、
というのが分かればこの課題は十分。

| 19,981 | 0.084ms | 1.511ms | 0.084ms | 18.1x | 1.01x |

### 結合のコスト

並びが一致しているデータに対して、わざと一般の経路を通した場合。

| 体数 | 添字をそのまま | 番号で引く | 比 |
|---|---|---|---|
| 1,000 | 0.018ms | 0.063ms | 3.45x |
| 19,981 | 0.087ms | 0.137ms | 1.57x |

**体数が多いほど比が小さくなる**のが面白いところで、
2万体ではどちらもメモリ帯域で頭打ちになり、余計な1段の相対的な重みが下がる。

### 1体あたりのバイト数

| | 1体 | 2万体 |
|---|---|---|
| `Sprite` 構造体 | 64 バイト | 1.3MB |
| ECS(定常状態) | 104 バイト | 2.1MB |
| GameObject | 515 バイト | 10.0MB |

ECS の内訳は、コンポーネント 68 バイト
(`Transform2D` 12 + `Previous2D` 12 + `Velocity2D` 16 + `Sprite2D` 28)に、
索引の配列 32 バイト(`denseToEntity` 4本 + `entityToDense` 4本)と
世代 4 バイトを足したもの。

`GC.GetTotalAllocatedBytes` での実測は 256 バイト/体だが、
これは**配列を倍々に伸ばす途中で捨てた古い配列**を含んだ数字。
最終的に生きているのは 104 バイト/体。

### 構築時間(19,981 体)

| | 時間 |
|---|---|
| GameObject 化 | 20.7ms |
| エンティティ化 | 20.0ms |

**ここは ECS でもたいして速くない**。
`world.Add` が1体につき4回、そのたびに `Store<T>()` が辞書を引いているため
(課題2で潰せる)。「ECS だから何でも速い」ではない。

### 検証の途中で分かったこと

- **3つの経路の結果がビット単位で一致した**。GameObject 版はクォータニオンを
  経由しているので位置だけの比較にしたが、それでも完全一致。
  設計を変えても演算の順序を変えていないことの裏付けになる
- 結合のコストは**体数が少ないほど比率が大きい**。
  少数だと全部キャッシュに乗るので、余計な1段の相対的な重みが増す。
  「大きいデータのほうが最適化が効く」とは限らない
- ECS の並びは**破棄では崩れない**(全ストアが同じ入れ替えをするため)のに、
  **後からコンポーネントを足すと崩れる**。
  直感と逆で、自己チェックを書くまで気づかなかった
