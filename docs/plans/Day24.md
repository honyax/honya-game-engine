## 理論の要点

### 1. なぜシーンをファイルに出すのか

Day 23 まで、シーンは `CreateDemoScene()` というメソッドの中にあった。動くが、

- レベルを1つ変えるたびに**ビルドが要る**
- 企画やアーティストが触れない(C# が書けないと何もできない)
- 「このシーンで落ちる」を人に渡せない
- セーブ/ロードが別の仕組みになる

シーンがデータになると、これが全部ひっくり返る。
エディタは「GUI でファイルを吐くプログラム」でしかなくなり、
セーブは「今の状態を同じ形式で書く」だけになる。

**エンジンとゲームの境目は、ここで初めてはっきりする**。
Day 23 までの Program.cs は「エンジン + ゲーム」が混ざっていた。
今日から Program.cs は「ファイルを読んで回すもの」になり、
ゲームの中身は `assets/scenes/` に移る。

### 2. 難しいのは形式ではなく、多態と参照

JSON を書くこと自体は簡単で、`System.Text.Json` が全部やってくれる。
詰まるのは次の2つ。

**多態** — `List<Component>` の要素は型がばらばらで、
ファイルに型の印が無いと読むときに何を作ればいいか分からない。

```json
{ "type": "SpriteRenderer", "data": { "Kind": 2, "Size": 68, "Color": [1, 1, 1, 1] } }
```

印に何を書くかが問題で、**`type.FullName` や `Type.GetType(name)` は使えない**。

- クラス名を変えた瞬間、過去のシーンが全部読めなくなる
- **ファイルに書いてある名前のクラスなら何でも作れてしまう**
  (`BinaryFormatter` が非推奨になった理由も突き詰めるとこれ)

だから `ComponentRegistry` に**明示的に列挙したものしか読み書きしない**。
コンポーネントを増やすたびに1行足すのは面倒だが、その面倒さが上の2つを防いでいる。

**参照** — 親子関係は C# のオブジェクト参照でつながっているが、
参照はメモリ上のアドレスなので書き出せない。「配列の何番目か」に翻訳する。

```json
{ "id": 2, "name": "Orbit0", "parent": 1, ... }
```

Day 21 のハンドル、Day 23 のエンティティ番号とまったく同じ発想で、
**持ち歩ける形にするには番号にするしかない**。

読むときは**3周する**。

1. オブジェクトを作る(親はまだ結ばない)
2. 親を結ぶ
3. コンポーネントを付ける

1と2を分けるのは、**子が親より先に書いてあっても読めるように**するため。
ファイルの並び順に依存する読み込みは、手で編集した瞬間に壊れる。
2と3を分けるのは、コンポーネントの `OnEnable` が `ActiveInHierarchy` を見るから
(Day 22 要点4)。親を結ぶ前に付けると、親が無効なのに `OnEnable` が走る。

### 3. 何を保存し、何を保存しないか

これは形式の問題ではなく**設計判断**で、間違えても動いてしまうぶん厄介。

| | 保存する? | 理由 |
|---|---|---|
| `Transform` の位置・回転 | する | シーンの初期配置そのもの |
| `SpriteRenderer` の色・大きさ | する | 見た目の設定 |
| `PlayerController.Velocity` | する | 「最初から右へ飛んでいる敵」を置きたいことがある |
| `PlayerController.DashCooldown` | **しない** | 今まさに走っている最中の一時的な値 |
| `Component.GameObject` | **しない** | 逆向きのリンク。保存すると無限に潜る |

`GameObject` を保存対象にすると
コンポーネント → GameObject → コンポーネント → … と無限再帰する。
**所有関係は1方向だけ書けば復元できる**ので、逆向きのリンクは書かない。

`DashCooldown` と `Velocity` の違いが分かりにくいところ。
**シーンは初期状態、セーブデータは実行時状態**で、目的が違う。
同じ形式で両方をまかなおうとすると必ずどちらかが歪む
(「シーンを開いたらダッシュのクールダウンが残っている」は明らかにおかしい)。

C# 側では `[JsonIgnore]` 1つで表明する。**コードの上で決着をつける**のが大事で、
「保存する側で気をつける」にすると必ず忘れる。

### 4. ECS のシリアライズは驚くほど簡単

同じファイルに ECS も書いているが、こちらは 20 行程度で済む。

```json
"ecs": {
  "count": 2000,
  "transform2D": [ {"Position": [123, 45], "Rotation": 0.5}, ... ],
  "velocity2D":  [ ... ]
}
```

多態が無い(コンポーネントはただの構造体)。
参照が無い(エンティティは番号)。
種類ごとに配列に詰まっているので、**配列を4本そのまま書く**だけ。

ただし**4本の並びが一致していること**が前提になる(Day 23 要点4)。
一致していないと「何番目がどのエンティティか」を別に書く必要がある。
並びを揃えておく利得が、性能だけでなく**保存の単純さ**にも効いてくる。

「ECS はシリアライズしやすい」はよく言われるが、
GameObject 側を先に書いてから比べると理由がはっきりする。

### 5. 「往復して一致する」は「正しく保存できている」ではない

今日いちばんの教訓。**この作業中、同じ罠に2回はまった**。

`System.Text.Json` は既定で**プロパティしか見ない**。フィールドは無視する。
ところがこのエンジンには、フィールドで持っている型が2種類ある。

- `System.Numerics` のベクトル(`X` / `Y` / `Z` / `W` はフィールド)
- ECS のコンポーネント(`Transform2D` などは全部フィールド)

どちらも**黙って `{}` になる**。例外も警告も出ない。

```json
"Color": {},        ← 色が消えている
"transform2D": [ {}, {}, {}, ... ]   ← 2000 体ぶん全部空
```

たちが悪いのは、**往復チェックのテキスト比較を通ってしまう**こと。
保存も再保存も同じように `{}` を書くので、当然一致する。

```
[OK] 保存 → 読み込み → 再保存でテキストが一致   ← 中身が空でも通る
```

だから往復チェックには**具体的な値の確認**を入れる必要がある。

```
[OK] Vector4 が保たれている  <0.125, 0.25, 0.375, 0.5>
[OK] Vector2 が保たれている  <123, -45>
[OK] ECS コンポーネントの値が保たれている  <10, 20>
```

わざと変な値(`0.125, 0.25, 0.375, 0.5`)を入れているのは、
既定値のままだと「保存できていない」と「たまたま既定値」の区別がつかないから。

直すのは `IncludeFields = true` の1行。
加えて `Vector2` などに専用の変換器を入れて `[1, 2]` の形にしている
(`IncludeFields` だけだと `{ "X": 1, "Y": 2 }` と3行に膨らむ)。

### 6. バージョン番号は最初から書く

```json
{ "version": 1, "name": "demo", ... }
```

後から足そうとすると「バージョンが書いていないファイル」を
特別扱いする分岐が永遠に残る。1バイトの節約より、
**「読めないと分かること」**のほうがはるかに価値がある。

そして**知らないコンポーネントは読み飛ばす**。落とさない。

```csharp
if (type is null)
{
    Console.WriteLine($"[scene] 知らないコンポーネント \"{typeName}\" を読み飛ばしました");
    continue;
}
```

新しいブランチで作ったシーンを古いブランチで開く、という状況は普通に起きる。
そこで例外を投げると、1つ知らない部品があるだけでシーン全体が開けなくなる。

### 7. JSON の代償

人が読めて diff が取れる代わりに、**太くて遅い**。

| エンティティ数 | ファイル | 保存 | 読み込み |
|---|---|---|---|
| 0(GameObject 8 個のみ) | 6.9KB | 0.1ms | 0.2ms |
| 1,000 | 611.8KB | 7.7ms | 12.1ms |
| 5,000 | 3,030.3KB | 31.2ms | 61.1ms |

1体あたり **605 バイト**。実行時のメモリは 104 バイト(Day 23)なので**約6倍**。
数値を1行ずつ改行して書いているのが効いている。

5,000 体の読み込みに 61ms かかるのは、
ロード画面のあるゲームなら気にならないが、
**ストリーミング(遊んでいる最中に読む)には遅すぎる**。

だから実際のエンジンは2つ持つのが普通。

- **編集用** … テキスト。人が読み、git で差分を取り、手で直せる
- **実行用** … バイナリ。ビルド時に変換しておき、実行時はこれだけ読む

Unity の `.unity`(テキスト)と `.assetbundle`(バイナリ)、
Unreal の `.uasset` がまさにこの関係。
今日はテキストだけ作った。**まずは読める形で正しく動かす**のが順番として正しい。

## 改造課題

### 課題1(易): コンポーネントを1つ増やして保存できるようにする

Day 22 の改造課題1で作った `FlashOnBounce`(または好きな部品)を、
シーンファイルに保存できるようにする。

- `ComponentRegistry` に `Register<FlashOnBounce>("FlashOnBounce")` を1行足す
- 保存したくないフィールドに `[JsonIgnore]` を付ける
- `F2` で保存して、ファイルの中身を目で確かめる

登録を**忘れたまま**保存するとどうなるかも見ておくこと
(`NameOf` が例外を投げて、何が足りないかを教えてくれる)。

### 課題2(中): プレハブを作る

同じ構成のオブジェクトを何個も置きたいとき、今の形式では
GameObject を丸ごと何度も書くことになる。これを

```json
{ "prefab": "enemy", "position": [100, 200, 0] }
```

と書けるようにする。`assets/prefabs/enemy.json` に1体ぶんを置いておき、
読み込み時に展開して位置だけ差し替える。

考えどころは**プレハブの値を1箇所だけ上書きしたいとき**。

```json
{ "prefab": "enemy", "position": [100, 200, 0],
  "overrides": { "SpriteRenderer": { "Color": [1, 0, 0, 1] } } }
```

Unity のプレハブオーバーライドがなぜあんなに複雑なのか、
自分で書くと一瞬で分かる。

### 課題3(難): バイナリ形式を足して、読み込み時間を比べる

要点7の「編集用テキスト / 実行用バイナリ」を実際に作る。

- `BinaryWriter` / `BinaryReader` で同じ内容を書く形式を足す
- ECS 側は `MemoryMarshal.AsBytes(store.Values)` で配列を丸ごと書ける
  (構造体が blittable なので、1回の `Write` で済む)
- 5,000 体で、ファイルサイズと読み込み時間を JSON と比べる

JSON の 3,030KB / 61ms が何倍になるか予想してから測ること。
そのうえで、**それでも編集用にテキストを残す理由**を考えてみてほしい。

### 検証の途中で分かったこと

- **`System.Text.Json` はフィールドを無視する**。`Vector2` も ECS の
  コンポーネントもフィールドなので、黙って `{}` になった。
  例外も警告も出ないので、保存したファイルを目で見るまで気づかない
- しかも**往復チェックのテキスト比較は通ってしまう**。
  保存も再保存も同じように `{}` を書くため。
  「往復して一致した」で安心してはいけない、という実例になった。
  対策として、わざと変な値を入れた目印のオブジェクトを1体置き、
  `Vector2` / `Vector4` / ECS コンポーネントの値を名指しで比べるようにした
- 同じ罠に**2回**はまった。1回目は GameObject 側の `Vector4`(変換器で修正)、
  2回目は ECS 側の構造体(`IncludeFields = true` で修正)。
  1回目の修正が2回目を隠していた——変換器は「プロパティの中の Vector」は直すが、
  「フィールドだらけの構造体そのもの」は直さない
