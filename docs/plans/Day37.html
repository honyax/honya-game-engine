理論の要点

1. AO は「レンダリング方程式の可視項」を先に抜き出したもの

Day 35 で書いたレンダリング方程式には、実は項が1つ足りていなかった。

  Lo(V) = ∫ f(V, L) * Li(L) * V(L) * (N・L) dω
                              ~~~~
                              可視項。その方向に何も無ければ 1、遮られていれば 0

平行光源1本のときは、これがシャドウマップ(Day 33)そのものだった。IBL(Day 36)ではこの項を丸ごと 1 と置いていた——「まわりの景色は全部見えている」という仮定で焼いたのが放射照度マップ。

環境遮蔽はその仮定を緩める。ただし方向ごとに解くのではなく、方向によらない1つの係数に潰す。

  AO(P) = (1/π) ∫ V(L) (N・L) dω        … 半球のうち、どれだけ空が見えるか

これを環境光に掛ける。厳密には嘘で、遮られている方向と明るい方向がずれていれば結果は合わない。それでも使うのは、方向を捨てたぶん、1画素あたり1つの数字で済むから。

2. 「画面に写っているもの」だけで遮蔽を測る

正しく AO を出すなら、点 P から半球じゅうへレイを飛ばして当たり判定をする。三角形が 100 万個あればその 100 万個が相手になる。

SSAO の発想は、その世界の模型として深度バッファを使うこと。

  1. P のまわりの半球に、点をばらまく
  2. その点が「画面のどこに写るか」を計算する
  3. その画素にすでに描かれている面が、点より手前にあるか?
       手前にある = その方向は何かで塞がっている

当たり判定を1回もしていないのが肝で、やっているのは射影と、テクスチャの読み込みと、大小比較だけ。だからコストは画素数 × 標本数で決まり、三角形が 100 万個あろうと 100 個だろうと同じ時間で終わる。

代償は「深度バッファは世界の模型として不完全」なこと。

失われるものどう見えるか
画面の外にあるものカメラを振ると画面の縁の暗がりが揺れる
手前の物の裏側柱の縁に沿って、背景側が不自然に明るい/暗い
厚み薄い板と分厚い柱が同じに扱われる

この3つは手法の欠陥ではなく定義で、どんなに丁寧に実装しても消えない。消したければ画面の外の情報を持つしかなく、それがボクセル化(VXAO)やレイトレーシング(RTAO)へ進む道になる。

3. 半球でなければならない

標本を球全体にばらまくと、平らな面でも半分が「遮られている」と出る。面の裏へ潜った点は、必ず面より奥にあるから。

      球でばらまく                  半球でばらまく
         ・ ・ ・                       ・ ・ ・
       ・   N   ・                    ・   N   ・
    ───●───────────            ───●───────────
       ・       ・   ← 全部遮蔽と判定される
         ・ ・ ・

Crytek の初代 SSAO(2007)はこれを球でやっていて、シーン全体が一律に薄暗くなるのが特徴的な絵だった。1 - 0.5 = 0.5 が「何も無いところ」の値になるので、そこから明るさを持ち上げる調整が必要になる。

半球にするには、法線を軸にした接空間が要る。Day 34 で法線マップのために組んだ TBN とまったく同じ手順で、違うのは接線を UV の傾きではなく乱数から作ること。

4. 少ない標本は「ノイズにしてからぼかす」

半球の積分を 16 点や 32 点で済ませているので、当然誤差が出る。全画素で同じ 16 方向を使うと、誤差も全画素で同じ形になる——これが縞やまだら(バンディング)として出る。

そこで画素ごとに接空間をランダムに回す。すると誤差は規則的な模様から、目に付きにくい砂嵐へ変わる。

砂嵐はぼかせば消える。縞はぼかしても縞のまま残る。これが「ノイズを入れてからぼかす」が定番になる理由で、Day 36 の事前フィルタ(重点サンプリング)とも、今後のテンポラル AA(Day 38 以降)とも同じ発想の系列にある。

ぼかしの幅はノイズの周期に合わせる。4x4 で敷いたなら 4x4 で平均する。そうすると 16 通りがちょうど1回ずつ混ざり、模様がきれいに消える。5x5 や 3x3 だと割り切れず、薄い格子が残る。

5. 遠くの物に遮られたことにしない

素朴に「手前に面があれば遮蔽」とすると、柱の向こうにある遠くの壁まで遮蔽物と数えてしまう。柱の縁に沿って、背景が黒く縁取られる形で出る。

対処は、深度の差が半径を超えたら効き目を落とすこと。

glsl
  float rangeCheck = smoothstep(0.0, 1.0, uRadius / abs(P.z - sampledZ));

この1行がスクリーンスペースの性格を全部表している。本当の遮蔽を測っているなら、こんな補正は要らない。深度バッファという不完全な模型を相手にしているから、「模型として信用できる範囲」を自分で区切る必要がある。

6. 半径はシーンの大きさで決まる。万能の値は無い

SSAO のつまみの中で、半径だけが物理的な長さを持っている。1辺 1m の箱が並ぶシーンなら 1m 前後、机の上の小物なら 5cm、街並みなら 3m——その都度決めるもの。

作例の数字をそのまま持ってくると効かない、というのがここの落とし穴で、LearnOpenGL が 0.5 なのはあちらの箱が小さいから。このリファレンスは 1辺 1m の立方体が並ぶ縮尺なので 1.0m にしてある。

半径を上げると暗がりは広がるが、遠くの物まで遮蔽物と数え始める。上の要点5の綱引きがそのまま出るので、「広く効かせたい」と「嘘を増やしたくない」の間で決めることになる。

7. AO を直接光に掛けてはいけない

AO はまわりから回り込んでくる光がどれだけ遮られるかの値なので、太陽から一直線に来る光とは無関係。遮っているものがあるなら、それは影(Day 33)の仕事。

掛けてしまうと、日向の壁際まで暗くなり、絵全体が薄汚れる。Ctrl+F11 でわざとそうできるようにしてある——「なんとなく汚い」がどこから来るのかを一度見ておくと、他人の絵を見たときにも気づけるようになる。

同じ話が Day 33 でも出ている(影は直接光にだけ掛ける)。AO と影はちょうど裏返しで、掛ける先が入れ替わっている。

何が遮られているか掛ける先
影(Day 33)太陽直接光
AO(Day 37)まわり全部環境光

正しい直し方は1回描いて複数のバッファへ同時に書く(MRT / G バッファ)で、それが Day 52 の主題になる。今日そこへ踏み込まないのは、Framebuffer にカラーアタッチメントを複数挿す口が無く、足すと差分が今日の主題から外れて広がるため。

どちらの読み何を答える

標本の先の画素その方向に何か写っているか

2本目が SSAO の全部で、当たり判定の代わりをしている。だから画面に写っていないものは絶対に遮蔽しない——画面の外の柱も、手前の物の裏側も、深度バッファには存在しない。

なぜ遮蔽バッファが2枚あるかは PostProcess のぼかしと同じ理由で、同じテクスチャを読みながら同じテクスチャに書けないから(GPU は読み書きの順序を保証しない)。あちらは4往復するので ping-pong だったが、こちらは1回で済むので_occlusion → _blurred の一方通行になっている。

ぼかしを切ると Result が _occlusion を指す。バッファを2枚持ったまま片方を使わない形にしてあるのは、切り替えのたびに確保し直すより、2MB(R8 なら)を持ち続けるほうが安いため。

改造課題

課題1(易): 遮蔽率を画面に出さずに数字で確かめる

Ctrl+F2 の全画面表示は便利だが、「この点はいくつか」には答えてくれない。

マウスカーソルの下の画素の遮蔽率を読み返して HUD に出せ。RunSsaoCheck の ReadOcclusion がそのまま使える(_input.Mice[0].Position が窓の左上原点なので、Y を反転する必要がある)。

毎フレーム glReadPixels を呼ぶと GPU の同期待ちが入るので、fps がどれだけ落ちるかも一緒に見ておくとよい——これが「デバッグ表示は画面に出すのが安い」理由になっている。

課題2(中): 半径をワールドではなくスクリーンで頭打ちにする

いまの実装は半径をワールド単位で持っているので、カメラが遠ざかると、探る範囲が画面上で数画素まで縮む。すると標本が全部同じテクセルを読み、遮蔽が出なくなる。

ssao.frag で、投影後の半径が一定の画素数を下回らないように制限せよ。ヒント: ビュー空間の半径 r は、画面上ではおよそr * (画面の高さ/2) / (tan(fov/2) * depth) 画素になる。

逆に近づきすぎると画面の半分を探ることになって重くなるので、上限も要る。実際のエンジンはどちらも入れている。

課題3(難): ぼかしを深度でエッジを守る形にする

いまの ssao-blur.frag は 4x4 の単純平均なので、手前の物と奥の壁の境目でも混ぜてしまう。柱の輪郭のまわりで AO がにじみ、輪郭が二重に見える。

幾何バッファの距離も一緒に読み、中心との深度差が大きい画素の重みを落とせ(バイラテラルフィルタ)。

glsl
  float w = exp(-abs(centerDepth - sampleDepth) / uDepthSigma);

テクスチャの読み込みが 16 回増えるので、Ctrl+F10 の計測でコストがどれだけ上がるかを必ず測ること。値打ちに対して割に合うかを自分で判断するのが、この課題の主題。

さらに進めるなら、法線の差でも重みを落とすと内角のにじみが止まる。そこまで行くと HBAO(事前に読む資料の最後)の入口に立っている。

検証の途中で分かったこと

1. カーネルを先頭から取ると、いちばん短い標本だけになる

BuildKernel は「中心寄りに密」にするため、標本を短いものから長いものの順に作っている。そこへ「標本数を減らすときは先頭から N 本」と素直に書くと、8本にした瞬間に手元 5cm しか探らなくなる。

最初はそれで、標本数を 8 に落とすと AO が全部 1.000 になった。半径を上げても何も起きないので、しばらく uRadius の送り忘れを疑っていた。

直し方は間引いて読むこと(uSampleStride = 64 / uSampleCount)。「配列の順序に意味がある」ことを、使う側が知っている必要がある——順序に意味を持たせた時点で、部分集合の取り方も設計の一部になる。

2. 平らな面の自己遮蔽は、平均値では捕まえられない

下駄(uBias)を 0 にしたときの不具合を確かめようとして、最初は「開けた床の AO が下がるはず」と考えた。下がらなかった(1.000 のまま)。

理屈のうえでも下がらない。完全に平らな面では、半球の標本は必ず面より手前にあるので、下駄が無くても遮蔽と判定されない。実際に出るのは深度の量子化と長さがほぼ 0 の標本による、当たり外れのばらつき——つまり平均ではなく分散に出る。

そこで自己チェックの物差しをノイズのタイル1枚の中の標準偏差に変えた(TileNoise)。4x4 の中では幾何がほぼ同じで乱数の向きだけが違うので、本物の濃淡が混ざらない。下駄なし 0.0221 / 下駄あり 0.0000 と、はっきり出る。

「何を測れば違いが出るか」を先に決めるのが、この種の確認では半分を占める。

3. 確認用の点をカメラの後ろに置いていた

自己チェックで「開けた床」の点を (4.5, -0.5, 3.5) に取ったところ、焼いた距離が -0.239(負)になった。カメラの後ろだった。

透視除算は w が負でも計算できてしまうので、符号が反転した座標が返り、画面の反対側の画素を読む。エラーにならず、それらしい数字が返るのがたちが悪い。

WorldToPixel に「カメラの前にあるか」の確認を入れる手もあるが、自己チェックが「焼いた距離が CPU の計算と一致」を見ているので、そこで必ず落ちる——チェックが1つあれば、点の取り違えもまとめて捕まる。

4. スプライトの群れが 3D の上に乗ったままだった(Day 34〜36 の不備)

Ctrl+F9 の構図を確認しようとしたら、1000 枚のスプライトが全面を覆っていた。

調べると、OnRender は「モデル表示中」と「ゲーム中」しかスプライトを飛ばしていなかった。材質グリッド(Ctrl+Shift+5)と材質テストの板(Alt+5)を選ぶ分岐はRender3D() の中にあって、OnRender からは見えていない——だから両方とも「ふつうのデモ」の枝に落ち、スプライトの群れとロードの帯が上に重なる。

Day 34〜36 の計画書の「1フレームの流れ」は、正しいほうの絵を描いていた (RG --> TX と RS2 --> TX でスプライトを飛ばしている)。図を実装から起こさずに意図から描くと、コードより先に図が嘘になる——Day 36 の設計書で Core ⇔ Render について書いたのと同じことが、ここでも起きていた。
