理論の要点

1. ジャギーは「1画素につき1回しか色を決めていない」ことの帰結

Day 14 から使っているラスタライザは、三角形の中に画素の中心が入っているかで塗るかどうかを決めている。縁が画素の途中を通っても、その画素は 0 か 1 に倒れる。

  本当の縁         画素で決めた結果
  ┌─────────       ┌─────────
  │ ／             │███
  │／              │███
  ／               │██
 ／│               │█

正しい答えは「その画素の面積のうち何割が三角形に入っているか」で、これを被覆率と呼ぶ。被覆率が出せれば階段は消える——斜めの縁に沿って、0 と 1 の間の値がなだらかに並ぶからだ。

アンチエイリアスの手法は、結局のところこの被覆率をどう手に入れるかの違いになる。

手法被覆率の出し方代償
SSAA4倍の解像度で描いて縮める全部が4倍(描画も帯域もメモリも)
MSAA深度と被覆だけ4点で取り、色は1回バッファが4倍。後処理と噛み合わない(要点2)
FXAA出来上がった絵から推測するフルスクリーン1パス。細い線が滲む
TAA前のフレームからもらう(Day 54)動くものに残像。実装が重い

今日入れるのは3行目。被覆率を測るのではなく、「階段になっているところを見つけて、それらしい中間値を置く」という割り切りで、情報が増えるわけではないぶん、限界も最初から決まっている。

2. MSAA が後処理と噛み合わない

MSAA は「深度と被覆は4点、色の計算は1回」という賢い節約で、前方レンダリング(Day 37 までの形)なら品質もコストも申し分ない。ではなぜ現代のゲームで主流でなくなったのか。

理由は3つあり、どれも Day 31 以降に自分で作ったものが原因になっている。

  1. HDR バッファが4倍になる。1920x1080 の RGBA16F は 15.8MB で、4x MSAA なら 63MB。ブルームの入力を作るには「解決(resolve)」も要る
  2. 解決の順番が難しい。トーンマップの前に平均すると、明るい画素1点が全体を白く引きずる(Day 31 で見た「畳む前と後」の話)
  3. ディファードだと G バッファまで4倍になる(Day 52)。位置・法線・材質を全部4標本ずつ持つのは、帯域として現実的でない

FXAA はこれを全部避ける。入力は最終画像1枚だけなので、パイプラインのどこにも触らずに後ろへ足せる。2009 年に出てから 10 年以上、事実上の標準として使われ続けた理由がここにある。

おまけとして、ポリゴンの縁以外にも効く。MSAA は「三角形の縁」でしか標本を増やさないので、テクスチャの模様や高輝度部の縁(今日のデモなら市松の床)はまったく直らない。FXAA は絵しか見ていないので、そこも同じように均す。

3. FXAA が見ているのは輝度。それもガンマを掛けたあとの値

fxaa.frag が最初にやるのは、中心と斜め4点の輝度を取ることだけ。

glsl
float Luma(vec3 color) { return dot(color, vec3(0.299, 0.587, 0.114)); }

色ではなく輝度で判断してよいのは、人の目が明るさの差に敏感で色の差に鈍いから。3成分を別々に見ても判定はほとんど変わらないのに、計算は3倍になる。

ここで大事なのはどの空間の値に掛けるか。

  • 係数 (0.299, 0.587, 0.114) は NTSC 由来で、ガンマ後の値に掛けるもの
  • 係数 (0.2126, 0.7152, 0.0722) は Rec.709 の輝度で、リニアな明るさに掛けるもの

今日は両方が1つのファイルの中に出てくる——composite.frag の彩度計算は後者、fxaa.frag は前者。同じ「輝度」でも係数が違うのはそのためで、取り違えると暗部の重みがずれる(絵は出るので、なかなか気づけない)。

そして FXAA がガンマ後の絵を入力に取るのも同じ理由。リニアな明るさで段差を測ると、暗部の差が小さく出すぎて縁を見逃す。人の目は暗部の差にこそ敏感なので、その感覚に近いのはガンマ後の値のほうになる。

だから FXAA はパイプラインのいちばん後ろにしか置けない。今日 PostProcess の出口が2段になった(合成 → LDR バッファ → FXAA → 画面)のは、この制約がそのまま形になったもの。

4. 混ぜるのは「縁をまたぐ方向」ではなく「縁に沿う方向」

FXAA でいちばん誤解されやすいのがここ。

glsl
dir.x = -((lumaNW + lumaNE) - (lumaSW + lumaSE));  // 上下の差 → x へ
dir.y =  ((lumaNW + lumaSW) - (lumaNE + lumaSE));  // 左右の差 → y へ

上下の差が大きい(=横に走る縁)とき、dir は横を向く。つまり dir は縁に沿った方向で、そちらへ数テクセル進んだ色を混ぜる。

縁をまたいで混ぜたら、それはただのぼかしで、輪郭が甘くなるだけで階段は消えない。縁に沿って混ぜると何が起きるか——階段の1段先の色が入ってくる。

  混ぜる前              混ぜたあと
  ████░░░░              ████▓▒░░
  ░░░░████  ← 段差      ░░▒▓████

段差の角に中間色が置かれ、被覆率のプロファイルが直線に近づく。これが今日の自己チェックで測っているものそのもので、「列ごとの白の量が、理想の直線からどれだけずれているか」が0.50 画素から 0.30 画素へ下がる(実測)。

dir の長さも意味がある。小さいほうの成分で正規化してあるので、縁の傾きがそのまま歩幅になる——45 度なら両成分が 1 テクセル、ほとんど水平な縁なら横成分だけが uSpanMax まで伸びる。傾きが緩い縁ほど階段の段が長いので、遠くまで取りに行く必要がある、という理屈。

5. FXAA が苦手なもの。だから UI を外に出す

情報を増やしていないので、本当は縁でないものまで縁に見えると滲む。

  • 1画素幅の線。両側に段差があるので必ず縁と判定され、両方向から混ざる
  • 文字。1画素幅の線の塊なので、いちばん犠牲になる
  • 時間方向のちらつき。前のフレームを知らないので、カメラが少し動くたびに「縁と判定されるか」が画素ごとに入れ替わる

1つ目と2つ目への対処は簡単で、FXAA を通さないところに描けばよい。今日 UI を後処理の外へ出したのはこれが決め手になっている(露出やトーンマップから外れるのは、そのついでに直った副作用のほう)。

Shift+F5 で Day 37 までの置き方に戻せる。露出(Shift+5)を上げるとHUD の文字が白飛びし、Shift+F7 を4回押してモノクロにすると文字まで灰色になる。

3つ目は原理的に直せない。時間方向の情報を持ち込むのが唯一の解で、それが TAA(Day 54)になる。

6. グレーディングはトーンマップの前。空間と順番が全部

composite.frag の中身は、今日で5段になった。

  1. 露出          何を 1.0 とみなすか
  2. ブルーム合成   滲みを足す
  3. グレーディング  ← 今日ここに入った
  4. トーンマップ   0〜∞ を 0〜1 へ畳む
  5. ガンマ        表示のための符号化

3 が 4 の前でなければならない。トーンマップは「フィルムの特性曲線」に当たるものなので、味付けはフィルムに写す前——まだ物理的な明るさである側——で行う。

後ろに置くとどうなるか。すでに 0〜1 に畳まれた絵のコントラストを上げれば、上は 1.0 に張り付き、下は 0 に潰れる。階調を作る前に階調を捨てることになる。前に置けば、コントラストで持ち上がったぶんもトーンマップが畳んでくれる。

グレーディング自身の中の順番も決まっている。

  ホワイトバランス → 色フィルタ → コントラスト → 彩度
  ←── 撮影条件の補正 ──→   ←── 表現としての味付け ──→

前半は「撮ったときの光の色を打ち消す」補正、後半は「どう見せたいか」。実際の現像もこの順で、順番を入れ替えると補正のつもりの操作が味付けに引きずられる。

7. ホワイトバランスは RGB ではなく LMS で掛ける

色温度のつまみを「暖色寄りにしたいから赤を 1.1 倍、青を 0.9 倍」と実装すると、肌色が緑や紫に転ぶ。RGB の3軸は人の目の3種類の錐体と一致していないので、軸ごとに定数を掛けると色相が引きずられる。

人の目が「白いものを白く見続ける」仕組み(色順応)は、3種類の錐体それぞれの感度が独立に変わることで起きている——これがフォン・クリースの順応則(1902)。錐体の応答を並べた空間が LMS(Long / Medium / Short 波長)で、そこで各成分に定数を掛けるのが、いちばん人の見え方に近い白の付け替えになる。

やることは3段。

  1. つまみから目標の白点の色度 (x, y) を作る。色温度を変えるとは「何 K の黒体が出す光を白とみなすか」を変えることで、その白点は CIE xy 平面上の1本の曲線(プランク軌跡)に載っている
  2. その色度を LMS へ変換する(xyY → XYZ → LMS)
  3. 基準の白との比を取る。これが各成分の増幅率

ColorGrade.ComputeWhiteBalance がここを担当する。1フレームに1回で済む定数なので CPU に置き、シェーダは受け取った vec3 を掛けるだけ(composite.frag の WhiteBalance)。

なお、コントラストのほうも同じく空間の選択が効いている。リニアのまま (x - 0.18) * c + 0.18 と書くと暗部が負になり、露出(掛け算)との合成もおかしくなる。対数の上で傾きを変えると、露出が平行移動、コントラストが傾きの変更になって素直に噛み合う——人の明るさの感覚もほぼ対数なので、見た目にも自然になる。

中心を 18% グレーに置くのは写真からの流用。0.5 を中心にすると、コントラストを上げただけで全体が暗く沈む。

出口が2段になった

Day 37 まで、画面(既定のフレームバッファ)へ書くのは Composite の1箇所だけだった。今日 FXAA が後ろに付いたので、こうなる。

  FXAA ON   … Composite → [_ldr] → ApplyFxaa → 画面
  FXAA OFF  … Composite ────────────────────→ 画面

素通しのコピーを1パス挟んで経路を1本にする書き方もできる(コードは短くなる)。そうしなかったのは、1920x1080 の読み書きが丸ごと1回増えるため。後処理では「パスを1つ増やす/減らす」が、そのまま帯域の話になる。

代わりに End を EndCore(Framebuffer? target, int w, int h) に割り、行き先を引数にした。null なら画面。これで

  • End(w, h) … 本番。画面へ
  • EndToTarget(fb) … 自己チェック。読み戻せるバッファへ

の2つが同じ経路を通る。確かめる側が本番と違う道を通ったら意味が無いので、分岐を増やさずに口だけ2つにしてある。

改造課題

課題1(易): グレーディングの下敷きを1つ足す

GradePreset に自分の1つを足して、ApplyPreset の switch に数字を書く。

作ってみると分かるが、「なんとなく良い」は再現できない。つまみを回しているうちに元がどこだったか分からなくなるので、Shift+F6 で ON/OFF するか、Shift+F11 で左右比較しながら決めること。

余裕があれば Filter(色フィルタ)と Temperature(ホワイトバランス)で同じ方向に振ったときの違いを見比べてみるとよい。色フィルタは白いものにも色が付き、ホワイトバランスは白を白のまま動かす。

課題2(中): 色温度を RGB の掛け算で実装して見比べる

composite.frag の WhiteBalance を、LMS を経由せずに

glsl
vec3 WhiteBalance(vec3 color) { return color * uWhiteBalance; }

と書き換えてみる(CPU 側はそのまま使える)。

Shift+F10 で色温度を ±40 まで振ると、違いが出る。特に見てほしいのは中間の明るさの色がどちらへ転ぶかで、市松の床の緑や、モデル(Shift+0)の肌色に近い部分が分かりやすい。

「見た目そんなに変わらない」と思ったら、それも正しい観察。±40 程度なら差は小さく、大きく振ったときに効いてくる——つまり LMS を使う値打ちは「壊れにくさ」であって「見栄え」ではない。どこまでやるかを自分で決めるための課題で、ColorGrade.CieXyToLms のコメントを読み直す口実でもある。

課題3(難): 縁の形を見てから重みを決める(SMAA の入口)

FXAA は「縁を見つけたら、その向きへ数テクセル混ぜる」だけで、縁がどんな形をしているかは見ていない。だから 45 度の縁も、ほとんど水平な縁も、同じ手続きで処理してしまう。

SMAA(事前に読む資料の最後)はここを変える。

  1. 縁を検出する(ここまでは FXAA と同じ)
  2. 縁に沿って両端まで歩き、どこで途切れるかを調べる
  3. その形(L 字 / Z 字 / U 字 …)から、正しい被覆率を計算で出す

3 が決定的な違いで、推測ではなく幾何から答えを出している。

最小の一歩として、fxaa.frag に「縁に沿って左右へ最大 N テクセル歩き、輝度が変わるところまでの距離を測る」ループを足してみるとよい。測った2つの距離から台形の面積として被覆率を出せば、同じ1パスのまま品質が上がる——FXAA 3.11 の後半(今日削ぎ落とした部分)がやっているのもだいたいこれになる。

Ctrl+F12 の「縁が理想の直線に近づく」の数字が0.302 からどこまで下がるかで、値打ちを測れる。

RTX 3070 で 0.03ms 弱。1920x1080 なら画素数が 3.4 倍なので 0.1ms 弱の見当になる。フレーム予算(60fps で 16.7ms)の 1% 未満。

HUD に出ている影パスの 0.08ms や SSAO の 0.07ms と並べて比べてはいけない。あちらは Stopwatch で測ったCPU が命令を積むのにかかった時間で、GPU が実際に走った時間ではない(glFinish を挟んでいない)。同じ土俵で測りたいなら、あちらにも glFinish を入れる必要がある——計測の作法が揃っていない数字を並べない、というのはDay 26 のブロードフェーズの計測でも一度ぶつかった話。

FXAA が 10 年以上使われ続けた理由がこの数字に出ている——ほとんど只で、どんな絵にも効く。代わりに払っているのは VRAM 2.3MB(1920x1080 なら 8.3MB)と、細い線の滲み。

検証の途中で分かったこと

「ジャギーが減った」をどう測るかで、結論がひっくり返った。

最初は全変動(隣り合う画素の差の絶対値の和)で測ろうとして、これは駄目だとすぐ分かった。段差をなだらかな傾斜に均しても、全変動は変わらない(単調な変化の全変動は端の差だけで決まる)。

次に2階差分の絶対値の和にした。直線なら 0 になるので筋はよさそうに見えたが、実測すると 92.0 → 97.5 と増えた。FXAA が縁の周りに作る細かい起伏を拾ってしまい、「まっすぐになった」ことより「局所的にでこぼこした」ことのほうが大きく出る。

最終的に最小二乗で直線を当てはめ、そこからの平均のずれにしたら0.499 → 0.302 と素直に下がった。同じデータで、同じ現象で、測り方を変えただけで OK と NG がひっくり返る——性能や品質を数字で語るときにいちばん怖いのがこれ。

しきい値のチェックが最初 NG になった。「相対しきい値を 1.0 にすれば何も縁にならないはず」と思って書いたら、最大差 0.333 が出た。理由は単純で、テスト画像が黒と白なので局所コントラストがちょうど 1.0 になり、range >= 1.0 を満たしてしまう。2.0 にしたら通った。「最大値ちょうど」は境界条件という、浮動小数点以前の初歩的な取りこぼし。

glClear はシザー矩形の中しか塗らないという性質が、確かめ用の絵を描くのに具合がよかった。シェーダも頂点バッファも要らず、glScissor を 24 回動かすだけで「傾き 1/4 の直線をラスタライズした階段」が手に入る。シザーテストを切り忘れると、そのあとのフルスクリーンパスが最後の短冊の中だけに描かれて画面がほぼ真っ黒になるので、そこだけ注意。
