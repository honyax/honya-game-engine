理論の要点

1. RGBE — 3色で1つの指数を共有する

.hdr の1画素は 4 バイト。(R, G, B, E) で、実際の色は

  色 = (R, G, B) x 2^(E - 128 - 8)

E は3色で共有する指数。128 は下駄(指数を符号なしバイトで持つため)、8 は「仮数を 0〜255 の整数で持っているぶんを 0〜1 に戻す」ぶん。E = 0 だけは特別扱いで真っ黒を表す。

これで 1 画素 4 バイトのまま 10 の何十乗という幅が入る。float を3つ並べる(12 バイト)より 3 倍小さく、8bit PNG より桁違いに広い。

弱点も一緒に見ておく。指数が共有なので、3色のうち一番大きい成分の精度で他の2色も決まる。夕焼けのように R が B より2桁大きい絵では、B の下位ビットがごっそり落ちる。OpenEXR(半精度 float x 3)がプロの現場で使われるのはこのため。

今日 .hdr を選んだのは、自分で読み切れる大きさだからでしかない。仕様全体でも 200 行で書ける。

2. 走査線は成分ごとに固めてから RLE を掛ける

.hdr の本体は、1本の走査線ごとに

  02 02 (幅の上位) (幅の下位)   ← 新形式の目印
  R の 1 行ぶん(RLE)
  G の 1 行ぶん(RLE)
  B の 1 行ぶん(RLE)
  E の 1 行ぶん(RLE)

という並びになっている。RLE は 1 バイトで、128 より大きければ「次の1バイトを (count - 128) 回」、128 以下なら「そのまま count バイト」。

なぜ成分ごとに固めるのかが読みどころ。RGBE を画素順に並べると隣の画素と R・G・B・E が交互に来るので、同じ値が続きにくい。成分ごとに分けると、たとえば E(指数)は空の広い面積でほぼ同じ値になり、ランが一気に長くなる。これだけで .hdr は 2〜3 倍縮む。

「圧縮する前にデータを並べ替える」——同じ発想がPNG のフィルタにも、頂点属性のインターリーブ解除にも出てくる。

3. 正距円筒の1画素が張る立体角には sinθ が要る

横 W・縦 H の正距円筒で、(x, y) の画素が張る立体角は

  dω = (2π/W) x (π/H) x sinθ        θ = (y + 0.5) / H x π

sinθ が肝。極(天頂・真下)に近い行ほど画素は横に引き伸ばされていて、実際に占める立体角は小さい。地球儀の緯線が極で短くなるのと同じ。

これを掛け忘れると、全部足したときに 4π(= 12.566)ではなく2π²(= 19.74)になる。つまり 合計が 4π になるかどうかで検算できる。

  Σ dω = 4π                     ← 掛け忘れると 19.74、7.2 もずれる

今日の自己チェックがまずこれを見ている。掛け忘れても絵はそれらしく出る——太陽の向きも空の色も一応それらしくなり、放射照度だけが静かに 2〜3 割ずれる。数字でしか見つけられない類の間違い。

なお、float で 200 万回足すと 2e-4 ずれる。1回ぶんの立体角(1e-5 程度)を 12 まで育った合計に足すので、下位ビットが毎回こぼれる。倍精度で足せば消える。残るのは中点則の打ち切り誤差 (π/H)²/24 x 4π = 4.9e-6 だけで、実測もぴったりそこに乗る。

4. 太陽は「絵から測る」— しきい値ひとつでよいが、破綻もする

やることは3行で書ける。

  1. いちばん明るい画素の輝度を求める(ピーク)
  2. ピークの 5% を超える画素を「太陽」とする
  3. その画素たちについて、向きは輝度で重み付けした平均、強さは放射照度 E = Σ L dω

3 で出てくる E が、そのまま平行光源の色になる。「太陽のほうを向いた面が受け取る光の量」なので、単位が合っている。

spruit_sunrise で実際に測るとこうなる。

量値
ピーク輝度245026
太陽と判定した画素9 個(2048x1024 のうち)
立体角0.000084 sr
見かけの半径0.30 度(本物の太陽は 0.27 度)

見かけの半径が本物とほぼ一致するのが気持ちよいところで、この1つの数字で「取り出せたかどうか」が判定できる。

そして破綻もする。露出段数の足りない HDRI (撮影時に太陽が飽和しているもの)だと、太陽の芯も空も同じくらいの値になっていて、しきい値をどこに置いても空の半分が「太陽」になる。

5. 二重計上 — IBL の中にも太陽が入っている

平行光源を足すと絵が明るくなるが、環境マップの中にも同じ太陽が居る。何もしないと 2 回数えることになる。

いちばん分かりやすい症状は影の中が明るくなりすぎること。影とは「平行光源が届かない場所」なのに、IBL の中の太陽は遮蔽を知らないので届いてしまう。

対処は「環境マップを焼く前に、太陽の画素を近所の色で埋める」。埋め草にはすぐ外側の輪の平均を使う。空の平均で埋めると、太陽のまわりが明るい絵ではそこだけ暗い染みになって穴が開く。

抜く基準は抽出したときと同じにするのが要点。「明るさで選んだものを、明るさで抜く」ので、平行光源に足したぶんと環境マップから消したぶんが必ず一致する。自己チェックがこれを数字で確かめている。

  抜く前の全天  (20.67, 15.45, 7.28)
  太陽ぶん      (16.72, 11.41, 3.36)
  抜いた後      ( 3.96,  4.05, 3.92)   ← 引き算とぴったり合う

今日の実装の限界も書いておく。抜けるのは芯だけで、しきい値のすぐ下のにじみ(グレア)は残る。太陽の芯の 5% でも空の 3 万倍あるので、粗い金属にはうっすら太陽が映り続ける。まじめにやるなら、抜いた太陽を面光源として別に持ち、鏡面では解析的に評価する(Karis 2013 の representative point)。改造課題3。

6. 空を回す — HDRI の太陽の方位はシーンの都合と無関係

HDRI の太陽は「その写真を撮った場所での方位」に居る。spruit_sunrise なら方位 35.8 度。組んだシーンで日を当てたい向きとは、当然なんの関係も無い。

対処は2つあって、

  1. シーンのほうを回す … 太陽の方位が HDRI ごとに違うので、差し替えるたびにやり直し
  2. 空のほうを回す … HDRI ごとに1つの角度で済む

2 を採る。しかも「何度回すか」ではなく「太陽にこの方位へ来てほしい」と書けるようにしておくと、

  空の回転 = 測った方位 - 来てほしい方位

の1行で済み、HDRI を差し替えても太陽の位置が動かない。Ctrl+Shift+F3 で3枚を回したときに向きが固定されるので、光の質だけを見比べられる。

実装は焼き込みパス(equirect.frag)で方向を回すだけ。そこで作ったキューブを放射照度も事前フィルタもスカイボックスも見るので、1か所直せば全部が付いてくる。

7. 太陽の仰角が、シーンの形を決める

これは理論というより、今日実際にぶつかった話。

最初は「両側に壁のある路地」を組んだ。ところが spruit_sunrise の太陽は仰角が 8 度しかない。高さ 5.5m の壁が落とす影は

  5.5 / tan(8度) = 39m

進む。路地の幅が 7m なら、床には一片の日も当たらない。両側に壁を立てられるのは、太陽の仰角がatan(壁の高さ / 路地の幅) を超えているときだけ——幅と同じ高さの壁なら 45 度、つまり真昼しか成立しない。

なので片側を開けた。壁は左と突き当りだけで、右は空。「夕方のシーンは壁を減らす」は絵作りの定石だが、太陽の仰角を測ってから決められるのが今日のやり方の値打ちで、勘で置いて暗い絵を作ってから悩む、を1周省ける。

同じ理由でシャドウマップの範囲も広げた。既定の半径 6m のままだと遠くの影が箱から出て途中で切れる——Day 33 で「実際のエンジンは箱を何段も作る」と書いたカスケードが要る理由が、そのまま絵に出る(shadowRadius を 6 に戻すと再現できる)。

Demo/ を新しい層にした理由

DemoScene を Scene/ に入れる案もあった。名前もそちらのほうが素直に見える。入れなかった理由は2つ。

1つ目。Scene/ は毎フレーム更新されるものの入れ物で、GameObject と Component と FixedUpdate が前提にある(Day 22〜24)。デモの背景は静止しているので、要るのは「メッシュ・マテリアル・行列」の平らな並びだけ。Model が glTF のノードの木を平らにしたのとまったく同じ理屈で、動かないものに階層は要らない。

2つ目。デモはエンジンではない。Game/(卒業制作)と同じ、エンジンを使う側の層に置きたかった。実際 DemoScene が知っているのは Render/ と Model/ と Core/ だけで、Scene/ も Ecs/ も Physics/ も知らない。

  Game/ … エンジンで作ったゲーム        (Day 29〜30)
  Demo/ … エンジンで作った見せもの      (今日)

キャラクターが歩き回る Day 51 では、動くものだけが Scene/ に載る。背景は今日の形のままでよい。

HdrImage と SkyAnalysis は GL を1回も呼ばない

Render/ に置いてあるが、この2つは Silk.NET.OpenGL を using していない。入力は float[]、出力も float[] か構造体だけ。

これは SkyImage(Day 36)と SurfaceMaps(Day 34)と同じ性格で、「絵を作る/読む CPU 側の道具」という一群になっている。

クラス入口出口GL
SurfaceMapsパラメータbyte[] x3呼ばない
SkyImage太陽の向きfloat[]呼ばない
HdrImageファイルのパスfloat[]呼ばない
SkyAnalysisfloat[]Sun / float[]呼ばない

GL を呼ばないことの配当がはっきり出るのが自己チェックで、RunSceneCheck の前半は窓もコンテキストも要らずに走る。「立体角の合計が 4π か」「RGBE の格子に乗っているか」は描かなくても確かめられる種類の問いなので、そこを分けておくと検算が軽くなる。

空の出どころが2つになった

Day 36 の EnvironmentMap.Bake は「太陽の向きを渡すと空を焼いてくれる」形だった。今日から HDRI も入るので、こう割れた。

  Bake(sunDirection, w, h)
      └→ SkyImage.Create で作る ──┐
                                  ├→ BakeFromPixels(pixels, w, h, screen, label)
  HdrImage.Load(path)  ───────────┘        └→ キューブ → ミップ → 放射照度 → 事前フィルタ

2 段目から先はまったく同じ道を通る。Day 36 の設計書に「Day 39 で本物の HDRI を差し込むときはこの層を差し替えるだけで済む」と書いた読みが、そのとおりに効いた形。

ついでに SkyImage.Create から clampToLdr の引数を外した。1.0 で頭打ちにする処理(Ctrl+Alt+6)は BakeFromPixels へ移してある——出どころが2つになったので、どちらから来た画像でも同じ場所で切るほうが辻褄が合う。

影を落とすかどうかが、データになった

Day 33 の RenderShadowPass にはこう書いてあった。

実際のエンジンはこれをマテリアルかコンポーネントのフラグ(CastShadow)で持つ。ここで手書きの分岐にしてあるのは、まず「選ぶ必要がある」ことを見るためで、フラグにするのはシーン側に影を載せる Day 39 の仕事になる。

その宿題が片付いた。DemoScene.Item が CastShadow を持ち、深度パスはそれを見るだけになる。

効き目は「分岐が消えた」ことより、3つのパスが同じ並びを回るようになったことのほうが大きい。

パス何を回すか選び方
深度(影)ItemsCastShadow が true のものだけ
幾何(SSAO)Items全部。そこにある物は必ず周りを遮る
本描画Items全部

SSAO に選択の余地が無いのが対比として面白いところで、影は「落とす側/受ける側」を選べるが、環境遮蔽は選べない。地面を外すと壁との入隅に暗がりが出なくなる。

Demo — エンジンを使う側の、もう1つの層

Item が平らな並びであることが、このクラスの全部と言ってよい。JSON には「マテリアルの一覧」「板の一覧」「glTF の一覧」という3種類の入れ物があるが、読み終わった時点でそれは1本のリストに潰れる。

  materials[]  ─┐
  surfaces[]   ─┼→  Items[]  ──→ 深度パス / 幾何パス / 本描画
  props[]      ─┘

誰が何を持っているかが、このクラスでいちばん気を使ったところ。

もの持ち主理由
板のメッシュProgram(借りている)Primitives.CreateQuad の1枚を全員で使い回す
板のマテリアルDemoSceneJSON にしか書いていないので、他に持ち主がいない
板のテクスチャRenderResources(参照カウントを借りる)Day 21 の作法。Dispose で同じ数だけ返す

板のメッシュだけ借りているのが例外に見えるが、これは Primitives.CreateQuad が返す 4 頂点の板を地面にも壁にも使い回しているため。行列と uvScale が違うだけで、頂点は全部同じ——1枚あれば足りるものを人数分作らない。

Load が Func<string, string> resolveAsset を受け取るのは、assets/ をどこから探すかの規則をこのクラスに持ち込まないため。Program.ResolveAssetPath は「実行ファイルの場所から親へ辿る」というこのリポジトリ固有の作法なので、Demo/ が知る必要は無い。

シーンが1つ組み上がるまで — JSON からドローコールの並びへ

足元合わせを回転より後に置くのが今日の学び。先に合わせてから回すと、タイヤを寝かせた瞬間に半分が床へ沈む——「合わせた足元」は回転で別の場所へ行ってしまうから。

  ✗  足元合わせ → 拡大 → 回転 → 平行移動     … 回すと沈む
  ○  拡大 → 回転 → 足元合わせ → 平行移動     … どんな向きでも床に乗る

回したあとの箱を取るには 8 隅を全部変換する。中心と大きさだけを回しても正しい箱にならない(斜めに回した AABB は元より必ず大きくなる)。

配当は JSON 側に出る。rotation: [90, 0, 20] と書くだけでタイヤが寝て床に乗り、y を手で調整する行が1つも要らない。自己チェックの「床より下に沈んでいるものが無い」がこれを見張っている。

HDRI から太陽が出るまで — 絵を測って光にする5段

Program.BakeSky と ApplyDemoLighting の中身。絵の中の太陽と、影を落とす平行光源を一致させるのが目的。

/ π が入っているのが引っかかりどころ。Render3D は PBR のとき_lightColor を π 倍して送っている——あれは「Day 34 までのランバートと明るさを揃える」ための辻褄合わせ(Day 35 の要点)で、物理としては放射照度をそのまま入れるのが正しい。抽出値をそのまま渡すと π 倍されて 3 倍明るくなるので、先に割ってある。

測るのは回す前の画像、回すのは焼くときと平行光源の向き、という分け方をひとことで言うとこうなる。

段座標系
Analyze / RemoveSunHDRI の座標(撮影時の方位)
equirect.frag / _sunWorldDirectionシーンの座標(回したあと)

_skyYaw を境に世界が切り替わる、と覚えておくと迷わない。片方だけ回すのがいちばんありがちな壊れ方で、空を回して光を回し忘れると「太陽が写っている方向と影の向きが違う」、逆にすると「空だけ元の方位のまま」になる。自己チェックの最後の項目がこれを見張っている。

実測(spruit_sunrise_2k)。

  太陽: 仰角 8.0度 / 方位 35.8度  放射照度 (16.72, 11.41, 3.36)  全体の 75%
  空の回転 10.8度 → シーンでの方位 25.0度
  見かけの半径 0.30度(9 画素 / 立体角 0.000084sr)  ピーク輝度 245026
  立体角の合計 12.5664(4π = 12.5664)  ※ 65504 を超える画素が 9 個(RGB16F で頭打ち)

最後の1行が地味に効く。太陽の芯は半精度 float の上限を超えるので、RGB16F へ上げた時点で 65504 に頭打ちになる。今日はその太陽を環境マップから抜いているので実害が無いが、Ctrl+Shift+F5 で抜くのをやめると、IBL に入る太陽は本来の 4 分の 1 の明るさになっている。「抜かないと二重計上」「抜かないと頭打ち」の両方が同じ方向を向いているのは、たまたまではなく太陽が桁違いに明るいことの帰結。

改造課題

課題1(易): 小物を1つ足して、影の付き方を確かめる

assets/scenes/demo-v1.json の props に1つ足すだけ。assets/models/ にある DamagedHelmet.glb を置いてみるのがよい。

json
    {
      "name": "ヘルメット",
      "model": "models/DamagedHelmet.glb",
      "position": [0.6, 0.0, 2.0],
      "rotation": [0.0, -30.0, 0.0],
      "scale": 1.0
    }

見どころ:

  • align が効いて床に乗るか。DamagedHelmet は原点が中心にあるモデルなので、足元合わせが無ければ半分埋まる。"align": false を足すと沈むのが確かめられる
  • ヘルメットの金属部分に夕焼けの空が映るか(Day 36 の IBL)
  • 発光する部分(emissive)がブルームで滲むか(Day 31)

発展: "rotation": [90, 0, 0] にして横倒しにしても床に乗ることを確かめる。乗らなかったら、AlignToGround を回転より前に呼んでいる。

課題2(中): 太陽を「重心」ではなく「最大の連結成分」で取り出す

いまの SkyAnalysis.Analyze は「しきい値を超えた画素全部」を1つの太陽として扱っている。だから画面のどこかに別の強い光(街灯、窓の反射)があると、その中間に太陽があることになる。

連結成分ラベリング(4近傍でよい)を入れて、いちばん明るいかたまり1つだけを太陽とするように直す。

  • 走査は上下だけつなげばよい(正距円筒なので左右は端でつながる——ここが罠)
  • 出来上がったら、the_sky_is_on_fire で試す。それでも破綻するはずで、あちらは「太陽が1つのかたまりとして空の半分に広がっている」ので、連結成分では救えない
  • 救えないことが分かるのが、この課題の到達点。露出段数が足りない HDRI はそもそも太陽の情報を持っていない

発展: 破綻を検出したら(視半径が 3 度を超えたら)自動で SunScale を 0 にし、IBL だけで照らす形にフォールバックする。

課題3(難): 抜いた太陽を「面光源」として鏡面に戻す

いまは太陽を環境マップから抜いているので、粗い金属に太陽が映らなくなっている(完成条件5の裏返し)。プロの実装は、抜いた太陽を面光源(円板)として別に持ち、鏡面反射だけ解析的に評価する。

Karis 2013 の representative point がいちばん短い解法。

  1. 反射ベクトル R と太陽の中心方向 L から、円板の上で R にいちばん近い点 L' を求める
   centerToRay = dot(L, R) * R - L
   L' = normalize(L + centerToRay * clamp(sunRadius / length(centerToRay), 0, 1))
  1. その L' を光の向きとして、いつもの Cook-Torrance を評価する
  2. エネルギーの正規化を掛ける。点光源を円板に広げたぶん、ハイライトの面積が増えて明るくなりすぎるので
   alphaPrime = clamp(alpha + sunRadius / (2 * distance), 0, 1)
   normalization = (alpha / alphaPrime)^2

見どころは粗さによる差。粗さ 0.05 の金属では「点だったハイライトが太陽の見かけの大きさに広がる」だけだが、粗さ 0.4 を超えると normalization が無いと 2 倍以上明るくなる。

材質グリッド(Ctrl+Shift+5)を出しながら実装すると、7x7 の全部で同時に確かめられる。

検証の途中で分かったこと

1. 立体角の合計が float では合わなかった。

最初は積分を全部 float で足していた。すると 4π の検算が12.5637(正解 12.5664、相対 2e-4)で通らない。

原因は大きい数に小さい数を足し続けていること。1回ぶんの立体角は 1e-5 程度で、合計は 12 まで育つ。200 万回足すと下位ビットが毎回こぼれる。倍精度にしたら 12.56637554 になり、残った差 4.93e-6 は中点則の打ち切り誤差 (π/H)²/24 x 4π とぴったり一致した。

数値積分の誤差が計算どおりに出ると、「実装が正しくて、あとは離散化の限界だけ」と言い切れる。自己チェックのしきい値も、勘ではなくこの式から 1e-5 と決めてある。

2. 「太陽を抜いたら空の平均が変わらない」は成り立たなかった。

最初の自己チェックには「空の平均は動かない」という項目を入れていたが、落ちた(0.314 → 0.272)。

理由は判定が動くから。太陽を抜くとピーク輝度が 245026 → 10807 に落ちるので、ピーク x 0.05 のしきい値も 1/23 になる。すると今まで「空」だった画素の多くが「太陽」に分類され、空の平均から抜けてしまう。比べているものが同じではなかった。

比べるべきは分類に依存しない量、つまり全天の放射照度。「抜いた後 = 抜く前 - 太陽ぶん」なら、平行光源に足した量と環境マップから引いた量が釣り合っている、と言える。これに直したら 0.1% 以内で合った。

チェック項目そのものが間違っていることがある、という当たり前のことを、2回目のチェックが落ちるまで疑わなかった。

3. 両側に壁のある路地は成立しなかった。

最初のシーンは「両側 5.5m の壁の路地」だった。組んで動かしたら床が真っ暗。

太陽の仰角が 8 度しかないので、5.5m の壁は 39m 先まで影を落とす。路地の幅が 7m なら、床は全面が影。壁の高さを 1.7m の塀に落としても 12m 進むので、やはり届かない。

両側に壁を立てられるのは仰角が atan(高さ / 幅) を超えるときだけ——幅と同じ高さの壁なら 45 度、つまり真昼しか成立しない。夕方のシーンで壁を減らすのは絵作りの定石だが、理由が「仰角と幅の比」だと分かって置くのと、勘で置いて暗い絵から悩むのとでは、次に応用が効くかどうかが違う。

4. 低い塀は真っ黒に写った。

上の対処として右側に 1.7m の塀を置いたが、その内側の面(法線が -X)は太陽と反対を向いているので直接光がゼロ。IBL だけで照らされ、直接光が当たっている隣の壁との差が 500 倍になり、トーンマップを通してもほぼ黒に潰れた。

これは実装の不具合ではなく物理どおりで、実際の夕方の路地も日陰の面はそう見える。ただし絵として読めないものを置いてもデモにならないので、塀は消してコンクリートのバリア2つで空間を区切る形に変えた。バリアは高さ 0.83m で上面が空を向いているぶん、IBL がよく効く。

5. スクリーンショットの名前が同じ秒でぶつかった。

連続で撮ったら1枚しか残らなかった。yyyyMMdd-HHmmss だけだと同じ秒に撮った2枚目が上書きされる。空いている番号を探す形に直した。撮ったつもりのものが消えているのはいちばん腹立たしい壊れ方なので、ここは横着しないほうがよい。

6. 太陽を抜かずに焼くと、画面が真っ黒になった。

Ctrl+Shift+F5 で太陽を抜くのをやめると、空の一部を残して画面がほぼ真っ黒になった。写経が終わったあとの確認で見つかったもの。

最初は「RGB16F へ上げると 65504 で頭打ちになる」と思い込んでいた。実際には半精度で表せる最大値を超えた値は、頭打ちにならず +Inf になる (IEEE 754 の丸めで、表せる最大値より大きいものは無限大へ行く)。太陽の芯は 24 万あるので、抜かずに上げると環境キューブに Inf が入る。それが放射照度と事前フィルタの畳み込みで周りへ広がり、トーンマップの x(ax+b) / (x(cx+d)+e) が Inf / Inf = NaN になって黒く出る。

BakeFromPixels で ClampSkyToLdr が OFF のときも 65504 で切ってから 上げるように直した。太陽を抜いているときは芯がもう残っていないので、この切り方は効かない。「GPU が勝手に頭打ちにしてくれる」は、整数のテクスチャ(UNORM)なら正しいが、float のテクスチャでは正しくない。
