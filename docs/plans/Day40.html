事前に読む資料

  • Cubic Hermite spline(Wikipedia)— Catmull–Rom spline の節 今日の本命その1。読むのは「Catmull–Rom spline」の節だけでよい。「両隣を見て接線を (p2-p0)/2 と決めた3次エルミート補間」という1行の定義から、制御点を必ず通ることとキーの上で速度が繋がることが両方出てくる
  • Kochanek–Bartels spline(Wikipedia) Catmull-Rom に tension / continuity / bias の3つのつまみを足したもの。アニメーションツールのカーブエディタはだいたいこれ。今日は書かないが、「接線の決め方だけを差し替えれば済む」ことが読み取れると、Catmull-Rom がどこまで一般化できるかの見当が付く
  • David Eberly, "Moving Along a Curve with Specified Speed" 改造課題2の下敷き。パラメータ u を等間隔に進めても曲線の上を等速には進まない、という今日いちばん引っかかる事実と、その直し方(弧長パラメータ化)。読むのは 1〜3 節
  • Ken Perlin, "Improving Noise" (SIGGRAPH 2002) smoothstep(3u²-2u³)の出どころと、その改良版(6u⁵-15u⁴+10u³)。2階微分まで 0 にすると何が良くなるのかが1ページで分かる。カメラの加速度が連続かどうかの話に直結する
  • John Nesky, "50 Game Camera Mistakes" (GDC 2014)カメラの「べからず集」。今日作るのは操作しないカメラなので直接は効かないが、画角と距離をどう決めるか、カットとパンをどう使い分けるかは今日の話
  • Unity Cinemachine のマニュアル実際のエンジンがカメラワークをどんなデータ構造で持っているかの実例。「Virtual Camera を並べて、Blend で繋ぐ」——今日書く CameraPath.Key と Travel がだいたいこれの最小版になっている

理論の要点

1. Catmull-Rom — 「両隣を見て接線を決める」だけの補間

キー p1 から p2 までを結ぶとき、その前後の p0 と p3 も覗いて

  p1 での接線 = (p2 - p0) / 2
  p2 での接線 = (p3 - p1) / 2

と決める。あとは「位置と接線が両端で指定された3次曲線」(エルミート補間)を解くだけで、展開すると実装のあの形になる。

  p(u) = 0.5 * ( 2p1
                 + (-p0 + p2) u
                 + (2p0 - 5p1 + 4p2 - p3) u²
                 + (-p0 + 3p1 - 3p2 + p3) u³ )

ここから性質が2つ出る。どちらもカメラワークで欲しかったものそのもの。

制御点を必ず通る。u=0 を入れると p1、u=1 を入れると p2 になる。ベジエ曲線は途中の制御点を通らないので、「ここを通ってほしい」と書いた構図が実際には映らない。JSON に書いた数字がそのまま画面になるのは、この性質のおかげ。

キーの上で速度が繋がる(C1 連続)。p1 を終点とする区間も、p1 を始点とする区間も、p1 での接線を同じ式 (p2-p0)/2 で決めている——だから通過する瞬間に速度が跳ばない。線形補間だとここが折れて、パンが「カクッ」と曲がる。

2. 補間方式とイージングは、別の軸

ここが今日いちばん取り違えやすいところ。

  補間方式    … キーとキーの間を、どんな形の線で結ぶか   → 軌跡が変わる
  イージング  … その線の上を、どんな速さで進むか         → 軌跡は変わらない

イージングは区間内の進み u(0〜1)を別の 0〜1 に付け替えるだけ。

  smoothstep(u) = 3u² - 2u³      u=0 と u=1 で微分が 0

微分が 0 ということはその瞬間だけ止まるということで、静止(hold)と滑らかに繋がる。イージングを切ると、止まっていたカメラがいきなり最高速で動き出し、その瞬間だけ切り貼りしたように見える。

u を付け替えても通る点の集合は1ミリも動かない。自己チェックの4番目がこれをそのまま確かめている——「イージング入りで時刻 t」と「イージング無しで、進みが smoothstep(u) になる時刻」は同じ点を指すはず、という形で。

Perlin の改良版(6u⁵-15u⁴+10u³)は2階微分まで 0 になる。加速度まで連続になるので、長いパンではこちらのほうが上品に見える。

3. 角度の補間には巻き取りが要る。ただし全部ではない

方位 350 度から 10 度へ動かしたい。数字をそのまま線形補間すると、

  350 → 340 → 330 → ... → 20 → 10      340 度ぶん、逆回り

正解は 20 度ぶん進むほう。直し方は、基準からの差を毎回 -180〜180 度に畳む。

  y2 = y1 + wrap(k2.Yaw - y1)        wrap は -π〜π へ畳む

こうすると y1 と y2 が「1本の数直線の上で近い2点」になり、そのあとは普通に補間すればよい。Catmull-Rom なら y0 と y3 も同じやり方で数直線に乗せてから渡す。

仰角は畳んではいけない、というのが対になる注意点。軌道カメラの仰角は ±86 度で止めてあって一周し得ないので、畳むと「89 度 → -89 度」を「近道は2度」と判断してカメラがひっくり返る。

  一周し得る角度(方位)      → 畳む
  一周し得ない角度(仰角)    → 畳まない

「角度だから畳む」ではなく、値域を見て決める。

4. カメラは「位置」ではなく「軌道のパラメータ」で持つ

キーが持つのは注視点・距離・方位・仰角・画角の5つで、カメラの位置そのものは持たない。位置は毎フレーム

  eye = target + d * ( cosθ sinφ,  sinθ,  cosθ cosφ )      θ=仰角, φ=方位

で作る(OrbitCameraController.EyePosition)。

手で数字を書くならこちらが圧倒的に楽、というのが選んだ理由。「もう少し引く」が distance の1か所で済み、注視点はぶれない。位置と注視点を直接持つ流儀(映像系のツールはたいていこちら)だと、引くたびに位置の3成分を計算し直すことになる。

代償もある。注視点から見て裏に回れない動きは書けない——たとえば「柱の後ろを通り抜けながら被写体を追う」は、軌道の言葉では表しにくい。キャラクターを追う Day 51 では位置ベースに寄せることになる。

5. 機能の表は、状態を持ってはいけない

ON/OFF の表が持っているのは bool ではなく、そこへの読み書きの手順(Func<bool> と Action<bool>)。

csharp
features.Add("SSAO", "接地の暗がりが消える",
    () => _ssao.Enabled,             // 読む手順
    on => _ssao.Enabled = on);       // 書く手順

値をコピーして持たせると必ずずれる。Ctrl+F1(Day 37 のキー)で直接 _ssao.Enabled を触られた瞬間に、表の言う ON と絵の中の OFF が食い違う。どちらが本当かを決める仕組みを足すと、今度はその同期がバグの温床になる。

状態の置き場所は1つ。Day 22 で Transform を GameObject に1つだけ置いたのと同じ判断で、今日はそれが「値ではなく手順を持つ」という形で出てくる。

6. デモの機能は、差分でしか見えない

SSAO を入れた絵を見せられても「そういうものか」としか思えない。同じ構図で切って戻すと、接地の暗がりが呼吸するように出入りするのが見える。

だから今日の道具は「一覧」ではなく「往復」で作ってある。

キー見せ方何が分かるか
Ctrl+Alt+F81つを切りっぱなしその機能だけをじっくり見る
Ctrl+Alt+F9全部 ⇔ 素8日ぶんの積み上げの総量
Ctrl+Alt+F101つずつ切っては戻す機能ごとの寄与を順に

Ctrl+Alt+F10 のツアーが「1つ切る → 全部戻す」を交互にやるのは、基準の絵を毎回挟むため。切りっぱなしで次へ進むと、2つ目からは「何と比べているのか」が分からなくなる。

7. 画角は「どのレンズで撮るか」であって、距離ではない

Camera.FieldOfView の既定は 60 度。これは操作するゲームの画角で、デモの絵には広すぎる。壁が倒れて見え、遠くのものが実際より遠くに見える。

  画角を狭く(望遠)  → 遠近が圧縮される。奥行きが平たくなる
  画角を広く(広角)  → 遠近が誇張される。近いものが大きく張り出す

距離を変えても同じことは起きないのが要点。距離は「どこから見るか」、画角は「どのレンズで撮るか」で、両方を動かすと「被写体の大きさは同じまま、背景の遠近だけが変わる」——ヒッチコックのめまいショット(ドリーズーム)がまさにこれ。

デモのショットは 35〜50 度に散らしてある。広い構図ほど広角、寄りほど望遠にしてあり、これは実際のレンズの使い分けと同じ。Ctrl+Alt+F3 で切り替えながら HUD の「画角」を見ると、数字と絵の印象が結び付く。

FeatureToggles が Render を知らない、ということ

このクラスの中には Ssao も PostProcess も ShadowMap も出てこない。出てくるのは Func<bool> と Action<bool> だけで、どの機能を並べるかを決めているのは Program.BuildFeatureToggles のほう。

  Program  ──「SSAO の読み方と書き方はこれです」──→  FeatureToggles
           ←──「いま ON です / 切ってください」──┘

この形にした配当は3つある。

1つ目。表が状態を持たない。本当の値は _ssao.Enabled のほうにあるので、Day 37 のキー(Ctrl+F1)で直接触られても食い違わない。

2つ目。Demo/ から Render/ への依存が増えない。DemoScene はすでに Render を知っているので実害は無いのだが、「機能を並べる知識」は Program の仕事——どの Day の何を見せたいかはデモの都合であって、表の都合ではない。

3つ目。bool でないつまみも bool に見せられる。PCF の半径(0〜3)や視差の方式(0〜3)は段階のあるつまみだが、表としては「ソフトかどうか」「凹凸があるかどうか」で足りる。on => _shadow.PcfRadius = on ? 2 : 0 のように、戻す先の値を Program 側で決め打ちにできるのは、表が型を知らないおかげ。

CameraPath も GL を呼ばない

HdrImage と SkyAnalysis(Day 39)と同じ性格のクラスがもう1つ増えた。入口は float、出口は Pose。

配当が出るのがまた自己チェックで、RunCameraCheck のカメラ側5項目は1枚も描かずに走る。「キーの上を通るか」「速度が跳ばないか」は絵にせずに確かめられる種類の問いなので、そこを分けておくと検算が軽い。

EyePosition を切り出した理由

CameraPath.SpeedAt は「そのときカメラは何 m/s で動いているか」を測る。そのためには姿勢(注視点・距離・角度)から目の位置を作る必要があり、それは OrbitCameraController.Apply がやっていることとまったく同じ計算になる。

式を写して2か所に置くと、片方だけ直したときに、測った速度と実際の動きがずれる。しかも絵は正しく出るので、疑うのは数字のほうになる——いちばん見つけにくい壊れ方。

  OrbitCameraController.Apply()   ──┐
                                    ├→ EyePosition(target, distance, yaw, pitch)
  CameraPath.SpeedAt()            ──┘

static にしてあるのは、CameraPath がコントローラのインスタンスを知らなくてよいようにするため。計算だけを共有して、状態は共有しない。

Path という名前が使えなかった話

DemoScene のカメラワークを持つプロパティは、最初 Path という名前だった。そのまま書くとビルドが通らない。

csharp
public CameraPath? Path { get; private set; }
...
string name = Path.GetFileNameWithoutExtension(relativePath);   // ← ここが壊れる

C# の名前解決では、同じクラスのインスタンスメンバーが型名より優先される。Path は System.IO.Path ではなく自分のプロパティを指し、「CameraPath に GetFileNameWithoutExtension は無い」と言われる。

System.IO.Path と完全修飾して逃げることもできるが、呼び出し側が全部長くなるのは筋が悪い。Shots に改名した。JSON のキー(shots)とも揃うので、結果的にこちらのほうが読みやすい。

カメラが1フレーム進むまで — 時刻から姿勢へ、5段

静止中は補間を1回も通らないのが、この図でいちばん効いている枝。hold の間はキーをそのまま返すので、どんな補間方式でも、どんなイージングでも、止まっている絵は完全に同じになる。Ctrl+Alt+F4 や F5 を押しても静止中は何も起きないのはこのため——押しても効かないように見えるが、正しい。

SpeedAt が最後にぶら下がっているのは、HUD のためだけにあるから。絵には1ミリも影響しない。それでも毎フレーム測っているのは、補間方式の違いが通過点の 0.1 秒にしか出ないので、数字が無いと Ctrl+Alt+F4 を押しても何が変わったか分からないため。

機能ツアーの2相 — 「1つ切る」と「全部戻す」

毎回 SetAll(true) から組み直すのが実装上の要点。「切ったものを憶えておいて戻す」形にすると、途中で Ctrl+Alt+F8 を押されたときに何を戻せばよいのか分からなくなる。常に全部 ON を基準にして、そこから1つ引くなら、状態は index と相の2つで足りる。

その代わり、走っている間に手で切り替えても数秒後に戻される。押しても効かないスイッチはバグにしか見えないので、Ctrl+Alt+F8 / F9 / F1 を押した時点でツアーのほうを終わらせている(Program.StopTourIfRunning)。

「全部戻す」相を挟むのは基準の絵を毎回見せるため。切りっぱなしで次へ進むと、2つ目からは何と比べているのか分からなくなる。

改造課題

課題1(易): ショットを1つ足して、引き継ぎの効き目を見る

assets/scenes/demo-v1.json の shots に、道路バリアの寄りを1つ足す。

json
{
  "name": "バリアの寄り",
  "target": [2.3, 0.5, 0.0],
  "distance": 3.4,
  "yaw": 120.0,
  "hold": 2.5,
  "travel": 5.0
}

pitch も fov も書いていないので、前のショットのものがそのまま引き継がれる。Ctrl+Shift+F10 で読み直し、Ctrl+Shift+F9 で展開後の数字を確かめる。

そのうえで確かめてほしいことが2つ。

  • 方位の合計が 0 でなくなると何が起きるか。1周するたびにカメラが同じ向きへ回り続け、何周かすると構図がずれていく——ように見えて、実は巻き取りが効いているのでずれない。なぜか
  • hold を 0 にすると、そのショットは「通過点」になる。イージングが効いたまま通過するので そこで一瞬止まって見える。イージングを切る(Ctrl+Alt+F5)と素通りする

課題2(中): 弧長パラメータ化で、区間ごとの速さを揃える

いまは travel が同じでも、区間の長さが違えば速さが違う。「ゴミ箱の金属 → 街灯を見上げる」は 5 秒で 4m しか動かないが、「通りを見渡す → ゴミ箱の金属」は 6 秒で 10m 近く動く。

直し方は Eberly の資料のとおり。

  1. 区間ごとに u を細かく刻んで折れ線の長さを積み、弧長の表を作る
  2. Sample で欲しいのは「弧長が s になる u」なので、表を二分探索して逆引きする
  3. travel を「秒」ではなく「m/s」で書けるようにする

表は CameraPath のコンストラクタで作るのが要点。毎フレーム積み直すと 600 回のサンプルが毎フレーム走る。

できたら、自己チェックに「区間ごとの平均速度のばらつき」を1項目足す。弧長パラメータ化の前後で数字が縮むはず。

課題3(難): 機能ツアーを PNG の連番で吐く(比較シート)

ツアーが切り替わるたびにスクリーンショットを撮って、screenshots/tour/00-all.png、01-hdr-off.png …… と並べる。デモの資料としてはこれがいちばん使いでがある。

引っかかるのはタイミングで、フラグを立てたそのフレームには撮れない。

  フレーム N   : 機能を OFF にする(OnUpdate)
  フレーム N   : その設定で描く(OnRender)
  フレーム N+1 : ← ここで撮る。glReadPixels は「描き終わった画面」を読む

Screenshot.Save(Day 39)は既定のフレームバッファを読むので、_post.End より後、SwapBuffers より前でなければ意味の無い絵が撮れる。撮影の予約をキューに積んで、OnRender の末尾で1枚ずつ消化する形になる。

余力があれば、撮った 13 枚を1枚のコンタクトシートに並べるところまで。Screenshot が持っている PNG の書き出しをそのまま使える——帯を並べて zlib に流すだけなので、画像を貼り合わせる処理は 30 行ほどで書ける。

自己チェック(8項目すべて合格)

上の「完成条件 10」のとおり。数字の読み方をいくつか。

  • キーの上を通るずれが 1.45E-006。float の精度の話しか残っていない。ここが 1E-3 くらいになるなら、区間の端で u が 1 に届いていないことを疑う
  • 速度の跳びが 線形 1.58 / Catmull-Rom 1.13。「Catmull-Rom は滑らか」という言葉が、1.4 倍という具体的な数字になる。0 にならないのは、イージングを外して測っているのと、hold の出入りが残っているため
  • 方位の最大 0.52 度 / 標本。1周を 2000 で割った 21.2ms 刻みなので、秒速にすると 25 度/s 弱。巻き取りを忘れると、ここが 300 度超になる

検証の途中で分かったこと

街灯を見上げるショットは、最初まったく成立しなかった。仰角 -6 度で街灯の頭を狙ったら、画面が壁のレンガで埋まった。高さ 5.5m の壁が近くにあると、カメラの位置から壁の上端までの仰角が40 度を超えていて、それより浅い角度では空が入らない。

直したのは仰角(-44 度)と距離(3.5m)で、壁のすぐ内側に立って空を向く構図にした。「見上げるショットは、まず何度から空が入るかを計算してから決める」——シーンの寸法から画角を逆算するのは、Day 39 で太陽の仰角から壁の高さを決めたのと同じ作業。

もう1つ。DemoScene.Path という名前が使えなかった話は設計書に書いたとおりで、これはコンパイルエラーで気づける類の問題だが、エラーメッセージ(「CameraPath に GetFileNameWithoutExtension は無い」)が原因からいちばん遠い場所を指すので、慣れていないと迷う。
