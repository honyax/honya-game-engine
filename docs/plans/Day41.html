理論の要点

1. 頂点ブレンディングは、行列を重みで混ぜるだけ

スキニングの式は1本しかない。

p' = Σ w[i] * M[i] * p        (i = 0..3、Σ w[i] = 1)

p は頂点の位置、M[i] は関節 i の関節行列、w[i] はその効き具合。「どの骨がこの頂点をどれだけ引っ張るか」を重みで表しているだけで、数学としてはこれ以上のものは出てこない。

実装では、行列を先に混ぜてから頂点に掛ける。

glsl
mat4 skin = M0 * w0 + M1 * w1 + M2 * w2 + M3 * w3;
vec4 skinned = skin * vec4(aPosition, 1.0);

順番を入れ替えて「掛けてから混ぜる」でも結果は同じ(行列とベクトルの積は線形なので分配できる)。混ぜてから掛けるほうが行列とベクトルの積が1回で済むので速い。

この手法の弱点も式から読み取れる。混ぜた skin は回転行列ではない。90 度回転と 0 度回転を 0.5 ずつ混ぜると、45 度回転ではなく縮んだ行列になる。肘を大きく曲げると内側が潰れるのはこれで、アメの包み紙のように絞れることから candy-wrapper artifact と呼ばれる。直すには二重四元数スキニング(dual quaternion skinning)が要るが、実際のゲームは「潰れる前に関節を足す」で回避することが多い。

重みの合計が 1 でないと壊れる。合計 0.9 ならp' = 0.9 * (混ぜた変換) * p になり、その頂点だけ原点へ 10% 引き寄せられる。モデル全体が縮むのではなく特定の頂点だけがへこむので、実装ミスと区別が付きにくい。ファイル側の丸めで合計が 1 からずれることは普通にあるので、読み込み時に正規化しておく(GltfLoader.NormalizeWeights)。

2. 逆バインド行列は、「バインドポーズを打ち消す」ためにある

関節行列の中身はこれ。

M[j] = IBM[j] * world(joint[j])         (行ベクトル規約。左から適用)

なぜ2段になるのか。ここが今日いちばんの引っかかりどころ。

頂点 p はメッシュの座標系で書かれている。一方 world(joint) は「その関節が今どこにあるか」なので、いきなり掛けるとメッシュを丸ごと関節の位置へ運んでしまう。

欲しいのは「バインドポーズからの差分」だけ。だから先にIBM = inverse(バインドポーズでの関節の世界行列) を掛けて頂点を関節のローカル座標系へ持っていく。そのうえで今の世界行列を掛けると、関節が動いたぶんだけ頂点が動く。

確かめ方が明快で、バインドポーズでは IBM[j] * world(joint[j]) が単位行列になる。関節を1本も動かしていなければ、頂点は1ミリも動かない。スキニングが壊れたときは、まずここを測る(Alt+F12 の自己チェックがこれをやる)。

ただし「ファイルのノードの姿勢」がバインドポーズとは限らない。書き出したときのフレームがそのまま入っていることが多く、今日の5体でも分かれる。

モデルファイルの姿勢での IBM * world
Fox単位行列(誤差 1e-5)
SimpleSkin単位行列(誤差 0)
CesiumMan単位行列ではない(最大ずれ 1.0)
RiggedSimple単位行列ではない

どちらも正しいファイル。バインドポーズは inverseBindMatrices の側にしか無い、というのがここで押さえるところ。

3. glTF のアニメーションには、行列が1つも出てこない

構造は2階建て。

  channel … 「どのノードの、どの属性(translation/rotation/scale)を」+ どの sampler を使うか
      ↓
  sampler … 「いつ(input)」と「どんな値(output)」の2本のアクセサ + 補間の種類

分かれているのは、同じ時間軸を複数のチャンネルで共有できるようにするため。CesiumMan は 19 関節 × 3 属性 = 57 チャンネルあるが、時間の配列は共有されている。

入っているのは「時刻 t でのノードの平行移動・回転・拡大」だけ。行列に畳むのは再生する側の仕事で、これが分担として効いてくる。

  • TRS は混ぜられる。歩きと走りを 30:70 で混ぜたければ、平行移動は lerp、回転は slerp、拡大は lerp で足りる(Day 42)
  • 行列は混ぜられない。回転行列を成分ごとに平均すると回転行列でなくなる

だから NodePose(平行移動・回転・拡大の3点セット)という型を作り、Model 側にはそれを持たせる。Day 32 のローダが「読んだそばから行列に畳んで捨てていた」のが、ここで足りなくなる。

Matrix4x4.Decompose で戻せばよいのでは、と思うところだが、せん断が入ると失敗するし、回転の符号も一意に決まらない。分解された形で読み込むのが唯一の素直な道になる。

4. 回転の補間は slerp。lerp では等速にならない

平行移動と拡大は素直に Vector3.Lerp でよい。回転だけが違う。

クォータニオンを成分ごとに線形補間すると、途中の長さが 1 でなくなる。正規化し直せば向きとしては使えるが(nlerp と呼ぶ)、回る速さが一定にならない。

自己チェックが測っている実際の数字がこれ。

0 度と 90 度を、時刻 1/4 で混ぜた結果
slerp22.500 度(等速なら当然こうなる)
成分ごとの lerp21.598 度(長さ 0.9435)

0.9 度の差なので、1本の骨だけを見ていれば気づかない。関節を 20 本重ねると、足の接地がわずかに滑るといった形で出てくる。

もう1つ、自作するときに必ず踏むのが遠回り問題。q と -q は同じ向きを表すのに、素直に補間すると 360 度近く回るほうを通ってしまう。Quaternion.Slerp(System.Numerics)は内積が負なら片方を反転してくれるので、標準ライブラリを使うぶんには自動的に面倒を見てもらえる。

補間の種類は3つ。LINEAR / STEP / CUBICSPLINE。今日のリファレンスは前2つを実装し、CUBICSPLINE は接線を捨てて値だけを拾い、直線で結ぶ(知らせは出す)。改造課題2で埋める。

5. スキン付きメッシュは、ノードの変換を無視する

glTF 仕様のこの一文が、今日いちばん見落としやすい落とし穴。

the transform of the skinned mesh node MUST be ignored

理由は式を見れば分かる。M[j] = IBM[j] * world(joint[j]) の world(joint) は根からたどった世界行列なので、メッシュをシーン空間へ運ぶ役目を最初から持っている。そこにメッシュノードの変換をさらに掛けると、二重にずれる。

見え方がはっきりしているので、間違えるとすぐ分かる。CesiumMan のメッシュノードには Z-up → Y-up の回転が入っているので、掛けてしまうと人が横倒しになる。

リファレンスでは、読み込みの時点でスキン付きパーツの Transform を単位行列にしている (GltfLoader.ReadPrimitive の partWorld)。描画側に「スキンがあるときは行列を使わない」という分岐を残すより、データの側で確定させておくほうが読み違えにくい。

副作用が1つある。バインドポーズでの境界箱が「メッシュ空間の箱」になるので、CesiumMan では高さが Y ではなく Z の 0〜1.51 に出る。そのままカメラを合わせると画面の端でモデルが切れるので、Program.MeasurePosedBounds で今のポーズの箱を CPU で測り直している。

6. モデルは共有、ポーズは個体ごと

Model は読み込んだまま変わらない(頂点・マテリアル・骨格・クリップ)。変わるのは「今この個体がどのポーズか」だけなので、そちらを AnimationPlayer に閉じ込める。

  Model(1つ)  ←  AnimationPlayer(100 個)   キツネ 100 匹
    頂点バッファ      時刻・ノードの姿勢・世界行列・関節行列
    テクスチャ
    骨格・クリップ

Model に Time を持たせてしまうと、同じモデルの2体目が作れない。Day 51 のプレイアブルデモで効いてくる形なので、ここで分けておく。

1フレームの評価は4段。

  1. ファイルの姿勢へ戻す        _pose[i] ← Nodes[i].RestPose
  2. クリップを当てる            clip.Apply(time, _pose)     触るノードだけ書き換わる
  3. 木を降りて世界行列          _world[i] = local(i) * _world[parent]
  4. 関節行列                    joint[j] = IBM[j] * _world[joints[j]]

1 を毎回やるのが大事。クリップが触らないノードは「前フレームの値」ではなく「ファイルの値」でなければならない。戻さずに済ませると、クリップを切り替えたときに前のクリップが最後に書いた値が残る。

3 には並び順の保証が要る。_world[parent] が確定済みでなければならないのに、glTF の nodes の並びに順序の保証は無い(子が親より前に書かれているファイルは実在する)。読み込み時に根から深さ優先で降りた順(Model.NodeOrder)を作っておき、毎フレームはその順に1回舐めるだけにする。これを怠ると腕だけ1フレーム遅れてついてくるという気味の悪い出方をする。

関節行列をどう送るかも設計判断で、今日はいちばん素朴な uniform mat4 uJoints[64]。

  CesiumMan(19 関節)  19 × 64 バイト = 1.2KB を、毎フレーム × パス3回
  100 体並べると       360KB/フレーム

1体なら誤差だが、台数に弱いのがこの方式。上限も 64 で、OpenGL 3.3 が保証する頂点 uniform の量(GL_MAX_VERTEX_UNIFORM_COMPONENTS = float 1024 個 = mat4 64 個)ぴったりに合わせてある。人型のフルリグ(指まで)は 60〜80 本になるので、実用ではここが最初に当たる壁。逃げ道は UBO/SSBO、関節行列のテクスチャ化、メッシュ分割の3つで、どれも先の話。

  1. 1
    ファイルの姿勢へ戻す
    読む Nodes[i].RestPose書く _pose[i]
    飛ばすと: クリップが触らないノードに、前のクリップが最後に書いた値が残る
  2. 2
    クリップを当てる
    読む time、clip書く _pose[i](触るノードだけ)
    TRS のまま書く。行列には畳まない(混ぜられなくなる)
  3. 3
    木を降りて世界行列
    読む _pose、NodeOrder書く _world[i] = local(i) * _world[parent]
    ファイルの並び順で回すと: 親より先に書かれた子が、1フレーム前の親を使う
  4. 4
    関節行列
    読む _world、Skin.InverseBindMatrices書く joint[j] = IBM[j] * _world[joints[j]]
    これを uJoints[64] で本描画・影・SSAO の3パスに送る(要点7)

7. スキニングは、頂点位置を使う全部のパスに入れる

本描画だけに入れると、次のような壊れ方をする。

入れ忘れたパスどう見えるか
depth.vert(影)キャラは動くのに影がバインドポーズのまま。自己遮蔽の縞も出る
geometry.vert(SSAO)足元の遮蔽だけが1歩ぶん置き去りになる

深度パスと SSAO の幾何パスは本描画とは別のシェーダなので、同じ関節行列を3回送ることになる。冗長に見えるが、「3つのパスが同じ頂点位置を見る」ほうが桁違いに大事。

法線と接線もスキニングするのも同じ話。忘れると形は正しく曲がるのに陰影だけがバインドポーズのまま張り付き、「腕を上げたのに影が動かない」という絵になる。

厳密には法線には逆転置が要るが、関節行列はほぼ回転と平行移動(非一様スケールを入れたリグは珍しい)なので mat3(skin) で足りる。

Part.Transform を残した理由

スキン付きのパーツの Transform は単位行列になり、使われない。アニメーション付きのモデルのスキン無しパーツも、AnimationPlayer.GetNodeWorld のほうを使う。では Transform は要らないのかというと、静的なモデルには要る。

  スキン付き              → 単位行列。位置は関節行列が持つ
  アニメあり・スキン無し  → AnimationPlayer.GetNodeWorld(NodeIndex)
  静的なモデル            → Part.Transform(Day 32 からの経路)

3つ目を残してあるのは互換のため。プレイヤーの世界行列は TRS から作り直すので、matrix で書かれたノード(BoxTextured)ではわずかに値が変わりうる。Day 39 のデモシーンの小物は全部この経路を通るので、今日の変更で過去の絵が1ピクセルも動かなかったことを保証しやすい形にしてある。

Program.PartMatrix がこの3分岐を1か所に閉じ込めていて、本描画・影・SSAO の3か所が同じ関数を呼ぶ。ここを3か所に写すと、いつか1つだけ直し忘れる——そのときの症状が「影だけずれる」なので、原因にたどり着くのに時間がかかる。

頂点が 96 バイトになったこと

Joints と Weights で 32 バイト増えた。性質が悪いのは、これを使うのはスキンを持つメッシュだけだという点。Day 39 のデモシーンの地面も壁も小物も、全部 0 が詰まった 32 バイトを運ぶ。

Day1頂点内訳
Day 1732 バイト位置12 + UV8 + 色12
Day 3248 バイト+ 法線12(色が Vector4 に)
Day 3464 バイト+ 接線16
Day 4196 バイト+ 関節16 + 重み16

本来は SkinnedVertex を別に定義して Mesh<SkinnedVertex> として分けるのが正しい。そうしなかったのは、描く側(Program.Draw / ShadowMap / Ssao)が全部 Mesh<Vertex> で書かれていて、型を1つ増やすと今日の主題と関係の無い差分が広がるため。DamagedHelmet の 14556 頂点で 1.4MB なので、この規模ではまだ払える。改造課題3で分ける。

1フレームの姿勢が決まるまで — 時刻から関節行列へ4段

1 を毎回やるのが要点。クリップが触らないノードは「前フレームの値」ではなく「ファイルの値」でなければならない。戻さずに済ませると、クリップを切り替えたときに前のクリップが最後に書いた値が残る——Fox で Walk → Survey にしたときに腰の高さだけ前のまま、といった壊れ方になる。

SkinningEnabled が false のときは 4 を単位行列で埋める。頂点は Σw * I * p = p になり、バインドポーズがそのまま出る(重みの合計を 1 に正規化してあるから成り立つ)。

頂点が画面に出るまで — CPU と GPU が出会う場所

同じ関節行列を3回送る。冗長に見えるが、3つのパスが同じ頂点位置を見ることのほうが桁違いに大事で、1つでも送り忘れると「影だけバインドポーズ」「遮蔽だけ1歩ぶん置き去り」という壊れ方をする。

行列を混ぜてから頂点に掛けるのがシェーダ側の判断。掛けてから混ぜても結果は同じ(積が線形なので分配できる)が、混ぜてからのほうが行列とベクトルの積が1回で済む。

Program.PartMatrix / PartJoints を1か所に置いてあるのは、3か所に写すといつか1つだけ直し忘れるから。そのときの症状が「影だけずれる」なので、原因にたどり着くのに時間がかかる。

改造課題

課題1(易): クリップ全体で最大の境界箱を作る

いまの Program.MeasurePosedBounds は読み込み直後の姿勢1つしか測っていない。だから Fox の Survey(頭を大きく振る)では、途中でモデルが画面からはみ出す。

直し方は素直で、クリップを一定間隔(たとえば 1/15 秒)で刻んで、各時刻の箱の和を取る。

csharp
for (float t = 0.0f; t < player.Duration; t += 1.0f / 15.0f)
{
    player.SelectClip(clip);
    player.Advance(t);
    (Vector3 min, Vector3 max) = MeasurePosedBounds(model, player);
    // 和を取る
}

そのうえで確かめてほしいことが2つ。

  • どれだけ大きくなるか。CesiumMan で数 % だが、Fox の Survey では1 割以上変わる。「アニメーションのある物体の境界箱」が静的なものより必ず大きくなる理由が実感できる
  • 1回の測定に何 ms かかるか。頂点を GPU から読み返すので、刻みを細かくすると読み込みが目に見えて遅くなる。実際のエンジンが関節の位置だけから大まかな箱を作るのはこれが理由

課題2(中): CUBICSPLINE を実装する

いまは接線を捨てて直線で結んでいる(読み込み時に知らせが出る)。glTF の CUBICSPLINE はキー1つにつき値が3つ並ぶ。

  [ 入り接線 a[0], 値 v[0], 出接線 b[0], 入り接線 a[1], 値 v[1], ... ]

補間は三次エルミート。仕様の付録にそのまま式がある。

  t2 = t*t, t3 = t2*t
  p(t) = (2t3 - 3t2 + 1) * v[k]
       + (t3 - 2t2 + t) * dt * b[k]
       + (-2t3 + 3t2) * v[k+1]
       + (t3 - t2) * dt * a[k+1]

dt はその区間の秒数(times[k+1] - times[k])。ここを 1 と決め打ちすると、区間の長さによって接線の強さが変わり、キーの上では合っているのに間で暴れる。

AnimationClip.Sampler に SampleVector3 / SampleRotation の分岐を足す。回転はエルミートで補間したあと正規化する(球面上には乗らないので近似になる)。

確かめる素材が手元に無いのが難所で、今日の5体はすべて LINEAR。Blender で適当なモデルにベジエ補間のキーを打って書き出すか、InterpolationTest.glb(glTF-Sample-Assets)を取ってくると比較できる。

課題3(難): スキン付きの頂点型を分ける

Vertex は 96 バイトになったが、Joints / Weights を使うのはスキンを持つメッシュだけ。デモシーンの地面も壁も小物も、全部 0 が詰まった 32 バイトを運んでいる。

分けるには、描く側が頂点の型を知らなくてよい形にする必要がある。

csharp
internal interface IMesh : IDisposable
{
    void Draw();
}

internal sealed class Mesh<TVertex> : IMesh where TVertex : unmanaged { ... }

そのうえで Model.Part.Mesh を IMesh にし、Program.Draw / ShadowMap.Draw / Ssao.Draw の引数も IMesh にする。Vertex から Joints / Weights を落とし、SkinnedVertex を新設する。

引っかかるのが3か所ある。

  • ReadVertices() が型を要求する。自己チェックがpart.Mesh.ReadVertices() を呼んでいるので、IMesh 越しには取れない。IMesh に ReadPositions() だけを置くか、チェック側で型を判別するか
  • Primitives が作るのは Mesh<Vertex>。立方体も板も球もスキンを持たないので、こちらは Vertex のままでよい
  • シェーダは2本要るのか。属性 5・6 を宣言したシェーダにSkinnedVertex でないメッシュを流すと、属性が刺さっていない状態になる。glVertexAttrib4f で既定値を入れるか、シェーダを分けるか

測ってから決めるのが本筋。デモ v1 の頂点数(21 万三角形ぶん)で何 MB 減るのかを先に計算して、それが払う複雑さに見合うかを判断する。

自己チェック(35 項目すべて合格)

上の「完成条件 9」のとおり。数字の読み方をいくつか。

  • slerp 22.500 度 / lerp 21.598 度。「slerp が要る」という言葉が0.9 度という具体的な差になる。1本の骨では気づかないが、20 本重ねると足の接地が滑る
  • Fox の関節行列のずれが 9.54E-006。float の精度の話しか残っていない。ここが 1E-3 くらいになるなら、逆バインド行列の転置を疑う
  • CesiumMan のずれが 1.00E+000。これは異常ではない。ファイルのノードがバインドポーズに置かれていないだけで、ここを「0 でなければおかしい」と決めつけると、正常なファイルを疑い始める
  • 1秒で 84.7cm 動く。CesiumMan の身長が 1.5m ほどなので、歩幅としては妥当。ここが 0 なら重みか関節番号が読めていない

検証の途中で分かったこと

SimpleSkin.gltf は自己完結していなかった。glTF-Sample-Assets の glTF/ 版は SimpleSkin_geometry.bin を外部参照していて、1ファイルだけ持ってきても読めない。glTF-Embedded/ 版のほうがbase64 の data URI で全部入っているので、そちらを置いた。結果として data URI の経路を通す唯一のモデルにもなっている。

カメラ合わせが最初まったく成立しなかった。FrameModel は Model.BoundsMin/Max からカメラを決めていたが、スキン付きのパーツの境界箱はメッシュ空間の箱(要点5)。CesiumMan はメッシュ空間が Z 上向きなので、高さが Y ではなく Z の 0〜1.51 に出て、中心が足元の外に来る。モデルが画面の右上で切れた。

直したのが MeasurePosedBounds で、今のポーズで頂点を CPU でスキニングして測り直す。「バインドポーズの箱」と「実際に描かれる場所」が違うというのは、スキニングを入れた日にしか起きない種類のずれで、絵を見るまで存在に気づけなかった。

_player という名前が使えなかった。Day 22 の PlayerController が先に Program._player を使っていて、AnimationPlayer を同じ名前で置くとCS0102: already contains a definition になる。_animation に改名した。DemoScene.Path(Day 40)と同じ種類の衝突で、Program.cs が 12,000 行を超えると名前の取り合いが普通に起きる。
