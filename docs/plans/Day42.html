理論の要点

1. クリップの合成は、必ず TRS の段でやる

Day 41 の要点3で書いたことの回収。

  TRS(平行移動・回転・拡大)  →  混ぜられる
  行列                        →  混ぜられない

回転行列を成分ごとに平均すると、回転行列でなくなる。90 度回転と 0 度回転を 50:50 で足すと、45 度回転ではなく縮んだ行列が出る。クォータニオンなら slerp で 45 度が出る。

だから AnimationPlayer.Evaluate の段取りは、混ぜる段を行列を作る前に置く。

  1. クリップごとに姿勢を評価      NodePose[]
  2. 重み付きで足し込む            ← ここが Day 42 で増えた段
  3. 姿勢を確定
  4. 行列にして木を降りる          ← ここから先は Day 41 と1文字も同じ
  5. 関節行列

4 と 5 に手を入れずに済んだのが、この順番にしておいた配当。逆に「行列を混ぜる」設計にしていたら、今日は全部書き直しになっていた。

  1. 1
    クリップごとに姿勢を評価
    読む 位相 × 各クリップの長さ書く _scratch[i](NodePose)
    位相同期を切っていれば、各クリップは自分の秒(_clipTimes)で回る
  2. 2
    重み付きで足し込む(Day 42 で増えた段)
    読む _scratch、ClipWeight.Weight書く _accumulator[i](PoseAccumulator)
    回転は符号を揃えてから足す(要点2)
  3. 3
    姿勢を確定
    読む _accumulator書く _pose[i]
    重みの合計で割り、回転は正規化する(要点6)
  4. 4

    読む _pose、NodeOrder書く _world[i]
    Day 41 と1文字も同じ。混ぜる段を行列より前に置いたので触らずに済んだ
  5. 5
    関節行列
    読む _world、IBM書く joint[j]
    同上。シェーダも1文字も変わらない

2. 3本以上を混ぜるときは、slerp ではなく weighted nlerp

2本なら slerp で足りる。問題は3本以上で、ブレンドツリーの2本 + クロスフェード中の前の状態の2本 = 4本が同時に効くことがある。

slerp を入れ子にすると2つ困る。

  • 混ぜる順番で答えが変わる(slerp は結合的でない)
  • 「重み 0.3」が何に対する 0.3 なのかが分からなくなる

そこで実際のエンジンと同じ手を使う。

  平行移動・拡大 … 重み付きの和 ÷ 重みの合計
  回転           … 重み付きで足してから正規化(weighted nlerp)

nlerp は slerp と厳密には違う——回る速さが一定にならない——が、差が出るのは元の2つが大きく離れているときで、中点(t = 0.5)では slerp と完全に一致する。歩きと走りのように似た歩容を混ぜるぶんには、この近似で十分。自己チェックが「50:50 の合成が Lerp と一致」で確かめている。

符号を揃えるのが肝。クォータニオンは q と -q が同じ向きを表すので、揃えずに足すと打ち消し合って長さが 0 に近づく。そのまま正規化すると、まったく関係のない向きが出る。

csharp
if (Quaternion.Dot(_reference, rotation) < 0.0f) { rotation = -rotation; }

最初に足したものを基準にして、内積が負なら裏返してから足す。自己チェックの「揃えずに足すと長さが 0 になる」がこの実演。

3. 位相同期 — 長さの違うクリップを、同じ物差しに乗せる

今日いちばん大事な考え方。Fox のクリップの長さはこうなっている。

クリップ長さ
Survey(立ち止まり)3.417s
Walk0.708s
Run1.158s

歩きと走りを 50:50 で混ぜるとき、秒で合わせてはいけない。0.3 秒の時点で、歩きは1周の 42%、走りは 26% を指す——つまり「歩きの左足が前に出ている瞬間」と「走りの右足が前に出ている瞬間」を混ぜることになる。結果は足が地面をこすり、歩幅が縮み、体が沈む。

正しくは正規化した位置(位相)で合わせる。

  位相 0.37  →  歩き 0.37 × 0.708 = 0.261s
                走り 0.37 × 1.158 = 0.427s

こうすれば「1周のうち同じところ」どうしが混ざる。リファレンスでは 再生位置そのものを秒から位相(0〜1)へ変えた——Day 41 の _time が _phase になったのがこの日の中心的な変更。

周期のほうは重み付きの平均にする。

  0.708 × 0.5 + 1.158 × 0.5 = 0.933 秒

走りに寄せるほど周期が短くなる、という当たり前のことが、この1行で手に入る。

同期を切るとどうなるかは Shift+Alt+F3 で見られる。2本の周期は 0.708 と 1.158 で約分できないので、位相の関係が毎周期ずれていき、同じ歩容の瞬間なのに毎回ちがう姿勢になる。自己チェックがこれを数字で出していて、「1周ぶん進めたときの姿勢のずれ」が同期時 0、非同期時 70 になる。

4. ブレンドツリーとステートマシンは、別のものを表している

同じ入力(移動速度)を受けて、同じクリップを混ぜるのに、性格がまるで違う。

速度 2.1m/s のときいつ混ざるか
ブレンドツリー歩き 0.50 / 走り 0.50常に
ステートマシン走り 1.00移り変わる瞬間だけ

どちらが正しいというものではなく、題材で決まる。

  • 移動の歩容は連続量。0.5m/s と 0.6m/s の違いは連続的に見えるべきなので、ブレンドツリーが向く
  • 攻撃・被弾・ジャンプは離散。「半分だけ攻撃している状態」に意味は無いので、ステートマシンが向く

実際のゲームは両方を重ねる。「ロコモーション」という1つの状態の中身がブレンドツリーになっていて、そこから「ジャンプ」状態へクロスフェードする、という形。今日は見比べるために2つを並列に置いてあるが、そのまま入れ子にできる形(どちらも出口が ClipWeight の並び)にしてある。

5. クロスフェードとヒステリシス — 状態機械の2つの必需品

ステートマシンには、素朴に作ると必ず出る問題が2つある。

1つ目: 切り替えが飛ぶ。歩きから走りへ瞬間で切り替えると、足の位置が別の場所へワープする。だからクロスフェードで「前の状態の重みを 1 → 0、次の状態を 0 → 1」と時間をかけて移す。

Shift+Alt+F8 で 0 秒にすると、この飛びをわざと見られる。長すぎる(0.5 秒)と今度は走り出しているのに歩きの脚が残るので締まりが無い。実務では 0.1〜0.3 秒あたりに落ち着く。

2つ目: しきい値の上でばたつく。速度がちょうど境目にあると、毎フレーム状態が行き来し、クロスフェードが始まっては打ち切られる。絵がぶるぶる震えるので、すぐ分かるが原因は分かりにくい。

直し方は上がるときと下がるときでしきい値をずらす(ヒステリシス)。

  歩き → 走り  … 速度 ≧ 2.08 で上がる
  走り → 歩き  … 速度 < 2.08 - 0.25 = 1.83 で下がる

自己チェックがこれを数えていて、しきい値をまたいで微小に振動させたとき、ヒステリシス 0 なら 100 フレームで 99 回、0.25 なら 1 回しか状態が変わらない。

6. 重みの合計は、ここでも 1 でなければならない

Day 41 の要点1(頂点の重み)とまったく同じ話が、クリップの階層でも出る。

合計が 0.9 のまま混ぜると、平行移動と拡大が 0.9 倍になる——つまりモデル全体がわずかに縮み、原点へ寄る。1フレームだけなら気づかないが、重みが動くたびに大きさが揺れるので、「なんとなく息をしているように見える」という妙な症状になる。

リファレンスでは2か所で守っている。

  • AnimationPlayer.SetBlend が受け取った重みを合計 1 に正規化する
  • PoseAccumulator.Resolve が重みの合計で割る

二重に見えるが、後者は「呼ぶ側が 0.9999 を渡してきたとき」の保険。同じ不変条件を、作る側と使う側の両方で守るのは、値が層をまたいで運ばれるときの定石になる。

7. ClipWeight — 決め方を知らない型を1つ挟む

ブレンドツリーもステートマシンも、出口は同じ。

csharp
internal readonly record struct ClipWeight(int Clip, float Weight);

AnimationPlayer は「なぜその重みなのか」を一切知らない。速度で決めたのか、状態遷移の途中なのか、手で置いたのかは呼ぶ側の都合。

Day 40 の FeatureToggles が Func<bool> と Action<bool> しか知らなかったのと同じ形で、知識を持たない側に置くほうが、あとから別の決め方を足せる。Day 45 でキャラクターコントローラを繋ぐとき、「接地しているか」「壁に当たっているか」で重みを決める経路が増えるが、そのとき AnimationPlayer には手が入らない。

決める側は姿勢を1ミリも触らない。ノードも関節も骨格も知らず、知っているのは「クリップの番号」と「重み」だけ。混ぜる側はなぜその重みなのかを知らない。

この線を引いた配当は3つ。

1つ目。決め方を並べて見比べられる。ブレンドツリーとステートマシンは同じ口に刺さるので、Shift+Alt+F2 で切り替えるだけで比較できる。片方を AnimationPlayer の中に書いていたら、こうはならない。

2つ目。自己チェックが軽い。決める側は入力も出力もただの数値なので、28 項目のうち 19 項目がモデルを1体も読まずに走る。Day 40 の CameraPath、Day 39 の SkyAnalysis と同じ性格で、「GL を呼ばないクラス」がまた2つ増えたことになる。

3つ目。入れ子にできる。ステートマシンの1つの状態の中身をブレンドツリーにする、という実際のゲームでよくある形が、どちらの型にも手を入れずに書ける。出口が同じ ClipWeight[] だから。

_time を _phase に変えたこと

Day 41 の AnimationPlayer は再生位置を秒で持っていた。今日それを位相(0〜1)に変えている。これが今日いちばん深い変更で、理由は要点3のとおり——長さの違うクリップを同じ物差しに乗せるため。

副作用が2つある。

  • Duration が混ぜる重みで変わる。歩き 0.708 と走り 1.158 を 50:50 なら 0.933 秒。つまり Time(= Phase × Duration)は、重みを動かすと飛ぶ
  • 位相同期を切っている間は、Phase が「代表値」でしかなくなる。各クリップは _clipTimes[] の自分の秒で回っている

2つ目のために _phase と _clipTimes を両方とも常に進めてある。片方だけにすると、Shift+Alt+F3 で切り替えた瞬間に姿勢が飛ぶ。使わない値を進めておくのは無駄に見えるが、切り替えを連続にするための代償として払っている。

PoseAccumulator を struct にした理由

ノードの数だけ(Fox なら 26 個)必要で、毎フレーム作り直す。class にすると 26 個のオブジェクトが毎フレーム GC のゴミになる。

配列に入れておいて Array.Clear で初期化すれば、確保は起動時の1回だけになる。Day 26 の均一グリッドで「毎フレーム List を作らない」と書いたのと同じ判断で、1フレームに何度も使い捨てるものは、struct の配列にして使い回す。

Add が in NodePose を取るのも同じ理由(40 バイトの構造体をコピーしない)。

速度から重みが決まるまで — 2通りの決め方(Day 42)

2つの経路が同じ出口(ClipWeight[])に落ちるのが今日の設計の要。AnimationPlayer は上の分岐を1つも知らない。

ヒステリシスは下向きの矢印にしか付いていない。上がるときはしきい値そのまま、下がるときだけ深く。両方向にずらすと「上がりにくく下がりにくい」ことになり、反応が鈍く感じられる。片方向だけが定石。

改造課題

課題1(易): ツリーの点の速度を、実測で決める

Program.BuildLocomotion の速度(歩き 1.0、走り 3.2)は目分量。実際にクリップが表している速さとずれていると、足が地面を滑る。

測り方は素直で、1周期のあいだに足が後ろへどれだけ流れるかを見る。

csharp
// 接地している足の骨(Fox なら b_LeftLeg / b_RightLeg の先)の
// 世界位置を1周ぶんサンプルして、後ろへ動いた総量 ÷ 周期

Alt+F11 で骨の名前が出るので、そこから足の骨を選ぶ。

そのうえで確かめてほしいことが2つ。

  • 測った値は目分量とどれだけ違うか。Fox は 100 倍スケールのモデルなので、そのままでは「m/s」にならない。単位を揃えるところがいちばん引っかかる
  • 直したあと、速度を手動(Shift+Alt+F5 / F6)で動かしながら足の接地点を見る。滑りが減っているか

課題2(中): クロスフェードを「今のポーズから」始める

いまの AnimationStateMachine は直前の状態を1つ覚えるだけ。走り出してすぐ止まると、混ざりかけの姿勢が捨てられて少し飛ぶ。

本物はポーズを1枚保存してからフェードする。

csharp
// AnimationPlayer 側に足す
public void SnapshotPose();                    // 今の _pose を控える
public void SetBlendFromSnapshot(float weight, ReadOnlySpan<ClipWeight> clips);

Evaluate の 3 段目で、控えたポーズと混ぜた結果をさらに weight で混ぜる。

引っかかるのが2か所ある。

  • 控えたポーズは時間とともに古くなる。フェード中に元のクリップは進まないので、0.5 秒もかけると「途中で止まった姿勢」から繋ぐことになる。実際のエンジンは短いフェード(0.1〜0.2 秒)を前提にしてこれを許している
  • ブレンドツリーとの併用。ツリーの2本 + 控えたポーズ1枚で、MaxBlendClips の勘定が変わる

課題3(難): 部位マスク付きレイヤーを足す

「下半身は走り、上半身は手を振る」を作れるようにする。実際のゲームでいちばん使われている仕組みで、必要なのはノードごとの重み。

csharp
internal sealed class AnimationLayer
{
    public float[] NodeWeights;             // ノードごとの効き具合(0〜1)
    public ClipWeight[] Blend;
}

AnimationPlayer.Evaluate を「レイヤーを下から順に適用する」形に変え、各レイヤーの寄与を NodeWeights[i] で重み付けする。

設計で悩むところが3つある。

  • マスクをどう作るか。骨の名前で選ぶ(Spine 以下を上半身とする)のが定番だが、Model.Nodes[].Parent をたどって部分木ごとに塗るほうが確実
  • 重みが 1 にならない境目。腰のあたりで上半身レイヤーの重みが 0.5 になると、そこだけ2つのクリップの中間になる。滑らかに落とすほうが自然
  • PoseAccumulator は使い回せるか。レイヤーは「足す」ではなく「上書きに近い」ので、素直に足すと下のレイヤーが薄まる。Resolve のあとに Lerp するほうが素直

まず1レイヤー(全身マスク = 今と同じ)で動くことを確かめてから、マスクを入れるとよい。

動作確認済み環境

  • Windows 11 / .NET 10 / RTX 3070 / 1920x1080(DPI 100%)
  • dotnet run --project reference/Day42 -c Release

Fox(576 三角形 / 24 関節)を影・SSAO・IBL・ブルーム・FXAA 込みで 658 fps。ブレンドしていないとき(Day 41 相当)と差が測れない。

理由は計算量を数えれば分かる。クリップを2本混ぜると、姿勢の評価が 26 ノード × 2 回、足し込みが 26 回増えるだけ——1フレームあたり 100 回に満たない浮動小数点演算で、描画の 0.17ms(影パス)に対して桁が3つ違う。

ブレンドは安い。高いのは頂点スキニング(GPU)とドローコールのほうで、そこは Day 41 から1文字も変わっていない。

自己チェック(28 項目すべて合格)

上の「完成条件 8」のとおり。数字の読み方をいくつか。

  • チャタリング 99 回 対 1 回。「ヒステリシスが要る」という言葉が、100 フレームで 99 回という具体的な数字になる。ここが 0 回なら、しきい値を跨げていない(テストの速度が間違っている)
  • 周期 0.9333s。walk 0.708 と run 1.158 の平均そのもの。ここが 0.708 や 1.158 に張り付くなら、重みが片方に寄っている
  • 位相同期 OFF のずれ 7.01E+001。Fox は 100 倍スケールなので、世界単位で 70 = 実寸で 70cm 相当。関節1本ぶんの長さより大きい
  • 同期 ON のずれが厳密に 0。Advance(Duration) で位相がちょうど 1 周する。float の丸めが乗って 1e-7 くらいになるかと思ったが、((1.0f % 1.0f) + 1.0f) % 1.0f が正確に 0 を返すので誤差も出なかった

検証の途中で分かったこと

キーの段が6つ目になって、順番の制約が効いてきた。Shift+Alt+F1 は case Key.F1 when alt:(Day 41)にもcase Key.F1 when shift:(Day 38)にも一致してしまう。

C# の switch はガード付き case を上から順に照合するので、今日の塊を Day 41 の下に置くとキーが1つも届かない——しかもコンパイルは通るし、警告も出ない。押しても何も起きないだけ。

Day 39 から「具体的なものほど上」と書き続けてきたが、段が6つになると書く前に「自分より一般的な case がどこにあるか」を探すのが先になった。次に段を足すとき(Ctrl+Shift+Alt しか残っていない)は、そろそろキー割り当ての表を別ファイルに出すべき時期だと思う。

Span<ClipWeight> をローカル関数から触れなかった。チャタリングを数えるところで、外側の stackalloc した Span をローカル関数の中で使おうとして CS8175 になった。ref 構造体はクロージャに入らないので、当然といえば当然。static なローカル関数にして中で stackalloc し直した。

Program.cs が 13,752 行になった。設計書に書いたとおり、今日足した 530 行のうち 300 行以上が自己チェックとキー操作で、エンジンの機能そのものは 200 行ほど。Phase 7 が終わったら切り出す。
