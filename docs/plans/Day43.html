理論の要点

1. セミインプリシット積分 — 2行の順番が全部を決める

微分方程式を数値で解くとき、いちばん素朴なのが陽的オイラー法。

  x(t+dt) = x(t) + v(t)·dt      ← 「今の速度」で位置を進める
  v(t+dt) = v(t) + a(t)·dt

これを1行入れ替えたのがセミインプリシット(シンプレクティック)オイラー法。

  v(t+dt) = v(t) + a(t)·dt
  x(t+dt) = x(t) + v(t+dt)·dt   ← 「更新後の速度」で位置を進める

数値解析の言葉では「どちらも1次精度」で、誤差の大きさは同じ。違うのは誤差の貯まり方になる。

自由落下1秒(60 ステップ)で確かめると、こうなる。

落ちた距離解析解との差
陽的オイラー4.8232m−81.75mm
解析解 ½gt²4.9050m—
セミインプリシット4.9867m+81.75mm

符号が逆で、大きさがぴったり同じ。だから2つの平均は解析解と一致する(自己チェックの3項目目がこれを見ている)。

これだけなら引き分けだが、振動する系にすると差が本質的になる。ばね(ω = 10 rad/s、初期エネルギー 50J)を回すと:

10 秒後の上限100 秒後の上限
セミインプリシット54.55J54.55J
陽的オイラー6.89 × 10⁸ J(とっくに数値が壊れている)

セミインプリシットの側は上限が時間で増えない。これは偶然ではなく、この積分器が「本当のエネルギーに似た別の量」を厳密に保存する(シンプレクティックである)ことの帰結で、誤差が無いのではなく、誤差が溜まらないのが値打ちになる。

ゲームの物理エンジンがほぼ全部これを使っているのは、この一点に尽きる。1行入れ替えるだけで、放っておいた物が勝手に暴れ出さないようになる。

Ctrl+Shift+Alt+F2 で陽的オイラーに切り替えても、60Hz ではなかなか差が見えない。増える量は 1 ステップあたり g²dt²/2 で dt の2乗に比例するので、数字キーの 4(5Hz)でシミュレーションレートを落とすと一目で分かる。

2. 力とトルク — 同じ力でも「どこに」掛けるかで変わる

並進と回転は、きれいに1対1で対応する。

並進回転
位置PositionOrientation(クォータニオン)
速度LinearVelocityAngularVelocity
動かしにくさ質量 m慣性テンソル I
動かす原因力 Fトルク τ
法則a = F/mα = I⁻¹τ

対応していないのは3行目だけ。質量はスカラー1つで済むのに、慣性は軸によって違うので 3x3 の行列になる(要点3)。

トルクは外積で決まる。

  τ = r × F        r は重心から作用点へのベクトル

外積なので、次の2つが自動的に出る。

  • 力が重心を向いていれば(r と F が平行)トルクは 0。押しても回らない
  • 重心から遠いほど、また力が r と直交するほどトルクが大きい

ドアの取っ手が蝶番から遠いところに付いているのは、この式そのもの。

Ctrl+Shift+Alt+F8 は、まったく同じ大きさの撃力を中心に掛けた場合と、中心を外して掛けた場合で交互に撃つ。片方は真上に飛ぶだけ、もう片方は飛びながら回る。

3. 逆数で持つ — 逆質量と、球だけ楽ができる慣性テンソル

物理エンジンは質量ではなく質量の逆数を持つ。理由が3つある。

  1. 式に出てくるのが必ず逆数のほう(a = F/m、Δv = J/m)。割り算が掛け算になる
  2. 0 が「無限の質量」になる。動かない床や壁を、分岐なしで書ける
  3. 0 除算の心配が消える
csharp
public bool IsStatic => InverseMass <= 0.0f;

静的な体にインパルスを掛けても Δv = J × 0 = 0。式のまま動かないので、解決のコードに if (isStatic) が1つも要らない。

慣性テンソルも同じで、逆行列のほうを持つ。ただしこちらは物体座標で持つ。物体が回っても、物体から見た回りにくさは変わらないからで、世界座標での値は毎ステップ作り直す。

  I⁻¹_world = Rᵀ · D · R        D は対角(主軸まわりの逆慣性)

(System.Numerics は行ベクトル規約なので、教科書の R · D · Rᵀ と左右が逆に見える。指しているものは同じ)

球はここで例外的に楽ができる。3つの主軸の値が全部同じ 1/(2/5 m r²) なので、回転で挟んでも元に戻る——つまり回しても慣性テンソルが変わらない。デモの球はこの行列が定数のままで、UpdateInertiaWorld は毎ステップ無駄に回っている。

それでも一般形で書いてあるのは、Day 44 の箱でここが効いてくるから。使わないうちから正しい形で書いておくと、後で足すのが 0 行で済む(自己チェックは「対角が違えば 90 度回すと x と y の回りやすさが入れ替わる」でその形を先に検証してある)。

4. 向きの積分 — q += ½ ω q dt の見慣れない式

位置は x += v·dt で済むのに、向きはこうなる。

csharp
var spin = new Quaternion(AngularVelocity, 0.0f);   // 実部 0 の「純クォータニオン」
Orientation += spin * Orientation * (0.5f * dt);
Orientation = Quaternion.Normalize(Orientation);

½ はどこから来るか。クォータニオンは「半角」で回転を表す(角度 θ の回転が cos(θ/2), sin(θ/2)·axis)。角速度は実角度の変化率なので、クォータニオンの世界へ持ち込むときに半分になる。

足し算をしていることが引っかかりどころで、これは「回転を合成する」のではなく「4次元のベクトルとして微分方程式を1歩進める」操作。だから足した時点で長さが 1 からずれる。

必ず正規化する。忘れると向きに拡大縮小が混ざり、モデルが少しずつ膨らんだり潰れたりする。しかも1フレームでは気づけない。

近似の誤差はごく小さい(角速度 2rad/s を 240Hz で1秒回して 1.99999rad)。気になるほど速く回るものがあるなら、正確な指数写像(Quaternion.CreateFromAxisAngle(ω/|ω|, |ω|dt) を掛ける)に差し替えればよい。

5. インパルス — 衝突は「力」ではなく「運動量の受け渡し」

衝突は「非常に大きな力が、非常に短い時間だけ」掛かる現象。力 [N] と時間を別々に持っても意味が無いので、掛け算の結果だけを扱う。

  インパルス J [N·s = kg·m/s]      Δv = J/m 、 Δω = I⁻¹ (r × J)

単位が運動量と同じなのがポイントで、インパルスとは運動量そのもの。2つの体に +J と −J を掛ければ、合計運動量は必ず保存する。自己チェックが「質量が違っても運動量は保存する」で見ているのはこれ。

大きさはこう決まる。

                    - (1 + e) · v_n
       j = ─────────────────────────────────────
            1/mA + 1/mB + n·((IA⁻¹(rA×n))×rA) + n·((IB⁻¹(rB×n))×rB)
  • 分子は「相対速度をどれだけ変えたいか」。e は反発係数(要点6)
  • 分母は「この向きに単位インパルスを掛けたら、接触点の相対速度がどれだけ変わるか」

分母は導出も難しくない。単位インパルス n を点 r に掛けるとΔω = I⁻¹(r × n)、接触点の速度変化は Δω × r。それを n に投影したものを足せばいい。動かしやすいものほど分母が大きく、同じ速度差を作るのに要るインパルスが小さい。

球どうしの衝突では、分母の回転の項が必ず 0 になる。接触法線は必ず両方の中心を通るので r と n が平行、外積が消える。つまり今日の球はぶつかっても回らない。ぶつかった球が回り始めるには摩擦(Day 47)が要る。回転の項が本当に効いてくるのは Day 44 の箱から。

6. 反発係数 — 目標は1回だけ決める。しきい値が無いと震える

e = 0 なら跳ねずにくっつき、e = 1 ならエネルギーを失わずに跳ね返る。落とした高さに対して、跳ね返る高さは e² 倍になる。

実装で引っかかるところが2つある。

1つ目: 反復すると跳ね返りが重ね掛けされる。速度の解決は複数回まわす(要点7)ので、そのたびに -e·v_n を計算し直すと、2周目は「1周目で跳ね返った速度」にさらに e を掛けることになり、球が天井まで飛ぶ。

だから目標の離れる速度を、接触を作った瞬間に1回だけ決めて固定する。

csharp
float bounce = approach < -RestitutionThreshold ? -restitution * approach : 0.0f;

自己チェックの「反復を8周にしても跳ね返りが増えない」がこれの確認で、1周でも8周でも跳ね返り速度は 2.0000 m/s(= 0.5 × 4.0)で一致する。

2つ目: しきい値が無いと、置いてある球が永久に震える。重力は毎ステップ 9.81 × dt ≈ 0.16 m/s を足すので、床に乗っているだけの球にも常に小さな接近速度がある。それに e を掛けると、いつまでも 0.1 m/s で跳ね続けてしまう。

csharp
public float RestitutionThreshold { get; set; } = 1.0f;   // これより遅ければ e = 0

「ゆっくりぶつかったものは跳ねない」は物理的にも正しい (ボールを床に置いても跳ねない)ので、これは誤魔化しではない。

7. 位置の補正 — インチキだが必要。そして素朴なインパルスの限界

インパルスは速度を直す。「これ以上めり込まない」ようにはできるが、既にめり込んだぶんは戻らない。

放っておくとどうなるか。重力は毎ステップ速度を足し、その速度で位置が進んでから接触が解決されるので、1ステップあたり 9.81 × dt² ≈ 2.7mm ずつ沈んでいく。何もしないと球は床の中へ消える。

そこで位置を直接動かす。

csharp
float overlap = MathF.Max(depth - Slop, 0.0f);
Vector3 correction = normal * (overlap * CorrectionRate / inverseMassSum);
a.Position += correction * a.InverseMass;
b.Position -= correction * b.InverseMass;

これは物理ではない。位置を勝手に動かせばエネルギーが湧く。それでもやるのは、代案(位置の拘束をきちんと解く)が桁違いに重いから。

3つのつまみが要る。

つまみ既定無いとどうなるか
CorrectionRate0.61 にすると一気に戻して弾ける
Slop(許すめり込み)5mm0 にすると接触が付いたり消えたりして震える
PositionIterations41 だと柱が沈む(下を上げると上が浮く)

周ごとにめり込みを測り直すのがここでいちばん大事なところ。判定した時点の深さを使い回すと、1周目で解消した重なりを2周目も押し戻して、柱が上へ弾け飛ぶ。

このページの「蓄積インパルス + 温存」は、改造課題3の2つ(蓄積インパルスと温存)を両方入れたもの。検証すると、蓄積インパルスだけでは今日の積み上げのめり込みは変わらず(各周のインパルスが負にならないため)、温存を足して初めて 4段・反復1周のめり込みが 6.44cm から 1.12cm に下がった。

そして、これでも足りない

積み上げの筋書きを反復1周でやると、柱は目に見えて沈む。

速度の反復残っためり込み4段目の高さ(理想 3.150m)
1 周64.4mm3.052m
8 周14.7mm3.114m

段を増やすとさらに悪くなる。6段だと 16 周まわしても 2cm 以上めり込む。

原因は素朴な反復のやり方にある。今日のコードは「めり込む向きの相対速度があれば、正のインパルスを足す」しかしていない。一度掛けたインパルスを後から減らすことができないので、接触どうしが押し合う積み上げでは収束が遅い。

これを直すのが Day 47 の Sequential Impulses で、要るのは2つ。

  • 蓄積インパルス: 接触ごとの合計を覚えておき、「合計が 0 以上」という条件で各周は増減どちらもできるようにする
  • 温存(warm starting): 前フレームの解を初期値として使う。積み上げは毎フレームほぼ同じ答えなので、1周目からほぼ正解にいる

今日はこの限界を数字で見えるところまでにしておく。「なぜ Sequential Impulses が要るのか」が体で分かっていないと、Day 47 は式を写すだけの日になってしまう。

B = -1 という分岐 — 今日わざと残した歪み

ContactPoint は相手を体の番号で持つが、相手が平面のときだけ -1 になる。

csharp
RigidBody a = _bodies[contact.A];
RigidBody? b = contact.B >= 0 ? _bodies[contact.B] : null;

この b?. が、速度の解決と位置の補正で合わせて 6 箇所出てくる。きれいではない。

逆質量 0 の体を置けば分岐は消える——実際 Box2D も Bullet もそうしている(静的な剛体)。そうしなかったのは、平面が無限に広いからで、RigidBody.Position が「重心の位置」であるという意味が保てない。

正しい直し方は、体から形を切り離すこと。

  今日:  RigidBody が Radius を直接持っている(形が球しか無いので成立している)
  Day 44: 形が箱・カプセル・地形と増える → Collider という型が要る
          → 静的な体も「動かない Collider を持った RigidBody」で書ける
          → B = -1 の分岐が消える

Day 44 で箱を足すときに、この2つ(B = -1 と RigidBody.Radius)は同時に片付く。今日先回りして Collider を作らなかったのは、形が1つしか無いうちに抽象化すると、たいてい間違った形の抽象になるため。

CorrectPositions の中の Measure に、その痕跡がはっきり残っている——めり込みを測り直すのに a.Radius を直接読んでいて、これは球以外では成り立たない。

位置の補正を反復にしたこと

素朴に書くと、位置の補正は「接触を1周なめて押し戻す」1パスになる。これだと柱が沈んで戻らない。

理由は接触どうしが打ち消し合うから。柱の下を押し上げると、その上の接触が深くなり、次にそれを解くと下が押し戻される。1周では平衡が出ない。

反復にするとき、周ごとにめり込みを測り直すのが肝になる。

csharp
(Vector3 normal, float depth) = Measure(contact, a, b);   // 今の位置から

判定した時点の深さを使い回すと、1周目で解消した重なりを2周目も押し戻して、柱が上へ弾け飛ぶ。速度の解決が毎周相対速度を読み直しているのと同じ理由で、Gauss-Seidel 型の反復では「今の状態を見る」ことが収束の条件になっている。

改造課題

課題1(易): 反発係数を「跳ね返る高さ」から逆算する

e² = 跳ね返る高さ / 落とした高さ なので、高さを測れば e が求まる。自己チェックが頂点を拾っているコードを流用して、実測の e を出してみる。

csharp
float measured = MathF.Sqrt(peaks[0] / 3.0f);   // 期待は 0.5

実際には 0.44 前後になるはず。設定値より小さい。

なぜか考えるのが課題の本体になる。手掛かりは3つ。

  • 跳ね返りの瞬間、球は既に Slop ぶん(5mm)めり込んでいる
  • 接触が立つのは「めり込んだあと」なので、接近速度は真の値より少し大きい
  • 位置補正で持ち上げたぶんのエネルギーはどこへ行ったか

dt を小さくすると 0.5 に近づく(数字キーの 1 で 120Hz)。ここまで確かめられれば、離散化の誤差だと納得できる。

課題2(中): 重力を「力」で掛けてみる

いま重力は IntegrateVelocity の中で加速度として足している。

csharp
LinearVelocity += ((Force * InverseMass) + gravity) * dt;

これを、毎ステップ body.ApplyForce(gravity * body.Mass) で掛ける形に変えてみる。結果は完全に一致するはず——F = mg を a = F/m で割り戻すと m が消えるから。

一致することを確かめたうえで、次の2つを考える。

  • 静的な体(逆質量 0)で何が起きるか。Mass は +∞ なので gravity * ∞ = NaN。加速度で足す形なら IsStatic で早期 return しているので問題にならない
  • どちらが速いか。力の形は体の数だけ乗算が増え、溜め場への書き込みも増える

「物理的に等価な2つの書き方のうち、特異点が無いほうを選ぶ」というのが逆数で持つ話(要点3)と同じ判断で、ここでもう一度出てくる。

課題3(難): 蓄積インパルスを入れて、積み上げを持たせる

要点7で書いた Day 47 の先取り。今日のコードに 10 行足すだけで、柱のめり込みが桁で改善する。

やることは2つ。

  1. ContactPoint を struct(可変)にして、float AccumulatedImpulse を持たせる
  2. SolveVelocity で、合計が 0 以上という条件でクリップする
csharp
float delta = contact.Bounce - normalVelocity;
float magnitude = delta / denominator;

// 合計が負にならない範囲で、減らすこともできるようにする
float previous = contact.AccumulatedImpulse;
contact.AccumulatedImpulse = MathF.Max(previous + magnitude, 0.0f);
magnitude = contact.AccumulatedImpulse - previous;   // 実際に掛けるのはこの差分

いまのコードは delta <= 0 で何もしないので、一度掛けたインパルスを減らせない。合計で見れば「押す向き」のままで各周は増減できる、という形にすると、Gauss-Seidel の収束が劇的に速くなる。

確かめ方は自己チェックの Stack を流用する。6段の柱で、反復 8 周のめり込みが 32mm から何mmになるか測る。

難しいのは List<ContactPoint> の要素を書き換えるところ。readonly struct を返す Contacts プロパティのままでは書けないので、配列にして ref で触るか、CollectionsMarshal.AsSpan を使うことになる。「値型を配列に置いて使い回す」ときに毎回出てくる話(Day 42 の PoseAccumulator と同じ)。

余力があれば温存(warm starting)も。前フレームの AccumulatedImpulse を初期値として使うには、接触に「前フレームのどれと同じか」を教える識別子(体の番号の組)が要る。

自己チェック(45 項目すべて合格)

上の「完成条件 9」のとおり。数字の読み方をいくつか。

  • 誤差 ±81.75mm。陽的とセミインプリシットで符号が逆で、大きさが同じ。これが「1次の積分器」ということの実物で、dt を半分にすると 40.87mm(ちょうど半分)になる
  • ばねの上限が 10 秒でも 100 秒でも 54.55J。ここが増えていくなら、IntegrateVelocity と IntegratePosition の順番が逆になっている
  • 陽的オイラーの 6.89 × 10⁸ J。1ステップあたり (1 + ω²dt²) 倍= 1.0278 倍で、600 ステップで 1.38 × 10⁷ 倍。指数で増える
  • 球を回しても慣性テンソルが (5.0000, -0.0000, -0.0000)。等方なので回転で挟んでも変わらない。ここが変わるなら Rᵀ · D · R の左右が逆になっている(対角が違う体のほうのチェックが、その場合に落ちる)
  • 1000 倍重い相手に当てて -4.990 / 0.0100。質量比が大きいと「壁で跳ね返った」のと区別が付かなくなる、の実演
  • 反復 1周でも 8周でも跳ね返りが 2.0000。ここが 8周のときだけ大きくなるなら、跳ね返り目標を毎周計算し直している(要点6の1つ目の罠)

検証の途中で分かったこと

位置の補正を1パスで書いたら、柱が 68mm 沈んだ。反復にしても、深さを判定時の値のまま使うと今度は弾け飛ぶ。周ごとに測り直すようにして初めて落ち着いた。

速度の解決が毎周相対速度を読み直しているのは当たり前に見えるのに、位置のほうを1回で済ませようとしてしまうのは、「位置は状態、速度は変化率」という感覚に引きずられているからだと思う。どちらも Gauss-Seidel の反復で、条件は同じ。

積み上げを6段から4段に減らした。6段だと反復 16 周でも 22mm めり込む。素朴なインパルスの収束の遅さが段数に対して急なので、「反復を増やせば持つ」と言い切れるのは4段まで、というのが実測。要点7と設計書に、この数字をそのまま書いてある。

反発係数の HUD 表示を「既定e」に直した。落下の筋書きは球ごとに e を振っているので、e:0.60 と出ていると「全部 0.6 なのか」と読めてしまう。実際は「これから作る球の既定値」で、Ctrl+Shift+Alt+F3 を押すと今ある球にも一括で適用される——そこまで含めて分かる表示にした。

LinearDamping / AngularDamping が最初は未使用で警告になった。使い道が「数値的な保険」なので、デモで必要になるまで書きたくなかったが、摩擦が無いせいで撃った球が永久に回り続けることに気づいてAngularDamping = 0.4 を入れた。LinearDamping のほうは自己チェック(「シミュレーションレートを変えても同じ」)でだけ使っている。

キーの段が7つ目(Ctrl+Shift+Alt)で打ち止めになった。修飾キー3つの組み合わせはこれで最後で、Day 44 以降は数字キーの段を使うか、Day 40 の FeatureToggles のようにキー割り当てそのものをデータにする必要がある。
