// 箱と平面: 8つの頂点を平面に落として、沈んだものを全部拾う
for (int i = 0; i < 8; i++)

    if (distance < 0.0f) manifold.Add(corner - (plane.Normal * (distance * 0.5f)), -distance);

理論の要点

1. 箱の慣性テンソル — 軸ごとに違う、が全部の始まり

Day 43 の球は等方だった。どの軸まわりにも回りにくさが同じ(2/5 m r²)なので、慣性テンソルは「同じ数が3つ並んだ対角行列」で、回しても変わらなかった。

箱は違う。

  I_x = 1/12 · m · (h² + d²)      h, d は y, z 方向の全長
  I_y = 1/12 · m · (d² + w²)
  I_z = 1/12 · m · (w² + h²)

x 軸まわりの回しにくさに、x 方向の長さが出てこないのが要点。回転軸に沿った方向にいくら伸ばしても、質量は軸から離れないので回しやすさは変わらない。長い棒を軸まわりに回すのが簡単で、横に振るのが大変なのはこれ。

半分の長さ e で書くと全長は 2e なので、コードは 1/3 m (e_y² + e_z²) になる。

csharp
Vector3 e = HalfExtents * HalfExtents;
return new Vector3(
    third * mass * (e.Y + e.Z),
    third * mass * (e.Z + e.X),
    third * mass * (e.X + e.Y));

3つの値が違うので、世界での慣性テンソルが向きによって変わる。Day 43 で「使わないうちから正しい形で書いておく」と言ってR^T · D · R(UpdateInertiaWorld)を書いておいたのが、今日ようやく効く。球のときは入力と同じものが返るだけの、何もしない関数だった。

2. 形を体から切り離す — Collider

Day 43 の RigidBody は Radius を直接持っていた。形が球1つなら成立するが、箱に半径は無い。今日は形を Collider という構造体に切り出す。

csharp
internal readonly struct Collider
{
    public readonly ColliderKind Kind;      // Sphere / Box / Plane
    public readonly float Radius;           // 球
    public readonly Vector3 HalfExtents;    // 箱
    public readonly Vector3 Normal;         // 平面
}

クラス階層にしないのがここの判断。SphereCollider : Collider のように書くと、判定のたびに仮想呼び出しと型チェックが入る——N² 組を回す内側のループでいちばん高いものを毎回踏むことになる。種類の札で分岐するほうが素直で速く、Box2D も Bullet も結局こうなっている。

代償は使わないフィールドが眠ること。球のときに HalfExtents は 0 のまま。32 バイトなので気にしないことにした。

Day 43 の設計書に、片付ける予定として2つ書いた。両方とも今日消えた。

Day 43 の歪みどう消えたか
RigidBody.Radius形が Shape に移った。慣性の式も形の側(Collider.InertiaLocal)へ
ContactPoint.B = -1(相手が平面)平面が「平面の形を持った静的な体」になり、相手は必ず体の番号で指せる

3. 接触マニフォールド — なぜ1点では足りないのか

Day 43 の接触は点が1つだった。球はどこで触れても1点なので、それで足りていた。

箱では足りない。床に置いた箱を1点で支えると、その点まわりにトルクが立って箱が傾く。次のステップでは傾いた先の角が最深点になり、そこを1点で押し戻すのでまた傾く——箱が永久にガタガタと揺れ続ける。

Ctrl+Shift+Alt+4 で上限を 1 にすると、この状態がそのまま見られる。自己チェックでも数字で出る。

  4点: 最後の1秒の角速度 0.00000 rad/s、傾き 0.0000 度
  1点: 最後の1秒の角速度 0.73 rad/s、傾き 0.94 度

面で触れているものは面で支えないと落ち着かない、というのがマニフォールドが要る理由のすべて。

箱と平面は、8つの頂点を落とすだけ

今日書く判定は「箱と平面」の1本だけで、中身は短い。平面は片側しか無いので、試すべき向きは平面の法線1本だけだと最初から分かっている。8つの頂点それぞれの符号付き距離を測り、平面より下にあるものを全部接触点にする。

置き方平面より下の頂点接触点
箱を平らに置く底面の4つ4点
45度傾けて辺で立てる1本の辺の両端2点
角で立てる角の1つ1点

接触点の数がそのまま支え方の数になっているのが、Ctrl+Shift+Alt+3 の光る玉で目に見える。接触点は頂点そのものではなく、頂点とその真上の面上の点の中点(めり込んだ領域の真ん中)に置く。

箱どうしになると話がまるで変わる。相手も向きを持っているので「試すべき向き」が決まっておらず、15 本の軸を調べることになる(Day 44b の分離軸定理)。今日の短い判定は、平面という相手に甘えている。

点は4つまで、法線は1本

凸多面体どうしの接触面は凸多角形なので、理屈のうえでは頂点がいくつでも出うる(箱どうしなら最大8つ)。ただし凸多角形を支えるのに要るのは4点——外周から4つ取れば、残りはその内側に入る。Box2D も Bullet も同じ上限。

法線は1本だけ持つ。面どうしの接触では4点とも同じ向きに押し戻すのが正しく、点ごとに法線を持たせると、床の箱が場所によって違う向きに押されて震える。

4. 位置の補正の測り直し — 体に貼り付けた印

Day 43 の位置補正は、周ごとに判定関数をもう一度呼んでめり込みを測り直していた。あれは「形が球しか無い」ことに寄りかかった書き方で、実際 Measure の中で a.Radius を直接読んでいた。

形が増えると判定を呼び直すのが重くなる(箱どうしは Day 44b で 15 本の軸 + クリップになる)ので、4周 × 接触の数だけ呼び直すわけにはいかない。

代わりに、接触点を両方の体に貼り付けた印として物体座標で覚えておく。

csharp
Vector3 localA = Transform(point - a.Position, Conjugate(a.Orientation));
Vector3 localB = Transform(point - b.Position, Conjugate(b.Orientation));

体が動けば印も一緒に動くので、周ごとに

  今の隙間 = 最初の隙間 + (印A - 印B)·法線

で追いかけられる。判定を1回も呼ばずに測り直せるのがこの持ち方の値打ちで、しかも形を1つも知らない——箱どうし(Day 44b)でもカプセル(Day 45)でも地形(Day 46)でもこのまま動く。

これは Box2D の位置ソルバとほぼ同じ手。

5. 4点をどう解くか — 今日いちばん深い分岐

マニフォールドを入れると、その4点をどう解くかという問題が新しく生まれる。

Day 43 と同じく「接触を順番に1つずつ」解くと、こうなる。

  • 1点目を解いた時点で、その点の相対速度は 0 になる
  • 残り3点は「もう離れている」と見て何もしない
  • つまり1点目だけが箱の重さを全部背負う

角1つで支えているのと変わらないので、そこを中心にトルクが立つ。次のステップでは別の点が1点目になり、今度はそちらが全部を背負う——支える点が毎ステップ入れ替わって、床に置いた箱1つでも揺れが止まらない。

  同時に解く: 最後の1秒の角速度 0.00000 rad/s
  順番に解く: 最後の1秒の角速度 0.118 rad/s

直し方は素直で、4点ぶんを同じ状態から計算してから、まとめて掛ける。

csharp
for (int k = 0; k < count; k++) magnitudes[k] = NormalImpulse(_contacts[start + k]);
for (int k = 0; k < count; k++) ApplyNormalImpulse(start + k, magnitudes[k] / count);

対称に置かれた箱なら4点の値が完全に一致するので、トルクが立ちようがない。

点の数で割るのは、「1点だけで速度差を消せる大きさ」を4点ぶん足すと4倍になってしまうから。割ったぶん1周で消せる量は減るが、反復回数で取り返す——ヤコビ法(同時に更新)とガウス・ザイデル法(順に更新)の古典的なトレードオフで、ここでは「速く収束すること」より「偏らないこと」を採った。

組と組の間は今までどおり順番(ガウス・ザイデル)。そちらは偏りが問題にならず、むしろ「直前の組の結果を見る」ことで柱の下から上へ荷重が伝わる(Day 43 の要点7)。

Ctrl+Shift+Alt+7 でこの2つを切り替えられる。Day 43 の積分法の切り替え(Ctrl+Shift+Alt+F2)と同じ性格のつまみで、正しい解き方と素朴な解き方を並べて見るためだけにある。床の箱1つでは「わずかに揺れ続ける」程度だが、積むと柱が崩れる——それは箱どうしが当たる Day 44b で見る。

改造課題

課題1(易): 箱の重心をずらしてみる

RigidBody.Create は慣性テンソルを「重心が箱の中心にある」前提で作っている。Collider.InertiaLocal の戻り値の1成分だけを 10 倍(あるいは 1/10)にして、Ctrl+Shift+Alt+1 で落としてみる。

  • どの軸を重くすると、着地後の転がり方が変わるか
  • 3つとも同じ値にすると(= 球と同じ等方にすると)何が起きるか

慣性テンソルは「どの向きに回しにくいか」の表なので、値をいじると箱の性格が変わる。物理的に正しくない値でも動くのが確かめどころで、「それらしく動く」ことは正しさの証拠にならない、を体で覚えるための課題。

課題2(中): 接触点を3点にしてみる

ContactLimits に 3 を足して([1, 2, 3, 4])、Ctrl+Shift+Alt+4 で 3 点にする。押す前に予想する——四隅のうち3点で支えれば、三角形で支えることになる。三脚は倒れない。

実際には揺れが止まらない(最後の1秒の角速度 0.15 rad/s。4点なら 0.00000)。理由は重心の真下がどこにあるかを描いてみると分かる。

  • 正方形の四隅から3つ選ぶと、残った三角形の斜辺は正方形の対角線になる
  • 箱の重心の真下は正方形の中心で、ちょうどその対角線の上に乗る
  • 支える三角形の「縁の上」に重心があるので、少しでも傾くと支えの外へ出る

三脚が倒れないのは、重心の真下が三角形の内側にあるから。「点が多いほど安定する」ではなく「重心の真下を囲めているか」が効いている——凸多角形を支えるのに4点を採る理由(要点3)を、裏側から確かめる課題。2点(辺で支える)と比べると、揺れ方の違いも分かる。

課題3(難): 位置の補正で向きも直す

CorrectPositions は位置だけを動かして、向きは直していない(コメントに理由がある)。Box2D の位置ソルバは、めり込みを並進と回転の両方に配って戻す。

  1. 印(LocalA / LocalB)から今の接触点を出し、rA / rB を作る
  2. 速度の解決と同じ分母(並進 + 回転)で「戻す量」を決める
  3. 並進は a.Position += n * (λ * InverseMass)、回転は I⁻¹ (r × n) λ の角度ぶん Orientation を回す

床の箱では差がほとんど出ない(4点で支えていれば並進だけで十分まっすぐ立つ)。差が出るのは、Ctrl+Shift+Alt+4 で 1 点にしたときと、角から落ちた直後の深いめり込み。向きを直すと反復が収束しにくくなる、というコメントの主張も、周回数を変えて確かめてみる。

数字の読み方をいくつか。

検証の途中で分かったこと

4点を順番に解くと、床の箱1つでも揺れが止まらなかった。「同時に解く」理由は箱を積んで初めて見えるものだと思っていたが、床に置いた箱1つでも、最後の1秒の角速度が 0.118 rad/s から下がらない。1点目を解いた時点で相対速度が 0 になり、残り3点が仕事をしないので、1点目だけが重さを全部背負う——その1点が毎ステップ入れ替わり、揺れが続く。摩擦も減衰も無い今日の世界では、この小さな揺れを止めるものが何も無い。デモの箱(減衰 0.25)でも 0.017 rad/s が残る。

平面を体にしたら、球が跳ねなくなった。Day 43 の自己チェックが2項目落ちて気づいた——跳ね返り目標が 2.0 のはずが 1.6 になっていた。

原因は反発係数の採り方。PhysicsWorld は2つの体の小さいほうを採るが、RigidBody の既定値は 0.4。Day 43 の平面は体ではなく反発係数も持たず、「ぶつけた側の値をそのまま使う」だった。平面を体にした途端、床の 0.4 が上限として効いてしまった。

直し方は CreatePlane と CreateStatic で Restitution = 1.0f にすること。最小を採る規則のもとでは、1 は「相手の値をそのまま通す」を意味する。静的な体の既定値は 1、と覚えておくのが正しい。

Day 43 の自己チェックのしきい値を1つ緩めた。「反復1周だと柱が沈む」が deep1 > deep8 × 3.0 を求めていたが、今日の位置補正(印で測り直す)で1周のときのめり込みが64.4mm から 37.4mm へ改善したため、倍率が 2.9 に落ちて通らなくなった。8周のほうも 14.7 → 12.8mm と良くなっている。数字が良くなったせいで落ちるチェックという珍しい形なので、主張は変えずに倍率だけ 2.0 へ緩めた。

減衰は 1.0 を超えると NaN になる。MathF.Pow(1.0f - damping, dt) の底が負になるため。Day 43 から入っている性質で、LinearDamping / AngularDamping は「1秒あたりに失う割合」なので 1.0 を超える値に意味は無いが、知らずに 2.0 と書くと座標が全部 NaN になって物が画面から消える。今日は直していない(Day 47 で減衰まわりを触るときに Clamp を入れる)。

接触点を光る玉で描いたら、デバッグが一気に楽になった。「4点出ているはず」が数字では追えても、どこに出ているかは絵にしないと分からない。物理のデバッグ表示を Physics/ の中に置きたくなる誘惑は強いが、Program 側に 20 行書けば済むと分かったのは収穫だった。
