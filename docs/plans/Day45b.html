理論の要点

1. キャラクターは剛体ではない — キネマティックという選択

なぜキャラクターを RigidBody にしないのか。

人間を剛体として物理に預けると、次のことが全部「起きてしまう」。

起きること物理としては操作としては
坂に立つと滑り落ちる正しい(摩擦しだいで必ず滑る)困る
歩き出すと転ぶ正しい(足元の力にトルクが立つ)困る
15cm の縁石で止まる正しい困る
キーを離しても止まらない正しい(慣性)困る

遊ぶ人が期待しているのは「45 度までの坂は登れて、30cm の段差は乗り越えられて、キーを離したらすぐ止まる」——これはゲームの都合であって、物理法則から出てくる答えではない。

だからキャラクターは物理シミュレーションの外に置く。「キネマティック」は力で動かさないという意味で、代わりに

  1. 行きたい場所へ位置を直に動かす(めり込んでよい)
  2. 当たっている面を集めて、法線の向きへ押し戻す
  3. 速度から「面へ食い込む成分」を抜く   ← これが「滑る」の正体
  4. 2〜3 を数周する

3 の1行が滑りを作る。v -= n (v·n) で、速度を消すのではなく面に垂直な成分だけを取り除くので、面に沿った成分がそのまま残る——壁に斜めに突っ込むと壁沿いに流れるのはこれ。Day 43 のインパルスの式から「跳ね返り」を抜いたものと見ることもできる。

4 が要るのは押し戻しが打ち消し合うから。部屋の角では2枚の壁に同時に当たり、片方を押し戻すともう片方へ深く入る。Day 44 の PositionIterations と同じ事情で、周ごとに当たり直しから測り直す。

代償もはっきりしている——押されない・押せない・回らない。動く床に乗っても運ばれず、箱を押しても箱は動かない。Unity の CharacterController も Unreal の CharacterMovementComponent もQuake 以来の PM_Move も、商用エンジンはどれもこの作りで、同じ代償を払っている。

世界の側には「読むだけの入口」を作る

キャラクターは剛体ではないので PhysicsWorld.Bodies には並ばない。それでも「世界の形と当たっているか」は知りたいので、シミュレーションを進めるのとは別に問い合わせ(クエリ)を足した。

csharp
public int QueryCapsule(in Capsule3D capsule, Span<ContactManifold> results);
public bool OverlapCapsule(in Capsule3D capsule);

Unity の Physics.OverlapCapsule、Unreal の SweepMulti、Bullet の contactTest が同じ役。「今この形を置いたら何に当たるか」を問える窓口は、キャラクターだけでなくカメラの遮蔽・銃弾・AI の視線にも要る。

結果は呼ぶ側が用意した Span に書く。キャラクターは1ステップで 10 回以上これを呼ぶので、List を毎回作るとそのままゴミになる。

2. 坂の上限 — 「登れる坂」は物理ではなく決めごと

面が「床」か「壁」かは、法線と真上のなす角で決める。

  normal.Y ≥ cos(SlopeLimitDegrees)   → 床(登れる)
  それ未満                             → 壁(登れない)

50 度なら cos 50° = 0.643。この数字はどこにも物理的な根拠がない——摩擦係数から出てくるわけでもなく、ただ「このくらいなら登れることにしよう」という決め。Alt+X で切ると 60 度の坂も、ほとんど垂直な壁もよじ登れるようになるので、決めごとであることが体感できる。

床は「真上へ」押し出す

ここが今日いちばん間違えやすいところ。押し戻しは法線の向きへ出すのが素直だが、坂ではそれが横滑りになる。

  30 度の坂に立っているだけ
    → 重力ぶん沈む
    → 法線の向きへ押し戻す = 斜め上へ動く
    → 横成分のぶんだけ坂を滑り落ちる(摩擦を入れていないので止まらない)

代わりに真上へ 深さ / 法線のY だけ持ち上げると、めり込みは同じだけ解けて横へは1ミリも動かない。平らな床(法線の Y = 1)では今までと同じ式になるので、失うものもない。

登れない急な面のほうは逆に、押し戻す向きから上向きの成分を抜く。抜かないと押し戻しの上向き成分が「登り」として効いてしまう——上限を切ったときにまさにそれが起きて、壁をよじ登る。

3. 段差の乗り越え — 「持ち上げて進んで落とす」ではだめだった

半径 35cm のカプセルが 15cm の段に当たる場面を考える。丸い底が段の角に触れるので、接触の法線は

  upness = (半径 - 段の高さ) / 半径 = (0.35 - 0.15) / 0.35 = 0.571

cos 50° = 0.643 より小さいので、この段は「壁」に見える。逆に言うと、段差の処理が無くても登れるのはh < r (1 - cos θ) = 12.5cm までで、それを超えると足を取られる。

素直に思いつくのは Quake 以来の「持ち上げて・進んで・落とす」。これを書いて、動かなかった。

  1. 段差ぶん(35cm)持ち上げる
  2. 1フレームぶん(5cm)進む
  3. 落とす
     → 丸い底が段の角に当たって止まる
     → そのときの法線はやはり寝ている(57 度)ので「壁」
     → 押し戻されて元の位置へ。進んだぶんが帳消し

1フレームで進める 5cm では角を越えられないので、何フレームかけても越えられない。掃引(スイープ)を持っていれば「触れたところで止まる」ので少しはましだが、それでも角に乗った瞬間の法線が寝ていることは変わらない。

先に覗いてしまえばこれが起きない。

        覗く位置(半径ぶん前・段差ぶん上)
          ↓
   ○──→ ┃▓▓▓▓        ○ ← 段の高さまで持ち上げてから進む
   ▔▔▔▔▔▔▔▔▔▔▔      ▔▔▔┃▓▓▓▓
  1. 半径ぶん前・段差ぶん上にカプセルを置いてみる。埋まっていたら段ではない
  2. そこから小刻みに下ろして、最初に触れた面を探す
  3. その面が歩ける床で、高さが段差の範囲なら「段」と認める
  4. 認めたら、その場で段の高さまで持ち上げてからもう一度進む

1 が坂を弾く。急な坂では半径ぶん前方の地面が段差ぶんより高く上がっているので、覗いた位置が坂の中に埋まる。45 度ならちょうど境目——つまり「段差ぶん持ち上げても半径ぶん前へ進めない勾配は段ではない」という素直な基準になる。「段か坂か」を、法線ではなく覗いた先の形で決めているのが肝。

3 の「歩ける床か」でも坂が弾かれる(1 をすり抜けた緩い坂の場合)。もっとも、緩い坂ならそもそも段差を使わずに登れるので実害は無い。

持ち上げたあと落とさないので、キャラクターは何フレームか段の上の空中を歩く。0.05 秒ほどで足が段の縁に乗るので、絵としては「滑らかに段を登った」ように見える。

4. 接地判定と床への吸い付き — 今日いちばん細かい 30 行

押し戻しの結果だけで接地を判定すると、毎フレーム途切れる。SkinWidth ぶん浮かせているので、立っているだけのときは床とどこにも当たっていない。これでは「歩いているのに常に落下中」になってジャンプが出せない。

そこで少し下げた位置のカプセルを当ててみる。当たった面のうち、登れる傾き以内のいちばん平らなものを立っている床に採る。探るだけで位置は動かさない——形が値(readonly struct)であることの利き所で、本体を動かさずに何度でも試せる。

探る距離は状況で変える。

状況探る距離なぜ
普段6cmskin ぶんの浮きを拾えればよい
直前まで接地していて落ちようとしている35cm(段差ぶん)床への吸い付き
上へ動いている(ジャンプの出だし)探らない拾うと何度でも跳べる

床への吸い付きが無いと、階段や坂を下るときに「一瞬浮いて、落ちて、着地する」を毎段繰り返してガタつく。自己チェックでは、切ると 180 ステップ中 22 ステップが空中になるのが測れる。

見つけた床までは実際に下ろす。見つけただけで下ろさないと、坂を下る間じわじわ浮いていって、6cm 溜まったところで落ちる周期的なガタつきになる。

「重力で床へ押し付ける」を書いてはいけない

接地中に Velocity.Y = -2 のような小さな下向きを入れて床へ押し付ける、というのはよくある実装で、実際そう書きたくなる。これで丸一日はまった。

  押し付ける
    → 段の縁にめり込む
    → その接触は法線が寝ているので「壁」
    → 横へ押し戻される
    → 前へ進んだぶんがちょうど帳消しになる
    → しかも「押し戻された」ことが水平移動の側から見えないので、段差の処理も走らない

キャラクターは段の手前でぴくりとも動かなくなる。しかも速度も位置も完全に静止するので、「引っかかっている」のか「そういう仕様」なのか絵では区別が付かない。

接地中は縦に動かさず、床へ張り付ける仕事は吸い付きに一本化するのが答えだった。

吸い付きで後ろへ押し戻されたら、その吸い付きは取り消す

吸い付きは「離れかけた床へまっすぐ引き戻す」ためのもので、進んだぶんを取り消すためのものではない。進行方向と逆へ動いたなら、下ろす途中で段の側面に当たって押し返されたということ。

取り消すのは「動き」だけで、「接地している」という判断は残す。真下に床があることは探りが確かめているので、段の縁に引っかかって少し浮いているだけなら接地扱いのままでよい。ここを落とすと、段を登りかけたキャラクターが空中扱いになり、段差の処理が走らなくなって永久に登れない。

剛体でないものを、物理の層にどう置くか — 今日の設計の中心

CharacterController は Physics/ にあるのに RigidBody ではない。PhysicsWorld.Bodies にも並ばない。この非対称が今日の設計そのものになる。

  RigidBody         : 世界に置かれ、Step(dt) が動かす。力とインパルスで動く
  CharacterController: 世界の外に居て、自分で動く。世界には「問い合わせ」だけする

これを成り立たせるために足したのが、PhysicsWorld の読むだけの入口。

csharp
public int QueryCapsule(in Capsule3D capsule, Span<ContactManifold> results);
public bool OverlapCapsule(in Capsule3D capsule);

Step が「世界を1歩進める」のに対し、こちらは「今この形を置いたら何に当たるか」を問うだけ。世界の側は『キャラクター』という言葉を1度も知らないままでいられる。

この分け方の値打ちは、要る場面がキャラクター以外にもあること——カメラの遮蔽、銃弾、AI の視線、設置可能かの判定。Unity・Unreal・Bullet がどれも同じ形の API を持っているのは偶然ではない。

代償は非対称。キャラクターは押されるが押さない。「障害物」の筋書きで転がってきた箱に当たると押し戻されるのに、箱を押しても箱は動かない。直すには当たった相手にインパルスを掛けてやることになる(改造課題3)。

判定の窓口が2つある理由が、今日はっきりする

Day 45a で、カプセルの判定の窓口を2つにしておいた。

csharp
Collide(RigidBody a, RigidBody b)                       // 体どうし。Day 44a
CapsuleAgainst(in Capsule3D capsule, RigidBody body)    // 形と体。Day 45a

2つ目が体ではなく形を受け取るのは、キャラクターのカプセルが体ではないから。今日 QueryCapsule がこの窓口を使う。RigidBody を1つでっち上げて Collide を呼ぶ形にはしたくなかった——質量も速度も持たないものに体の皮をかぶせると、「静的な体が1つ増えている」ように見えて DynamicCount も PairTests も嘘になる。

今日いちばん時間を溶かしたこと

書き上げたコードを読んでも分からない類のものなので、残しておく。

接地中に床へ押し付けたら、段差が越えられなくなった(要点4)。Velocity.Y = -2 で床へ軽く押し付ける、というよくある実装をそのまま書いた。すると段の縁に少しめり込み、その接触は法線が寝ているので「壁」として横へ押し返され、前へ進んだぶんがちょうど帳消しになる。しかも押し戻されたことが水平移動の側から見えないので、段差の処理も走らない。

症状は「段の手前で完全に静止する」。速度も位置も1ミリも動かないので、絵を見ても「引っかかっている」のか「そういうものなのか」が分からない。フレームごとの位置と速度をコンソールに出して初めて、水平には進んでいるのに縦の移動で押し戻されていることが見えた。

答えは「接地中は縦に動かさず、床へ張り付ける仕事は吸い付きに一本化する」。つまみを1つ足すのではなく、役目が重なっていた2つを1つに寄せるのが直し方だった。

今日残した歪み

段を登る間、キャラクターが少し浮く。要点3のとおり「段の高さまで持ち上げてから進む」ので、足が段の縁に乗るまでの数フレーム(0.05 秒ほど)は空中を歩いている。掃引(スイープ)を入れれば「触れたところで止まる」形にできるが、そのぶん判定が重くなるので今日は入れなかった。

キャラクターが1ステップ動くまで — 水平と垂直を分ける(Day 45)

3 と 4 を分けるのが肝(要点3)。一度に動かすと、段差に当たったときに「壁にぶつかったのか、床に着いたのか」が区別できない。分けておけば、水平の移動が止められたときだけ段差を試せばよくなる。Quake の PM_StepSlideMove から続く定石で、斜めに走って段を上がるような場面でも破綻しない。

2 で「接地中は縦に動かさない」のが Day 45 でいちばん手こずった判断。床へ軽く押し付ける実装にすると、段の縁にめり込んで横へ押し戻され、前進がちょうど帳消しになる(要点4)。

押し戻しの中身 — 床は真上へ、壁は法線へ(Day 45)

床だけ真上へ押すのが要点2。法線の向きへ押すと、坂に立っているだけで横成分のぶん滑り落ちてしまう(摩擦を入れていないので止まらない)。真上へ 深さ / 法線のY なら、めり込みは同じだけ解けて横へは動かない。

4周まわすのは押し戻しが打ち消し合うから。部屋の角では2枚の壁に同時に当たり、片方を押し戻すともう片方へ深く入る。Day 44 の PositionIterations と同じ事情で、周ごとに当たり直しから測り直す。

stepping が true(段差を降ろしている最中)のときだけ、「歩ける基準」を 0.1 まで緩める——段の角に触れたときの法線は寝ているので、普段の基準では「登れない壁」に見えてしまう。

段差を越えるまで — 覗いて、持ち上げて、進む(Day 45)

落とさないのが今日の答え(要点3)。「持ち上げて・進んで・落とす」と書くと、カプセルの丸い底が段の角に当たって止まり、そのときの法線が寝ているので「壁」と判定されて押し戻される——1フレームで進める 5cm では角を越えられないので、何フレームかけても越えられない。

覗く位置が坂を弾く。急な坂では半径ぶん前方の地面が段差ぶんより高く上がっているので、覗いた位置が坂の中に埋まる。「段か坂か」を、法線ではなく覗いた先の形で決めている。

持ち上げたあと落とさないので、足が段の縁に乗るまでの数フレーム(0.05 秒ほど)は段の上の空中を歩くことになる。絵としては「滑らかに段を登った」ように見える。

接地を決めるまで — 探って、吸い付いて、取り消す(Day 45)

探るだけで位置は動かさないのが Probe の性格。形が値(readonly struct)なので、本体を動かさずに何度でも試せる——ToCapsule(footPosition) を用意したのはこのため。

吸い付きが無いと階段を降りるときに毎段跳ねる。自己チェックでは、切ると 180 ステップ中 22 ステップが空中になるのが測れる。

取り消すのは「動き」だけで、「接地している」という判断は残すのが要点4。真下に床があることは Probe が確かめているので、段の縁に引っかかって少し浮いているだけなら接地扱いのままでよい。ここを落とすと、段を登りかけたキャラクターが空中扱いになり、段差の処理が走らなくなって永久に登れない。

csharp
// 立ち上がれるか = 立った高さのカプセルがどこにも埋まっていないか
bool canStand = !world.OverlapCapsule(ToCapsule(Position, standingHeight));

OverlapCapsule が「当たったかどうかだけ」を返すよう作ってあるのが、ここで効いてくる(要点1)。

課題3(難): キャラクターが物を押せるようにする

キネマティックの代償(押されるが押さない)を埋める。

CharacterController.MoveAndSlide で押し戻した相手が動的な体なら、その体にインパルスを掛けてやる。

csharp
// 押した向きへ、押した強さに応じたインパルスを掛ける
body.ApplyImpulseAtPoint(-normal * pushStrength, contactPoint);

考えどころが3つある。

  • QueryCapsule が体を返していない。今は ContactManifold しか返さないので、「誰に当たったか」を持ち回る必要がある——戻り値の形を変えることになる
  • 押す強さをどう決めるか。物理的に正しくやるなら質量比だが、それだと重い箱がびくともせず「押せない」のと変わらない。ゲームでは上限付きの定数にすることが多い
  • 押し返されないこと。相手が動けば接触が消えるので、次のフレームでまた押すことになる。振動しないか確かめる

うまく動いたら「箱を押して段差の代わりにする」ができるようになり、パズル要素が1つ生まれる。

検証の途中で分かったこと

「持ち上げて進んで落とす」では段差が越えられなかった(要点3)。Quake 以来の定石をそのまま書いたが、カプセルの丸い底が段の角に当たったときの法線が寝ているため、落とした先で「壁」と判定されて押し戻される。先に前方を覗いて段かどうかを決める形に変えた。

接地中に床へ押し付けると、段差が越えられなくなった(要点4)。Velocity.Y = -2 で軽く押し付ける実装にしたところ、押し付けたぶんだけ段の縁にめり込み、横へ押し戻されて前進が帳消しになった。症状は「段の手前で完全に静止」で、絵からはまったく原因が読めない。接地中は縦に動かさず、床への張り付けは吸い付きに一本化して直した。

坂の置き方でも一度詰まった。傾けた箱を素直に持ち上げて置くと、坂の切り口(下を向いた法線の面)が床から飛び出し、キャラクターは坂ではなくその壁にぶつかって止まる。「坂が登れない」のに坂の上限は無関係、という分かりにくい詰まり方をした。上面が床と滑らかにつながるように置き直してある(BuildSlopeCourse と自己チェックの SlopeWorld の両方)。

坂を横に並べたら互いにめり込んだ。緩い坂ほど水平方向に長いので、x 方向に等間隔で並べると重なる。z のレーンに分けて解決した。
