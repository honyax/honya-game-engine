理論の要点

1. ブロードフェーズ — 「答えを変えずに速くする」層

Day 43 から Day 46a まで、判定は全部の組を試す総当たりだった。

  n = 100 →   4,950 組
  n = 200 →  19,900 組
  n = 1000 → 499,500 組

n² は 100 個までは平気で、その先で急に壁になる。Day 26 で 2D にやったことを 3D へ広げる。考え方は一言のまま——世界を格子に切り、同じマス(あるいは隣のマス)にいるものだけを調べる。

肝はブロードフェーズが形を1つも知らないこと。渡すのは外接箱(Aabb3D)の列だけで、返ってくるのは番号の組だけ。だから形が増えても格子は1行も変わらない。Day 46a で地形という5つ目の形が増えたが、SpatialGrid3D は「大きすぎて入らないもの」としてしか地形を知らない。

外接箱の作り方は形ごとに違う。

形外接箱
球中心 ± 半径
カプセル端の球2つを包む
箱(OBB)各世界軸への投影の絶対値の和(SAT の ProjectedRadius がそのまま使える)
地形格子の広がり × 高さの最小〜最大(下へ 2m 厚く)
平面作れない(無限)

回すと外接箱は太る。45 度回した立方体の外接箱は一辺が √2 倍、体積は 2.8 倍。「当たっていないのに候補に出てくる」原因の多くはこれで、箱を回しながら落とす筋書きでは候補の数が目に見えて増える。

2. 格子に入らないもの — 無限と巨大は別の問題

3D ではじめて出てくる問題がこれ。2D の Day 26 では、体は全部同じくらいの大きさの円と箱だった。

何が起きるか判定
平面マス番号が inf になって壊れる外接箱が有限でない
地形全部のマスに登録されて格子の意味が消えるまたぐマスが 64 個を超える

答えは「入れない」。格子に入らないものは別の列に置き、全部の相手と組にする。数は数個(平面5 + 地形1)なので、n 個の体に対して 6n の候補が増えるだけで済む。

ブロードフェーズは余計な候補を出すのは許されるが、取りこぼすのは許されない。取りこぼした瞬間に物が床をすり抜けるので、迷ったら候補に入れる。Query(1点からの問い合わせ)でも、はみ出し組はいちばん最初に詰めてある——あふれて捨てられるのが床や地形になると致命的だから。

「無限」を値として持っておくと分岐が消えるのが地味に効く。

csharp
public static Aabb3D Infinite => new(new Vector3(float.NegativeInfinity), ...);

Aabb3D.Overlap は無限の箱に対して必ず true を返すので、はみ出し組の足切りを場合分け無しで書ける。「作れません」を例外や null ではなく値で表す、という設計の配当。

地形の外接箱は下へ厚くしてある

地形ははみ出し組なので全部の相手と組になるが、組を作ったあと AABB で足切りする。ここで地形の外接箱が地面にぴったり張り付いていると、潜った物が足切りで落とされる。

そこで地形の外接箱を下へ 2m 厚くしてある(Terrain3D.RecoveryDepth)。面には厚みが無いので、1ステップで自分の厚みより深く潜った物体はそのまま抜ける(60Hz で 13m/s なら1ステップ 22cm。直径 32cm のカプセルが山から落ちてくると実際に抜けた)。外接箱が地面にぴったり張り付いていると、抜けた瞬間にそもそも組にならなくなるので、Day 46a の要点3の「潜った物体を押し上げる」枝が一度も走らない。本当の直し方は掃引(スイープ)だが、今日は「抜けさせない」ではなく「抜けても戻す」という安いほうで手当てしてある。

3. マスの大きさ — 3D では小さいほうへ外す罰が重い

Day 26 で「小さすぎると1個が大量のマスにまたがり、大きすぎると1マスの中で総当たりになる」と書いた。3D でも同じだが、罰の重さが変わる。

  2D: セルを半分にすると、1個がまたぐマスは 4 倍
  3D: セルを半分にすると、1個がまたぐマスは 8 倍

マスの総数も3乗で増える。32m 四方・高さ 24m を 0.5m で切ると 196,608 マス。中身が無くても構築のたびにこの配列をクリアし、混み具合を数えるためになめるので、小さすぎる側では空のマスの走査だけで遅くなる。Ctrl+Shift+G で 0.5m まで落とすと、この谷の左側が実際に見える。

目安は「物体の平均的な差し渡しの2〜3倍」。今日のデモは体が 0.4m 前後なので 2m を既定にしてある。迷ったら大きめに外すほうが安い、というのが 2D との違い。

格子は毎フレーム丸ごと作り直す(Day 26 と同じ)。3パスのカウンティングソートで List<int>[] を1本も作らないので、毎フレーム作り直しても割り当てがゼロ。差分更新(動いた物体だけマスを移す)は、全員が毎フレーム動く物理では意味がないうえに状態が増える。

1回組んだ格子を2通りに使うのが今日の配当。

csharp
CollectPairs(bounds)      // 全部の組。Step が使う
Query(box, results)       // 1つの箱の近く。QueryCapsule が使う

後者が効くのがキャラクター。Day 45 の QueryCapsule は1ステップに 10 回以上呼ばれ、そのたびに世界じゅうの体をなめていた。自己チェックでは 206 体の世界で 206 体 → 6 体に減っている。

  • 差分更新 … 格子は毎ステップ丸ごと作り直している(要点3)。動いた物だけマスを移す作りは、全員が動く物理では割に合わないので入れていない
  • 壁を格子に入れる … 今日の壁は無限の平面なので、はみ出し組として全員と組になる(改造課題2)
  • 掃引(スイープ) … 地形には厚みが無いので、速い物は抜けうる。今日は地形の外接箱を下へ厚くして「抜けても戻す」で手当てしてある(要点2)

判定の層は1行も変わっていない

もう1つ、意識して守った線。

  Collision3D / Sat / Shapes3D  →  ブロードフェーズを知らない

PhysicsWorld.GenerateContacts の中で候補の作り方が2通りに分かれたが、その下(1組を実際に当てるところ)は共通のままにしてある。そのために切り出したのが TestPair(i, j)。

csharp
// Day 46a: 二重ループの内側に判定・間引き・登録が直接書いてあった
// Day 46b: 「候補をどう作るか」と「候補をどう当てるか」を分けた
foreach (BroadPair pair in _grid.Pairs) { TestPair(pair.A, pair.B); }

ブロードフェーズを足すときにいちばん先にやる整理がこれになる。分けておかないと、総当たりと格子で同じ 30 行を2箇所に書くことになり、片方だけ直したときに「絵は同じなのに数字が違う」という追いにくい状態が生まれる。

配当は自己チェックに出る。同じ状態から1ステップだけ切り替えて、接触の組がぴったり一致することを 200 体で確かめられる——TestPair が共通だから、違いは候補の作り方だけだと言い切れる。

「設定した」と「組んだ」は別

SpatialGrid3D で1つ躓いたところ。

csharp
Configure(origin, size, cellSize);   // マスの数が決まる
Build(bounds);                        // 中身の配列ができる

Configure はマスの数だけを決めるので、Build より先にマスの数が確定する。その隙間で CellContents を呼ぶと、まだ長さ 0 の配列を「マスの数ぶんある」つもりで引いて落ちる。可視化(Alt+G)を最初のフレームで有効にすると必ず踏んだ。

IsBuilt を足して塞いだが、そもそも Configure と Build を分けているのが原因でもある。1つにまとめれば起きない。分けてあるのは、マスの大きさを変えても次のステップまで再構築を遅らせたいから——遅延して用意する種類のオブジェクトには、たいていこの段差がある。

同じ形の段差が PhysicsWorld にもある(_gridReady)。QueryCapsule は Step とは別の入口なので、格子がまだ無い状態で呼ばれうる。そのときは黙って総当たりに落ちる——速さのための仕掛けが、正しさの前提になってはいけない。

今日残した歪み

はみ出し組が増えるとブロードフェーズが鈍る。今日の世界には平面が5枚と地形が1枚あり、この6つは全部の相手と組になる。200 体なら 6 × 200 = 1,200 組で、候補全体(約 1,000 組)の大半がこれ。壁を有限の箱にすれば格子に入るので、そこは直せる余地がある。無限の平面は「床だけ」にして、壁は箱にするのが実際のゲームでの作り方になる。

課題2(中): 壁を有限の箱にして、はみ出し組を減らす

今の世界には無限の平面が5枚あり、この5枚が全部の相手と組になっている(設計書の「今日残した歪み」2つ目)。これを静的な箱に置き換えると、格子に入るぶんだけ候補が減る。

csharp
// 高さ 6m・厚さ 0.5m の壁を4枚。長さは 24m あるので、
// MaxCellsPerEntry(64 マス)を超えないようにマスの大きさか壁の分割を考えること
RigidBody wall = RigidBody.CreateStatic(Collider.Box(new Vector3(0.25f, 3.0f, 12.0f)));

引っかかりどころが2つある。

  • 24m の壁は 2m マスなら 12 マスにまたがる。1枚では 64 マスに収まるが、マスを 0.5m にすると 48 マス × 12 マス = 576 ではみ出し組に落ちる。「壁を4分割する」か「MaxCellsPerEntry を上げる」か——どちらが筋がよいか考える
  • 有限の壁は飛び越えられる。無限の平面は高さの制限が無かった。ジャンプで越えられてしまうなら高さを増やすか、天井を張るか

候補の数が何%減ったかを HUD で確かめる。

課題3(難): Sweep and Prune を書いて、格子と突き合わせる

均一グリッドは「物の大きさが揃っている」ときに強い(要点3)。大小が混ざる世界でよく使われるもう1つの定番が Sweep and Prune(SAP)——外接箱を x 軸に落とした区間を並べて、区間が重なっている組だけを y・z で確かめる。

  1. 全員の外接箱の x 区間 [Min.X, Max.X] を、Min.X の小さい順に並べる
  2. 左から順に見て、「まだ閉じていない区間」の列と今の区間を比べる
  3. x で重なった組だけ、y と z でも重なっているか確かめる

BroadphaseMode に SweepAndPrune を足し、GenerateContacts の分岐を1つ増やす。TestPair へ合流させるだけで判定は1行も変わらないのが、要点1の線引きの配当になる。

確かめ方は自己チェックの「格子と総当たりで接触の組がぴったり一致する」と同じ——同じ状態から1ステップだけ切り替えて、接触の組が一致することを見る。そのうえで、次を測って格子と比べる。

  • 200 体の世界での候補の数と、1ステップの時間
  • はみ出し組(平面と地形)をどう扱うか——SAP は無限の区間を並べられない。格子と同じく別の列に置くことになる
  • 並べ替えを毎回やり直すか、前のステップの並びを使い回すか(使い回すと挿入ソートでほぼ O(n) になるのが SAP の値打ち)

検証の途中で分かったこと

1. 地形には厚みが無いので、速い物は素直に抜ける。

Day 46a の2つ(逆慣性テンソルと格子点の真下)を直しても、格子で組んだ世界では 200 体のうち1体(カプセル、落下速度 13m/s)が抜けた。1ステップ 22cm 進むのに対して直径が 32cm しかないので、判定が1回も走らないまま通り抜ける。掃引(スイープ)を入れるのが本筋だが、今日は地形の外接箱を下へ 2m 厚くして「抜けても次のステップで戻す」ほうを採った。「潜った物体を押し上げる」枝は書いてあったのに、外接箱が地面に張り付いていたせいで一度も走っていなかった——書いたコードが動いていないことに気づくには、通しで動かすしかなかった。

2. マスを組む前に覗くと落ちる。

可視化(Alt+G)を有効にしたまま筋書きを切り替えると、描画が物理より先に走って CellContents が空の配列を引いた。Configure(マスの数を決める)と Build(中身を作る)が分かれているせいで、「マスの数は決まっているのに中身が無い」瞬間がある。IsBuilt を足して塞いだ。
