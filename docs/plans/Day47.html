2つ目は「前のステップの答えから始める」(ウォームスタート)。

    温存あり  2.746m(4mm)

// 2本を平面上のベクトルとして扱い、長さでクランプする
var sum = new Vector2(oldX + lambda1, oldY + lambda2);
float limit = contact.Friction * contact.NormalImpulse;   // クーロン

理論の要点

1. クランプを置く場所 — Sequential Impulses の核心

接触の拘束は「めり込む向きに近づかないこと」で、数式では

  v_n ≥ 0        (法線方向の相対速度)
  λ  ≥ 0        (掛けるインパルス。接触は押すことしかできない)
  v_n · λ = 0    (触れていないなら押さない)

3つ目まで含めて線形相補性問題(LCP)と呼ぶ。厳密に解くのは重いので、1つずつ順に直して何周もする(射影ガウス・ザイデル法)。

問題は「1つずつ直す」ときに λ ≥ 0 をどう守るか。

  Day 46 まで   1周ごとの λ を max(0, λ) で切る
  Day 47        合計 Σλ を max(0, Σλ) で切る

前者では掛けすぎを戻す手が無い。柱の下のほうを解くと上が持ち上げられ、次の周でまた押し戻される——反復を増やしても振動するだけで答えに近づかない。

後者なら途中の周で負の補正が出せる。合計さえ 0 以上なら、途中でどう行き来しても最後に正しい答えへ落ちる。「制約は最終的な合計に掛かっている」と読み替えるのがこの手の値打ちで、コードの差は本当に MathF.Max の位置だけになる。

正直に書くと、蓄積クランプ単体では絵が変わらない。柱がゆっくり落ち着くだけの場面では λ が常に正なので、負の補正を出す機会が来ない——自己チェックでも「蓄積 2.46257m / 素朴 2.46257m」と1ビットも違わないことを確かめている。

では何のためにあるのか。次の要点2を可能にするため。

2. ウォームスタート(温存)— 良い初期値は反復回数を買う

反復法なので、初期値が良ければ少ない周回で収束する。そして接触の答えは前のステップとほとんど同じ——床に置かれた箱を支えるインパルスは、毎ステップ m·g·dt のままでよい。

csharp
// 下ごしらえの段で、前のステップの答えをそのまま掛けてから反復に入る
Vector3 impulse = (n * cached.NormalImpulse)
                + (t1 * cached.TangentImpulse1)
                + (t2 * cached.TangentImpulse2);
a.ApplyImpulseAtPoint(impulse, point);
b.ApplyImpulseAtPoint(-impulse, point);

効き目は反復回数を落としたときにいちばん出る。

設定6段の柱の最上段(理想 2.750m)めり込み
反復8周 + 温存なし2.592m42.5mm
反復4周 + 温存なし2.460m81.4mm
反復2周 + 温存なし2.212m154.4mm
反復2周 + 温存あり2.683m17.1mm
反復8周 + 温存あり2.746m3.6mm

温存ありの2周が、温存なしの8周を上回る。反復は掛け算の回数、温存は記憶の量——時間をメモリで買っている。

難しいのは「同じ接触点」をどう見分けるか。接触点は毎ステップ作り直されるので、番号も並び順も当てにならない。2通りある。

特徴 ID(Box2D)位置で照合(Bullet)
見分け方「基準面3番 × 入射面の頂点2番」物体座標での距離が近い
正確さ完全しきい値しだい
影響範囲クリップのコードを全部書き換える(交点にも ID が要る)判定に一切触らない
形が増えたら形ごとに ID の振り方を決めるそのまま通る

今日は後者を採った。形が5種類(球・箱・カプセル・平面・地形)ある世界では1本の照合で全部通るほうが圧倒的に安い。しきい値は 2cm——1ステップで接触点が動く距離より広く、接触点どうしの間隔より狭ければよい。

取り違えても壊れないのがこの手の強みでもある。初期値が少しずれるだけで、反復が正しい答えへ引き戻す。

そしてこの2つは切り離せない。素朴なクランプでは1ステップに溜まる量が必ず 0 以上なので、持ち越しを続けると単調に増え続ける。置いてあるだけの箱が数秒後に跳ね上がるので、AccumulateImpulses を切ると温存も自動的に止まるようにしてある(WarmStartActive)。

3. クーロン摩擦 — 接線2本と、円で切ること

摩擦は接触面に沿った向きに、滑りを止めようとして掛かる。上限がクーロンの法則で決まる。

  |λ_t| ≤ μ · λ_n

面積も速さも出てこない。レンガを立てて置いても寝かせて置いても滑り出す角度が同じ、という高校物理の結論がそのままモデルになっている。

面は2次元なので、向きを表すには法線と直交する2本が要る。

csharp
// 法線の成分がいちばん小さい軸を選ぶ → 外積が 0 にならない
Vector3 axis = MathF.Abs(normal.X) < 0.57735f ? Vector3.UnitX
             : MathF.Abs(normal.Y) < 0.57735f ? Vector3.UnitY : Vector3.UnitZ;
tangent1 = Vector3.Normalize(Vector3.Cross(normal, axis));
tangent2 = Vector3.Cross(normal, tangent1);

0.57735 は 1/√3。法線は長さ 1 なので、3成分のうち最小のものは必ずこれより小さい——選んだ軸が法線と平行になることがありえない。

2本をどう回して取ってもよいのは、上限を合成した長さで決めるから(摩擦円錐)。別々に ±μλn で切ると上限が正方形になり、斜め 45 度で √2 倍の摩擦が出る。

    円で切る                正方形で切る
       ___                   ┌─────┐
     /     \                 │     │      ← 斜め 45 度だけ
    |   ●   |  半径 μλn      │  ●  │        1.414 倍まで出る
     \ ___ /                 └─────┘

摩擦は法線より先に解く。上限に使う λ_n はその時点で溜まっている値、つまり1周前のものになる。逆順にすると、その周で新しく増えた法線ぶんまで上限に入って、着地の瞬間だけ摩擦が過剰に効いて物が張り付く。(代償として、上限を 2% ほど超えることがある。Box2D も同じ性質を持っている)

2つの体の μ は相乗平均で混ぜる √(μa · μb)。反発係数が「小さいほう」なのと式が違うのは、片方が 0(氷)なら全体も 0 にしたい一方で、ざらざら同士が両方の値より大きくならないでほしいから。物性ではなくモデルの選択。

静止摩擦角が今日の実験になる。斜面に置いた物が滑り出す条件は

  m g sinθ > μ m g cosθ    ⇔    tanθ > μ

で、質量が両辺から消える。デモは tan θ = 0.5(26.57 度)にしてあるので、μ = 0.7 / 0.9 は止まり、0.1 / 0.3 は滑り、0.5 がちょうど境目になる。自己チェックでは 1kg と 20kg で滑る距離が 0.01% 以内に一致することも見ている。

転がり摩擦は入れていない。デモの黄色い球は μ = 1 でも転がり落ちる——転がっている物は接触点での相対速度が 0 なので(それが「転がる」の定義)、滑りに対する摩擦が仕事をする場面が無い。モデルに無いものは係数をいくら上げても出てこない、という実演として置いてある。

4. 段の順番 — 位置は「解いたあとの速度」で進める

今日いちばん地味で、いちばん効いた1行。Day 43 から Day 46 まで、Step の中はこうなっていた。

  1. 速度を進める(重力を足す)
  2. 位置を進める      ← 解く前の速度で進めている
  3. 判定
  4. 速度を解く
  5. 位置を補正する

床に置いてある箱で何が起きるか。段1で v = -g·dt(下向き 0.16m/s)になり、段2でその速度のまま g·dt² ≈ 2.7mm 沈む。段4で速度が 0 に戻され、段5がめり込みを押し返す——沈んでは押し戻す、を毎ステップ繰り返している。

平らな床ならこれで釣り合う。傾いた面では釣り合わない。

     沈むぶん(真下)          押し戻すぶん(法線)
          ↓                        ↗
     2.7mm                    2.7mm·cosθ
                              ← 面に沿った成分 2.7mm·sinθ が戻らない

位置の補正は法線の向きにしか押さないので、面に沿った成分が残る。結果、止まっているはずの箱が毎ステップ g·dt²·sinθ ずつ坂を下る——26.57 度なら 1.2mm/フレーム、1秒で 7cm。速度は 0 のままなので、μ をいくら上げても止まらない。

直し方は順番を入れ替えるだけ。

  1. 速度を進める
  2. 判定
  3. 下ごしらえ(温存を掛ける)
  4. 速度を解く
  5. 位置を進める      ← 解いたあとの速度で進める
  6. 位置を補正する

速度が 0 に解けている物は、位置も 1mm も動かない。実測で、坂に置いた μ = 0.7 の箱の滑りが1.5 秒で 111mm → 2.4mm になった(2.4mm は最初の1フレームぶんで、そこから増えない)。

Box2D も Bullet もこの順で、Day 43 の並びのほうが例外だった。代償は「最初の接触が1フレーム遅れる」こと——判定が位置を進める前に走るので、浮いている物は次のステップまで接触を持たない。実測では地形に落とす筋書きですり抜けがむしろ減った(Day 46 で5体 → Day 47 で3体。残りは端から落ちたもの)ので、実害は無いと判断している。

この不具合は摩擦を入れるまで絵に出なかった。Day 46 までは坂に物を置いても滑り落ちるのが正しかったので、「毎フレーム 1.2mm 余分に滑っている」ことに気づきようがない。Day 46 の逆慣性テンソルと同じで、機能を足すと前の日の抜けが見えるという形が続いている。

5. 眠りと島 — 止まっている塊を計算から外す

止まった物を計算し続けるのは無駄で、しかも数値誤差でじりじり動く。一定時間ゆっくりだった体を眠らせる。

csharp
bool slow = 速度² < 0.05² && 角速度² < 0.10²;
body.SleepTimer = slow ? body.SleepTimer + dt : 0.0f;

眠った体は積分もされず、解くときは逆質量 0として扱う——つまり静的な体とまったく同じ振る舞いになる。違いは起きられることだけ。

厄介なのは「1体では決められない」。積み上げた6段の箱は上から順に止まる。1体ずつ判定すると、上だけ眠って下がまだ起きている状態が生まれ、そこへ7段目を落とすと塊の途中で力が伝わらなくなる。

答えは「触れ合っているものはまとめて眠り、まとめて起きる」。接触で繋がった体を1つの塊(島)とみなす。

csharp
// Union-Find。接触の組を union するだけ
foreach (組 in _manifolds)
{
    if (a.IsStatic || b.IsStatic) continue;   // ← ここが肝
    _islands.Union(contact.A, contact.B);
}

// 島の中でいちばん眠りが浅い時計に合わせる
timers[root] = MathF.Min(timers[root], body.SleepTimer);

静的な体を繋いではいけない。床は世界じゅうの物と触れているので、繋いだ瞬間に全部が1つの島になり、どこかで誰かが動いている限り誰も眠れない。静的な体は眠りも起きもしないので、島に入れる意味も無い。

「いちばん浅いほうに合わせる」ので、島に1体でも動いているものが居ればその体の時計が 0 になり、島全体が起きたままになる。6段の柱に7段目を落とすと、触れた瞬間に柱ぜんぶが一斉に起きる。

眠らない体(AllowSleep = false)も同じ仕掛けで扱える——時計を 0 として混ぜれば、最小値が 0 になって島ごと起きたままになる。分岐が1つも要らない。

眠っていても判定は走る。省いているのは積分と解決だけで、ブロードフェーズもナローフェーズも今までどおり動く——そうしないと、眠っている体に何かがぶつかっても気づけない。判定まで省くには「眠った体を格子から抜いて、動くものが近づいたら戻す」仕掛けが要るが、効いてくるのは体が数千個の規模から。

6. 実効質量を先に出す — 反復の外へ出せるもの

Day 46 まで、インパルスの分母は反復のたびに計算し直していた。

  分母 = 1/mA + 1/mB + n·((IA⁻¹(rA×n))×rA) + n·((IB⁻¹(rB×n))×rB)

この値は反復の間に変わらない。体の姿勢も接触点も、速度の解決の中では1ミリも動かないからで、8周 × 4点なら 32 回同じ答えを出していた。

csharp
// 下ごしらえの段で1回だけ。逆数で持つので割り算も1回で済む
contact.NormalMass   = EffectiveMass(a, b, rA, rB, contact.Normal);
contact.TangentMass1 = EffectiveMass(a, b, rA, rB, contact.Tangent1);
contact.TangentMass2 = EffectiveMass(a, b, rA, rB, contact.Tangent2);

「反復の外に出せるもの」を見つけるのは反復法を書くときの定石。物理そのものは1文字も変わらないのに、接線が2本増えて計算量が3倍になるはずのところが、先出しのおかげでほぼ据え置きになっている。

接触点が「結果」から「状態」になった日

Day 43 から Day 46 まで、ContactPoint は readonly struct だった。判定の結果を運ぶだけの入れ物で、解いている間に書き換わるものは何も無かった。

csharp
// Day 46: 全部 readonly。作ったら最後まで変わらない
internal readonly struct ContactPoint
{
    public readonly Vector3 Normal;
    public readonly float Separation;
    public readonly float Bounce;
}

今日、後半が可変になった。

csharp
internal struct ContactPoint
{
    public readonly Vector3 Normal;      // ← 判定が決めるもの(不変)
    public readonly float Friction;
    // ここから下は解いている間に書き換わる
    public float NormalMass;             // 下ごしらえで1回
    public float NormalImpulse;          // 反復のたびに
    public float TangentImpulse1;
}

readonly と可変が1つの型に同居しているのは気持ちのよい形ではない。分けるなら ContactPoint(判定の結果)と ContactConstraint(解くときの作業領域)の2つにするのが Box2D の形で、あちらは実際にそうなっている。

今日1本のままにしたのは、2本にすると添字の対応を保つ責任が増えるから。接触点は毎ステップ数百個生まれるので、2つの配列を並走させると「片方だけ Clear し忘れる」種類の事故が入り込む。型が 2 つ・配列が 2 本になる価値が出るのは、解くところを並列化するとき——そのとき作業領域だけをスレッドごとに分けたくなる。今日はまだ早い。

List<T> の中身を書き換えるのに CollectionsMarshal.AsSpan を使った。

csharp
private Span<ContactPoint> ContactSpan => CollectionsMarshal.AsSpan(_contacts);

_contacts[i].NormalImpulse += x と書けないのは、List<T> の添字が値のコピーを返すため。class にすれば書けるが、毎ステップ数百個のゴミが出る。AsSpan は内部配列をそのまま指すので、添字で書き換えたものがリストに残る——要素を足したり消したりしている間に使ってはいけない(内部配列が作り直される)という制約付きの窓で、ここでは判定が終わってからしか使わないので安全。

持ち越しをどこに置くか

ContactCache を PhysicsWorld が1つ持つ形にした。組ごとに持たせる案もあったが、組は毎ステップ生まれては消えるので置き場所が無い。

  PhysicsWorld
    ├─ _contacts    今ステップの接触点(毎回作り直す)
    ├─ _manifolds   組の区切り(毎回作り直す)
    └─ _cache       ステップをまたいで残る唯一のもの

鍵が体の番号なので、Clear() で必ず捨てないといけない。体を入れ替えたのにキャッシュが残っていると、まったく別の組のインパルスを引き継ぐ——筋書きを切り替えた1フレーム目だけ物が弾け飛ぶ、という形で出る。

同じ性格の落とし穴が Day 46 にもあった(_gridReady)。ステップをまたいで残るものは、世界を組み直したら必ず捨てる。PhysicsWorld に「またぐもの」が2つになったので、3つ目が増えたら ResetPersistentState() のようにまとめる頃合いになる。

島は「眠りのため」だけに使っている

IslandBuilder は Union-Find そのもので、133 行のうち半分がコメント。使っているのは UpdateSleep の1箇所だけ。

Box2D は島をもっと使う。解くのも島ごとに分けていて、島どうしは干渉しないので並列に解ける。今日それをやらなかったのは、島を解くために必要なものが多いから——体・接触・拘束をそれぞれ島ごとに詰め直す配列が要り、PhysicsWorld の形が大きく変わる。

眠りだけなら Union-Find 1本で足りる。「触れ合っているかどうか」しか要らないので、接触の組を Union して、代表で引ければそれでいい。同じデータ構造でも、何に使うかで必要な作り込みが2桁変わるという例になっている。

段を1つ増やしたこと

Step の段が5つから8つになった。増えた3つはどれも「解く」ことそのものではない。

増えた段何のためにあるか
下ごしらえ(PrepareContacts)反復の外に出せるものを出す。実効質量と温存

反復法だという性格が、そのまま段の形に出ている。反復の前に「良い初期値を作る段」があり、反復の後に「次の初期値を残す段」がある——この前後の対称性は、反復法を書くとほぼ必ず現れる形になる。

法線 J の合計が理屈と合うのを確かめられる。1kg の箱が4点で支えられているなら、m g dt = 1 × 9.81 / 60 = 0.1635 N·s を4点で分けて 1点あたり 0.0409。上の数字と一致する。接線 J が 0 で、上限が 0.0204(= μ × 法線J)なのも読みどころ——止まっている物に摩擦は仕事をしていないが、上限だけは常に用意されている。

課題1(易): 温存の照合しきい値を掃引して、当たり率と沈み方を測る

ContactCache.MatchDistance は 2cm。広すぎると隣の点のインパルスを引き継ぎ、狭すぎると照合に失敗して温存が効かなくなる。

ContactCache の定数を PhysicsWorld から差し替えられるようにして、RunSolverCheck の末尾で掃引する。

foreach (float distance in new[] { 0.0001f, 0.001f, 0.005f, 0.02f, 0.1f, 0.5f })
{
    PhysicsWorld world = BuildStackWorld(6, true, true, 2);
    world.MatchDistance = distance;

}

確かめてほしいこと。

  • 当たり率が 100% になる下限はどこか(1ステップで接触点が動く距離のはず)
  • 広げすぎると何が起きるか。箱を1つ回しながら落として、隣の角のインパルスを引き継いだ瞬間を探す
  • 反復を8周にすると、しきい値の影響が減るのはなぜか

課題2(中): 静止摩擦と動摩擦を分ける

今は係数が1つしかないので、動き出す瞬間のがくんとした加速が出ない。

csharp
public float StaticFriction = 0.6f;    // 動き出す前
public float DynamicFriction = 0.4f;   // 滑っている間

SolveFriction で「今この接触は滑っているか」を判定して係数を選ぶ。

csharp
// 接線方向の相対速度がしきい値より速ければ「滑っている」
float slipSpeed = (relative - normal * Vector3.Dot(relative, normal)).Length();
float mu = slipSpeed > SlipThreshold ? contact.DynamicFriction : contact.StaticFriction;

引っかかりどころが2つある。

  • 判定が毎ステップ揺れるとがたつく。しきい値のすぐ上を行き来する場面(境目の坂に置いた箱)で係数が振動し、箱が小刻みに震える。ヒステリシス(動き出すしきい値と止まるしきい値を別にする)が要るかもしれない
  • 坂の実験で、静止摩擦角と動摩擦角が別々に測れるようになる。RampSlide を「滑り出す傾き」を二分探索で求める形に書き換えると、2つの係数が数字で見える

Box2D も Bullet も既定では1つしか持たない理由が、書いてみると分かる。

課題3(難): 特徴 ID を通して、照合を添字1つにする

今の照合は物体座標の距離で 2cm 以内を探す(要点2)。Box2D のように接触点に名前を付けると、添字1つで引けるようになる。

名前は「どの部品どうしが触れたか」で作る。

csharp
// 基準面の軸と符号 / 入射面の軸と符号 / 頂点の番号 を1つの int に詰める
public readonly struct ContactId
{
    public readonly int Value;   // refAxis(2bit) refSign(1) incAxis(2) incSign(1) vertex(3)
}

山場は Sat.cs のクリップ。入射面の4頂点には素直に番号を振れるが、クリップで生まれる交点は元の頂点ではない。Box2D はここで「どの面で切られたか」を ID に混ぜている。

  頂点そのまま     → (入射面の頂点番号)
  クリップの交点   → (切った面の番号) を混ぜる

段階的に進めるのを勧める。

  1. まず球・カプセル・平面(点が1つしか出ない判定)に ID を振る。ここは自明
  2. 次に箱と平面(BoxPlane)。角の番号がそのまま使える
  3. 最後に箱と箱(Sat.BoxBox)。クリップを ID 付きに書き換える

各段で距離での照合と結果を突き合わせると、どこで食い違ったかが分かる。自己チェックに「ID 照合と距離照合で当たり率が一致する」を1項目足すとよい。

やってみると分かるのは、正確さより配管の量。ID を運ぶために ManifoldPoint / ContactManifold / Sat / Collision3D の4ファイルが書き換わる——判定に一切触らない位置照合を選んだ理由がここで腑に落ちる。

検証の途中で分かったこと

1. 段の順番が Day 43 から間違っていた(要点4)。

摩擦を入れて坂に箱を置いたら、μ = 0.9 でも 1.5 秒で 11cm 滑った。速度は 0 なのに位置だけが毎フレーム 1.22mm 動く——計算したら g·dt²·sinθ = 9.81 × (1/60)² × 0.447 = 1.218mm でぴったり一致した。位置を解く前の速度で進めていたのが原因で、位置の積分を速度の解決の後ろへ動かして直した。滑りは 2.4mm になり、そこから増えない。

この不具合は摩擦が無ければ絵に出ない。Day 46 までは坂に乗ったものが滑り落ちるのが正しかったので、余分に 1.2mm 滑っていることに気づきようがなかった。Day 46 の逆慣性テンソルと同じ形で、機能を足すと前の日の抜けが見える。

2. 蓄積クランプ単体では、柱の沈み方が1ビットも変わらなかった(要点1)。

「蓄積クランプのほうが沈まない」を確かめる自己チェックを書いたら、2つの世界が完全に同じ数字を出した(2.46257m)。柱がゆっくり落ち着くだけの場面では λ が常に正なので、負の補正を出す機会が来ない——素朴版とまったく同じ道を通る。

チェックの主張を「同じ結果になること」へ書き換えたうえで、負の補正が出せることは別の場面で確かめるようにした——落ち着いた柱から重力を消すと、持ち越したインパルスが全部余分になる。蓄積クランプなら合計を 0 まで減らせる(1.64 → 0.00 N·s)。

「効くはず」と思って書いたチェックが通らなかったときに、しきい値を緩めるのではなく主張を確かめ直す——今日はそれが2回あった。

3. 素朴なクランプに温存を載せると発散する(要点2)。

つまみを2つ用意したので、素朴 + 温存の組み合わせも作れてしまう。これは必ず壊れる——1ステップに溜まる量が 0 以上なので、持ち越しを続けると単調に増え、置いた箱が数秒後に跳ね上がる。WarmStartActive という読み取り専用のプロパティを足して、蓄積を切ったら温存も止まるようにした。Erin Catto の資料でこの2つがいつも一組で説明される理由が、実装して初めて分かった。

4. Day 43・44 の自己チェックが5項目、嘘になった。

「反復1周だと沈む」「順番に解くと床の箱1つでも揺れが止まらない」「順番に解くと崩れる」「段数ぶん沈む」——どれも Day 47 の機能で解消したので、主張のほうを書き直した。とくに Day 44 の「ただし段数ぶん沈む(蓄積インパルスが無いから。Day 47 の宿題)」は、3日前の自分が今日への宿題として書いたもので、それが片付いた形になる。

しきい値をいじって延命させないことが今日いちばんの教訓。Day 44 で1度しきい値を緩めているが(3.0 → 2.0)、それは「数字が良くなったが主張は生きている」場合の話で、今回のように主張そのものが古くなったら書き換えるのが正しい。

5. 眠りは位置の補正も止めないといけない。

眠った体の逆質量を 0 にするのを、速度の解決だけに入れて位置の補正に入れ忘れた。すると眠っている体が位置の補正でじりじり動き、眠っているのに沈んでいくという妙な状態になった。SolverInverseMass という1つのプロパティを通すようにして塞いだ——「一時的に無限に重い」を元の値を壊さずに表す1枚があると、入れ忘れる場所が減る。

6. 摩擦を入れたら、地形のすり抜けが減った。

Day 46 の自己チェックで「200 体中1体がすり抜ける」と書いた。今日 60 体で測り直したら、Day 46 が5体・Day 47 が3体(どちらも端から落ちたもので、すり抜けではない)。段の順番を変えると最初の接触が1フレーム遅れるので増えると予想していたが、摩擦で速度が落ちるぶんのほうが効いた。連続衝突判定(要点7)が要ることに変わりはない。
