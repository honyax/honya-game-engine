ガード付きの case は、具体的なものほど上に置かなければならない。これは C# の仕様であって間違いではないのだが、「正しさが行の位置に宿っている」状態は、コンパイラも警告してくれないし、テストも書きにくい。実際 Day 39 以降の reference には、毎日のように「この塊はいちばん上に置くこと」というコメントが足されている。

表にすると、この危うさが構造ごと消える。

csharp
// 引くのは「今のページの、このキー」。完全一致なので、並び順はどこにも効かない
if (_menu.TryInvoke(key))
{
    return;
}

2つ目は「キーを書かせない」こと。

Add にキーの引数は無い。登録した順に F2, F3, … F12, 1, 2, … 9, 0 が割り当たる。

csharp
_entries.Add(new Entry(Slots[_entries.Count], name, effect, action));

書かせると必ず重複する。しかも重複しても動いてしまう——先に見つかったほうが実行され、後ろのほうは押しても何も起きない。昨日までの switch で起きていたのと同じ壊れ方で、「押しても何も起きないキー」は原因を探すのがいちばん面倒な種類だ。順番で決まるなら重複はあり得ないし、割り当ては一覧を読めば分かる。

3つ目は「一覧を手で書かない」こと。

昨日まで、起動時のコンソールには 140 行のキー一覧が手で並んでいた。その日の到達点の case も、" Shift+F:摩擦 ON/OFF Alt+F:蓄積インパルス …" のような行を自分で書いて出していた。どちらも項目を足すたびに書き足す必要があり、書き忘れても動く。だから必ずずれていく。

実際、消す前の一覧を読むと Day 40 の行は Ctrl+Alt+F11 で終わっていて、Ctrl+Alt+F12(シーンの自己チェック)が抜けていた。8日間、誰にも気づかれずに抜けていたわけで、これが手書きの一覧の実力になる。今日からは DebugMenu.PrintIndex() と PrintCurrent() が表から起こすので、ずれようが無い。

事前に読む資料

  • Day 40 の Demo/FeatureToggles.cs(このリポジトリ)— 今日の下敷き。「表は状態を持たない」「本当の状態は向こうにあり、ここが持つのは読み書きの手順だけ」という判断をそのまま引き継ぐ
  • switch ステートメント — C# リファレンス— case は上から順に照合される、when を付けると評価順が意味を持つ、の一次資料
  • Command パターン(Game Programming Patterns)— 入力を「キー → 処理」の対応表にする話。今日やっているのはこの最小形
  • テーブル駆動(table-driven)という言い方も同じものを指す。「分岐で書けることを、データで書く」——switch を消すのが目的ではなく、分岐の構造そのものをデータにして、検算できるようにするのが目的

理論の要点

1. なぜ 17 日で使い切ったのか — 数えてみる

修飾キーは Ctrl / Shift / Alt の3つ。組み合わせは 2³ − 1 = 7 通り (全部押さないのは「素のキー」なので別枠)。これにキーの束を掛けると席の数になる。

束キー数7 通りを掛けて
ファンクションキー1284
数字キー1070

理屈のうえでは 154 席あるので、159 個はそもそも入らない。実際には Alt+F4(窓が閉じる)を避け、Day 24 の Shift+F3 のような先客もあり、F4 を飛ばした日もあったので、使えたのはもっと少ない。

一方ページにすると、1ページ 21 席(F2〜F12 の 11 と数字 10)。足りなくなったらページを1枚足せばよく、上限は無い。掛け算だったものが足し算になった、というのが構造として起きたこと。

昨日までのやり方が悪かったわけではない。Day 31 の時点でスイッチは 9 個しかなく、Shift+1〜Shift+8 で足りていた。足りているうちは表にする理由が無い——表のほうが、そのときは行数が多い。17 日積んではじめて元が取れる、という順番になっている。

2. when ガードの罠 — 「一致」ではなく「最初に成立したもの」

C# の switch 文は、上から順にそれぞれの case を評価して、最初に成立したものを実行する。when ガードが付いていても同じで、「いちばん具体的なもの」を選んではくれない。

csharp
switch (key)
{
    case Key.F1 when ctrl:               // ← Ctrl+Shift+Alt+F1 でも成立する
        RunSsaoCheck();
        break;

    case Key.F1 when ctrl && shift && alt:   // ← ここには永遠に来ない
        RunRigidBodyCheck();
        break;
}

これが警告されないのが厄介なところ。case 1: を2回書けば「到達できない」とコンパイラが教えてくれるが、when が付いた瞬間、成立するかどうかは実行時にしか分からないので、コンパイラは黙る。

昨日までの reference が採っていた守り方は2つあった。

  1. 具体的なものほど上に置く(Day 39 から毎日コメントで念押ししていた)
  2. 否定を書き足す — case Key.F when ctrl && !shift && !alt:

2 のほうは効くのだが、書き忘れても半分は動くのが質が悪い。Ctrl+F は正しく動き、Ctrl+Shift+F を押したときだけ間違ったほうが走る。

表にすると、この話が丸ごと無くなる。TryInvoke が引くのは「今のページの、このキー」で、キーは席の順番で決まっていて重複し得ない。「どちらが先か」を考える場所が、コードのどこにも無い。

3. モードには必ず表示が要る

ページ切り替えはモーダルな入力だ。同じ F3 が、いま開いているページによって「SSAO の半径」にも「反発係数」にもなる。

モーダルな入力には決まった弱点がある。いまどのモードに居るかが分からなくなる。vi の insert / normal がそうであるように、これは「憶えておく」で解決すべきものではなく、表示で解決すべきものになる。

だから今日は3か所から出している。

どこ何を出すかなぜ
HUD の1行メニュー[12/16]:剛体力学 12項目絵からは1ピクセルも読めないのに、キーの意味が丸ごと入れ替わる
ページを切り替えた瞬間そのページの割り当て一覧送った先に何があるかを、押す前に知りたい
Ctrl+F1ページの目次16 枚あると順送りだけでは探せない

HUD の行がいちばん効く。これが無いと、「F3 を押したのに半径が変わらない」の原因が「別のページを開いていた」なのか「そもそも壊れている」なのかが切り分けられない。Day 46 のブロードフェーズで「絵が変わらないものは数字を出す」と書いたのと同じ判断になる。

4. 閉じた状態を1つ挟む — 素のキーを取り上げない

Index は -1 を「閉じている」に使っている。ページを 0 番から数えて、輪の中に閉じた状態を1つ挟んである。

csharp
public void Next() => Index = Index + 1 >= _pages.Count ? -1 : Index + 1;

これには2つ理由がある。

1つ目は、素のキーを取り上げないため。F5 のシェーダ再読込も、数字キーのスプライト数も、Space の一時停止も、Day 14 から手が憶えている。メニューが常に F2〜F12 を持っていると、これらが押せなくなる。開いている間だけ席として借りて、閉じれば元に戻る、という形にした。

2つ目は、閉じ方を別のキーにしないため。Esc で閉じる作りにすると、「Esc で閉じる」を憶えていないと戻れない。輪に閉じた状態が挟まっていれば、F1 を押し続ければいつか必ず元に戻る。出口を1つのキーに集めておくのは、デバッグ用の道具では特に効く——道具の使い方でつまずくと、本当に見たいものから遠ざかる。

F1 だけはメニューが常に取っているのも同じ理由になる。どのページに居ても F1 は必ずページ送りなので、開き方も閉じ方も1つで済む。自己チェック(要点7)がこの不可侵を確かめている。

5. 表は「値を持たない」— Day 40 からの引き継ぎ

DebugMenu は ON/OFF の状態を1つも持っていない。持っているのはAction(そこへの書き込み手順)だけで、本当の状態は_ssao.Enabled や Physics.FrictionEnabled のほうにある。

これは Day 40 の FeatureToggles がした判断とまったく同じで、理由も同じ。二重に持つと必ずずれる。キー以外の経路——たとえばCtrl+F1 の「決めの構図」がフラグをまとめて倒す——で触られた瞬間、表の言う ON と絵の中の OFF が食い違う。

「状態の置き場所は1つ」は Day 22 のコンポーネント設計から続いている判断で、Day 40、そして今日と、層が変わっても同じ形で出てくる。

今日の差分を数えると、Program.cs は 20,639 行から 20,726 行と、むしろ少し増える。OnKeyDown から出ていった 1990 行が BuildDebugMenu に入っただけで、そこにラムダの包み(159 個 × 3 行)と DebugMenu.cs の 279 行が乗るからだ。

行数を減らすのは今日の目的ではない。変わったのは形のほうになる。

7. 表は検算できる — 自己チェックが 15 項目に化ける

昨日までの switch は、検算のしようが無かった。「Ctrl+Shift+Alt+F5 を押したら反復回数が変わる」を確かめるには押すしかなく、押さないと分からないなら、押し忘れたところは壊れたままになる。

表になると、押さずに分かることが一気に増える。

確かめることなぜ大事か
159 項目すべて入っている移し忘れが1つあっても絵は出る
どのページも席(21)に収まっている溢れると登録時に例外になる(黙って落とさない)
同じページにキーの重複が無い重複しても動いてしまう。押しても効かないキーになる
F1 はどのページも取っていない取られると、そのページから出られなくなる
名前と効果がすべて埋まっている一覧が読めないと、ページを開いた意味が無い
閉じている間は何も引き当てない素のキーを取り上げていないことの確認
送り続けると閉じる / 戻ると最後のページ押し続ければ元に戻ることの確認

とくに F1 の不可侵は、押して確かめようとすると気づきにくい種類のものになる。うっかり F1 を席に入れてしまったページは、そのページを開くまで何も起きず、開いた瞬間に出られなくなる。起動時に分かる間違いなので、起動時に落としておきたい。

引き当ての確認だけは、_menu ではなく使い捨ての DebugMenu を作ってやっている。本物の表は SSAO を切ったりデモを出したりするので、チェックが世界を書き換えるのは筋が悪い。

課題1(易): 純粋な ON/OFF を Toggle にまとめる

159 項目のうち 34 個は、まったく同じ形をしている。

csharp
page.Add("摩擦", "切ると坂の箱が全部滑り出す", () =>
{
    Physics.FrictionEnabled = !Physics.FrictionEnabled;
    WakeAllBodies();

Page に Toggle を足して、文言のほうを表に預ける。

csharp
public Page Toggle(string name, string onText, string offText, Func<bool> get, Action<bool> set)
{
    return Add(name, $"ON:{onText} / OFF:{offText}", () =>
    {
        bool next = !get();
        set(next);
        Console.WriteLine($"{name}: {(next ? "ON" : "OFF")}({(next ? onText : offText)})");
    });
}

呼ぶ側はこうなる。

csharp
page.Toggle("摩擦",
    "クーロン摩擦。上限は μ × 押し付けている強さ",
    "Day 46 までの世界。坂の箱が全部滑り出す",
    () => Physics.FrictionEnabled,
    value => { Physics.FrictionEnabled = value; WakeAllBodies(); });

確かめること: 34 個を移して、ON/OFF の文言が入れ替わっていないこと。Get と Set を取り違えると押すたびに同じ側へ倒れるので、自己チェックに「2回押すと元に戻る」を足しておくと早く気づける。

FeatureToggles.Feature が Get / Set を持っているのと同じ形で、Day 40 の判断がもう一段先まで効くのが見どころになる。

課題2(中): ページ番号で飛べるようにする

16 枚を順送りするのはまだるっこしい。目次から番号で飛ぶを足す。

素直なのは「Ctrl+F1 で目次を出したあと、次に押した数字キーをページ番号として読む」形になるが、これは2打鍵のモードを1つ増やすことになる。要点3のとおり、モードを増やすなら表示も増やさなければならない——「いま番号待ちです」が HUD に出ていないと、数字キーが効かない理由が分からなくなる。

もう1つの手は Ctrl + 数字キーをページ番号に使う形。修飾キーを1つ復活させることになるが、メニュー自身の操作は F1 に集めてあるので、Ctrl+1〜Ctrl+0 を「ページ 1〜10 へ」に当てても今日の話とは衝突しない。

確かめること: どちらを選んでも、「F1 を押し続ければ必ず閉じる」が壊れていないこと。出口が1つであることは、道具として譲れない性質になっている(要点4)。

課題3(難): 割り当てをファイルから読む

BuildDebugMenu は 1,960 行ある。中身はほとんどデータなので、JSON に出して起動時に読むようにできる。

json
{
  "pages": [
    {
      "name": "摩擦とソルバ",
      "summary": "Day 47。クーロン摩擦・Sequential Impulses・眠り",
      "entries": [
        { "name": "摩擦", "effect": "切ると坂の箱が全部滑り出す", "action": "toggle:Physics.FrictionEnabled" }
      ]
    }
  ]
}

ここで必ず突き当たる壁がある。Action はコードなので、JSON には入らない。つまり「action の文字列から実際の処理を引く表」がどこかに要る——結局 Program.cs の中に {"toggle:Physics.FrictionEnabled", () => ...} の辞書が生まれて、同じ量のコードが名前付きで残る。

だから課題としては「やってみて、割に合わないことを確かめる」ほうに値打ちがある。割に合うのは次のどちらかになったときで、そこまでは今の形が正しい。

  • 並び順や名前だけを外に出す(処理はコードのまま、順番と文言だけ JSON)——これは割に合う
  • スクリプト言語を積む(Lua など)——処理そのものを外に出せるが、エンジンに言語処理系が1つ増える

Day 24 でシーンを JSON にしたときは、シーンがデータしか持っていなかったから素直に外へ出せた。入力の割り当てが出せないのは、処理を持っているからになる。「何がデータで、何がコードか」の線引きが、同じリポジトリで2回目に出てくる場面になっている。
