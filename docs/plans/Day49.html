今日いちばん大事な3つ

1つ目はビルボード。粒はただの点だが、画面には四角い絵として出したい。そこでカメラの右と上で四角形を張る。

csharp
Vector3 axisX = ((_cameraRight * cos) + (_cameraUp * sin)) * half;
Vector3 axisY = ((_cameraUp * cos) - (_cameraRight * sin)) * half;

カメラの右と上はビュー行列から取れる。回転部分は正規直交なので転置が逆行列で、ビュー空間の (1,0,0) に対応するワールドのベクトルは1列目——(M11, M21, M31) がそれになる。cos / sin は粒ごとの回転で、回した結果を頂点の位置に焼き込んでしまうのでシェーダは何も知らなくてよい。

2つ目は混ぜ方。同じ粒が、混ぜ方1つで火にも煙にもなる。

csharp
// 加算    重なるほど明るい。暗いところでしか効かない
glBlendFunc(GL_SRC_ALPHA, GL_ONE);

// アルファ 重ねても明るくならない。順番が要る
glBlendFunc(GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA);

加算は dst + src·a なので、背景が既に明るいと何も起きない。花火が夜にしか上がらないのと同じ話で、演出ではなく前提条件になる。今日のデモが空を消しているのはこのため(要点2)。

3つ目は深度を書かないこと。

csharp
_gl.Enable(EnableCap.DepthTest);   // 読む: 箱の裏に回った粒は隠れてほしい
_gl.DepthMask(DepthWrite);         // 書かない: 既定は false

半透明が深度を書くと、後から描く粒が深度テストで落ちる——手前の粒が壁になって、その裏の粒が四角く消える。F6 でわざと ON にすると一目で分かる。

  • Day 43 の計画書 要点1(セミインプリシット積分)— 粒の運動はこれと同じ。速度を先に進めてから位置に足す

理論の要点

1. ビルボード — カメラの基底で四角形を張る

粒は点だが、画面には絵として出したい。一番素直なのは常にカメラを向いた四角形を置くことで、これをビルボードと呼ぶ。

四隅は中心からカメラの右と上へ半分ずつずらせば作れる。

        center + (-X + Y) ┌──────┐ center + (X + Y)
                          │      │
        center + (-X - Y) └──────┘ center + (X - Y)

カメラの右と上をどこから取るか、が唯一の技術的な点になる。ビュー行列 V はワールドからビューへの変換で、その回転部分 R は正規直交。正規直交行列は転置が逆行列なので、ビュー空間の (1,0,0) に戻るワールドのベクトルはR の1列目になる。System.Numerics は行ベクトル規約なので、これは (M11, M21, M31)。

csharp
_cameraRight = new Vector3(view.M11, view.M21, view.M31);
_cameraUp = new Vector3(view.M12, view.M22, view.M32);

自己チェックで確かめているのはここ(要点7)。長さが1で、直交していて、外積が奥行き軸に一致すること——どれか1つでも崩れると四角形が歪むか裏を向く。

CPU で四隅を作るのは Day 18 と同じ判断になる。頂点シェーダで展開する手(インスタンシングやジオメトリシェーダ)もあるが、そちらは「粒ごとの uniform」か「追加の頂点属性」が要る。CPU で焼き込めば uniform はフレームに1本で済み、1万粒でもドローコールは1回のまま。

代償は転送量で、1粒あたり4頂点 × 24 バイト = 96 バイト。8000 粒なら毎フレーム 750KB を送ることになる。そこが効いてくるのが GPU パーティクルで、教養編 Day 57 のコンピュートシェーダに繋がる。

2. 加算合成は「暗いところ」でしか効かない

ブレンドは 結果 = src × S + dst × D の形で、S と D を選ぶのが glBlendFunc。

混ぜ方SD式性格
加算SrcAlphaOnedst + src·a重なるほど明るい。順番不問
アルファSrcAlphaOneMinusSrcAlphasrc·a + dst·(1-a)重ねても明るくならない。順番が要る
事前乗算OneOneMinusSrcAlphasrc + dst·(1-a)1式で両方。RGB に A を掛けておく

加算の式をよく見ると、dst に足すだけで引く手段が無い。つまり dst が既に明るいと、何を足しても変わらない。

これは理屈としては当たり前なのだが、実際にやると必ず一度は引っかかる。今日のデモも、最初は炎が1粒も見えなかった——空(スカイボックス)が白く、その前で足し算をしていたため。

csharp
// ShowParticleDemo。空を消すのは演出ではなく前提条件
_env.SkyboxVisible = false;

花火が夜にしか上がらないのと同じ話になる。加算を使うなら背景を暗くする、あるいは明るい背景ではアルファ合成に切り替える、のどちらかしかない。

事前乗算はこの2つを1つの式に畳む手になる。RGB にあらかじめ A を掛けておくと、a = 0 の粒は src + dst で加算そのもの、a = 1 の粒は src + 0 でアルファ合成そのものになる。1回のドローコールの中で火と煙を混ぜられるのが値打ちで、今日は選択肢として置くだけだが、Day 50 のエフェクト応用で効いてくる。

3. 粒が見えないときに疑う3つ

要点2の背景の話も含めて、「描けているのに出ない」には決まった原因がある。今日はこの3つを順に踏んだので、順番に書いておく。

1つ目: 背景が明るい(要点2)。加算合成なら空を消す。

2つ目: 1粒が小さい。これがいちばん引っかかった。

テクスチャの減衰が (1-r)² なので、四角形の中で実効的な不透明度はかなり低い。さらに寿命に沿ってアルファが 0 へ落ちるので、小さい粒はいくら数を増やしても濃さが積み上がらない。

  0.5m の粒を 200 個   →  画面には何も出ない
  1.0m の粒を 130 個   →  はっきり煙に見える

画面に出るかどうかを決めているのは数ではなく1粒の面積になる。煙や埃のように「もや」を出したいときは、粒を大きくして数を減らすのが正しい。

3つ目: 二重に薄れている。

コマ送りのテクスチャが最後のコマで透明になり、かつ色のカーブも EndColor のアルファを 0 にしていると、両方が掛かる。寿命の後半がまるごと消えることになり、「煙が続かない」という形で出る。

csharp
// ParticleTextures.CreateSmokeFlipbook。0 まで落とさない
float fade = 1.0f - (0.55f * t);

コマ送りが持つのは形、消え方は色のカーブが持つ、と分けておく。どちらか一方に寄せないと、片方を調整したときにもう片方が効いて訳が分からなくなる。

4. 深度は読むが書かない

半透明を描くときの原則になる。

csharp
_gl.Enable(EnableCap.DepthTest);   // 読む
_gl.DepthMask(false);              // 書かない

読むのは、不透明な床や箱の裏に回った粒に隠れてほしいから。深度テストを切ると、粒が壁を突き抜けて手前に出てしまう。

書かないのは、半透明が深度を書くと後から描く粒が落ちるから。手前の粒が「壁」になって、その裏の粒が四角く消える——四角いのは、消えているのがビルボードの矩形そのものだからになる。

F6 で ON にすると実演できる。焚き火の筋書きでいちばん分かりやすく、炎が四角い穴だらけになる。

ここは「借りたら返す」も要点。End() で DepthMask(true) に戻し忘れると、次のフレームの不透明な描画が深度を書かなくなり、前後関係が崩れる。しかも症状はパーティクルではなく床や箱のほうに出るので、原因を探すのが難しい。Day 18 のスプライトバッチから続いている作法がここでも効く。

5. 並べ替えは「アルファのときだけ」要る

加算合成は足し算なので、順番を変えても結果が同じになる(交換法則)。アルファ合成はそうではない。src·a + dst·(1-a) はdst を上書きしていく形なので、奥から手前へ描かないと正しくならない。

しかも ParticleEmitter は死んだ粒を末尾と入れ替えて詰めるので(要点6)、配列の順番は奥行きと何の関係も無い。だから描く直前に並べ替える。

csharp
// 負の距離にして昇順に並べると、そのまま「遠い順」になる
_depths[i] = -Vector3.DistanceSquared(alive[i].Position, _cameraPosition);
Array.Sort(_depths, _order, 0, alive.Length);

平方根を取らないのは、大小の比較にしか使わないため(平方根は単調増加なので、取っても順序は変わらない)。

代償は HUD に出る。並替:ON 0.42ms のように、掛かった時間をそのまま出してある——アルファに切り替えた瞬間に増えるので、出していないと気づけない。8000 粒だと数 ms 掛かるので、負荷の筋書きでは並べ替えを切ってある。

6. プールと swap-remove — 順番を捨てて O(1) を買う

粒は毎フレーム生まれて死ぬ。毎回 new しないのが大前提で、配列を1本持って「生きている数」だけを動かす。

死んだ粒は末尾の生きた粒と入れ替えて数を1つ減らす。

csharp
if (particle.Age >= particle.Lifetime)
{
    Count--;
    _particles[i] = _particles[Count];
    continue;   // 添字を進めない。入れ替えた先はまだ進めていない
}

詰め直しが O(1) で済み、生きている粒は常に配列の先頭から連続して並ぶ。描く側は Alive をそのまま舐めればよい。

代償は順番が保たれないことで、これが要点5の並べ替えに繋がっている。continue で添字を進めないのを忘れると、入れ替わってきた粒が1フレーム飛ばされる——症状は「たまに粒が1フレーム止まる」で、まず気づけない。

7. 撒く向きは「一様」が難しい

球面上や円錐の中に一様に向きを撒くのは、素朴にやると必ず偏る。

球面: 緯度と経度を両方一様に振ると、極に密集する。地球儀の目盛りが極で詰まっているのと同じで、緯度が同じ幅でも、そこが表す面積は極に近いほど狭い。正しくは高さ(cos θ)を一様に振る(アルキメデスの定理)。

csharp
float z = ((float)_random.NextDouble() * 2.0f) - 1.0f;   // 高さを一様に
float r = MathF.Sqrt(MathF.Max(0.0f, 1.0f - (z * z)));

円錐: 角度 θ を一様に振ると軸の近くに密集する。同じ理由になる。cos θ を [cos θmax, 1] で一様に振るのが正しい。

円盤: 半径を一様に振ると中心に寄る。面積は半径の2乗に比例するので、√u で振る。

csharp
float radius = Radius * MathF.Sqrt((float)_random.NextDouble());

どれも「一様」がどの測度で一様かという話で、自己チェックでは統計量で確かめている——円錐なら平均 cos が (1 + cos θmax) / 2 に一致すること、円盤なら半径 1/√2 の内側にちょうど半分入ること。偏っていても絵はそれらしく見えるので、数で見るしかない。

8. 端数を持ち越す — fps で絵が変わらないために

毎秒 200 個を 60fps で撒くと、1フレームあたり 3.33 個。切り捨てると毎秒 180 個にしかならず、144fps では 1.39 → 1 で毎秒 144 個。fps が変わると絵が変わることになる。

csharp
_carry += EmitRate * deltaSeconds;
int toSpawn = (int)_carry;
_carry -= toSpawn;

Day 19 の固定ステップが「溜まった時間を持ち越す」のとまったく同じ形になる。自己チェックでは 60fps と 144fps で 1 秒ぶん回し、どちらも 200 個になることを確かめている。

「進める」と「描く」を分けた

ParticleEmitter は GL を1行も触らない。逆に ParticleRenderer は粒を1つも持たない。この分け方は PhysicsWorld と RenderPhysics の関係と同じで、理由も同じになる——片方だけをテストしたい。

実際、今日の自己チェック 27 項目のうち 20 項目は窓を開かずに走る。端数の持ち越しも、円錐の分布も、抵抗の指数減衰も、ParticleEmitter が GL を知らないからこそ数で確かめられる。

矢印が片方向だけなのが要点になる。ParticleEmitter は Camera も Texture も GL も知らない。だから Day 57 で GPU へ移すときに置き換わるのは右半分だけで、設定の意味(寿命・重力・色のカーブ)はそのまま持っていける。

粒が1つ描かれるまで

並べ替えが Append の手前にしかないのが構造として大事なところ。ParticleEmitter 側は順番を保証しない(swap-remove で壊れる)ので、順番が要るのは描く直前だけと決めてある。ここを逆にして「常に順番を保つプール」にすると、死んだ粒を消すたびに O(n) の詰め直しが要る——加算合成では必要ない仕事を、全部の筋書きに払わせることになる。

状態を借りて返す

ParticleRenderer.Begin は GL の状態を4つ変える。

状態何にするか戻すか
Blend有効 + ApplyBlend()End で無効に戻す
DepthTest有効戻さない(不透明の描画も有効のまま使う)
DepthMaskDepthWrite(既定 false)End で true に戻す
CullFace無効戻さない(次の Render3D が自分で設定する)

DepthMask を戻し忘れると症状が向こうに出る。次のフレームの不透明な描画が深度を書かなくなり、床と箱の前後関係が崩れる——パーティクルを疑うところまで辿り着けない種類の壊れ方になる。

「戻すもの」と「戻さないもの」を分けているのは、次に描く人が必ず自分で設定するかどうかで決めている。Render3D は毎フレーム深度テストとカリングを設定し直すので、そこは戻さなくてよい。DepthMask は誰も設定し直さない(既定が true のまま使われている)ので、返す。

絵を数式で作った

ParticleTextures は素材を1枚も使わない。

これは素材を増やさないための判断でもあるが、それ以上にパーティクルの絵は「形」ではなく「減衰の仕方」だということが、作ってみるといちばんよく分かる。中心が明るくて縁へ滑らかに落ちる——それだけで火にも煙にも埃にも見える。

縁を切り立たせないのが唯一にして最大のコツになる。(1 - r) と線形に落とすと粒が円板に見えて重なりが目立ち、(1 - r)² にするだけで「もや」になる。

コマ送りのほうは、形だけを持たせて消え方は持たせないと決めてある(要点3)。最初は最後のコマを透明にしていて、色のカーブの EndColor アルファ 0 と二重に掛かり、寿命の後半がまるごと消えていた。「1つの見た目を2箇所で作らない」は Day 40 の FeatureToggles で「状態の置き場所は1つ」と決めたのと同じ形の判断になる。

今日残した歪み(3つ)

1つ目: 混ぜ方が1パスに1つしか無い。ParticleRenderer.Blend はレンダラ全体の設定なので、同じフレームに加算の炎とアルファの煙を同時に出せない。本当にやるなら「加算のものを全部描く → アルファのものを全部描く」と2パスに分けるか、事前乗算に寄せて1式に畳むことになる。今日は筋書きごとにどちらかを選ぶ形で逃げた。Day 50 で必要になる。

2つ目: 並べ替えが放出口ごと。AppendSorted は Draw の中で呼ばれるので、放出口が2つあるとそれぞれの中でしか並ばない。放出口をまたいだ正しい順序にはならない。今日は同時に出しているのが焚き火(加算・並べ替え不要)だけなので表に出ないが、アルファの放出口を2つ出した日に必ず気づくことになる。

3つ目: カーブが線形しかない。ColorAt も SizeAt も始点と終点の Lerp だけなので、「出た瞬間だけ大きい」「中盤で一番明るい」が作れない。本物のエンジンはここにカーブエディタを持っている。足すなら「制御点の配列 + 線形補間」で十分で、改造課題1にしてある。

改造課題

課題1(易): 色と大きさにカーブを入れる

いまの ColorAt / SizeAt は始点と終点の Lerp だけなので、「出た瞬間だけ大きい」「中盤で一番明るい」が作れない。

制御点の配列を持たせて、区間ごとに線形補間する。

csharp
/// <summary>寿命に沿ったカーブ。制御点は 0〜1 の順に並んでいること。</summary>
internal sealed class ParticleCurve
{
    private readonly (float T, float Value)[] _keys;

    public float Evaluate(float t)
    {
        // 区間を探して線形補間。両端は端の値で止める
    }
}

StartSize / EndSize を SizeCurve に置き換えて、焚き火を (0, 0.1) (0.15, 0.5) (1, 0.05) にすると、火が「ぼっ」と立ち上がるようになる。

確かめること: 制御点が1個・0個でも落ちないこと、t が 0 未満や 1 超でも端で止まること。自己チェックに「両端で止まる」を足しておくと、区間探索の境界がすぐ分かる。

課題2(中): 加算とアルファを1パスで混ぜる

いまは ParticleRenderer.Blend がレンダラ全体の設定なので、炎(加算)と煙(アルファ)を同時に出せない。

事前乗算(ParticleBlend.Premultiplied)に寄せると、1つの式で両方を扱える。

  src + dst·(1-a)    a = 0 なら 加算そのもの
                     a = 1 なら アルファそのもの

ParticleEmitter に「加算寄りか、アルファ寄りか」を 0〜1 で持たせて、ColorAt が返すアルファを掛け分ける。炎の粒はアルファを 0 に寄せ、煙の粒は 1 に寄せる。

確かめること: 焚き火の上に煙を足して、炎が光ったまま、煙が背景を隠すこと。1パスで済んでいるか(HUD の DC: が 1 のまま)も見る。

ここが今日と Day 50 の橋渡しになる。土埃・爆発・トレイルを同じシーンに置くと、混ぜ方の異なる粒が必ず同居することになる。

課題3(難): 更新をコンピュートシェーダへ移す

負荷の筋書きで 更新 が 1ms を超える。8192 粒で 1ms なら、10 万粒なら 12ms でそれだけで 1 フレームを使い切る。

粒の状態(位置・速度・寿命)を SSBO に置いて、更新をコンピュートシェーダでやる。CPU からは「何個描け」しか言わなくなる。

段取りはこうなる。

  1. Particle を GPU 側の構造体に合わせる(std430 のアラインメントに注意)
  2. 更新のシェーダを書く。生死の判定と詰め直しが難所——atomicCounter で生きている数を数えるか、死んだ粒を「大きさ 0」で描く
  3. 描画は glDrawArraysIndirect にして、描く数も GPU が決める
  4. ビルボードは頂点シェーダへ移す(CPU で四隅を作れなくなるため)

3 と 4 まで行くと「CPU がドローコールの中身を知らない」形になり、これは教養編 Day 65 の GPU 駆動レンダリングと同じ発想になる。

確かめること: 10 万粒で 更新 が 0 に近づくこと。そして絵が CPU 版と同じに見えること——乱数の作り方が違うので粒の並びは一致しないが、「釣り合いの数」と見た目の濃さは合うはず。

手を出す前に読む: 教養編 Day 57(コンピュートシェーダ入門)。そこで GPGPU の実行モデル(ワークグループ・共有メモリ)を通してからのほうが早い。

動作確認済み環境

  • Windows 11 / .NET 10 / NVIDIA GeForce RTX 3070 / OpenGL 3.3

とくに強いのは次の4つ。

  • 60fps と 144fps で同じ数 — 端数を切り捨てていると 200 個が 180 個と 144 個に割れる。絵では気づけないが、数なら一発で出る
  • 円錐の平均 cos が理論値と一致 — 実測 0.9699 / 理論 0.9698。角度を一様に振ると軸寄りに偏り、ここが 0.980 まで上がる。偏っていてもそれらしく見えるので、数で見るしかない
  • 円盤の半径 1/√2 の内側がちょうど半分 — 実測 50.2%。半径を一様に振ると 70% ほどになり、土埃が中心に固まる
  • 抵抗で逆走しない — (1 - Drag·dt) にしているとDrag=20, dt=0.5 で速度が -90 になり、粒が逆向きに吹き飛ぶ。dt が跳ねたフレームで一度でも起きると目に見える

検証の途中で分かったこと

1. 「描けているのに見えない」を3回踏んだ(要点2・3)。

最初は炎が1粒も出なかった。ParticleCount も DrawCallCount も正しく、粒の座標をクリップ空間まで出しても画面の中央に居る。原因は順に3つあった。

症状原因直し方
炎が1粒も見えない空が白い。加算は明るい背景では何も足せないデモで SkyboxVisible = false
炎が箱に埋まっている中央の箱が y = -0.5〜1.0 を占めていた放出口を天面(y = 1.0)へ
煙が出ない1粒が小さい。0.5m を 200 個出しても濃さが積み上がらない1.0m → 3.0m に

切り分けは「真っ赤・不透明・3m」に振ってみるのが早かった。それで出るなら経路は生きていて、あとは見た目の話でしかない。

2. コマ送りと色のカーブが二重にフェードしていた(要点3)。

コマ送りの最後のコマを透明にし、かつ EndColor のアルファを 0 にしていたので、寿命の後半がまるごと消えていた。コマ送りが持つのは形、消え方は色のカーブが持つと分けて直した。

「1つの見た目を2箇所で作らない」は Day 40 で「状態の置き場所は1つ」と決めたのと同じ形の判断になる。

3. 500fps 出ているので、フレーム数で待つと足りない。

検証中、決まったフレーム数でスクリーンショットを撮っていたら、寿命 3 秒の煙が育たなかった。この構成は 400〜600fps 出るので、400 フレームでも 1 秒未満になる。時間で待つように直したら、粒の数が理論値(放出 × 寿命)にぴたりと合った。

GameLoop の固定ステップ(Day 19)は物理を守っているが、パーティクルは可変 dt 側に置いてあるので、この速さで回っている。そのぶん端数の持ち越し(要点8)が効いているのが、実測 200 個で確かめられる。
