今日いちばん大事な3つ

1つ目はソフトパーティクル。粒はカメラを向いた四角形なので、床と交わったところに直線の切り口が出る。これが「板が地面に刺さっている」ように見える正体になる。

glsl
float sceneDistance    = LinearizeDepth(texture(uSceneDepth, screenUv).r);
float particleDistance = LinearizeDepth(gl_FragCoord.z);

return clamp((sceneDistance - particleDistance) / uSoftFade, 0.0, 1.0);

手前にある面に近い画素ほど薄くする。それだけで交線が消える。薄めるのはアルファだけで、RGB を薄めるとアルファ合成の土埃が黒ずむ(要点1)。

2つ目は「読むために写す」。上の uSceneDepth は、いま描き込んでいるフレームバッファの深度そのものではない。

csharp
_post.CaptureDepth();   // glBlitFramebuffer で深度だけコピー
_particles.SetSceneDepth(_post.SceneDepth, near, far, width, height);

挿さっているテクスチャを同じ描画で読むのはフィードバックループで、OpenGL では結果が未定義になる。しかもエラーは出ない——ドライバによっては動いてしまうので、いちばん気づきにくい種類の間違いになる(要点3)。

3つ目はリングバッファ。トレイルは節を順に繋いでリボンを張るので、Day 49 の swap-remove(死んだ粒を末尾と入れ替える)が使えない。

csharp
// 粒: 順番が壊れてよいので、末尾と入れ替えて O(1)
_particles[i] = _particles[--Count];

// 節: 順番が命なので、いちばん古いものを指す添字を進めて O(1)
_start = (_start + 1) % _points.Length;

同じ「詰め直しを O(1) で」という目的でも、順番を保つという制約が1つ増えるだけで答えが別のものになる(要点4)。

理論の要点

1. ソフトパーティクル — 手前の面に近い画素を薄くする

粒はカメラを向いた四角形なので、床と斜めに交わる。交わったところは四角形と平面の交線——つまり直線になり、「もやもやした煙」の中に不自然にまっすぐな縁が現れる。これがパーティクルが板だと分かってしまう瞬間で、土埃・霧・煙のように地面に接するものでは必ず出る。

直し方は拍子抜けするほど単純で、その画素の奥にある不透明な面までの距離を測り、近いほど薄くする。

  fade = clamp((面までの距離 − 粒までの距離) / フェード距離, 0, 1)

交線の上では両者が一致するので fade = 0、つまりちょうど交わる線が消える。そこから離れるにつれて 1 に戻るので、境目がぼやけて溶ける。

薄めるのはアルファだけにする。RGB を薄めると、加算合成では同じ結果になるが(dst + src·a の src を縮めても a を縮めても同じ)、アルファ合成では黒へ寄ることになって土埃が床の手前で黒ずむ。アルファだけなら、どちらの混ぜ方でも「消える」に落ちる。

フェード距離見え方
0.1m切り口が消えきらない。よく見ると線が残る
0.35m(既定)交線が溶ける。粒の存在感はそのまま
0.8m床の近くが全体に薄い。「地面から離れたところにしか埃が無い」
2.0m粒がほとんど見えない。カメラから 2m 以内の面がすべて消しゴムになる

粒の大きさと同じくらいが目安になる。土埃の直径が 0.7m なら 0.3〜0.5m。

2. 深度バッファは線形ではない

上の式は距離の引き算なので、深度バッファの値をそのまま引いてはいけない。

射影行列は z を 1/z に近い形へ潰して深度バッファへ書く。手前に精度を厚く配るための仕掛けで、そのぶん値の差が距離の差に比例しない。

  near = 0.1、far = 100 のとき
    深度 0.0  →  0.100m
    深度 0.5  →  0.200m     ← 距離の真ん中(50m)ではない
    深度 0.9  →  0.991m
    深度 1.0  →  100.0m

深度の半分がもう near のすぐ先、というのが実感しにくいところで、自己チェックにそのまま項目として入れてある。

戻す式はこれ1本。

glsl
float LinearizeDepth(float depth01)
{
    float ndc = depth01 * 2.0 - 1.0;
    return 2.0 * near * far / (far + near - ndc * (far - near));
}

同じ式を C# 側にも置いてある(ParticleRenderer.LinearizeDepth)。GPU の中身は読めないので、片方を CPU に持ってきて数で確かめるのが唯一の手になる。2箇所に同じ式があるのは重複だが、「シェーダの式が合っているか」を確かめる方法が他に無い以上、これは払う価値のある重複になる。

遠くでは効かないのも覚えておく。深度の精度が遠方でスカスカなので、カメラから 50m 先の煙に細かいフェードは掛からない。気になるなら深度を 32bit float にするか、ビュー空間の z を別のバッファへ書く(Day 52 の G-Buffer がそれになる)。

3. 読むために写す — フィードバックループ

今日いちばん危ない箇所。ソフトパーティクルが読みたい深度は、まさにいま描き込み先として挿さっているものになる。

  [シーンバッファ]  カラー(RGBA16F) + 深度(レンダーバッファ)
        ↑ 粒はここへ描く                ↑ 粒はここを読みたい

OpenGL では、描き込み先に挿さっているテクスチャを同じ描画で読むと結果が未定義になる。「深度は書いていない(DepthMask(false))から大丈夫では?」と思うところだが、GL 3.3 の仕様ではそれでも未定義で、GL 4.4 で「書き込みマスクが 0 なら安全」という緩和が入った経緯がある。

そしてエラーは出ない。ドライバによっては動いてしまい、別の環境で真っ黒になる。いちばん見つけにくい種類の間違いになる。

逃げ方は読む用のコピーを1枚持つ。

csharp
_gl.BindFramebuffer(FramebufferTarget.ReadFramebuffer, シーン);
_gl.BindFramebuffer(FramebufferTarget.DrawFramebuffer, コピー);
_gl.BlitFramebuffer(0, 0, w, h, 0, 0, w, h,
    ClearBufferMask.DepthBufferBit, BlitFramebufferFilter.Nearest);

これは実際のエンジンでもそうで、Unity の _CameraDepthTexture はまさにこれになる。glBlitFramebuffer は GPU の中のコピーなので CPU は待たないが、画面1枚ぶんの帯域は毎フレーム消える(1920x1080 の 24bit 深度で 5.9MB)。

制約理由
フィルタは Nearest 必須Linear を指定すると GL_INVALID_OPERATION。深度の平均に意味が無い
呼ぶのは不透明を全部描いたあと早いと床や箱が入っていない
呼ぶのは半透明を描く前遅いと粒どうしが互いを消し合う
終わったらシーンへ描き戻せる状態にするBlitFramebuffer は読み書きの割り当てを変える

確保は遅延にしてある。ソフトパーティクルを一度も使わないなら 5.9MB を払う理由が無い。おかげで HUD の VRAM が切り替えた瞬間に増えるのが目で見える。

4. トレイルはリングバッファ — 順番が命だから

Day 49 の ParticleEmitter は、死んだ粒を末尾の生きた粒と入れ替えて詰めていた。詰め直しが O(1) で済み、生きている粒が常に先頭から連続する。代償は順番が保たれないことだが、加算合成では足し算の順番が結果を変えないので困らなかった。

トレイルではこれが使えない。節を順に繋いでリボンを張るので、1つでも入れ替わるとリボンがねじれて自分自身を横切る。

順番を保ったまま O(1) で捨てるには、いちばん古いものを指す添字を進める——リングバッファになる。

csharp
public TrailPoint this[int index] => _points[(_start + index) % _points.Length];

private void Push(Vector3 position)
{
    if (Count == _points.Length)
    {
        _start = (_start + 1) % _points.Length;   // いちばん古いものを捨てる
        Count--;
    }
    _points[(_start + Count) % _points.Length] = new TrailPoint { Position = position };
    Count++;
}

寿命で捨てるほうは while 1本で済む。節は置かれた順に並んでいるので、いちばん古いものが寿命内なら、その先も寿命内——全部を舐める必要が無い。粒は順番がバラバラなので、こちらは全部見なければならなかった。順番を保つ制約は、捨てるときには逆に効く。

5. 先端だけは特別扱い — 節を置くのは距離、動かすのは毎フレーム

素朴に「毎フレーム節を1つ置く」と、fps でリボンの節の数が変わる。「一定距離ごとに置く」にすると、今度はゆっくり動いているときにリボンの先が本体から遅れる——剣先とリボンの間に隙間が空くのがいちばん目に付く不具合になる。

答えは両方で、最後の節は常に「いまの位置」に貼り付けておく。

csharp
Vector3 committed = this[Count - 2].Position;   // 直前に「固めた」節

if (Vector3.DistanceSquared(position, committed) >= MinDistance * MinDistance)
{
    Push(position);            // 離れた: 新しい先端を足す
}
else
{
    tip.Position = position;   // 近い: 先端を動かすだけ
}

距離を測る相手が「先端の1つ手前」なのが要点になる。先端から測ると、先端は毎フレーム動くので距離が常に 0 で、節が永久に増えない。

節の数の見積もりは粒とまったく同じ形になる。

  釣り合いの節数 = 速さ ÷ 最小距離 × 寿命
    2.2m/s ÷ 0.06m × 0.35秒 = 13 節

Day 49 の「放出 × 寿命」と同じで、容量を超えると尾が寿命より短くなる(HUD の「捨てた節」が増える)。

6. リボンの横方向 — ビルボードとの違い

ビルボード(Day 49 の要点1)はカメラの右と上で四角形を張っていた。縦も横もカメラが決めてよかったからで、そのおかげで粒は常に正面を向く。

リボンはそうはいかない。帯は進行方向に沿っていなければならないので、縦(長さ方向)は動きが決めてしまう。選べるのは横だけになり、「進行方向に垂直」かつ「カメラから見ていちばん広く見える」向き——つまり進行方向 × カメラへの向きになる。

csharp
Vector3 side = Vector3.Normalize(Vector3.Cross(direction, toCamera));

縮退点が1つある。剣先がカメラへ真っ直ぐ向かってくると2本が平行になり、外積が 0 に潰れる。正規化すると 0/0 で NaN が出て、リボンが丸ごと画面から消える(NaN の頂点はクリップ段で落ちる)。この1点のためだけに逃げ道が要る、というのがビルボードとの実装上の差になる。

横方向は節ごとに1回だけ出す。帯ごとに計算すると、隣り合う2枚が共有するはずの辺がわずかに違う場所に来て、継ぎ目に隙間が開く。節の向きは前後の節を結んだ向きにする(端は片側だけ)——曲がり角で入る向きと出る向きの中間を取ることになり、これが無いと急カーブの外側で帯が折れて尖る。

7. 混ぜ方を切り替えると、そこがドローコールの境目になる

Day 49 の混ぜ方は Begin で1回決めるだけだった。筋書きごとに加算かアルファのどちらかを選べばよかったからで、「同じフレームに炎と煙を出す」はできないまま残してあった(Day 49 の歪み1つ目)。

エフェクトを扱い始めるとこれが通らない。爆発は閃光(加算)と煙(アルファ)の両方で1つの出来事になる。

混ぜ方は GL の状態なので、途中で変えるにはそれまでに積んだぶんを描き切ってからでないといけない。テクスチャの切り替えとまったく同じ理屈で、切り替えの回数がそのままドローコールの数になる。

だから EffectSystem.Draw は混ぜ方でまとめて回す。

csharp
DrawGroup(renderer, ParticleBlend.Additive, dot, smoke);   // 光るものを全部
DrawGroup(renderer, ParticleBlend.Alpha,    dot, smoke);   // 濁るものを全部

出た順に回すと、爆発と土埃が交互に並んだときに毎回フラッシュする。2周するだけで、何本出ていてもドローコールは 2 回に収まる。半透明どうしの前後関係は正しくならないが、光るものを先に敷いて濁るものを重ねるほうが絵としても素直になる。

なお Day 49 の改造課題2(事前乗算で1パスに畳む)は今日も有効な手で、そちらへ寄せるとドローコールは 1 回になる。今日は「切り替えると何回になるか」が数字で見えるほうを選んだ。

8. 一発ものはプールから借りて、自分で返す

ParticleEmitter は「1つの放出口をずっと出しっぱなし」の道具だった。ゲームで要るのはそうではなく、出来事のたびに1回だけ出て、勝手に片付くものになる——足が着いた、弾が当たった、樽が爆発した。

呼ばれるたびに new ParticleEmitter すると、256 個の構造体配列の確保が毎回走って GC が刻む。あらかじめ何本か作っておいて、空いているものを貸す。

段やること
借りるActive でない本を探す。無ければ数えて諦める
設定するConfigure が種類ごとの設定を丸ごと入れる。EmitRate = 0 / Emitting = false
撒くBurst(n) で一気に
返すUpdate で Count == 0 になったら Active = false

空きが無いときに古いものを潰さないのが1つの判断になる。潰すと、いちばん見てほしい爆発が足音に横取りされて消える。出せなかったことを数えて HUD に出すほうが、あとから容量を決められる。

EmitRate = 0 と Emitting = false を忘れると本が永久に返らない。撒き続ける放出口は Count が 0 にならないので、プールが埋まって「しばらく遊んでいるとエフェクトが出なくなる」という形で出る。自己チェックに項目として入れてある。

9. 距離で刻む — 足取りとフレームレート

「歩いている間ずっと土埃を出す」だと、止まっているときも出続けるし、走るとフレームレートのぶんだけ濃くなる。実際の足音がそうであるように、距離を刻んで一歩ごとに1回にする。

csharp
_carry += distance;
int steps = (int)(_carry / Stride);
_carry -= steps * Stride;
return steps;

端数を持ち越すのは Day 49 の ParticleEmitter._carry とまったく同じ形になる。切り捨てると、1フレームで進む距離が歩幅より短いときに永久に一歩も出ない。

上限も要る。ブレークポイントで止めたあとの巨大な dt で何十歩ぶんも一度に出ないよう、1回の呼び出しで 4 歩までにしてある。

走ると歩幅を広げるのも見た目のうち。同じ歩幅のままだと、速いぶんだけ土埃の数が増えて煙幕になる。

10. 明るさ倍率は加算のためのもの

Day 49 の ParticleRenderer.Intensity は加算のための倍率だった。RGB を持ち上げたぶんが素直に明るさになり、1.0 を超えればブルームのしきい値を越えてにじむ。

ところがアルファ合成の粒に同じ倍率を掛けると色が飛ぶ。土埃の色 (0.62, 0.55, 0.44) を 2 倍すると (1.24, 1.10, 0.88) で、3成分とも 1.0 付近に張り付いて土の色が消える——おまけにブルームも拾うので、足元だけが白く光る。

Day 49 は加算の粒しか同時に出さなかったので表に出なかった。加算とアルファが同居した今日、初めて症状が出た箇所になる。

csharp
private float IntensityFor(ParticleBlend blend) =>
    blend == ParticleBlend.Alpha ? 1.0f : Intensity;

アルファの粒を明るくしたいなら StartColor のほうを上げる。「明るさ」と「色」を混ぜないための線引きになる。

「刺さり」が消えるまで

_scene.Bind() を忘れると症状が遠くに出る。BlitFramebuffer は読み書きの割り当てを変えるので、戻さないまま続きを描くと粒が画面へ直接描かれ、後処理を1つも通らない。「ソフトパーティクルを ON にしたらブルームが効かなくなった」という形で出るので、深度のコピーを疑うところまで辿り着きにくい。

LinearizeDepth が2箇所にある(particle.frag と ParticleRenderer)。重複だが、シェーダの式が合っているかを確かめる方法が他に無い——GPU の中身は読めないので、片方を CPU に持ってきて数で確かめるしかない。自己チェックの1〜3項目がそれになる。

トレイルの節が1つ増えるまで

while 1本で捨てられるのがリングバッファの配当になる。節は置かれた順に並んでいるので、いちばん古いものが寿命内ならその先も寿命内——全部を舐める必要が無い。粒(Day 49)は順番がバラバラなので全部見る必要があった。順番を保つ制約は、捨てるときには逆に効く。

Side を節ごとに出すのは継ぎ目のため。帯ごとに計算すると、隣り合う2枚が共有するはずの辺がわずかに違う場所に来て隙間が開く。節で1つに決めておけば、両側の帯が同じ2点を使うので必ず閉じる。

エフェクトが1つ出て、自分で片付くまで

EmitRate = 0 と Emitting = false が生命線になる。撒き続ける放出口は Count が 0 にならないので本が返らず、「しばらく遊んでいるとエフェクトが出なくなる」という形で出る。自己チェックの「一発ものは放出を止めてある」がこれを見ている。

爆発だけが2本使うのは、閃光(加算)と煙(アルファ)が1つの放出口に同居できないため。実際のエンジンでも1つのプレハブに ParticleSystem が何個もぶら下がるのは同じ理由になる。

今日残した歪み(3つ)

1つ目: 深度のコピーが全画面のまま。CaptureDepth は毎フレーム画面1枚ぶんの帯域を使う。粒が1つも出ていないフレームでは呼ばないようにしてあるが、出ている間は解像度なりに掛かる。本気で削るなら粒を半解像度で描いて、深度も半分に落とすことになり、そうすると今度は縁のアップサンプルが要る(bilateral upsample)。オーバードローが問題になった日に手を付ける。

2つ目: 混ぜ方の切り替えがドローコールを増やす。要点7で書いたとおり、加算とアルファの同居は 2 回で済ませてある。Day 49 の改造課題2(事前乗算に寄せる)を通せば 1 回になるが、今日は切り替えの代償が数字で見えるほうを残した。EffectSystem.Draw が混ぜ方でまとめている前提が崩れると(たとえば正しい前後関係のために出た順に描くと)ここは一気に増える。

3つ目: トレイルが1本しか無い。Program が _trail を1本だけ持っていて、複数のトレイルを扱う仕組みが無い。EffectSystem と同じようにプール化すればよいが、今日の時点で2本目が要る場面が無いので入れていない。Day 51 でキャラクターの手足に付けたくなったら、EffectSystem とまったく同じ形で TrailSystem を書くことになる。

改造課題

課題1(易): 着地の強さを落下速度に応じて変える

いまの EffectKind.Landing はいつも同じ大きさで出る。1cm 落ちても 10m 落ちても同じ土埃なので、高さが伝わらない。

csharp
// UpdateFootsteps の着地の枝
float impact = MathF.Max(0.0f, -_previousVerticalVelocity);   // 着地直前の落下速度
if (impact > 1.0f)
{
    _effects.Spawn(EffectKind.Landing, Character.Position, Character.GroundNormal, impact);
}

EffectSystem.Spawn に強さ(0〜1)を足して、Configure の中で Radius / SpeedMax / バーストの数に掛ける。

確かめること: 段差(35cm)を降りたときはほとんど出ず、高いところから落ちたときだけ大きく出ること。そして坂を下っているだけでは出ないこと——接地が途切れていないので着地の枝に入らない(Day 45 の吸い付きが効いている)。

課題2(中): トレイルを Catmull-Rom で滑らかにする

MinDistance を 0.3m くらいまで上げると、リボンが目に見えて折れ線になる。節を減らしたいが角は丸めたい、というのがトレイルでは普通の要求になる。

節の間に補間点を入れる。Day 40 のカメラワークで使った Catmull-Rom がそのまま使える(Demo/CameraPath.cs の要点を参照)。

csharp
// 節 i と i+1 の間を n 分割し、i-1 と i+2 を制御点に使う
Vector3 CatmullRom(Vector3 p0, Vector3 p1, Vector3 p2, Vector3 p3, float t)

ParticleRenderer.Draw(trail, ...) の中で、節の列を補間した列に置き換えてから帯を張る。Side と幅は補間後の点で出し直す。

確かめること: MinDistance を 0.3m にしても角が出ないこと。節の数は変わらないのに帯の枚数(HUD の 帯:)だけが増えること。そして端(最初と最後の節)で制御点が足りない場合に落ちないこと。

課題3(難): 粒を半解像度で描いて合成する

土埃を画面いっぱいに出すと、塗る画素の数(オーバードロー)が効いてくる。1粒 0.7m を 30 個重ねると、同じ画素を何十回も塗ることになる。

半分の大きさのバッファに粒だけを描いて、最後に拡大して合成する。

  1. 半解像度の Framebuffer(RGBA16F、深度なし)を1枚
  2. 深度も半分に落とす。Nearest で間引くのではなく、2x2 のうちいちばん奥を採る——手前を採ると縁が欠ける
  3. そこへ粒を描く(ソフトパーティクルは半分の深度を読む)
  4. 拡大してシーンへ加算 / アルファ合成

難所は4段目になる。素直に bilinear で拡大すると、物の輪郭で半分の解像度が透ける(近くの床と遠くの空が混ざる)。実際のエンジンは bilateral upsample——深度が近い画素だけを重み付けして混ぜる——を使う。

確かめること: 塗る画素が 1/4 になっても絵がほぼ変わらないこと。そして箱の輪郭で粒がにじまないこと。にじむなら4段目の重み付けができていない。

手を出す前に読む: Bandwidth-Efficient Rendering(Bavoil, NVIDIA)。「粒は帯域の問題」という見方が最初から最後まで通っている。

動作確認済み環境

  • Windows 11 / .NET 10 / NVIDIA GeForce RTX 3070 / OpenGL 3.3
  • 960x640 / Release で 330〜1100fps(粒の数と塗る面積で大きく振れる)

とくに強いのは次の4つ。

  • 深度 0.5 が 0.200m — 深度バッファの真ん中はもう near のすぐ先。線形化を忘れたまま引き算してもそれらしくフェードするので、絵では気づけない。数字で見ると桁が違う
  • 溢れても並びが古い順のまま — swap-remove で書いていたらここで落ちる。絵では、速く動かしたときだけリボンがねじれるという形で出る
  • 真正面から見ても NaN にならない — 剣先がカメラへ真っ直ぐ向かう1点だけの症状で、リボンが丸ごと消える。手で再現するのは難しく、数なら確実に踏める
  • 空きが無ければ黙って潰さず数える — 潰す実装にすると、見せたい爆発が足音に横取りされる。数が出ていれば容量を決められる

検証の途中で分かったこと

1. 明るさ倍率がアルファの粒を白く飛ばしていた(要点10)。

土埃を出したら足元だけが白く光った。色を暗くしても変わらない。原因は Day 49 から引き継いだ uIntensity(既定 2 倍)で、土の色 (0.62, 0.55, 0.44) が (1.24, 1.10, 0.88) になって 1.0 に張り付き、ついでにブルームのしきい値も越えていた。

Day 49 は加算の粒しか同時に出していなかったので表に出ていない。加算とアルファが同居した今日、初めて症状が出た形になる。IntensityFor(blend) で分けて直した。

2. カメラを 34 度回しただけで、隅の箱の中に潜り込んでいた。

最初、エフェクトデモのカメラを Yaw = 0.6(34 度)にしていたら、画面の右半分が市松模様で埋まった。Day 31 の背景の箱は (±3, 0, ±3) に置いてあるので、距離 5.2m・仰角 4 度で斜めから覗くと、カメラの座標がちょうど箱の中に入る。

正面(Yaw = 0)へ直した。低い視点は「刺さり」を見るために要るので、高さのほうは動かせない——見る向きのほうを譲った。

3. 「刺さり」を見せるには、粒を床に置くだけでは足りない。

最初は発生源(高さ 0.2m あたりを回るもの)の位置にそのまま土埃を出していた。床から離れているので四角形が床と交わらず、ソフトパーティクルを切っても絵が1ピクセルも変わらなかった。

発生源の真下の床(y = -0.46)へ落とすように直したら、0.7m の粒が床を貫いて切り口が出た。技法の効き目を見せるには、その技法が効く状況を作りに行く必要がある、という当たり前のことを1回踏んだ。
