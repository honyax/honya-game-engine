if (uGBufferPass == 1)

理論の要点

1. G-Buffer — 光を当てるのに要るものの全部

光を当てる側(deferred.frag)が三角形を知らずに済むには、画素ごとに表面の性質を全部置いておく必要がある。

枚形式中身バイト
0RGBA8ベースカラー(平方根で詰める。要点3)。A は空き4
1RGBA8R = AO / G = 粗さ / B = 金属度(glTF の ORM と同じ並び)4
2RGBA16Fビュー空間の法線 + 距離(Day 37 の幾何バッファと同じ形)8
3RGBA16F発光(1.0 を超えるので 16F)8
深度24bit深度テストのためと、あとでシーンのバッファへ写すため3

1画素 27 バイト、960x640 で 15.8MB。全部を 16F にすると 35 バイトになるので、中身ごとに必要な精度を選んでいる。

1回の描画で4枚へ同時に書くのが MRT(Multiple Render Targets)。画素シェーダが layout(location = N) out vec4 で出口を分け、フレームバッファ側は glDrawBuffers で「出口 N → アタッチメント N」の対応表を持つ。

csharp
Span<DrawBufferMode> buffers = [ColorAttachment0, ColorAttachment1, ColorAttachment2, ColorAttachment3];
_gl.DrawBuffers(4, buffers);

これを忘れると完全性チェックは通るのに、0 番のアルベドだけが書かれる。法線と材質が真っ黒のまま、エラーは1つも出ない(Day 33 の glDrawBuffer(GL_NONE) と同じ種類の呪文)。

番号は Material の表を引き継ぐ。読む側で G-Buffer を 0・1・2・4 番に刺す——0 がベースカラー、1 がメタリック・ラフネス、2 が法線、4 が発光で、その番号に居る値の意味までマテリアルと同じになる。ライティングパスにはマテリアルが無いので 0〜4 は空いている。

2. 位置は持たない — 距離1つから戻す

LearnOpenGL の作例は位置を RGBA16F のまま G-Buffer に持つ。今日は持たない。「どの画素か」は gl_FragCoord が知っているので、距離が1つあれば位置は決まる。

glsl
vec2 ndc      = (gl_FragCoord.xy / uScreenSize) * 2.0 - 1.0;
vec3 viewPos  = vec3(ndc * uProjScale * depth, -depth);   // ssao.frag の ViewPosition と同じ
vec3 worldPos = (uInverseView * vec4(viewPos, 1.0)).xyz;

持たないぶん RGBA16F 1枚(8 バイト/画素)が浮く。G-Buffer は1フレームに「書く1回 + 読む1回(全画面)」通るので、帯域はそのまま速度に効く——Day 52b で光の球が覆った画素のぶんだけ、読む回数がさらに増える。

代償は精度で、距離は 16F に入っている。半精度の刻みは距離に比例して粗くなる (4〜8m で 4mm、8〜16m で 8mm)。自己チェックは 6.3m の床で 3.1mm のずれを出していて、これが影の縁でだけ絵に出る——PCF の升目がたまに1つずれる(検証の途中で分かったこと 1)。深度バッファ(24bit)から戻せば手前ほど精度が上がる。それが改造課題2。

3. 8bit に色を入れるなら平方根で

ベースカラーは 0〜1 に収まるので RGBA8 で足りる……と言いたいが、リニアのまま入れると暗部が潰れる。8bit は 0〜1 を 256 段に均等に配るので、0.002 未満は全部 0 になり、0.02 のあたりでは1段が値の 10% を超える。

  0.02〜1 での最大の相対誤差   リニアの 8bit  8.8%   平方根で詰める  2.7%

平方根にしてから入れ、読むときに2乗する。暗い側に段が寄るので誤差が 1/3 になる。これは sRGB の符号化(ガンマ 2.2)と同じ発想の簡易版で、本番のエンジンはsRGB 形式のテクスチャ(GL_SRGB8_ALPHA8)に書いてハードウェアに変換させる。

4. 深度を写す — あとから描く粒のために

ライティングパスはシーンのバッファ(_post.Scene)に描く。ところがそのバッファの深度は_post.Begin でクリアされたままで、G-Buffer パスの深度は G-Buffer の側にある。

csharp
_gbuffer.Target.BlitDepthTo(_post.Scene);   // Day 50 で足した口
_post.Scene.Bind();                         // Blit は割り当てを 0 に戻して帰る

写さないとあとから描く粒(Day 49)が壁の向こうに透けて見え、ソフトパーティクル(Day 50)も効かない。LearnOpenGL の Deferred Shading の章が最後に glBlitFramebuffer を呼んでいるのと同じ理由になる。

Day 52b の光の球も、この深度と比べて塗る画素を選ぶ。写さないと比べる相手がいちばん奥のままなので、球が1つも通らない——今日のうちに写しておくことの値打ちは、明日もう1つ増える。

5. SSAO が G-Buffer を借りる — 3回が2回に

SSAO の遮蔽の計算(ssao.frag)が読むのは「ビュー空間の法線 + 距離」の1枚だけで、G-Buffer の2枚目はそれとまったく同じ形にしてある。だから Ssao.Compute に渡すだけでよい。

csharp
_ssao.Compute(_camera, width, height, _gbuffer.NormalDepth);   // 幾何パスを描かない

Ssao は GBuffer を知らない。受け取るのは Texture 1枚で、自前か借り物かはシェーダからも区別が付かない。自己チェックは、法線マップの無い物で両者の遮蔽が完全に一致(平均の差 0.0000)することを見ている。

1つだけ変わることがあり、G-Buffer の法線は法線マップを当てたあとのもの(Day 37 の幾何パスは頂点法線だった)。レンガの目地に細かい暗がりが乗るようになる。実際のエンジンもほとんどが G-Buffer の法線で SSAO を計算している。

点線の1本(ApplyLighting → DeferredLighting)は Day 51 の FollowCamera と同じ形。DeferredLighting は太陽の向きも IBL も知らず、Action<Shader> 1本で受け取る。2か所に書き写すと、片方だけ直したときに2つの絵が食い違う——しかも両方ともそれらしく見えるので、見比べるまで気づけない。

Ssao から GBuffer への矢印は無い。借りるのは Texture 1枚で、Ssao は自分が G-Buffer を読んでいることを知らない。Day 37 の幾何バッファと同じ形にしておいたことが、そのまま「知らずに済む」になっている。

1フレームが決まるまで — フォワードとディファードの分かれ道

ジオメトリを描く箱が、左の道には3つ、右の道には2つある(影・SSAO の幾何・本描画 と、影・G-Buffer)。これが HUD の「幾何パス」の数字になる。

右の道は Render3D を呼ぶ場所が前に移っただけで、中身は1行も変わっていない。その代わり、左の道の Render3D があった位置には三角形を1つも描かないパスが2本並ぶ。

RenderParticles が両方の道の合流点に居るのが大事なところ。半透明は G-Buffer に入れられない(1画素に表面を1つしか持てない)ので、どちらの道でも最後にフォワードで重ねる。深度を写してある(要点4)ので、ディファードの道でも粒は壁の向こうに透けない。

textured.frag を真ん中で切る

切る場所は SSAO の手前でなければならない。SSAO はディファードのとき G-Buffer から作るので、G-Buffer パスの時点ではまだ出来ていない。発光を SSAO の上へ移したのは、出口で書くものが全部、切れ目より前に揃っている必要があるから。

成分表示の窓(Shift+9 の類)が後半に居るので、ディファードでは出せない。成分表示中は UseDeferred がフォワードに戻す——ディファードの側の同じ窓が「G-Buffer を見る」(F3)になる。

改造課題

課題1(易): G-Buffer の表示に「復元した位置」を足す

要点2の「距離1つから位置が戻る」を、数字ではなく絵で確かめる。GBufferView に Position を足し、gbuffer-view.frag で距離から世界の位置を戻して色にする。いまの gbuffer-view.frag は uniform を6つしか持っていないので、deferred.frag と同じ3つ(uScreenSize / uProjScale / uInverseView)を送るところから始める(GBuffer.DrawDebug に Camera を渡す必要が出る——Apply はもう受け取っている)。

glsl
// ndc と距離だけで、まずビュー空間の位置が決まる
vec3 viewPosition = vec3(ndc * uProjScale * depth, -depth);
vec3 worldPosition = (uInverseView * vec4(viewPosition, 1.0)).xyz;
FragColor = vec4(fract(worldPosition), 1.0);   // 1m ごとに色が一周する

fract を使うと1m ごとの等高線が床と壁に出る。カメラを動かしても模様が world に貼り付いたまま動かないのが正しい姿で、式を1文字間違えるとカメラと一緒に模様が滑る。自己チェックの「位置の復元」(3.1mm)が数字で言っていることの、絵の側になる。

課題2(中): 位置を深度バッファから戻す

いまは G-Buffer の2枚目(16F の距離)から位置を戻していて、影の縁で 0.2% の画素がずれる(要点2)。深度バッファ(24bit)から戻すように変える。

  1. GBuffer の深度をレンダーバッファから深度テクスチャに替える(Framebuffer に「カラー N 枚 + 深度テクスチャ」の形を足す。Day 33 の CreateDepthOnly の応用)
  2. deferred.frag で深度を読み、逆射影行列で戻す
glsl
float depth = texelFetch(uGDepth, pixel, 0).r;                  // 0〜1
vec4 clip = vec4(ndc, depth * 2.0 - 1.0, 1.0);                  // OpenGL の NDC は z も -1〜1
vec4 view = uInverseProjection * clip;
vec3 viewPosition = view.xyz / view.w;                          // 透視除算を自分でやる

自己チェックの「位置の復元」(いまは 6.3m で 3.1mm)と、フォワードとの一致(5% を超える画素)がどう変わるかを見る。手前ほど 24bit のほうがずっと細かい (24bit の深度は 1/z に比例した刻みなので、刻みは距離の2乗で粗くなる。16F は距離の1乗)——どこで入れ替わるかを計算してみるとよい(near 0.1m / far 100m では、遠クリップ面より奥で入れ替わる)。

課題3(難): 法線を2成分に畳んで G-Buffer を1枚減らす

法線に RGBA16F を1枚まるごと使っている(8 バイト/画素)。単位ベクトルは自由度が2つしかないので、八面体マッピングで2成分に畳める。

glsl
// 書く側: 単位球 → 八面体 → 正方形
vec2 OctEncode(vec3 n) {
    n /= abs(n.x) + abs(n.y) + abs(n.z);
    return (n.z >= 0.0) ? n.xy : (1.0 - abs(n.yx)) * sign(n.xy);
}

2成分 + 距離で RGB16F 相当に収まるので、2枚目を RGBA16F から RG16F + R32F に分けるか、材質の1枚(RGBA8)の空きへ押し込むかを設計する。難しいのは畳み方ではなく、SSAO が借りている形を変えてしまうこと——ssao.frag は「RGB = 法線、A = 距離」を前提にしているので、そちらも同時に直さないと遮蔽が壊れる。自己チェックの「SSAO: G-Buffer から作った遮蔽が、自前の幾何パスとほぼ一致」が、まさにその見張りになっている。畳んだあとに平均の差がどこまで増えるかを見ること。

検証の途中で分かったこと
