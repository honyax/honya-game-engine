Day 54 の2日目で、reference は Day 54a の完全コピー + 差分。Day 54a で TAA の骨格ができた。ずらして描き、カメラの動きで履歴を引き戻し、近所の色で疑って混ぜる。カメラだけが動く絵には完全に効く——決めの構図もカメラワークも、FXAA よりずっと滑らかになった。

崩れるのはカメラが物を追いかけたとき。プレイアブルデモでキツネを追うと、画面の上でキツネは止まって見え、地面が下へ流れる。ところがキツネの画素に入っている速度は「地面と同じだけ動いた」——深度には「今どこにあるか」しか書かれていないので、自分で動いた物の前の位置はどこにも無い。別の場所から引いた履歴は疑いに捨てられ、履歴が溜まらないので、キツネの輪郭だけ TAA が効いていないのと同じになる。

理論の要点

1. 自分で動いた物 — 速度の2段目

Day 54a の速度は深度から作った。深度に入っているのは「この画素に今写っている点は、カメラから何 m か」だけで、その点が前のフレームにどこに居たかは書かれていない。カメラの動きだけなら、世界の点は動いていないので前の行列で写し直せば出る——けれど物自身が動いたぶんは、どこからも出てこない。

  1段目(Day 54a)  深度 → 世界の点 → 前のフレームの VP で写し直す     … 世界の点が動いていない前提
  2段目(今日)     前のモデル行列・前の関節行列で頂点を運ぶ           … 物が動いたぶんを上から描く

2段目は動いた物だけをもう一度描く。頂点シェーダ(velocity.vert)が同じ頂点を2回運ぶ。

glsl
vec4 currentWorld  = uModel         * skin(aPosition, uJoints);
vec4 previousWorld = uPreviousModel * skin(aPosition, uPreviousJoints);
// 画素シェーダで、それぞれを NDC にしてから引く
FragVelocity = (current - previous) * 0.5;      // 1段目とまったく同じ式

GL の状態は3か所ふだんと違う。

状態なぜ
深度テスト LEQUAL、深度は書かないシーンの深度と「同じ深さ」の画素だけが通る = その物が実際に見えている画素だけに書く。手前に柱があれば柱の画素は1段目のまま
ポリゴンオフセット −1.0 で少し手前へ本描画(textured.vert)とこちらは別のシェーダなので、同じ式を書いても深度が最後の1ビットまで一致する保証が無い。1ビット奥に出れば LEQUAL で落ちて、動く物に点々と穴が開く
裏面を捨てない材質ごとの両面の設定(Material.DoubleSided)を知らずに済む。閉じた物の裏面は表面より奥なので、深度テストで勝手に落ちる

比べる相手は自分で用意する。速度バッファは今日から「RG16F + 深度」になり、Render の頭でシーンの深度をそこへ写す(Framebuffer.BlitDepthTo)。1段目が読む深度(PostProcess.SceneDepth)とは別の1枚——描き込み先に挿さっている深度を同時にテクスチャとして読むとフィードバックループになる(Day 50 と同じ話)。

TAA は近所 3x3 でいちばん手前の画素の速度を使う(この仕掛けは Day 54a から入っている)。動く物の輪郭の画素は、半分が物で半分が背景。ジッターでたまたま背景を取ったフレームに背景の速度で履歴を引くと、輪郭がちぎれて残る。手前(= 物)の速度に寄せると、輪郭が物と一緒に動く——2段目を足して初めて、この寄せ方が効く(Day 54a では手前も奥も同じカメラの速度だった)。

2. 何が動いたかを、描画の分岐を書き写さずに知る

2段目で描き直すのは「前のフレームから動いたもの」だけ。それをどう知るか。

影パス(Day 33)と SSAO の幾何パス(Day 37)は、描くものの並びを Program の中で手で書き写している。Day 51 でキャラクターを足したときに3か所を直すことになった(Day 52a の RenderGBufferPass のコメント)。速度で4か所目を作るのはやめて、本描画が必ず通る Program.Draw で記録する。

csharp
mesh.Draw();
_motion.Record(mesh, model, joints);      // Program.Draw の最後の1行(Day 54b)

MotionVectors.Record は、鍵 (メッシュ, このフレームで何回目か) で行列と関節を覚え、前のフレームの同じ鍵と比べる。行列か関節が1ビットでも違えば「動いた」、同じなら「止まっている」、前のフレームに無ければ「新しく出てきた」(前の位置が分からないので1段目に任せる)。止まっている物は毎フレーム同じ計算で同じ行列が出るので、ぴったり一致する。

絵記録描き直し
デモ v1(止めた決めの構図)250
プレイアブルデモ(キツネが歩く)261(キツネのパーツ)
確認用のシーン(箱を動かした)21

鍵が「何回目か」なのが今日の歪み。描く順番が毎フレーム同じなら同じ物を指すが、途中に1つ増えると後ろが全部ずれて、別の物の行列と比べてしまう(設計書「今日残した歪み」の1つ目)。

カットの3つ目の条件もここから来る(Day 54a の要点7)。記録したもののうち半分以上が前のフレームに居なかったなら、絵が丸ごと切り替わったとみなして履歴を捨てる——デモ v1 から材質グリッドへ切り替えたとき。

3. 履歴の読み方 — 双線形はぼけが積もる

履歴は「前に居た場所」から読むので、たいてい画素の中心から外れた場所を読む。双線形は近い4テクセルの平均なので読むたびに少しぼける。TAA は毎フレーム読み直すので、カメラが動いている間、ぼけが積もって絵がじわじわ眠くなる。

Catmull-Rom(3次)は外側に負の重みを持つ曲線で、ぼけずに間を埋める。4x4 の 16 テクセルを読むが、重みの和が 1 なので真ん中の2本を「間の1点を双線形で読む」にまとめられ、双線形 9 回で済む。

自己チェック(縦の縁を 1 フレーム 0.5 画素ずつ動かして 40 フレーム。縁の 10〜90% の幅):

  今の絵そのもの 0.80 画素  /  双線形 3.61 画素  /  Catmull-Rom 1.95 画素

負の重みがあるので明暗の境目では 0 を下回ることがあり、読んだあとで 0 に切る。

4. 明るさで畳む — 明るすぎる点が勝ちすぎないように

TAA は後処理の入口、リニアな HDR のまま走る(Day 54a の要点6)。混ぜる(平均する)なら、光の量として足し算が効く値で混ぜるのが筋だから。

ただし HDR のまま混ぜると、明るすぎる点が勝ちすぎる。太陽の映り込みのような 50 を超える画素がジッターで出たり消えたりすると、1 割しか混ぜなくても 5 足されるので、まわりの暗い画素ごと白くちらつく。そこで混ぜる前に x / (1 + 最大成分) で畳み(どんな明るさでも 1 未満に収まる)、混ぜたあとで戻す(Karis 2014)。

自己チェック(1画素が 1 フレームおきに 0 と 50 を行き来する):

  ちらつきの振れ幅  2.67 → 0.21     明るさの平均  25.35 → 1.00(本当の平均は 25)

代償は偏り。明るい画素ほど軽く数えるので、明るい点の平均は本当の平均より暗くなる。ちらつきが消えるのと引き換えに、ジッターで見え隠れする明るい点は暗く寄る。

TAA の1フレーム — 揺らして描き、速度を描き、入口で混ぜる

今日この図に足したのは2つ。頭の BeginTemporalFrame が記録を始めるようになり、その間の Program.Draw が毎回 MotionVectors.Record を呼ぶ。描画の分岐(デモ・プレイアブル・物理・材質グリッド・モデル)は今日も1行も変わっていない——Draw を必ず通ることだけを頼りにしているので、何を描くかの条件を1つも書き写さずに済んでいる。

今日足したものは、どこに繋がったか

TemporalAA と MotionVectors は互いを知らない。MotionVectors は速度を RG16F に描くだけで、誰が読むかを知らず、TemporalAA は速度をテクスチャで受け取るだけで、それがカメラの動きなのか物の動きなのかを知らない。繋いでいるのは Program の2行(_post.Velocity = _motion.Velocity と、カットのときの Reset)。Day 55 のモーションブラーは、この速度バッファをそのまま読める——速度を作る側を1行も変えずに、読む側を足すだけで済む形になっている。今日 MotionVectors に2段目が入っても TemporalAA が1行も変わらなかったのは、この線引きの配当になる。

TemporalAA は Camera を知らない。ずらしは NextJitter が NDC の Vector2 を返し、それを Program がカメラに入れる。TemporalAA から見れば「今の絵・履歴・速度・深度」の4枚のテクスチャを混ぜるだけの部品で、自己チェックが 64x8 の作り物の絵で解決の式を確かめられる(今日の要点3・4 の数字)のはこのおかげ。

速度バッファができるまで — 記録して、比べて、2段で描く

2段目は「外が描くものを決めない」最初のパス。影(ShadowMap)も SSAO(Ssao)も G-Buffer(GBuffer)も、Begin と End の間に何を描くかを外(Program)が決めてきた。MotionVectors は本描画で描いたものを記録し、描き直すものを自分で選ぶ。代わりに「鍵が何回目か」という弱い約束に乗っている(今日残した歪みの1つ目)。

深度を2か所に写している。1段目が読む深度(PostProcess.SceneDepth、Day 50 の写しと同じもの)と、2段目の深度テストの相手(MotionVectors の中の深度)。描き込み先に挿さっている深度を同時にテクスチャとして読むとフィードバックループになる(Day 50 と同じ話)ので、1枚で済ませられない。

1画素の色が決まるまで(TAA)— 引き戻して、疑って、混ぜる

関門は3つ(履歴が無い・画面の外・疑い)。前の2つは「履歴を使わない」で、3つ目だけが「履歴を直して使う」。疑いが TAA の品質を握っているのは Day 54a で見たとおり。

今日この図に足したのは2か所。近所の色を集める前に明るさで畳み(要点4)、最後に戻す。履歴を読むところが双線形から Catmull-Rom になった(要点3)。どちらも「混ぜ方」ではなく「混ぜる前の下ごしらえ」で、指数移動平均そのものは Day 54a のまま。

今日残した歪み(3つ)

1つ目: 記録の鍵が「メッシュと何回目か」。描く順番が毎フレーム同じなら同じ物を指すが、途中に1つ増えると後ろが全部ずれて、別の物の行列と比べてしまう。物理デモの接触点の光る玉は数が毎フレーム変わるので、玉の速度はたまに1フレームだけ嘘になる。本物のエンジンは物ごとに消えない番号を持ち、前のフレームの行列もその物自身が覚えている(UE の PreviousLocalToWorld)。シーンの物に番号を振るのは、多光源シーン化で DemoScene を整理する Day 56 の仕事になりそう。

2つ目: スキニングの式が4か所目(textured.vert / depth.vert / geometry.vert / velocity.vert)。しかも velocity.vert は前のフレームのぶんも持つので、式が2本入っている。Day 52b の BRDF の写し(3か所)と同じ種類の歪みで、見張り方も同じ(自己チェックの文字列の突き合わせ)。GLSL 3.3 に #include が無いのが根で、シェーダを読み込むときに自前で #include を展開する仕組みを入れれば1か所にできる。

3つ目: 速度を持たないものが残っている。粒・トレイル・2D のスプライト・後処理を通す文字(「FXAA と色調整」の F5)。どれも Program.Draw を通らないので記録されず、後ろにある物の速度で履歴を引く。疑いが色を引き戻すので残像は出ないが、粒の縁は履歴が溜まらずに揺れる。本物は「反応マスク」で粒の画素だけ今の絵の割合を上げるか、TAA のあとに描く。

Day 54a の歪みのうち、2つは今日消えた。「速度を持たないもの」から自分で動いた物が抜け、「履歴を双線形で読んでいる」は Catmull-Rom になった。残っているのは「ずらしを知らない位置の復元が3か所」(Day 54a の改造課題3)と「深度を2回写している」の2つ。

改造課題

課題1(易): 記録の鍵を壊してみる

設計書「今日残した歪み」の1つ目を、目で見る。物理デモ(「剛体力学」ページ)を出して箱を落とし、接触点の光る玉が増えたり減ったりする瞬間の速度の表示(F3 を2回)を見る。玉の数が変わったフレームだけ、後ろの箱の速度が一瞬おかしくなるはず(鍵が1つずつずれて、別の物の行列と比べる)。

確かめたら、MotionVectors.Record の鍵をわざと「メッシュだけ」にしてみる(occurrence を常に 0)。同じメッシュを何度も描くシーン(物理デモの箱、材質グリッド)で、ほとんどの物が「動いた」と判定される——最後に記録した1つとしか比べられないため。HUD の 描き直しN/M の N が跳ね上がる。鍵の設計がそのまま「何を同じ物とみなすか」の定義になっていることが分かる。

課題2(中): TAA のあとに鮮鋭化を足す

TAA の絵は FXAA より少し柔らかい。実際のエンジンは TAA のあとに鮮鋭化(アンシャープマスク)を1段足す(UE4 の r.TemporalAASharpness、AMD の FidelityFX CAS)。

glsl
// 十字の4近傍の平均との差を強める。strength は 0.2〜0.5
vec3 center = texelFetch(uSource, p, 0).rgb;
vec3 around = (texelFetch(uSource, p + ivec2(1, 0), 0).rgb + ... ) * 0.25;
FragColor = vec4(max(center + ((center - around) * strength), vec3(0.0)), 1.0);

鮮鋭化するのは出力だけで、履歴には掛けないのが肝。履歴に掛けると、毎フレーム掛けた鮮鋭化が積み重なり、輪郭に縁取り(リンギング)が育っていく。TemporalAA.Resolve が返したテクスチャを読んで別の1枚に鮮鋭化し、PostProcess の明部と合成にはそちらを渡す(履歴の2枚はそのまま)。レンガの目地が FXAA 並みに戻るかと、強くしすぎたときに輪郭の外側に明るい線が出るのを見る。

課題3(難): 速度を G-Buffer で一緒に書く

いまの2段目は、動いた物をもう一度描いている(ドローコールが増える)。ディファード(Day 52)のときは G-Buffer パスで同じ物を描いているので、G-Buffer に5枚目(RG16F)を足して、本描画のついでに速度も書ける。

  1. GBuffer.Layout に Rg16F を足し、textured.frag の G-Buffer の枝に layout (location = 4) out vec2 GVelocity; を足す
  2. textured.vert が前のモデル行列・前の関節行列でもう1つの位置を運ぶ(velocity.vert の中身をそのまま持ってくる)
  3. MotionVectors は、ディファードのときだけ2段目を飛ばす

難しいのは「前の行列をどこから取るか」。いまは MotionVectors が記録して持っているが、本描画の時点ではまだ記録の比較が終わっていない(Draw の中で記録している最中)。前のフレームの記録を先に引ける形(MotionVectors.PreviousOf(mesh, occurrence))を足すか、物自身が前の行列を持つ形(今日残した歪みの1つ目の直し)へ進むことになる。歪みが2つ繋がっているのが見えるのがこの課題の読みどころ。

検証の途中で分かったこと

1. 疑わないと、キツネの足元から画面の下へ尾が伸びた。完成条件2の絵。速度は正しく出ている(速度の表示ではキツネが黒く、地面が黄緑)のに尾が出るのは、隠れていた地面が現れるときの履歴にキツネの色が入っているから。速度が正しくても、前のフレームに写っていなかったものの色は、どこからも読めない。疑いは「速度の間違い」のためではなく、「現れたもの」のためにある。

2. 物の速度を切ると、追いかけているキツネの輪郭が階段に戻った。完成条件1の絵。物の速度を切ると、キツネの画素にはカメラの動きだけの速度——後ろの地面とほぼ同じ速度——が入る。画面の上では止まっているのに「地面と同じだけ動いた」とみなされ、別の場所の履歴を引いて疑いに捨てられる。尾は出ない(疑いが働いている)が、履歴が溜まらないので AA が効かない。自己チェックの「追いかけている箱」は、最初は箱の画素全体で測っていて、差が 2.8 倍(0.0012 / 0.0034)しか出なかった。箱の面の真ん中はどこから履歴を引いても同じ色の面なので揺れようがなく、差が薄まっていた。輪郭の画素だけで測るようにして 3 倍(0.0048 / 0.0142)。

3. 隠れているはずの箱が 322 画素の速度を書いていた。自己チェックの「床に隠れた箱」が最初に落ちたとき。原因は Day 54a と同じところで、確認用のシーンを描く前に深度テストが切れていた——深度を1画素も書かないまま描いたので、2段目の深度テストの相手が遠クリップ面(1.0)になり、床の下の箱を素通しにしていた。Day 54a の時点で RenderTaaProbe が深度テストを自分で入れるように直してあるので、今日は踏まずに済んでいる。2段目は「シーンの深度と同じ深さか」だけで見える画素を決めているので、深度が壊れると静かに間違える。

4. velocity.vert を写し忘れると、起動の時点で落ちる。シェーダは MotionVectors のコンストラクタで読むので、TAA を入れる前、OnLoad で落ちる。Day 54a で camera-velocity.frag だけを読んでいたのが2本になったぶん、写経の順番(1・2 をシェーダ、4 をクラス)を守らないと引っかかりやすい。

5.(Day 56 で追記)自己チェックのつまみを既定に揃えた。Day 56 の検証で、自己チェックを状態を変えて押し比べて見つかった。節2の最後で本番のつまみに戻していたので、「TAA」ページで今の絵の割合を 50% にしたまま押すと、「追いかける箱の輪郭が止まる」が落ちていた。節3の頭で「今の絵の割合 10%・分散で切る・Catmull-Rom・明るさで重み・表示なし・物の速度あり」に揃え、戻すのは節4の saved.Restore にした。Day 54a・55・56 にも同じ文面で入れてある。
