1つ目は「錯乱円は 1/奥行き の1次式」。ピントの奥行きを S、画素の奥行きを z とすると、ボケの半径は

2つ目は「散らすものを、集めるで書く」。ボケは、本来は「1つの点がまわりへ光を配る」処理(scatter)。画素シェーダは自分の色しか決められないので、「まわりの誰の光が自分まで届いているか」を集める(gather)形に裏返す。このとき届くかどうかを相手の半径で決めるのが要で、自分の半径で決めると、ピントの合った物が奥のボケににじみ出し(ハロー)、手前のボケは物の輪郭で切り抜いたように止まる(要点4)。そして「相手が届く」可能性がある範囲を知るために、画面を 16 画素の升目に切って、近所でいちばん大きく配っている物を先に記録しておく(要点5)。この地図と升目(BlurField)は、Day 55b のモーションブラーもそのまま読む共通の下ごしらえとして作る。

2. 錯乱円 — 1/奥行き の1次式と、過焦点距離

薄レンズの式から、奥行き z の点がセンサーの上に作る円(錯乱円)の直径は

  c = A f (z − S) / (z (S − f))          A: 口径、f: 焦点距離、S: ピントの奥行き

S が f よりずっと大きい(3.2m と 38mm)とみなし、センサーの高さで割って画面の画素に直すと、今日の式になる。

  錯乱円の半径 [画素] = L × (1/S − 1/z)
  L = A × 画面の高さ[画素] / (4 tan(画角/2))           … レンズの係数 [画素・m]

自己チェックは L = 10、S = 2m で「ピント 0 / 無限遠 +5 / S/2 −5 / S/4 −15 画素」を見ている。近似の誤差は f / S で、画角 35 度・f/1.4・ピント 3.2m・奥行き 10m では「2.93 画素 / 薄レンズの式 2.97 画素(差 1.2%)」。

錯乱円は深度バッファの値の1次式でもある。深度は 1/z に比例して並ぶ(Day 7)ので、1/z の1次式はそのまま深度の値の1次式になる(自己チェック: 0.5〜50m の5点で直線からのずれ 4.4E-15 画素)。「手前ほど深度の刻みが細かい」のと「手前ほどボケが急に変わる」のが、同じ形をしている。

過焦点距離。無限遠のボケ L / S が 1 画素になるのは S = L のとき。そこにピントを合わせると、S / 2 から無限遠までが全部1画素以内に収まる。

  決めの構図: 画角 40°・f/1.4・画面の高さ 640 → L = 10.35 [画素・m]  → ピント 10.5m は過焦点距離そのもの

今日の冒頭の話で、決めの構図に被写界深度を入れても1画素も変わらない(完成条件1)。

L をもう一度読み直すと、無限遠のボケの直径(画面の高さに対する割合)は A ÷ (2 S tan(画角/2))——口径を、ピントの奥行きで画面に写る範囲の高さで割ったもの。センサーの大きさも焦点距離も残らない。

  口径 A = 焦点距離 / F 値 = 0.012 / (F 値 × tan(画角/2))   [m]

4. 散らすものを、集めるで書く — 相手の半径で届くかを決める

ピントの外れた点は、画面の上で錯乱円に広がる——「点がまわりへ光を配る」処理(scatter)。点ごとに円を描けば素直だが、画素の数だけ円を描くことになる。そこで画素シェーダで裏返し、「まわりの点のうち、誰の円が自分まで届いているか」を集める(gather)。

素朴な集め方は「自分の錯乱円の中を平均する」。これは2つの場面で壊れる(F5 で見られる)。

場面素朴に集めると本当は
ぼけた背景の画素の隣に、ピントの合った物背景の円の中に物が入るので、物の色が背景ににじみ出す(ハロー)物は点なので背景まで光を配らない
ピントの合った背景の画素の隣に、手前のぼけた物自分の半径は 0 なので何も集めない。手前のボケが物の輪郭で切り抜いたように止まる手前の物の大きな円が、背景の上まで被さる

どちらも「自分の半径で決めた」のが原因で、正しくは相手の円が自分まで届くかで決める。そこで2つの層に分ける。

層混ぜる条件重み何になるか
奥の層自分と相手の小さいほうの半径が、距離に届く1(平均)その画素の背景。ピントの合った相手(半径 0)は混ざらない
手前の層相手の半径が距離に届く(R / 相手の半径)²上に被さる半透明の膜。重みの和 ÷ 点の数 = どれだけ覆うか

手前の層の2乗は光の量の保存。半径 rs の円に配られる光は、1画素あたり 1 / (π rs²) に薄まる。撒いた1点は π R² / N の面積を代表しているので、1点ぶんの重みが (R / rs)² / N になる——大きくぼけた物ほど薄く広く被さる。手前の層は色 × 覆いの「前掛けのアルファ」で書いておく(双線形で読んでも、覆いの無い画素の意味の無い色が混ざらない)。

自己チェック(128x64 の作り物の絵。無限遠のボケ半径 8 画素、16x16 の明るい四角の縁から 4.5 画素の画素を見る):

  ピントの合った四角が、ぼけた奥の前   … 散らし 0.013 / 素朴 0.164       (ハローが出ない)
  手前にぼけた四角が、ピントの合った奥の前 … 散らし 0.149 / 素朴 0.000   (円の欠けた部分の面積の割合は 0.16)

5. 升目 — 近所でいちばん大きく配っている物を、先に記録する

集めるには「どこまで探すか」が要る。自分がぼけていなくても、隣の手前の物の大きな円が自分まで届く。探す範囲を画面全体の最大に固定すると、ほとんどぼけていない画素でも遠くまで探すことになり、決まった数の点(48 点)がまばらに散る。

そこで画面を 16 画素の升目に切り、升目ごとに「いちばん手前の錯乱円」と「いちばん速い速度」を記録し、さらに 3x3 の近所で最大を取る (McGuire 2012 の TileMax / NeighborMax)。Day 53 で光を升目に振り分けたのと同じ発想で、今度は升目に「ぼけの届く範囲」を振り分ける。速度を記録するのは Day 55b のモーションブラーのため。動く物の尾も、隣の升目から自分まで伸びてくることがある。今日は速度を渡さないので、その欄は 0 のまま。

ぼけの半径の上限を升目の大きさ(16 画素)にしてあるのが肝。3x3 の近所は自分の升目からどの向きにも 16 画素以上を含むので、半径 16 画素までのぼけなら、自分に届く物を必ず近所の最大に数えている。これを超えると、ぼけが升目の形に切れる。

升目の最大は、横と縦の2段で取る。1段で 16x16 をなめると、1画素が 256 回読む。升目は 960x640 で 2400 個しかないので、GPU が同時に走らせる画素が足りず、待ち時間を隠せない。最大は「横の最大の、縦の最大」に分けても同じ答えになる(Day 31 のぼかしを縦横に分けたのと同じ理屈)。同じ構図で 0.35ms → 0.09ms(検証の途中で分かったこと 2)。

6. 半分の大きさで集め、原寸で重ねる

ぼけたものは縮めても分からない(Day 31 のブルームと同じ)。被写界深度は1画素あたり 48 点を読むので、集める仕事は半分の大きさでやる。

  1. 下ごしらえ(半分): 2x2 画素の平均の色と、いちばん手前の錯乱円(ピントの合った物と奥が同じ 2x2 に入ったら、ピントの合った物が勝つ——奥のボケににじまない)
  2. 集める(半分、2枚同時。Day 52a の MRT): Vogel の円盤(i 番目の点を半径 √((i + 0.5) / 48)、角度 i × 黄金角に置く)に 48 点を撒き、奥の層と手前の層
  3. 重ねる(原寸): 原寸の絵 → 奥がぼけた分だけ奥の層に差し替え → 手前の層を被せる

半径 1〜2 画素でなめらかに切り替え、1 画素より小さいボケは原寸の絵のままにする。半分の大きさの絵は 2 画素より細かいものを持っていないので、そこで差し替えると逆にぼけすぎる。切り替えに使う錯乱円は原寸(半分の大きさの錯乱円だと、ピントの帯の縁が 2x2 のギザギザになる)。

Day 55b のモーションブラーは原寸のまま走らせる。尾は向きのあるぼけで、横に流れる絵でも縦の目地はくっきり残る——縮めると、残るべき縦の細部まで失う。

改造課題

課題1(易): ボケを六角形にする

本物のレンズの穴は絞り羽根で作る多角形なので、明るい点のボケは多角形になる(6枚羽根なら六角形)。dof-gather.frag の円盤の点を六角形の中に撒き直し、届くかどうかも六角形で判定する。

glsl
// 角度 angle の向きの、半径 1 の六角形の縁までの距離(内接円の半径は cos(π/6))
float Hexagon(float angle)
{
    const float Sector = 3.14159265 / 3.0;
    return cos(Sector * 0.5) / cos(mod(angle, Sector) - (Sector * 0.5));
}

撒く点は r × Hexagon(angle) に置き直し、Cover(radius, r) の半径にも同じ向きの Hexagon を掛ける(相手の円が六角形になる)。「ディファード」ページの F4(夜にする)と F3(点光源 64 個)で光を撒いてから、ピントを手前に外すと、光が六角形のボケになる。六角形の角が画面に対して回らないのは、本物のレンズと同じ(羽根はレンズに固定されている)。

課題2(中): オートフォーカス — 画面の真ん中にピントを合わせる

いまのピントは注視点まで。画面の真ん中の深度を読んでピントにする(カメラのオートフォーカス)。素直に glReadPixels で深度の写しの真ん中を1画素読むと、GPU がこのフレームを描き終わるまで CPU が待たされる(GpuTimer が避けた待ち方そのもの)。

GpuTimer と同じ輪の考え方で、読み戻しをピクセルバッファ(GL_PIXEL_PACK_BUFFER)に数本積み、数フレーム遅れて届いたものを拾う。届いた奥行きにそのまま合わせると、カメラが揺れるたびにピントが跳ねるので、FollowCamera の追従と同じ指数平滑(Day 51 の要点1)でゆっくり寄せる——映画の「ピント送り」になる。GPU の時間(HUD)に、待ちが乗っていないことも確かめる。

課題3(難): 画面の端のボケを猫目にする

本物のレンズは、画面の端へ行くほど斜めに入る光が鏡筒の縁で削られ、丸いボケがレモン形(猫目)に欠ける(口径食)。点のボケの形を「半径 rs の円」と「同じ半径の円を、画面の中心の向きに k × (画面の中心からの距離) × rs だけずらしたもの」の重なりにする。

dof-gather.frag の「相手の円が自分まで届くか」(Cover)を、「自分が相手の形(2つの円の重なり)の中にいるか」に置き換える。判定するのは相手の形なので、ずらす向きと量は自分ではなく相手の画面の位置で決めること(散らしを集めるで書いた裏返しがここでも効く。要点4)。円盤に撒く点の範囲は今日のままでよい(重なりは元の円より小さいので、探す半径は足りている)。

確かめ方は2つ。k = 0 で今日の絵と1画素も変わらないこと。課題1と同じ手順で光を撒いてピントを手前に外すと、画面の真ん中のボケは丸いまま、四隅のボケが中心を囲むように細くなること(レモンの長い向きが、中心からの向きと直角になる)。

検証の途中で分かったこと

1. 決めの構図に被写界深度を入れても、1画素も変わらなかった(今日の冒頭の話)。最初に疑ったのは「掛かっていない」ことで、HUD は 被写界深度:ON、パスの数も 11 → 18 に増えていた。錯乱円を見ると、ピントの帯に何も無い構図の中で、奥の壁でも半径 1 画素に届いていない。計算すると、画角 40 度・f/1.4・画面の高さ 640 のレンズの係数は L = 10.35 [画素・m] で、無限遠のボケが 1 画素になるピントの奥行きがちょうど 10.35m——決めの構図のピント(10.5m)はほぼ過焦点距離だった。重ねる段は半径 1 画素未満を原寸の絵のまま出すので、差は 0 になる。物理に合わせたボケは、思ったよりボケない。映画の絵がボケて見えるのは、寄っているか、望遠で撮っているか(同じ F 値で画角を半分にすると約4倍)。デモの絵づくりでボケを使うなら、ショットごとに画角と F 値を決めることになる(Day 56 の仕事)。

2. 升目の最大を1段で取ると、地図が被写界深度と同じくらい重かった。GPU の時間を見ると、奥行きと錯乱円を出すだけのはずの「地図」が 0.35ms で、48 点を読む被写界深度の本体(0.5ms)と変わらなかった。原因は升目の段で、16x16 を1画素で全部なめるので1画素が 512 回読む(速度と錯乱円)。升目は 960x640 で 2400 個しかなく、GPU が同時に走らせて待ち時間を隠すには少なすぎる。横 16 → 縦 16 の2段に分けると、1段目は 60x640 = 38400 画素がそれぞれ 16 画素ずつ読むだけになり、同じ構図で 0.35ms → 0.09ms になった。「読む回数の合計」より「同時に走る画素の数」が効く場面で、GPU の書き方としていちばん大事な勘所の1つ。

3. カメラワークを再生したままプレイアブルデモに入ると、追従カメラが勝手に回った(Day 51 からの不備。Day 51 まで遡って直した)。検証用の手順で、カメラワークを回したあとにキツネを出したら、内訳のピントが 3.20m(『ゴミ箱の金属』の距離)になっていた。追従カメラの距離のはずが、カメラワークのショットの距離になっていた。UpdateDemoCamera は再生中なら _orbit の方位・仰角・距離を毎フレーム書き、UpdateFollowCamera はそれを借りて目の位置を決めるので、追従カメラがショットの並びに引きずられてキツネのまわりを回っていた。設計書は Day 51 から「プレイアブルデモとカメラワークは排他」と書いていたが、ShowPlayableDemo が止めていたのは機能ツアーだけだった。_cameraPlaying = false の1行を足し、Day 51〜54b の reference にも同じ場所・同じ文面で入れた(Mesh.ReadIndices を Day 35 まで遡って直したのと同じ扱い)。文面を揃えてあるので、Day 54b と今日の差分には出ない。すでに Day 51〜54b を写経していれば、その1行を足し直すこと。

4. 「ピントの合った絵は変わらない」が 2E-4 で落ちた。被写界深度は何もしていないのに、出てきた絵が作った絵と 0.0002 違った。0.2 と 0.8 の市松模様を RGBA16F に流し込んだ時点で、0.8 が 0.7998 に丸まっていた(16F は 0.5〜1.0 で 0.0005 刻み)。比べる相手を「流し込んだ絵を読み返したもの」にすると差は 0 になった。確かめたいものの手前で、入力が丸まっていないか——Day 54a で深度テストを切ったまま描いていた話と同じ種類の、検査側の穴。

5. 明るい点のボケの縁が、半径より 4 画素外まで広がっていた。「半径 7.8 の円の外は真っ暗」を半径 11 で見ると 0.013 残っていた。半分の大きさの絵を双線形で2回読む(集めるときと、原寸で重ねるときのテント)ので、縁が 1 回につき 2 画素ずつなだらかになる。半径 12 の外では 0.004。半分の大きさで集める代金は、ボケの縁の甘さで払っている。ボケは縁が柔らかいほうが自然に見えるので、実害は無い。
