今日いちばん意外だったのは、「共有メモリで畳んだほうが速い」が、このカードでは出なかったこと

100 万個の atomicAdd を2つの番地にぶつける素朴な書き方と、共有メモリで畳んでから 4096 回だけぶつける書き方を、同じフレームの中で続けて 7 通りの条件で測ったら、差は ±7% の中に収まり、どちらが速いかも測るたびに入れ替わった。VRAM を叩く回数は 256 倍違うのに、である。理由は2つあって、(1) 最近の GPU はワープの中の atomic をまとめてから1回だけ発行する、(2) そもそもどちらも 32MB を読むところで頭打ちになっている(実測 373〜399GB/s。RTX 3070 の帯域は 448GB/s)。しかも最初は「共有 1.22ms ↔ atomic 0.63ms で2倍」という数字を出していた——片方ずつ切り替えて測っていて、その間に GPU のクロックが変わっていた(検証の途中で分かったこと 1)。畳み込みの値打ちは「速いから」ではなく「VRAM を叩く回数を設計で決められるから」のほうにある(要点6)。

今日いちばん大事な3つ

1つ目は「コンピュートは、出口の無いシェーダ」。頂点シェーダには「次の段へ渡す頂点」、画素シェーダには「フレームバッファの画素」という決まった出口があった。コンピュートシェーダには出口が無い。代わりに、自分で書いた場所がそのまま結果になる。だから GL は「どこに何を書いたか」を知らず、書いたものを別の経路で読む前に glMemoryBarrier が要る(要点5)。

glsl
// particle-sim.comp。この1本が 100 万回走る
layout (local_size_x = 256) in;                    // ← 塊の大きさ(コンパイル時に決まる)
layout (std430, binding = 0) buffer Particles { Particle particles[]; };

void main()
{
    uint index = gl_GlobalInvocationID.x;          // 自分は通しで何番目か
    if (index >= uCount) { return; }               // ← 切り上げたぶんの番人(要点2)
    ...
    particles[index] = p;                          // ← 出口はこれだけ
}

2つ目は「バッファは型を持たない」。OpenGL のバッファオブジェクトはただのバイト列で、何であるかは挿した口が決める。GL_SHADER_STORAGE_BUFFER に挿せば SSBO、GL_ARRAY_BUFFER に挿せば頂点バッファ。同じ1本を両方に挿せるので、コンピュートが書いた結果を、写し替え無しでそのまま描ける(要点4)。これが無いと 100 万粒 = 32MB を毎フレーム CPU へ往復することになり、GPU で計算した意味がそこで消える。

3つ目は「速いのは計算。高いのは持って帰ること」。100 万粒を進めるのが 0.18ms、数えるのが 0.09ms なのに対して、その結果の 8 バイトを CPU が読むと 0.1〜3.5ms 止まる(要点7)。理由はバイト数ではなく、glGetBufferSubData が「その時点の中身」を約束するためにGPU が追いつくまで CPU を待たせるから。Day 54 の GpuTimer がクエリを輪にして「数フレーム前の結果」を拾っていたのと、まったく同じ形の問題になる。

理論の要点

1. コンピュートシェーダ — 出口の無いシェーダと、ワークグループ

描画のシェーダには決まった入口と出口がある。頂点シェーダは頂点属性を受け取って gl_Position を返し、画素シェーダは補間された値を受け取ってフレームバッファへ色を返す。間の段(ラスタライズ・深度テスト・ブレンド)は GPU の固定機能。

コンピュートシェーダには、その入口も出口も無い。あるのは「自分が何番目か」だけ。

頂点 / 画素コンピュート
入口頂点属性 / 補間された値番号(gl_GlobalInvocationID)だけ
出口gl_Position / FragColor無い。自分で書いた場所が結果
何個走るか頂点の数 / 画素の数(GPU が決める)glDispatchCompute で人が決める
走る単位ワープ/ウェーブ(見えない)ワークグループ(見える。大きさを決められる)

呼び出しは「ワークグループ」という塊に分かれて走る。

決まるところ今日の値
ワークグループの大きさlayout (local_size_x = N) in;。コンパイル時の定数64 / 128 / 256 / 1024(F5)
ワークグループの数glDispatchCompute(x, y, z)。実行時100 万 ÷ 256 = 4096
呼び出しの総数大きさ × 数1,048,576

塊に分かれているのはGPU の作りがそうだから。1つのワークグループは必ず1つの演算ユニット(NVIDIA なら SM、AMD なら CU)に載り、その中でだけ共有メモリと barrier() が使える。別のワークグループどうしは、走る順番も、同時に走るかどうかも決まっていない——だからグループをまたいで待ち合わせる手段は無い。

大きさを uniform にできないのは、shared 配列の大きさとして使うから。配列の大きさはコンパイル時に決まっていなければならないので、64 と 256 を見比べるには焼き直すしかない。そこで #version の次の行に #define LOCAL_SIZE 64 を差し込んでコンパイルし直す(Shader.InjectDefines)。本物のエンジンが「シェーダバリアント」と呼んでいるものの、いちばん小さい形になる。

2. 切り上げと番人 — ディスパッチの数え違いは静かに壊れる

glDispatchCompute に渡すのはワークグループの数であって、呼び出しの数ではない。100 万粒を 256 ずつ処理するなら、渡すのは 3907(= ⌈1,000,000 / 256⌉)。

ワークグループは丸ごとしか走らせられないので、3907 × 256 = 1,000,192 呼び出しになり、192 個が余る。余ったぶんが particles[1000000] 以降を書かないように、シェーダの先頭で弾く。

glsl
uint index = gl_GlobalInvocationID.x;
if (index >= uCount) { return; }     // ← これが無いと配列の外を書く

書き忘れたときの壊れ方が厄介で、SSBO の範囲外アクセスは落ちない。仕様は「書き込みが捨てられるか、バッファの中のどこかに落ちる」と決めていて、後者なら関係ない粒が壊れる。落ちてくれないぶん、原因が「粒が数個だけ変な方向に飛ぶ」という形でしか出てこない。

逆方向の間違い——粒の数をそのままディスパッチに渡す——もよく起きる。これは 256 倍のワークグループが走るだけで答えは合うので、絵を見ても気づけない。今日の数(6.5万・26万・100万)はどれも 256 の倍数なので余りが 0 になる。自己チェックが 1,000,000 という割り切れない数をわざわざ持ち出しているのはそのため(完成条件 7 の3項目め)。

3. SSBO と std430 — C# の構造体と1バイトずつ合わせる

SSBO(シェーダストレージバッファ)は OpenGL 4.3 で入った、シェーダから読み書きできる大きなバッファ。Day 53 で光の一覧を渡すのに TBO(テクスチャバッファ)を選んだのは、あのときのエンジンが 3.3 だったからで、4.3 に上げた今は SSBO がそのまま使える(Day 53 の計画書の表の3行目)。

std430 は詰め方の決まりで、std140 との違いが落とし穴になる。std140 は配列の要素を必ず 16 バイト境界に丸めるので、float の配列が4倍に膨らむ。std430 はそれをしないので、C# の構造体とそのまま突き合わせられる。

ただし vec3 が 16 バイトに整列する(12 ではない)という規則は std430 にも残る。今日の粒はそこを踏まえて組んである。

   0    4    8   12   16   20   24   28   32
   +----+----+----+----+----+----+----+----+
   |  position (vec3)  |age |  velocity (vec3) |life|
   +----+----+----+----+----+----+----+----+

vec3 のうしろに float を置いて 16 バイトぴったりにする、という組み方。age を抜くと velocity の前に 4 バイトの穴が空いて、C# 側と 4 バイトずれる。ずれると「速度を位置として読む」ことになり、粒が明後日の方向へ飛ぶだけでエラーは1つも出ない。自己チェックが Marshal.OffsetOf で 12 / 16 / 28 を確かめているのはこのため。

4. バッファは型を持たない — SSBO のまま頂点として読む

今日いちばん効く1手。OpenGL のバッファオブジェクトは中身に型を持たないただのバイト列で、「何であるか」は挿した口(ターゲット)が決める。

csharp
// GpuParticles.CreateVertexArray。同じ _particleBuffer を GL_ARRAY_BUFFER へ挿す
_gl.BindVertexArray(array);
_gl.BindBuffer(BufferTargetARB.ArrayBuffer, _particleBuffer);   // ← SSBO と同じ1本

_gl.VertexAttribPointer(0, 3, Float, false, 32, (void*)0);      // position
_gl.VertexAttribPointer(1, 1, Float, false, 32, (void*)12);     // age
_gl.VertexAttribPointer(2, 3, Float, false, 32, (void*)16);     // velocity
_gl.VertexAttribPointer(3, 1, Float, false, 32, (void*)28);     // lifetime

std430 の並びが、そのまま歩幅 32 バイトの頂点配列として読める。写し替えは1バイトも要らない。もしこれが無ければ、コンピュートの結果を CPU へ戻して頂点バッファへ詰め直すことになる——100 万粒で毎フレーム 32MB の往復(実測で片道 10.3ms)。GPU で 0.2ms かけて計算したものを、運ぶのに 50 倍かけることになる。

描くのは GL_POINTS。粒1つにつき頂点1つで、四角形を張らない。

5. メモリバリア — 「書いた」と「読める」は別

コンピュートが SSBO へ書いた値を、そのあとの描画が頂点属性として読む。この2つの間には順序の保証が無い。

GL は命令を積んだ順に実行するが、シェーダが自分で書いたメモリが他の経路から見えるようになる時期までは約束していない。画素シェーダの出力のような「決まった出口」は GL が面倒を見てくれるが(要点1の裏返し)、コンピュートが particles[i] = p; と書いた場所は書いた本人にしか分からないので、面倒の見ようがない。

6. 共有メモリとアトミック — 畳み込みと、測ってみたら差がほとんど無かった話

「生きている粒が何個か」を GPU に数えさせる。C# なら foreach で sum++ するだけだが、GPU では 100 万個が同時に走るので、その sum++ が全部ぶつかる。「読んで、足して、書く」の間に割り込まれると、足したはずの値が消える。

割り込まれない足し算が atomicAdd。ただし同じ番地への atomic は順番待ちになるので、100 万回ぶつけると、そこが1本の行列になって並列性が消える……というのが教科書の話。

そこで2段にするのが定番(リダクション)。

glsl
shared uint sAlive[LOCAL_SIZE];        // ワークグループの中だけで見えるメモリ

sAlive[local] = alive;
barrier();                             // 全員が書き終わるまで待つ

for (uint stride = LOCAL_SIZE / 2u; stride > 0u; stride >>= 1u)
{
    if (local < stride) { sAlive[local] += sAlive[local + stride]; }
    barrier();                         // ← if の外。全員が同じ回数通る
}

if (local == 0u) { atomicAdd(aliveCount, sAlive[0]); }   // グループにつき1回

barrier() の置き場所が制約そのものになっている。barrier() はワークグループの全員が同じ回数通ることが条件なので、if の中に入れてはいけない。同じ理由で、このシェーダは範囲外の呼び出しを早期 return させられない——帰ってしまうと残りが永久に待つ。だから「帰る」のではなく「0 を持って参加する」と書いてある(要点2の番人とは書き方が変わる)。

もう1つの制約は GLSL 4.3 の atomicAdd が整数にしか無いこと(float 版は NV_shader_atomic_float などの拡張)。高さの合計は uint(clamp(y, 0, 20) * 100) と固定小数にしてから足している。上限を決めてあるのは桁あふれのためで、1個あたり最大 2000 × 100 万個 = 2.1e9 が uint の 4.29e9 に収まる。外すと静かに一周する(エラーは出ない)。

  2. そもそも両方とも 32MB を読むところで頭打ち。いちばん速い行(0.084ms)で33.5MB ÷ 0.084ms = 399 GB/s。RTX 3070 のメモリ帯域 448 GB/s の 89% で、もう読むこと以外にはほとんど時間を使っていない。共有メモリの木(8段の barrier())と atomic の発行の差は、その残り 1 割の中の話になる

畳み込みの値打ちは速さではなく、VRAM を叩く回数を設計で決められることにある。出力の番地が1つしかない場合、入力がもっと多い場合、ワープをまたいで値を共有したい場合(接頭辞和・ソート・ビットニックなど)には、共有メモリでしか書けない。今日ここで書いた形は、その入口になる。

7. 読み戻しが同期を呼ぶ — 8 バイトで数ミリ秒

集計は uint 2つ、たった 8 バイト。それを CPU が読むのに 0.1〜3.5ms かかる。

csharp
_gl.GetBufferSubData(BufferTargetARB.ShaderStorageBuffer, 0, 8, pointer);

glGetBufferSubData は「その時点の中身」を返す約束なので、GPU が積まれた命令を全部こなすまで CPU が待つ。高いのはバイト数ではなく、CPU と GPU の並走が切れることそのもの。GPU は普段 CPU より1〜2フレーム後ろを走っているので、ここで待つとそのぶん丸ごと止まる。

検証の途中で分かったこと

1. 「共有メモリのほうが2倍速い」という嘘の数字を、危うくそのまま書くところだった(今日の冒頭の話)。最初は F6 で片方ずつ切り替えて測っていて、次の数字が出た。

測った順数え上げGPU の時間そのときの「進める」
1回目共有メモリ1.221ms2.175ms
2回目全部 atomicAdd0.633ms1.158ms

「共有メモリのほうが2倍遅い」と読めるが、同じフレームで測っていない。右端の「進める」(どちらのときもまったく同じ処理)が 2.175 → 1.158 と半分になっていることが、そのしるしになる。VSync を入れていると GPU は1フレームのうち 1ms しか働かないので深く休み、負荷が続くとクロックが上がる。切り替えの前後で、GPU が別の速さで走っていた。

直し方は「同じフレームの中で、続けて両方走らせる」。クロックの揺れは両方に等しく乗るので、比のほうは信用できる。ReductionMode.Both を既定にして、タイマーも2本に分けた。測り直すと差は ±7% の中に収まり、向きも一定しない(要点6)。

Day 54 の計画書が「VSync 中はクロックが上下して走行ごとに倍以上ぶれる」と書いていたのと同じ罠だが、あのときは「絶対値がぶれる」話だった。今日は2つを比べる話で、ぶれが片方にだけ乗ると結論そのものが逆になる。

2. 加算合成は、粒の数をそのまま明るさにする。最初は1粒の明るさを固定していて、26 万粒で既に画面の半分が真っ白、100 万粒では床も立方体も見えない白い塊になった。加算合成は重なったぶんが足し算なので、個数を4倍にすると絵が4倍明るくなる——考えれば当たり前だが、Day 49 の1万粒では気づけない(重なりが浅いので飽和しない)。直し方は「群れ全体の明るさを決めて、個数で割って配る」(GpuParticles.ParticleIntensity)。基準を 65,536 個に置くと、6.5 万・26 万・100 万のどれで見ても同じ明るさになり、変わるのは粒の細かさだけになる。本物のエンジンがエフェクトの明るさを「1粒いくら」ではなく「この炎ぜんぶでいくら」で持っているのは、これが理由。

3. 筋書きを切り替えた直後、数秒間だけ形が違った。渦に切り替えると、最初の数秒は床に貼り付いた平たい円盤で、柱になるのは 6 秒後(寿命ぶん)だった。撒き直し(uReset)が全員を撒き口に置いていたため。寿命の途中の齢を配るだけでは足りない——齢を配っても位置は撒き口のままなので、脈打ちは消えても形は出ない。そこでそのぶん先へ進めた位置から始めるようにした(噴水は放物運動の式で厳密に、渦は上向きのぶんだけ、引力は殻がそのまま定常なので送らない)。3つで扱いが違うのは、「だいたい定常の形」で始められればよいから。

4. 引力の粒が、全部まとめて中心の1点に落ちた。最初は接線方向へ「適当な速さ(2〜3.5 m/s)」で蹴り出していて、1秒後には直径 1m ほどの真っ白な玉になっていた。円軌道の速さは距離で決まる(v = sqrt(GM / r))ので、半径 3m の粒には 4.5 m/s が要る——遅い粒は全部まっすぐ落ちる。距離から速さを出すようにし(0.8〜1.3 倍に散らして楕円にする)、減速も 0.15/s から 0.02/s に下げたら、殻のまま回り続けるようになった。物理を並列にしても物理は物理で、初期値の与え方を間違えれば同じように壊れる。

5. #define を差し込むと、コンパイルエラーの行番号がずれる(先に潰した)。InjectDefines は #version の次の行に割り込むので、素直に書くとログの行番号がファイルより差し込んだ行数ぶん大きくなる。Day 14 で「ログの行番号はファイルの行番号と一致するので、ファイル名を添えておくとエディタからそのまま飛べる」と書いた性質が、そこで壊れる。差し込みの最後に #line 2 を置いて数え直させると一致したまま保てる(GLSL の #line N は「次の行は N 行目」の意味)。ワークグループを切り替えるたびに焼き直す作りなので、ずれたまま運用すると効いてくるのは間違いない——シェーダを書き換えている最中に、ログの行番号だけが1つずれているのがいちばん気づきにくい。
