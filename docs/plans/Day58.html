今日いちばん大事な3つ

1つ目は「返った距離だけ進めば、踏み越えない」。距離関数が h を返したということは、半径 h の球の中には何も無いということ。だから光線を h 進めても、途中で面を通り過ぎることはない。これを繰り返すのが球面追跡(sphere tracing)で、レイマーチングの安全の全部はこの1行にある(要点2)。

glsl
// raymarch.frag の march。この for が画素ごとに走る
for (int i = 0; i < MAX_STEPS; i++)
{
    float h = map(origin + direction * t).x;   // いちばん近い面までの距離
    if (h < uHitEpsilon * t) { return ...; }     // 1画素より十分近づいた = 当たり
    t += h * uStepScale;                         // ← 返った距離だけ進む。uStepScale は普段 1
    if (t > uMaxDistance) { break; }             // 空へ抜けた
}

裏返すと、距離関数が本当の距離より長い値を返すと壊れる。ねじった柱がまさにそれで、F5 を切ると光線が面の中へ踏み込んで止まり、柱の縁がガタガタに崩れる(要点5)。

2つ目は「形は、点のほうを動かして作る」。SDF は「点に聞く関数」なので、形を回したければ聞く点を逆に回す。形を無限に並べたければ、聞く点を升目1つに畳む。形どうしは min(和)・max(積)・smin(滑らかな和)で組む。

glsl
vec3 carved = rotateY(p - vec3(-1.5, 0.15, 0.0), -uTime * 0.5);    // 形を +θ 回す = 点を −θ 回す
float carvedBox = max(sdRoundBox(carved, vec3(0.55), 0.05),        // 箱の中で、
                      -sdSphere(carved, 0.72));                     // かつ球の外 = くり抜き

vec3 q = repeatXZ(p, CELL_SIZE);                                    // 1本ぶんの式で、柱が地平線まで並ぶ

メッシュなら頂点を足し、モデル行列を掛け、インスタンスを並べていたものが、全部「点の座標をいじる」と「距離を比べる」になる(要点4)。

3つ目は「深度を書けば、エンジンの一員になる」。当たった点をビュー射影で写し、ラスタライズと同じ約束で gl_FragDepth に入れる。

glsl
vec4 clip = uViewProjection * vec4(p, 1.0);
gl_FragDepth = (clip.z / clip.w) * 0.5 + 0.5;    // ← ラスタライザが頂点にやっていることと同じ

理論の要点

1. 符号付き距離関数 — 形を「点に聞く関数」で持つ

SDF(signed distance function)は、点 p を渡すと、いちばん近い面までの距離を返す関数。外なら正、中なら負、面の上で 0。

glsl
float sdSphere(vec3 p, float radius) { return length(p) - radius; }

球ならこれだけで、中心からの距離から半径を引けば、そのまま面までの距離になる。箱も1行の式で書ける(Sdf.Box)。

メッシュSDF
形の置き場所頂点バッファ(VRAM)関数の中(シェーダのコード)
「ここは中か外か」分からない(聞く手段が無い)符号を見れば分かる
「いちばん近い面までどれだけか」全部の三角形と比べる1回呼べば分かる
角を丸める頂点を足す距離から半径を引く(sdRoundBox)

「本当の距離」を返す SDF は、傾きがどこでもちょうど 1 になる(1m 動けば、距離はちょうど 1m 変わる向きがあり、それより速くは変わらない)。自己チェックの1項目めは、球・箱・トーラスの外側の 11,796 点で傾きを測り、1 からのずれが最大 7.3e-4(差分の誤差ぶん)だと確かめている。

ただし本当の距離である必要は無い。要るのは「本当の距離を超えない」ことだけで、短めに見積もるぶんには光線が少し余計に歩くだけで済む(要点2・5)。この3種類を区別しておくと、今日の話が全部読める。

返す値傾き球面追跡今日の例
本当の距離(exact)ちょうど 1最短の歩数で当たる球・箱・トーラス
短めの見積もり(bound)1 以下安全。歩数が少し増える滑らかな和・差・積
長めの見積もり1 を超える踏み越える。歩幅を縮めないと壊れるねじれ

2. 球面追跡 — 返った距離だけ進めば、踏み越えない

光線の上の点 origin + direction × t で距離関数を呼び、返った h だけ t を進める——を繰り返す。半径 h の球の中には何も無いので、h 進んでも面を通り過ぎない。面に近づくほど h が小さくなり、歩幅も縮んでいく。

終わり方は3通り。

出口条件画素の色
当たりh < ε × t(ε = 0.0005)陰影を付ける
外れt > 80m空(ラスタと混ぜるときは捨てる)
歩数切れ128 歩空。当たったとは言えない

当たりの幅を t に比例させているのが1つ目の工夫。960x640・画角 60° なら、1画素の幅は距離 t のところで t × 2tan(30°) / 640 ≒ 0.0018t。その4分の1(0.0005t)まで寄れば画素の中では区別がつかないので、遠い画素ほど粗く止めてよい。決まった幅(1mm)にすると、遠くの画素ほど必要以上に面へ寄ってから止まることになり、そのぶん余計に歩く。

かすめる光線が高いのが2つ目の要点。F8 で面の真正面の画素を追うと数歩で当たるが、形の縁の画素は h が縮まないまま少しずつしか進めない。自己チェックの6項目めは、「積」の形に正面から当てる光線が 2 歩、その上の面の 2cm 上をかすめて抜ける光線が 66 歩だと確かめている。F4 の歩数の表示で形の縁と地平線だけが赤くなるのはこのため(地平線は、床とほぼ平行な光線が床をかすめ続ける場所)。

h が毎歩およそ 0.7 倍ずつ縮んでいる。床に角度 θ で入る光線は、1歩ごとに床までの高さが (1 − sinθ) 倍になるので、当たりに近づくほど1歩が小さくなる。最後の h(4.8mm)が当たりの幅(5.6mm)を割ったところで止まる——つまり球面追跡は必ず面の手前で止まる。どれだけ手前かは「当たりの幅 ÷ 床に入る角度の sin」まで広がりうる(自己チェックの9項目め。完成条件)。

3. 画素から光線を作る — ビュー射影の逆行列

画素の中心 gl_FragCoord.xy を NDC(−1〜1)に直し、ビュー射影の逆行列で近クリップ面(z = −1)と遠クリップ面(z = +1)の点へ戻す。その2点を結んだものが、その画素の光線になる。

glsl
vec2 ndc = (gl_FragCoord.xy / uResolution) * 2.0 - 1.0;

Shadertoy の作品はカメラの位置と向きと画角から光線を組み立てることが多いが、エンジンの中では逆行列のほうが素直になる。理由は3つ。

4. 形を組む — min / max / smin と、点を動かすこと

形どうしの組み合わせは、距離の比べ方で書く。

演算式意味傾き
和min(a, b)どちらかの中1 以下
積max(a, b)両方の中1 以下
差max(a, -b)a の中で、かつ b の外1 以下
滑らかな和smin(a, b, k)差が k より小さいところで min から少し引く1 以下(つなぎ目では 1 を割る)

min も max も傾きを増やさないので、本当の距離の形をいくつ組んでも「長く見積もらない」は保たれる。差と積は中身がもう本当の距離ではない(くり抜いた穴の中での距離は短めに出る)が、安全側にずれるだけ。

滑らかな和は、距離から引いている。

glsl
float smin(float a, float b, float k)
{
    float h = max(k - abs(a - b), 0.0) / k;     // 差が 0 で 1、差が k で 0
    return min(a, b) - h * h * k * 0.25;         // 差が 0 のとき k/4 だけ膨らむ
}

a と b の傾きを 0〜1 の重みで混ぜた形になるので、傾きは 1 を超えない。むしろ2つの球のつなぎ目では向きの違う傾きが打ち消し合って 0.1 まで下がる (自己チェックの2項目め)——短めに見積もるので、つなぎ目の近くでは光線が余計に歩く。

形を動かすのは点のほう。SDF は「点に聞く関数」なので、形を +θ 回したければ、聞く点を −θ 回して渡す。

glsl
vec3 ring = rotateY(p - vec3(4.5, 0.15, 0.0), -uTime * 0.7);   // 平行移動も回転も逆向きに
float torus = sdTorus(ring.xzy, 0.5, 0.18);                    // 成分を入れ替えて輪を立てる

メッシュでは「モデル行列を頂点に掛ける」だった。SDF では「モデル行列の逆行列を点に掛ける」になる。回転と平行移動は距離を変えない(剛体の動き)ので、傾きも 1 のまま。

繰り返しも点のほうで、点を「いちばん近い升目の中心から見た座標」に畳む。

glsl
vec3 repeatXZ(vec3 p, float cellSize)
{
    return vec3(p.x - cellSize * floor(p.x / cellSize + 0.5), p.y, p.z - cellSize * floor(p.z / cellSize + 0.5));
}

これで柱が地平線まで並ぶが、1歩の手間は1本ぶんのまま(F3 の2つ目の場面)。ただし条件が1つあって、形が升目の半分に収まり、升目の境目に対して左右対称でなければならない。そうでないと、隣の升目の形のほうが近いのに自分の升目の形までの距離を返し、長く見積もる。今日の柱・玉・輪が全部 y 軸まわりに回転対称で、輪の高さも全部の升目で同じなのはそのため(升目ごとに輪の高さをずらすと絵は楽しくなるが、隣の輪のほうが近い点ができる)。

丸めを round ではなく floor(x + 0.5) で書いているのは、GLSL の round が「ちょうど半分」の向きを実装に任せていて、C# の MathF.Round(偶数へ丸める)と食い違いうるから。鏡を持つなら、丸め方まで揃える。

5. 距離の約束が破れるとき — ねじれと、傾きの上限 L

点を高さに比例して回すと、柱がねじれる。

glsl
vec3 twistY(vec3 p, float rate) { return rotateY(p, rate * p.y); }

回転そのものは距離を変えないが、高さごとに回す角度が違うと空間が伸び縮みする。柱の面を向いて、軸から横に w 離れた点を真上へ 1m 動かすと、ねじった側の座標では面に沿って τw 余分に動いたことになる(τ = 1m あたりの角度)。距離の変わり方は「縦の 1」と「横の τw」の合成になり、傾きが最大

L = √(1 + (τw)²) = √(1 + (2.5 × 0.6)²) = 1.80

まで伸びる。返った距離が本当の距離の最大 1.8 倍になりうるので、そのまま進むと面の中へ踏み込む。

raymarch.frag の当たりの判定は h < ε × t で、負になった(中に入った)ときもここで止まる。踏み込んだ先で止まるので、深さも法線もずれ、柱の縁が縞と欠けになって崩れる。F5 を切って画素を2つおきに C# で追うと、当たった 98,462 画素のうち 2,637 画素が h < 0(面の中)で止まっていた(完成条件7に1本の例)。

直し方は歩幅に 1/L を掛けること(F5)。L 倍長く見積もっていても、1/L 倍しか進まなければ本当の距離を超えない。

6. 法線・影・AO — 距離関数にもう何回か聞くだけ

法線は距離関数の傾き。四面体の4つの頂点の向きに少しずつずらして聞き、向きごとに重みを付けて足す。

glsl
const vec2 k = vec2(1.0, -1.0);
return normalize(k.xyy * map(p + k.xyy * h).x + k.yyx * map(p + k.yyx * h).x
               + k.yxy * map(p + k.yxy * h).x + k.xxx * map(p + k.xxx * h).x);

4つの向きを足すと 0 になり、向きどうしの外積の和が単位行列の 4 倍になるので、Σ kᵢ f(p + kᵢh) ≒ 4h ∇f と傾きだけが残る。素直な中心差分(±x ±y ±z)なら 6 回呼ぶところが 4 回で済む。形の式を知らなくても法線が出るのがこの方法の値打ちで、自己チェックの3項目めは「積」の形の丸い面で、本当の法線とのずれが最大 0.034° だと確かめている。

影は、当たった点から光のほうへもう1本歩く。何かに当たれば影。柔らかい影は、当たらなかった光線についても途中でいちばん際どく外れたときの k × h / t を覚えておく。

glsl
result = min(result, PENUMBRA * h / t);   // h = どれだけ際どいか、t = どれだけ遠くで際どかったか
t += clamp(h, 0.02, 0.5);                 // 歩幅の下限と上限

h / t は「光線から見て、遮るものが何度の角度にあるか」に近い値で、遠くの遮るものほど少しの外れで暗くなる——半影が遮るものから離れるほど広がるのは、本物の太陽の影と同じ。Day 33 のシャドウマップで PCF を何点も取って作っていたものが、1本の光線から出てくる。

AO は、法線の向きに離れた高さ h で距離を聞く。距離が h より短ければ、そのぶん近くに何かある。Day 37 の SSAO が画面に写っているものしか拾えなかったのに対して、距離関数は場面全体を知っているので、画面の外のものも拾う。

代わりに払うのは呼び出しの回数で、その内訳が要点8になる。

鏡が要るのは、シェーダの中を覗く手段が画素の色しか無いから。傾きが 1 を超えているか、1画素で何回呼んでいるか、どこで止まったか——どれも GPU からは読めないが、同じ式を C# に持っていれば数字で出せる。Day 57 の StepFountainOnCpu と同じ役回り。

共有しているのは当たりの幅(SdfScene.HitEpsilon を uniform で送る)だけで、形の数字(位置・半径・ねじれの強さ)は両方に書いてある。片方だけ直すと、絵はそれらしく出るのに自己チェックの8項目め(GPU と C# の深さ)が落ちる——今日残した歪みの1つ目。

今日残した歪み(4つ)

1つ目: 式と数字が2か所にある。raymarch.frag と Sdf.cs / SdfScene.cs。GLSL と C# は別の言語なので、Day 57 の歪み(struct Particle が3か所)と違って #include を足しても解けない。本物のエンジンの行き先は2つで、(1) 1つの記述(ノードグラフや専用の言語)から GLSL と C# の両方を生成する、(2) 鏡を持たず、確かめたいことを全部 GPU に計算させて読み戻す。今日は「数字で確かめられる」ことを優先して鏡を残した。

2つ目: 影が片道ずつしか落ちない(F7 で混ぜたとき)。SDF の形はシャドウマップにも SSAO の幾何パスにも入らず、ラスタの箱は SDF の影の光線にも AO にも入らない。直し方は影パスでも同じシェーダを光の目から描き、gl_FragDepth を書くこと——逆ビュー射影で光線を作っているので、光の正射影の行列を渡せば平行な光線がそのまま出る(改造課題3)。UE の Distance Field Shadows のように「メッシュのほうを距離場に焼いて SDF の側へ寄せる」逆向きの解き方もある。

3つ目: 動く SDF の形は速度バッファに載らない。TAA の速度はカメラの動きを深度から計算するだけ(Day 54 の1段目)なので、回るトーラスやくっつく球には「止まっている」速度が付く。TAA は履歴を動いていない場所から読むので、動く形の縁で履歴を読み違える(今日は止めた絵でしか TAA を確かめていない)。直すには、シェーダの中で 1フレーム前の時刻でも同じ点の位置を計算し、速度を2枚目の出力に書く(Day 54 の2段目がメッシュでやっていることを、距離関数でやる)。

4つ目: 画面の全画素をなぞる。形が画面の一部にしか写っていなくても、三角形1枚が全画素を覆うので全部の画素が歩く。しかも gl_FragDepth を書くので早期深度テストが効かず、F7 でラスタの床の裏に隠れる画素も、歩き切ってから捨てられる。本物の SDF 描画は、形ごとの境界の箱をラスタライズしてそこからだけ歩き始めるか、解像度を落として歩いてから拡大する。改造課題2(ねじれの近くでだけ歩幅を縮める)は、この「形の外側では手を抜く」考え方のいちばん小さい形になる。

課題2(中): ねじれの近くでだけ歩幅を縮める

今日は F5 で場面全体の歩幅を 0.55 倍にしていて、柱から遠い空や床を歩く光線まで 1.86 倍歩いている(要点5)。距離を長く見積もるのは柱の近くだけなので、そこでだけ縮めればよい。

  1. mapTwist で、柱ごとにねじる前の外接円柱までの距離を先に出す(半径は √2 × 横の半分)
  2. 外接円柱まで 0.2m 以上あるなら、その距離をそのまま返す(外接円柱までの距離は、柱までの本当の距離より短いので安全)
  3. 近ければ、ねじった箱の距離を L で割って返す(L 倍長く見積もる関数を L で割れば、本当の距離を超えない)
  4. C# の鏡も同じにし、F5 を切った(歩幅 x1.00)まま柱の縁が崩れないこと、F9 の「進む」が 37.0 からどこまで減るかを見る

自己チェックの5項目めと10項目めが落ちるはず。なぜそれで正しいのかを説明できれば、要点5は読めている(ヒント: 「距離関数の傾きが 1 以下」は安全のための十分条件で、必要なのは「本当の距離を超えない」ことだけ)。Day 58 の設計書「今日残した歪み」の4つ目にある「形の外側では手を抜く」の、いちばん小さい形になる。

課題3(難): SDF の形に、ラスタの床へ影を落とさせる

今日残した歪みの2つ目。影パスでも同じシェーダを光の目から描く。

  1. Raymarcher に、カメラではなく行列を受け取って深度だけ書く入口を足す(DrawDepth(Matrix4x4 viewProjection, int width, int height))。色は書かないので、陰影を飛ばす uniform(uView に新しい番号)を足す
  2. RenderShadowPass の _shadow.Begin と _shadow.End の間で、_shadow.LightSpaceMatrix を渡して描く。光は正射影なので、逆行列から作った光線はそのまま平行な光線になる(要点3。平行投影でも同じ式が動く)
  3. 「シャドウマップ」の F8 で焼いたシャドウマップを隅に出し、SDF の形の影が写っていることを確かめる
  4. F7 で混ぜた状態で、Day 31 の床に SDF の形の影が落ちることを見る

見どころは深度バイアス。シャドウマップの比べ方(Day 33 の落とし穴)は三角形でも SDF でも同じ。球面追跡は「面の手前で止まる」(要点7。止まる幅 εt / sinθ)ので、光の目から焼いた深度も少し手前に出る——これが影のアクネを防ぐ下駄として効くのか、影が浮くほど大きすぎるのかを、バイアスを 0 にして確かめてみること。t は近クリップ面から測っているので、光の目の行列で ε × t がどのくらいの長さになるかを先に見積もっておくとよい。逆向き(ラスタの箱の影を SDF の形に落とす)は、raymarch.frag の shade でシャドウマップを引けばよい。

検証の途中で分かったこと

1. 本当の距離しか組んでいない場面なのに、傾きの最大が 1.014 と出た。最初の MaxGradient は、x・y・z の3方向の中心差分でベクトルを作り、その長さを傾きにしていた。自己チェックの4項目めが「基本形 1.0141 / 繰り返し 1.0138」で落ち、min と max しか使っていないのに距離を長く見積もっているように見えた。

原因は測り方で、min / max の折れ目のそばでは、x の差分は片方の形、y の差分はもう片方の形……と別々の枝の傾きを拾う。どの方向の傾きも 1 以下なのに、別々の枝の 1 を寄せ集めたベクトルは長さが 1 を超える(極端な場合 √3)。中心差分で向きだけを出し、その向きに実際に動かして距離の変わり方を割る(1本の線に沿った変わり方は折れ目をまたいでも本当の傾きを超えない)ように直したら、1.0003 になった。ねじれの 1.718 はこの測り方で出した値。

式ではなく物差しが間違っていた、という Day 57 の「クロックの違いを実力の違いと読み違えた」と同じ形の罠で、しかも「距離の約束が破れている」というそれらしい結論が出てしまうのが厄介だった。

2. ねじれの「狂った画素」が、歩幅 1 でも 1/L でも2万画素あった。最初は床を入れたまま数えていて、「歩幅 x1.00: 20,099 / x0.55: 18,587」と、縮めても1割しか減らなかった。

数が多いのは遠くの床を浅い角度で見ている画素で、当たりの幅(面からの距離 εt)が光線の向きには 1/sinθ 倍に伸びるので、歩幅によらず基準の絵(1/(2L) で丁寧に歩いた絵)と少しずつずれる。数えたいのは柱の踏み越えだけなので、自己チェックでは床を外して(ラスタと混ぜるときと同じ uGround = 0)柱だけを数えるようにした。7,145 / 47 になり、効き目がそのまま数字に出た。

3. 床の深度の比べ方を「1画素の幅」で決めていたら、窓を広げると落ちる作りだった。最初は「SDF の床とラスタの床のずれが、1画素の幅(0.0018t)より小さい」で比べていて、0.85 倍で通っていた。ところが1画素の幅は解像度で縮む(1920x1080 なら 0.0011t)のに、球面追跡が止まる幅(0.0005t / sinθ)は解像度によらない——窓を広げるだけで落ちる比べ方になっていた。止まる幅そのもので割るように直したら、ちょうど 1.00 倍が出た。最後の1歩が幅ぎりぎりで止まった画素があれば幅いっぱいまでずれうる、という理屈どおりの数字なので、「奥に出た画素が無い」と「止まる幅の2倍以内」(深度バッファの丸めのぶんの余裕)を合わせて合格の条件にした。
