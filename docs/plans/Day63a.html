今日いちばん大事な3つ

1つ目は「この段にしか見えないものがある」。頂点シェーダは自分の頂点1個しか見えないので、「この三角形はどっちを向いているか」を知る手段が無い——隣の2点が分からないと外積が取れないから。面法線・面ごとの番号・隣の三角形は、全部この段で初めて見える(要点2・3)。

理論の要点

1. 段が1つ増えると、段の間の受け渡しが問題になる

ジオメトリシェーダは入口が配列になる。triangles を受けるなら3つ、triangles_adjacency なら6つ。そして出口は画素シェーダへの1つ。つまりこの段は、同じ名前の変数を in と out の両方で宣言したくなる。

glsl
in  vec3 vWorldPosition[];   // 手前の段から(配列)
out vec3 vWorldPosition;     // ← 同じ名前は再宣言エラー

これを避けるために名前を変える(gWorldPosition にする)と、今度は画素シェーダの入口の名前が変わる。GS を挟むかどうかで画素シェーダを2本用意することになり、「GS を挟むと何 ms 増えるか」を同じ画素シェーダで比べられなくなる。

インターフェースブロックがこれを解く。

glsl
// gs.vert
out Varying { vec3 worldPosition; vec3 normal; vec4 color; vec2 texCoord; } OUT;
// gs-passthrough.geom
in  Varying { ... } IN[];
out Varying { ... } OUT;
// gs-surface.frag
in  Varying { ... } IN;

段どうしの突き合わせはブロック名(Varying)と中身の並びで決まり、手前に付ける名前(IN / OUT)はそのシェーダの中だけの呼び名になる。おかげで in と out に同じ Varying を使えて、画素シェーダは GS があるかどうかを知らずに済む。今日の「GS の値段」が成り立つのはこの1点のおかげで、自己チェックの10項目めが「素通しの GS を挟んでも 245 万成分が1つも変わらない」ことを確かめている。

2. 面法線は、この段でしか作れない

cross(b - a, c - a) は3点が要る。頂点シェーダには1点しか来ないので、どうやっても書けない。

どこで作るか何ができるかできないこと
CPU面ごとに頂点を分ければ持てる頂点が3倍に増える(立方体が 8 → 24 頂点になるのと同じ話)
頂点シェーダ頂点法線で代用丸い形だと面がばらけず、ただ膨らむ
ジオメトリシェーダ3点から作る。押し出す向きにも、平らな陰影にも使える—
画素シェーダdFdx / dFdy で近い値あれは画面の上での傾き。面の向きそのものではない

平らな陰影だけが目的なら、今は flat 補間子(provoking vertex の値をそのまま配る)のほうがずっと安い。GS が要るのは、頂点を動かすほう——今日の「面を押し出す」は、面法線の向きへ三角形ごと動かしている。

gl_PrimitiveIDIn(何枚目の三角形か)も同じ性質を持つ。頂点シェーダには「何枚目の三角形か」という概念が無い(同じ頂点が何枚もの三角形に使われるので、決めようがない)。押し出しの題材で三角形ごとに色が変わるのは、この番号を使っている。

3. 隣接付き三角形 — 6つで1枚

GL_TRIANGLES_ADJACENCY はインデックスを6つずつ束ねて1枚の三角形として読む。

      1
     / \
    0---2
   / \ / \
  5---4---3
添字何か
0, 2, 4真ん中の三角形そのもの
1辺 0-2 の向こう側の頂点
3辺 2-4 の向こう側の頂点
5辺 4-0 の向こう側の頂点

隣の三角形は (0,1,2) / (2,3,4) / (4,5,0) になる。共有する辺を逆向きに辿る並びで、これは「隣り合う2枚は辺を逆向きに共有する」= 巻き順が揃っている、という約束そのもの。

この並びは GL が作ってくれるものではない。誰が隣かは CPU 側が組んで渡す(要点4)。インデックスバッファは三角形1枚につき6つになるので、ふつうの索引の2倍の大きさになる(細かい球なら 72,960 個 → 145,920 個 = 570KB)。

4. 隣を見つけるには、先に位置で溶接する

素直に組むと、たいてい隣が見つからない。頂点が重複しているから。

形頂点なぜ重複するか
立方体8 隅を 24 頂点面ごとに法線が違う。1つの頂点は1つの法線しか持てない
UV 球(16x12)221 頂点継ぎ目の1列が2重(U が 0 と 1 で違う)。極は 17 個が同じ場所

インデックスだけを突き合わせると、隣り合う面が「別の頂点」を使っているので辺が共有されていないことになる。だから先に位置で溶接して、その上で辺をたどる。

                溶接あり            溶接なし
  立方体   8 頂点 / 18 辺 / 境界 0    24 頂点 / 30 辺 / 境界 24
  球       178 頂点 / 528 辺 / 境界 0  221 頂点 / 604 辺 / 境界 56

ぴったり一致は見ない。位置は計算で作られるので、UV 球の継ぎ目は φ = 0 と φ = 2π で作られ、sin(0) = 0 に対して sin(2π) は +1.7e-7 になる——同じ点のつもりでも同じ float にならない。0.1mm の升目で丸めてから突き合わせる(MeshAdjacency.WeldGrid)。

溶接すると潰れる三角形が出る。UV 球の極に接する四角形は、2枚のうち1枚が「3頂点のうち2つが極」になるため(16x12 の球で 32 枚)。面積 0 なので絵には出ないが、辺として数えると帳尻が合わなくなるので、組むときに外す。

隣が無い辺は、その辺の始点をもう一度書く。すると隣の三角形が潰れて面積 0 になり、シェーダ側の外積が 0 ベクトルになる——つまり必ず「裏を向いている」と判定されるので、表の面から見た端の辺は必ず輪郭として出る。「隣が無い」を番兵の番号で表さないのは、シェーダ側に分岐を足したくないから。

5. 輪郭は「表と裏の境目」。だから毎フレーム変わる

三角形が表を向いているかは、巻き順から作った法線と「面からカメラへ向かうベクトル」の内積の符号で決まる(Day 10 の背面カリングと同じ式)。輪郭(シルエット)の辺とは、片側が表・片側が裏の辺のこと。

glsl
if (!isFrontFacing(v0, v2, v4)) return;        // 真ん中が裏なら何も出さない
if (!isFrontFacing(v0, v1, v2)) emitEdge(v0, v2);
if (!isFrontFacing(v2, v3, v4)) emitEdge(v2, v4);
if (!isFrontFacing(v4, v5, v0)) emitEdge(v4, v0);

表の側からだけ出すのが要点。輪郭の辺は必ず「表の三角形」と「裏の三角形」で共有されているので、表の側からだけ出せば1本の辺がちょうど1回出る。両側から出すと同じ線を2回描くことになる。

カメラが動けば表裏が変わるので、輪郭は事前に焼いておけない。これが「見る側で決まる量を GPU で出す」という、この段のいちばん正当な使い道になる。シャドウボリューム(特論 B-12 の前半)は、この輪郭の辺を光と反対へ引き伸ばして「影の柱」を作る技法で、GS が入った頃いちばん期待されていた使い道だった。

出る本数はごくわずか。細かい球(24,320 枚)で輪郭になるのは 36,480 本の辺のうち 270 本(0.7%)。三角形が細かくなるほど、輪郭の辺の割合は下がっていく(輪郭は形の「縁」なので、面の数の平方根でしか増えない)。

6. この段が遅い理由は、計算量ではない

「何もしない GS」が 4.89 倍になる(下の表)。計算は gl_Position を写すだけなのに。

頂点シェーダジオメトリシェーダ
出る数必ず1つ0 〜 max_vertices
出力の置き場所要らない(そのまま次へ流せる)溜める場所が要る(何個来るか分からないので)
順番入力の順がそのまま出力の順出た順を守らせる待ち合わせが要る

GL は「描いた順にラスタライズされる」と約束しているので、あとの三角形が先に終わっても先へ出せない。並列に走らせながら順番を保つには待ち合わせが要り、そのぶん並列度が落ちる。

max_vertices の上限にもこれが出ている。

GL に聞いた上限(RTX 3070)値
1回に出せる頂点1024
1頂点あたりの成分128
総成分1024
同時実行(invocations)32

総成分が「1回に出せる頂点数 x 1頂点の成分数」に掛かる。今日の Varying は 12 成分 + gl_Position の4成分 = 16 成分なので、出せるのは 1024 / 16 = 64 頂点まで。max_vertices を大きく書くほど、1頂点に持てる情報が減る——出力を溜める場所が要る、という性質がそのまま数字に出ている。

7. GS を測るには、画素の仕事を揃える

今日の値段の表は3行あるが、値段として読めるのは上2行の差だけ。

測ったもの(細かい球 24,576 枚 x 64 回)GPU の時間出した図形
GS 無し44.3us24,576
素通しの GS216.4us(4.89 倍)24,576
輪郭を出す44.0us270

上2行は同じ .vert と同じ .frag で、絵も1成分も変わらない(自己チェックの10項目め)。だから差は段そのものの値段になる。

3行目は画素の仕事が違う。線は面よりずっと塗る画素が少ないので、GS を通っているのに GS 無しと同じ時間になる。「GS を通すと必ず遅くなる」ではなく、「図形を1枚通すのが高い」のであって、出す図形が減れば取り返せる、というのが正しい読み方。輪郭のように「入力 24,576 → 出力 270」なら、段の値段よりラスタライズの節約のほうが大きい。

VSync を入れたまま測っているので GPU のクロックは上下する。順番を入れ替えて2周してから平均を取っているが、それでも走行ごとにぶれる(Day 57 の要点8)。同じ条件で何度か押して、落ち着いた値を読むこと。

8. 線は面に埋もれる。クリップ空間で手前へ引く

法線の線の根元も、輪郭の線も、面のちょうど上にある。そのまま描くと深度が同じ値の取り合いになり、線が虫食いになる。Day 33 のシャドウアクネとまったく同じ「深度の刻みの細かさ」の問題。

glsl
clip.z -= uDepthBias * clip.w;

w を掛けるのは、クリップ空間の z が w に比例する量だから。こうしておくと、遠くでも近くでも「画面の奥行きで」同じだけ引ける。今日は 0.0012 にしてある。

線の太さも同じく実装任せの部分がある。コアプロファイルでは 1.0 しか保証されていないので、GL_ALIASED_LINE_WIDTH_RANGE を聞いてから、その範囲に収めて渡す(超えた値を渡すと GL_INVALID_VALUE になり、絵は出るので気付きにくい)。

三角形1枚が線4本になるまで — この段の実行モデル

EmitVertex は「いま OUT に入っている値で頂点を1つ出す」。代入の時点では何も起きず、この行で初めて1つ確定する。出し終えた OUT の中身は未定義になるので、次の頂点で全部入れ直す。EndPrimitive は「ここでひと繋がりを切る」で、line_strip なら切らずに出した頂点が1本の折れ線になる——法線の線で切り忘れると、法線の先から次の頂点へ戻る線が余分に描かれる。

max_vertices を小さく書くと、超えたぶんはエラーも警告も無く捨てられる。絵は「なんとなく足りない」だけなので睨んでも気付けない。だから PrimitiveCounter で数える(自己チェックの7項目め: 三角形 384 枚 → 線分 1,536 本)。

出力を溜める場所と順番の待ち合わせが、この段の値段の正体(要点6)。素通しの GS を挟むだけで 4.89 倍になるのは、計算が増えたからではなく、この2つが要るから。

隣接付きインデックスが組み上がるまで — 2周して、辺の表を1つ作る

偶数番を元の番号のままにするのが効きどころ。ここを代表に置き換えると、継ぎ目の反対側の法線と UV がやってきて、球の継ぎ目に縦の筋が出る。奇数番は位置しか読まれない(gs-silhouette.geom が IN[1].worldPosition しか見ない)ので、代表でよい。

向きを付けて持つのも効きどころ。「隣り合う2枚は辺を逆向きに共有する」= 巻き順が揃っている、という約束がそのまま検査になる。向きを無視して持つと、裏返った面が混じっていても気付けない。

検算はオイラーの多面体定理に任せてある。穴の無い閉じた面なら V - E + F = 2。細かさにも形にもよらないので、絵を見ずに「ちゃんと閉じたか」を1つの数で言える(自己チェックの4項目め)。

輪郭の辺が選ばれるまで — 表の側から1回だけ

表の側からだけ出すので、1本の辺がちょうど1回出る。輪郭の辺は必ず「表の三角形」と「裏の三角形」で共有されているから。両側から出すと同じ線を2回描くうえに、裏側から見ると隣の判定が逆になって辻褄が合わなくなる。

隣が無い辺は必ず出る。隣接を組むときに潰れた三角形を書いてあるので、外積が 0 ベクトルになり、dot(0, eye - a) > 0 が偽 = 裏、と判定されるため。これが「溶接を切ると立方体の辺が全部出る」の正体(F7。12 枚の三角形のうち表の6枚が、自分の3辺を全部出して 12 本になる)。

同じ式を C# にも写してある(MeshAdjacency.CountSilhouetteEdges)。GPU に数えさせた本数(PrimitiveCounter)と突き合わせると、両方が同じ辺を選んでいることまで言える(自己チェックの9項目め。姿勢を4通り変えて 34:34 / 32:32 / 27:27 / 34:34)。Day 58 の SdfScene と同じ「C# の鏡」の作法で、今日は鏡のほうが本物より短い(30 行ほど)。

今日残した歪み(3つ)

1つ目: 同じ頂点バッファが3重に置かれている。Mesh<TVertex> は VBO と EBO を組で持つ形なので、「同じ頂点を別の索引で読む」ができない。形1つにつき三角形用・溶接あり隣接用・溶接なし隣接用の3つを作っていて、細かい球なら 12,513 頂点 x 96 バイト x 3 = 3.4MB を持っていて、1つで済むはずのところの余分は 2 つぶんの 2.3MB ある。本来は VAO だけ差し替えて VBO を共有したいところ(改造課題3)。

2つ目: 板の題材だけ DrawVertices を使っている。索引を使わずに頂点を順に描くので、「板1枚 = 頂点1つ」の対応が保たれて数えられる——が、メッシュの意味では正しくない。UV 球の極の 17 頂点は同じ位置にあるので、そこだけ板が 17 枚重なっている。溶接した頂点の配列を別に持てばきれいになるが、今日の主題ではないので置いた。

3つ目: MeshAdjacency の溶接が升目の丸めだけ。升目の境目をまたぐ2点(0.09mm しか離れていないのに別の升)は溶接されない。自分で作ったメッシュには効くが、外から読んだモデル(Day 39 の glTF)では取りこぼしうる。本気でやるなら格子の 27 近傍を見るか、空間分割で近傍を探す。

改造課題

課題1(易): 面ごとの番号を画素シェーダで受け取る

gl_PrimitiveIDIn(ジオメトリシェーダの入口)と gl_PrimitiveID(画素シェーダの入口)は別物。ジオメトリシェーダがある場合、画素シェーダの gl_PrimitiveID は「この段が gl_PrimitiveID に入れた値」になる。

  1. gs-explode.geom で gl_PrimitiveID = gl_PrimitiveIDIn; を書く(EmitVertex の前)
  2. gs-surface.frag で gl_PrimitiveID を読み、色を作る(primitiveColor を画素シェーダへ写す)
  3. .geom の代入を消してみる。何色になるか。なぜそうなるか
  4. F3 で素通しの下地(ShowBase)を見る。下地の三角形にも番号が付いているか

「段を挟むと、組み込み変数の出どころが変わる」ことの手触りを掴むのが目的。3 で何が起きるかは実装によって違う(未定義)ので、手元の答えが仕様ではないことも確かめておくとよい。

課題2(中): シャドウボリュームの「柱」を出す

今日の輪郭は線だが、輪郭の辺を光と反対へ引き伸ばすと影の柱になる(特論 B-12 の前半)。

  1. gs-silhouette.geom を写して gs-shadowvolume.geom を作る。出すものを line_strip から triangle_strip へ、max_vertices を 6 から 12 へ
  2. 輪郭の辺 a-b を出す代わりに、4点 a / b / a + L*d / b + L*d で四角形を1枚出す(d は光の向き、L は 20m ほど)。巻き順に注意——triangle_strip の Z 字の順に並べること
  3. 半透明(glEnable(GL_BLEND)、アルファ 0.15)で描き、深度は書かない。カメラを回すと、球から光と反対へ伸びる影の柱が見える
  4. F7 で溶接を切る。柱がどう壊れるか(隣が無い辺も柱を出すので、全部の辺から柱が生える)

見どころは「柱の側面だけでは閉じていない」こと。本物のシャドウボリュームは前面(表の三角形をそのまま)と後面(裏の三角形を L だけ伸ばしたもの)も要る。なぜ要るのかは、柱の中にカメラを入れてみれば分かる。

課題3(難): 頂点バッファを3重に持つのをやめる

設計書の「今日残した歪み」の1つ目。形1つにつき Mesh を3つ作っているので、細かい球で 3.4MB(3つぶん)を持っていて、2.3MB が余分になっている。索引だけ差し替えられるようにする。

  1. Mesh<TVertex> に、VAO と EBO だけを追加で作る口を足す(CreateIndexView(ReadOnlySpan<uint> indices)。VBO は使い回し、頂点属性の設定も同じものを繰り返す)
  2. 返り値は「VAO とインデックス数」を持つ小さな型にする。Mesh 本体の Dispose で一緒に畳む
  3. GeometryLab.Shape の WeldedAdjacency / RawAdjacency をこれに置き換える
  4. F10 の内訳に、頂点バッファのバイト数を出して 1/3 になったことを確かめる

見どころは「VAO はインデックスバッファの結び付けを記録する」こと(Day 13 の要点3)。VAO を差し替えれば EBO も一緒に切り替わるので、描く側は BindVertexArray を変えるだけでよい。ここでつまずくなら、Mesh のコンストラクタの最後で VAO を先に外している理由を読み直すこと——同じ罠がここでも待っている。
