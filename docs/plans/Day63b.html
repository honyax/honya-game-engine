今日いちばん意外だったのは、割れば割るほど1枚あたりが安くなったこと

パッチ 64 枚を 32 回描いて、三角形1万枚あたりの GPU の時間を測った。レベル 1(三角形 128 枚)で 573us、レベル 64(524,288 枚)で 6.8us。84 倍の開きがある。三角形の数はレベルの2乗で増えるのに、時間はそこまで増えない——パッチあたりの固定費(制御シェーダ4回・テッセレータのセットアップ)が薄まるから。「細かく割るのは高い」より「パッチを細かく分けるのが高い」ほうが実態に近い。同じ三角形の数なら、パッチを減らしてレベルを上げるほうが安い、ということでもある。

今日いちばん大事な3つ

1つ目は「割るのは自分ではない」。この段が書くのは gl_TessLevelOuter[4] と gl_TessLevelInner[2] の6つの数だけ。実際に点と三角形を作るのは、プログラムできない回路(テッセレータ)。Day 63a のジオメトリシェーダが「出力を溜める場所」の制約を抱えていたのは自分で出すからで、回路に任せればその制約が消える——レベル 64 なら1パッチから 8,192 枚(GS の上限は 1024 頂点)。

2つ目は「隣が見えない」。パッチは互いを知らないので、共有する辺のレベルが食い違うとそこに隙間が開く(亀裂)。直し方は「共有しているものから決める」の一言——辺の中点は両側で同じ点なので、そこから決めれば必ず同じ値になる(要点5)。

3つ目は「割っただけでは何も変わらない」。レベルを 64 にしても、評価シェーダが4隅を双一次補間するだけなら絵は1画素も変わらない(平らな四角形が細かい平らな四角形になるだけ)。細かくする意味は、変位(高さを付ける)や曲面へ写す(球にする)といった「割った点を動かす」式があって初めて出る(F8 で変位を 0 にすると手触りが分かる)。

理論の要点

1. パッチは三角形ではない

GL_PATCHES で描くと、GL はインデックスを n 個ずつ束ねて1つのパッチにする。n は glPatchParameteri(GL_PATCH_VERTICES, n) で決める GL 側の状態で、シェーダの layout ではない。

csharp
_gl.PatchParameter(GLEnum.PatchVertices, 4);   // 4つで1パッチ
mesh.Draw(PrimitiveType.Patches);
三角形(Day 14〜)パッチ(Day 63b)
インデックスの束ね方3つn 個(今日は4。上限は 32 以上)
頂点の意味形の点。そのまま画面に出る形を決める数。そのままでは画面に出ない
頂点シェーダ出した gl_Position がラスタライザへ出した値は制御シェーダが読むだけ
描いたあとラスタライズ制御 → テッセレータ → 評価を通ってからラスタライズ

glPatchParameteri の数と、制御シェーダの layout (vertices = 4) out; は別のもの。前者は入れる制御点の数、後者は出す制御点の数で、食い違うと GL_INVALID_OPERATION になるが——絵が出ないだけで理由は言ってくれない。

2. 制御シェーダが書くのは6つの数だけ

glsl
gl_TessLevelOuter[0..3]   // 4つの辺を、それぞれ何等分するか
gl_TessLevelInner[0..1]   // 内側を、横と縦に何等分するか

外側の4つがどの辺に対応するかは GL が決めている。四角パッチなら:

対応する辺
Outer[0]u = 0 の辺
Outer[1]v = 0 の辺
Outer[2]u = 1 の辺
Outer[3]v = 1 の辺

ここを1つでも取り違えると、特定の向きの辺にだけ亀裂が出る——「なぜか縦の継ぎ目だけ割れる」という、原因の見当が付きにくい壊れ方をする。

内側は外側からはみ出さない値にしておく。辺に置く点の数は外側で決まっているので、内側だけ細かくしても「中だけ細かい歪んだ割り方」になるだけ。

この段はパッチの制御点1つにつき1回走る(四角パッチなら4回)。レベルを決めるのは1回でよいので、gl_InvocationID == 0 の回だけが書く。4回走るのは「制御点を作り変える」使い方(ベジエの制御点を計算する等)のためで、今日は使わない。

3. 評価シェーダは「升目の (u,v) を、形の上の点に翻訳する」

テッセレータが 0〜1 の升目の上に点を作り、その点1つにつき1回、評価シェーダが呼ばれる。受け取るのは gl_TessCoord(四角パッチなら (u, v)、三角パッチなら重心座標)で、制御点は gl_in[] で全部見える。

glsl
vec3 base = mix(mix(p00, p10, u), mix(p01, p11, u), v);   // 双一次補間
world = base + up * height(base.xz) * uDisplacement;      // ここが変位

レベル 64 の四角パッチなら 65 x 65 = 4,225 回走る。CPU が送った頂点は4つだけ。投影(uViewProjection)を掛けるのはこの段——割る前の制御点は画面に出ないので、クリップ空間へ写すのはいちばん後ろで1回でよい。

割っただけでは絵が変わらない。双一次補間しかしないなら、平らな四角形が細かい平らな四角形になるだけで1画素も変わらない。細かくする意味は割った点を動かす式(変位・球面への写像)があって初めて出る。

4. 割り方は3つ。uniform にできない

glsl
layout (quads, fractional_odd_spacing, ccw) in;

割り方は layout 修飾子なので、コンパイル時に決まる。3通りを見比べるには同じソースを3回コンパイルするしかない——Day 57 でコンピュートのワークグループの大きさに使った #define の差し込みが、そのまま効く。

割り方丸め方レベル 4.3 →特徴
equal_spacing整数へ切り上げ51 刻みでしか変われない。変わる瞬間に面全体の頂点が一斉に動く(ポッピング)
fractional_odd_spacing奇数へ切り上げ5端の2本だけを伸び縮みさせる。1 から連続に変えられる。LOD の定石
fractional_even_spacing偶数へ切り上げ6同じく連続。レベル 1 が作れない(最低 2)

fractional_odd はレベル 4 でも 5 等分になる(奇数へ切り上げるので)。自己チェックの10項目めがこれを GPU に数えさせている(レベル 4 も 5 も 3,200 枚で同じ)。

5. 亀裂 — パッチは隣を知らない

隣り合う2枚のパッチは辺を共有している。その辺に置く点の数が両側で違うと、辺の上の点が一致せず、隙間が開く。これがテッセレーションでいちばん有名な落とし穴。

直し方は「共有しているものから決める」の一言に尽きる。

決め方隣と一致するか理由
辺の中点から必ずする中点は両側で同じ点。同じ入力に同じ式なら同じ答え
パッチの中心からしない中心は両側で違う点。距離が違えばレベルも違う

今日は距離レベルを2 の冪へ落としている(1, 2, 4, 8, 16, 32, 64)。実務でよくやる形で、段を粗く刻むとカメラが少し動いただけでレベルが揺れない。代わりに隣り合うパッチのレベルが 2 倍違いうるので、揃えなかったときの亀裂がはっきり出る。

「亀裂が出ないこと」は絵では言えない——カメラを動かせばいつか出るかもしれない、を否定できない。だから C# の鏡で、すべての内部の辺(112 本)を4通りのカメラで調べて食い違い 0 を数で言う(自己チェック5・6)。

隙間の大きさは、辺の等分の数の食い違いで決まる。

等分の組辺の上の点のずれ(辺の長さに対して)
4 と 510.0%
8 と 160.0%(割り切れるので、片方の点が全部もう片方に含まれる)

直線の辺なら点がずれても同じ線の上に乗るので隙間は開かない。開くのは変位したあと——辺の上の違う場所の高さを取るので、片方が山の上、片方が谷の途中になる。

6. 距離 LOD — 「画面での三角形の大きさ」を揃える

glsl
level = clamp(uLevel * uLodDistance / distance, 1.0, 64.0);

距離に反比例させるのは、画面に写る大きさが距離に反比例するから。「割ったあとの三角形が、画面でだいたい同じ大きさになる」ようにしたい。

値打ちは何と比べるかで決まる。

三角形備考
全体をレベル 32 で固定131,072 枚いちばん細かいパッチに合わせた場合
距離で決める48,176 枚(36.8%)遠いパッチが粗くなるぶん

基準のレベル(8m でレベル 16)とそのまま比べると、距離で決めたほうが多くなる——近いパッチはそれより細かくなるので当然。「同じ細かさを全体に配るより、距離で配るほうが少なくて済む」が正しい言い方になる。

7. 値段は「三角形の数」ではなく「パッチの数」で決まる

パッチ 64 枚を 32 回描いた測定。

レベル三角形GPU三角形1万枚あたり
11287.3us573us
42,04812.7us61.9us
88,19222.6us27.5us
1632,76854.8us16.7us
32131,072129.4us9.9us
64524,288355.5us6.8us

三角形の数はレベルの2乗で増えるのに、時間は2乗まで増えない。パッチあたりの固定費(制御シェーダ4回・テッセレータのセットアップ)が薄まるから。

同じ三角形の数なら、パッチを減らしてレベルを上げるほうが安い、ということでもある。「テッセレーションは細かくすると高い」より、「パッチを細かく分けると高い」ほうが実態に近い。

なお実際のゲームでは、細かすぎる三角形はラスタライザの側で高くつく (1画素より小さい三角形は 2x2 の画素の塊で処理されるので、4倍近く無駄になる)。これが Nanite(Day 65)や、そもそもメッシュシェーダ(Day 64)が解こうとしている問題の1つ。

8. Varying ブロックは段が増えても効く

今日の画素シェーダは Day 63a の gs-surface.frag をそのまま使っている。ブロック名(Varying)と中身の並びが揃っていれば、間に何段挟まっていても繋がるから。

  gs.vert   →                                      → gs-surface.frag   (Day 63a・GS 無し)
  gs.vert   → gs-passthrough.geom                  → gs-surface.frag   (Day 63a)
  tess.vert → tess.tesc → [回路] → tess.tese       → gs-surface.frag   (Day 63b)

Day 63a の要点1で「画素シェーダが GS の有無を知らずに済む」と書いた仕掛けが、段が2つ増えてもそのまま効いた。tess.vert → tess.tesc の間だけブロック名を Control に分けてあるのは、あそこだけ制御点の受け渡しという別の役割だから(画素シェーダへは行かない)。

四角形1枚が三角形 8,192 枚になるまで — 段2つと回路1つ

CPU が送るのは 4 隅だけ。パッチ 64 枚なら制御点 256 個(24KB)で、そこから三角形が 8,192 枚出る(レベル 8 のとき。レベル 64 なら 524,288 枚)。同じ形を頂点バッファで持つなら、その3倍の頂点を送って VRAM に置くことになる。

割るのは回路というのが Day 63a との決定的な違い。ジオメトリシェーダは「何個出すか」を自分で決めて自分で出すので、出力を溜める場所と順番の待ち合わせが要った。テッセレータは 6 つの数を見て決まったやり方で割るだけなので、そのどちらも要らない——だから GS の上限(1回に 1024 頂点)をはるかに超えた量を出せる。

制御シェーダが4回走るのに、レベルを書くのは1回。4回走るのは「制御点を作り変える」使い方(ベジエの制御点を計算する等)のためで、今日は使わない。gl_InvocationID != 0 で早く返るのは、1回でよいものを4回書いていると読まれないため。

亀裂が出るまで / 出ないまで — 「共有しているものから決める」

「共有しているものから決める」の一言に尽きるのがこの問題の面白いところ。パッチは隣を知らないし、知る手段も無い(隣接付き三角形のような仕掛けはパッチには無い)。知らないまま同じ答えを出すには、両側から見て同じものを入力にするしかない。

「亀裂が出ないこと」は絵では言えない。カメラを動かせばいつか出るかもしれない、を否定できないから。C# の鏡で、内部の辺 112 本をカメラ4通りで調べて食い違い 0 を数で言う(自己チェック5)。同じ条件で中心から決めると 33 本食い違う(同6)。

隙間の大きさは、辺の等分の数の食い違いで決まる。

等分の組辺の上の点のずれなぜ
4 と 510.0%互いに素なので、いちばん離れた点が 1/(4x5) x 2 ぶんずれる
8 と 160.0%割り切れるので、8 等分の点が全部 16 等分の点に含まれる

2 の冪へ落としているのは実務どおり。段を粗く刻むと、カメラが少し動いただけでレベルが揺れない(連続だと毎フレーム 12.3 → 12.4 と変わり、equal_spacing ではそのたびに頂点が一斉に動いてチラつく)。代わりに隣との差が 2 倍になりうるので、辺を揃えることがいっそう効く。

今日残した歪み(3つ)

1つ目: 割り方が3本のプログラムになっている。equal / odd / even を見比べるために同じソースを3回コンパイルしていて、起動時に 3 本ぶんのリンクを払う。実際のエンジンは「シェーダバリアント」として何百通りも焼くので、これはその最小形だが、切り替えのたびに焼き直す(SetDefines)形にすれば1本で済む。どちらが良いかは焼く時間と本数次第。

2つ目: パッチの並びが専用のメッシュになっている。TessellationLab が自分で格子と立方体を作っていて、Primitives には足していない。理由は並びの約束が違うから——パッチは (0,0) (1,0) (0,1) (1,1) の順で4つ、三角形は3つ。同じ Mesh<Vertex> に両方入れると、「この索引は何個ずつ読むのか」が型から読めなくなる。本来は PatchMesh のような別の型にしたいところ(改造課題3)。

3つ目: 距離 LOD が世界の距離だけを見ている。画面での大きさを揃えたいなら、本当は画角とパッチの世界での大きさも要る(近くの小さいパッチと遠くの大きいパッチが同じ扱いになる)。今日は格子が均一なので問題にならないが、大きさの違うパッチが混じると破綻する。

  2. F11 で値段を測る。レベル 64 は 355us 払っているのに、絵は何も変わっていない
  3. 球のほうで同じことをする。こちらは変わる——なぜか
  4. F9 で線にすれば違いは見える。「絵が変わる」と「三角形が増える」は別

見どころは 3 で、球は評価シェーダが normalize して割った点を動かしているから変わる。「割ること」自体には意味が無く、割った点をどう動かすかに意味があるというのが要点3。

課題2(中): 三角パッチにする

四角パッチ(quads)を三角パッチ(triangles)に変えると、gl_TessCoord が(u, v) から重心座標 (a, b, c) に変わる。

  1. TessellationLab に、三角形のパッチを作る CreateTriangleGrid を足す(制御点は3つ)。glPatchParameteri(GL_PATCH_VERTICES, 3) も忘れずに
  2. tess.tesc の layout (vertices = 3) out;、外側のレベルは3つ(Outer[0..2])、内側は1つ(Inner[0])
  3. tess.tese の layout (triangles, ...)。位置はp0 * gl_TessCoord.x + p1 * gl_TessCoord.y + p2 * gl_TessCoord.z
  4. F11 で三角形の数を測る。レベル n の三角パッチは三角形 n^2 枚(四角の半分)。合うか

見どころは外側のレベルがどの辺に対応するか。四角と三角で約束が違う(三角は Outer[i] が「gl_TessCoord[i] が 0 になる辺」)。ここを間違えると、やはり特定の向きの辺にだけ亀裂が出る。

課題3(難): パッチを型として分ける

設計書の「今日残した歪み」の2つ目。Mesh<Vertex> に三角形の索引とパッチの索引の両方が入るので、「この索引は何個ずつ読むのか」が型から読めない。

  1. Render/ に PatchMesh<TVertex> を足す。コンストラクタで制御点の数を受け取り、Draw() の中で glPatchParameteri も自分で呼ぶ
  2. Mesh<TVertex> から Draw(PrimitiveType.Patches) を呼べないようにする(PrimitiveType を受ける Draw から Patches を弾く、あるいは専用の列挙型にする)
  3. TessellationLab の PatchMesh を、この新しい型に置き換える
  4. Day 63a の隣接付きインデックス(TrianglesAdjacency)も同じ問題を抱えている。あちらは 6 つずつ。同じ型で扱えるか、別の型が要るかを考える

見どころは「索引の束ね方」は誰の責任かという線引き。GL は描くときの引数で決める形にしているが、バッファを作った側がいちばんよく知っている。4 を考えると、「束ね方をメッシュが持つ」のが素直だと分かるはず。
