Day 67 まで、絵はフォトリアル(PBR)一本だった。今日から5日間は、ノンフォトリアルの代表として VRM 1.0 のアバターと MToon を扱う。

トゥーンの作り方はタイトルごとにまったく違う。だから今日は手法を自由に組むのではなく、仕様で式まで決まっている MToon を、仕様どおりに書く。アバターの作者は UniVRM や three-vrm の上の MToon で見た目を調整して書き出しているので、式を自分の好みで変えると、同じ値を読んでも「なんか違う」絵になる。

もう1つの主題は、MToon をディファードのエンジンにどう混ぜるか。G-Buffer には「影の色」も「境目の硬さ」も書く欄が無い。そこでキャラだけを別のフォワードパスで描く。夜の灯り・焼いたプローブ・TAA の速度バッファとの付き合い方も、ここで決める。

今日いちばん大事な3つ

1つ目は「MToon は N・L を掛けない」。PBR(Day 35)の拡散は「光の強さ x N・L」で明るさが決まり、暗い側は黒へ沈む。MToon は N・L を2色のどちらを選ぶかの物差しにしか使わない。

glsl
// mtoon.frag(Day 68)。影の度合い → 2色を混ぜる → 光の色を掛ける
float shading = LinearStep(-1.0 + toony, 1.0 - toony, dot(n, l) + shift) * ShadowFactor(n, l);
vec3 direct   = mix(shadeColor, baseColor, shading) * lightColor;   // N・L は掛けない

暗い側は黒ではなく作者が塗った影の色になる。VRoid の体と服は shift 1 / toony 1 で書き出されていて、この式に入れると真後ろ以外ぜんぶ明るい側になる(自己チェック1)。影が出ないのは不具合ではなく、作者の設定だ。

2つ目は「VRM は glTF そのもの」。拡張子が .vrm なだけで、中身は glb。Day 32 のローダーで、メッシュ・PBR の値・スキンまでは読める。VRM が足しているのは 人型の約束(ヒューマノイドの骨の表)と利用条件と、MToon のような拡張だけ。

3つ目は「キャラだけ別のフォワードパス」。ディファードの G-Buffer には MToon の値を書く欄が無い。だからシーンを描き終えたあと、深度だけ借りて、キャラを同じバッファに描き足す(要点6)。灯りは届く8個だけを CPU で選んで渡し、環境光は焼いたプローブをそのまま引く。

理論の要点

1. VRM は glTF。足しているのは「人型の約束」と「利用条件」

VRM 1.0 は glTF 2.0 の拡張の束になっている。今日のアバター(AvatarSample_A)の extensionsUsed はこの5つ。

利用条件がファイルの中に入っているのも VRM の特徴だ。アプリはこれを読んで表示する(あるいは使わせない)責任を負う。今日のアバターは、最初に VRoid Studio から書き出したとき、ここが既定の「作者のみ・再配布禁止」のままだった。公開リポジトリに置けないファイルになるので、VRoid Hub の利用条件に合わせて書き出し直した(完成条件の前に「素材」の節)。自己チェック10 が、置いてよいファイルかを確かめる。

VRM 0.x は読まない。0.x は拡張の名前(VRM)も、向き(-Z 向き)も、MToon の持ち方も違う。VRoid Hub に上がっているファイルの多くは 0.x なので、VrmAvatar.Load は 0.x を見つけると「VRoid Studio で VRM 1.0 に書き出し直す」と言って止まる。

2. MToon の影 — N・L にずらしを足して、2色のどちらかを選ぶ

MToon の陰影は3段でできている。

  1. 物差し     x = N・L + shift                      shift で境目を光の側へ / 影の側へずらす
  2. 段を付ける shading = linearstep(-1 + toony, 1 - toony, x)   toony で境目の幅を狭める(1 なら段差)
  3. 2色を混ぜる color = mix(影の色, ベースカラー, shading) x 光の色

足してから段を付けるのが順番の肝。境目(shading = 0.5)は N・L = -shift の所に来て、幅は 2 - 2 x toony になる。今日のアバターは3通りの値を持っている。

マテリアルshifttoony境目の N・L幅(N・L で)見え方
顔・目-0.050.050.051.9なだらか。ほぼ半ランバート
髪-0.350.350.351.3光の側へ寄った境目。N・L が -0.3 以下は影の色だけ
体・服・靴1.001.00-1(真後ろ)0影が出ない。真後ろの1点以外ぜんぶ明るい側

実験台の「体と服」を押して光を回すと、球が1色のまま変わらない。「影の度合い」にすると真っ白で、実機の F4 と同じ絵になる。

影(シャドウマップ)は shading に掛ける。光が遮られた所は「明るい側」から「影の側」へ寄る——黒くなるのではなく影の色になる。トゥーンの影がにごらないのはこのため。点光源にも同じ式を使う。灯りに背を向けた面は、影の色 x 灯りの色で照らされる。

環境光は影の色を使わない。環境光 x ベースカラー を足すだけ。ただし向きの環境光と「真上と真下の平均」を giEqualizationFactor(既定 0.9)で混ぜる。1 に近いほど向きによらない一様な明るさになり、環境光が作る陰影が消える。トゥーンの陰影は直接光の2色で決めたいので、環境光の陰影は邪魔になる。

glsl
vec3 giDirectional = Irradiance(n);
vec3 giUniform     = (Irradiance(vec3(0, 1, 0)) + Irradiance(vec3(0, -1, 0))) * 0.5;
vec3 gi = mix(giDirectional, giUniform, uGiEqualizationFactor);
vec3 indirect = gi * base.rgb;   // 影の色は使わない

光の強さは 1 前後の約束で作られている。MToon の作者は「白い平行光 1 + 環境光わずか」で見た目を決めている(three-vrm の見本がそう)。N・L を掛けないぶん、同じ光でも PBR より明るく出る。Day 36 の昼の光(太陽 1.15 + 空 1.0 前後)の床の上に立たせたら、白い服がベースカラーの2倍になって真っ白に飛んだ。床の上で見るときだけ、太陽を白の 1.0、空を 1/4 に差し替えている(Day 35 の材質グリッドが光を差し替えたのと同じ扱い。下ろすと戻す)。

3. リムとマットキャップ — 光と関係なく「縁」と「向き」で色を足す

直接光と環境光のほかに、MToon には3つ目の足し算がある。

  rim  = リムの色 x pow(saturate(1 - N・V + lift), power)        縁の光(フレネル風)
  rim += マットキャップの色 x matcap(ビュー空間の法線)            「こちらを向いた面ほど何色」
  rim *= リムの掛け算テクスチャ x mix(1, 届いている光, rimLightingMix)

N・V は面がこちらを向いているほど 1、縁ほど 0。1 - N・V を power 乗すると縁の細い帯に縮み、lift を足すと正面寄りの面にも乗る。AvatarSample_A は lift 0.1・power 8 で、正面では 1e-8、N・V = 0.5 で 0.017、縁で 1 になる(自己チェック5)。

マットキャップは「球を1枚撮った絵」で、ビュー空間の法線の xy で引く。光源と関係なく決められるので、髪の天使の輪や金属の照り返しに使う。引くときの基底は画面の軸ではなく視線の軸で作る(three-vrm と同じ)。画面の端にある物は斜めから見ているので、画面の軸で引くとマットキャップが横へずれるからだ。今日のアバターは髪と体が MatcapWarp を、顔と目は黒い絵(Shader_NoneBlack)を指している。

rimLightingMix が 1 なら、リムに届いている光(直接光の色 + 環境光)を掛ける。暗い所では縁も暗くなる。0 にすると暗闇でも縁が光る(わざとそう作るアバターもある)。

4. 比べる描き方 — 同じマテリアルを3通りに読む

VRM のマテリアルは、MToon の値と一緒に glTF の値(ベースカラー・PBR の金属度と粗さ・KHR_materials_unlit)を持っている。MToon を知らないビューアのための代わりの見た目で、GltfLoader は両方を残す(Material に PBR、Material.MToon に MToon)。

F3式見え方
MToonmix(影の色, ベース, shading) x 光 + 環境光 x ベース + リム暗い側も作者の塗った色
ベースカラーだけベースKHR_materials_unlit の見た目。陰影がまったく無い
N・L の陰影だけベース x (光 x N・L x 影 + 環境光)写実の素朴な陰影。暗い側が黒く沈み、影の色は出ない

3つとも mtoon.frag の中で分けている。textured.frag で比べなかったのは、あちらはアルファを見ていないから(MASK も BLEND も無視する。Day 32 から)。髪の毛先が四角いまま描かれ、比べたいもの以外の差が混ざる。

F4 の成分表示は MToon のときだけ効く。uMToonView の番号 3〜6 が「影の度合い / 直接光 / 環境光 / リム」で、実験台の「影の度合い」と同じ絵が実機で出る。

5. アウトラインは背面法 — 膨らませた裏面を描くだけ

線の描き方には大きく2系統ある。画面の深度や法線の段差を探す画像処理と、ポリゴンを膨らませて描く背面法。MToon は背面法で、手順はこうなる。

  1. ふつうに描く(表を描き、裏は捨てる)
  2. 同じメッシュを、頂点を法線の向きへ太さぶん押し出して、表を捨てて裏だけ描く

膨らんだ裏面は、元の形より一回り大きい「裏返しの殻」になる。手前は1回目の表面が深度で勝つので、殻のうち元の形からはみ出した縁だけが残る。それが線になる。ポリゴンを描くだけなので、ディファードにもフォワードにも、どの後処理にも依存しない。

outlineWidthMode太さの単位距離による見え方
worldCoordinatesメートル遠いほど細い(遠くの人の線は細い)。今日のアバターはこれ(0.75mm)
screenCoordinates画面の高さに対する割合距離によらず同じ太さ。押し出しに「その距離で画面の縦半分が何メートルか」を掛ける(three-vrm の式)

0.75mm は思ったより細い。画角 60 度・高さ 1080 画素で、カメラから 0.75m(F6 で顔に寄った距離)なら約 0.9 画素、全身が入る 2.3m なら 0.3 画素で、ほぼ見えない。VRoid の線は「顔に寄ったときに輪郭が締まる」程度の太さで作ってある。下の実験台で距離を動かすと確かめられる。

細かい作法が3つある。

  • 押し出すのはスキニングの後、世界空間で。前に押し出すと、関節の行列で太さが伸び縮みする
  • 太さのテクスチャ(G)で場所ごとに消す。顔は目の周りや口の中の線を、outlineWidthMultiplyTexture で 0 にしてある。頂点シェーダでテクスチャを読むので、ミップは選べない(textureLod で 0 段目)
  • 線をほんの少し奥へ(gl_Position.z += 1e-6 * w)。押し出しが 0 の頂点は1回目の面と同じ深度になり、どちらが勝つかが画素ごとに揺れて、面に線の色が斑に出る

6. キャラだけ別のフォワードパス — 深度を借り、灯りを選び、プローブを引く

ディファード(Day 52)は「表面を G-Buffer に書く → 画面の画素ごとに光を当てる」。G-Buffer に書けるのはベースカラー・法線・金属度・粗さ・AO・発光だけで、MToon の影の色・境目のずらしと硬さ・リム・マットキャップを書く欄が無い。欄を足せば全員の G-Buffer が太り、ライティングパスに MToon の枝が入る。

そこでキャラだけを、半透明と同じ扱いで後から描く。

  • どこで … シーンを描き終えたあと(ディファードなら光を当て終えたあと)、粒の手前。ライティングパスは頭で G-Buffer の深度をシーンのバッファへ写している(Day 52)ので、キャラは壁の陰に入れば隠れる
  • 灯りは届く8個だけ … フォワードは光を uniform の配列で渡すしかない。シーンの全部(群れを出せば 1000 個)は渡せない。キャラは小さいので、キャラを包む球に届く光だけを CPU で選び、明るい順に8個まで渡す(MToon.SelectLights)。Unity のフォワードが「1つの物に効く光の数」に上限を持つのと同じ考え方。比べる明るさはキャラのいちばん近い点で測る。中心で測ると、肩には当たっているのに中心には届かない大きな光が落ちる(自己チェック6)
  • 環境光はプローブをそのまま … MToon の環境光は「その向きの放射照度」を3回(法線・真上・真下)引くだけなので、空1枚(IBL)でも格子(Day 66a のプローブ)でも同じ関数で済む。ProbeSh / ProbeIrradiance は textured.frag から1文字も変えずに写した(自己チェック15)
  • 速度バッファにも載せる … Program.Draw を通らないので、_motion.Record を自分で呼ぶ。載せないと、キャラが動いたとき(Day 72)に TAA が「カメラの動きだけ」で前のフレームを引き、残像が出る
  • 影は落とす、SSAO には入れない … 影パスは G-Buffer と無関係なので、キャラも焼く(床と壁に影が落ち、髪の影が顔に落ちる)。SSAO はディファードでは G-Buffer から作るので、キャラが居ない。フォワードのときだけ入れると、描き方を切り替えたときに足元の暗がりが出たり消えたりするので、どちらでも入れない(今日残した歪みの1つ目)

結果、F9 でシーンを Forward+ ↔ ディファードに切り替えても、キャラの描き方は1行も変わらない。変わるのは背景だけだ。

7. 関節 91 本と、uniform の枠 64 本

Day 41 から、頂点シェーダの関節行列は 64 本まで(AnimationPlayer.MaxJoints)。OpenGL 3.3 が頂点シェーダに保証する uniform は 1024 成分(float 1024 個)で、4x4 行列ならちょうど 64 個だからだ。

VRoid のアバターは、1つのスキンに 91 本を並べてくる(体・髪・揺れものの骨を全部)。Day 66a のままなら AnimationPlayer が「多すぎる」と言ってバインドポーズで描く(今日はまだ動かさないので、それでも見た目は同じになる)。

ところがメッシュごとに数えると、使っている関節はずっと少ない。

メッシュ重みが 0 より大きい関節中身
顔3 本頭・左目・右目
体60 本腰から指先まで・フード・胸の揺れもの
髪18 本頭・髪の揺れもの
3つを合わせると79 本1つのスキンには詰めきれない

だから GltfLoader.CompactJoints は、関節が 64 本を超えるスキンのときだけ、プリミティブが使う関節だけを並べたスキンを作り、頂点の関節番号を付け替える。上限を上げる道(シェーダ5本の配列を全部広げる)より差分が小さく、シェーダは1行も変えずに済む。

詰めても絵は変わらない。関節行列は関節ごとに独立している(逆バインド行列 x 関節の世界行列)。並びから使わない関節を抜き、頂点の番号を新しい並びへ付け替えれば、頂点が掛け合わせる行列は元と同じになる。自己チェック13 は GPU から頂点を読み返し、体のいちばん左の頂点(x = 0.69m)が左手の中指、いちばん右が右手の中指に付いていることを確かめる。付け替えを間違えると番号が別の骨を指すので、名前が合わなくなる。

2つ目: 影パスはアルファを見ない(depth.frag は空っぽ)。髪の毛先は四角いまま影に落ちる(改造課題3)。

3つ目: 置き場所と光の差し替えが Program.cs に直書き(VrmAlleySpot / VrmAlleyYaw / VrmStageLight*)。Day 72 でデモの主役に差し替えるときは、demo-final.json の player の出現位置を使うことになる。

4つ目: 頂点を4倍持っている。VRoid は1つのメッシュの全プリミティブで同じ頂点の並び(顔 4,060 個・体 7,964 個・髪 8,435 個)を共有するが、ローダーはプリミティブごとに Mesh を作るので、15 本のバッファに 94,016 頂点(1頂点 96 バイトで 9.0MB)を持つ。共有すれば 20,459 頂点(2.0MB)で済む。glTF は「同じアクセサを複数のプリミティブが指す」のを許しているので、アクセサの番号で頂点バッファを使い回せばよい。

5つ目: UV アニメーションと KHR_texture_transform を読まない。今日のアバターは全部 0 / 単位なので絵は変わらない(改造課題2)。

6つ目: 選ぶ灯りが入れ替わる瞬間に明るさが飛ぶ。8個の枠からあふれた9番目の灯りは、キャラが近づいて順位が上がった瞬間に 0 から全部へ跳ねる。今日の裏通りは届く灯りが1個なので起きない。群れ(Day 52)の中を歩かせると見える。

試して分かったこと

  • 体と服に影が出ないのは不具合ではない。最初は式の誤りを疑ったが、ファイルの値が shift 1 / toony 1 だった。F4 の「影の度合い」で真っ白なら正しい
  • 昼の光では MToon が飛ぶ。要点2の最後の囲み。MToon は「光 1 のとき明るい側 = ベースカラー」の約束で作られている

改造課題

課題1(易): アウトラインを「画面の割合」に切り替える

「VRMビューア」に1項目足し、線を持つ5枚の OutlineWidthMode を Screen、OutlineWidthFactor を 0.002 にする(元の値は覚えておいて戻せるように)。F6 で寄ったときと全身のときで、線の太さが画素で同じになることを確かめる。mtoon.vert の画面の割合の枝(uTanHalfFov)は、今日のアバターでは一度も通っていない。ついでに全マテリアルの ShadingToonyFactor を 0.9 に上書きする項目も足すと、実験台の「toony 1」に近い絵が実機で見られる。

課題2(中): UV アニメーションを読む

MToon の uvAnimationScrollXSpeedFactor / uvAnimationScrollYSpeedFactor / uvAnimationRotationSpeedFactor と uvAnimationMaskTexture(B)を読み、mtoon.frag の先頭で UV を時刻でずらす(マスクが 1 の所だけ)。今日のアバターは全部 0 なので、自分で値を入れて(例えば髪だけ X に 0.1)確かめる。時刻をどこから送るか(一時停止で止めたいか)と、ずらした UV をどのテクスチャに使うか(仕様は全部のテクスチャ)を決めるのが課題。

課題3(難): 影パスでアルファを見る

髪の毛先が四角いまま影に落ちる(今日残した歪みの2つ目)。depth.vert に UV を通し、depth.frag でベースカラーのアルファを読んで discard する。ShadowMap.Draw はマテリアルを受け取らないので、MASK のパーツだけテクスチャとしきい値を渡す口を足すことになる。既存の呼び出し(デモの小物・キツネ)を1つも書き換えずに済む形(既定引数)にできるかが鍵。Day 33 の「影を落とすかどうかはフラグで選ぶ」と同じく、描く側がどこまで知るべきかを考える。
