道具は2つ。1つ目は モーフターゲット(ブレンドシェイプ・シェイプキーとも呼ぶ)。Day 32 から glTF ローダーが読み飛ばしていた、「頂点をどれだけ動かすか」の差分の束だ。骨では作りにくい「まぶたが下りる」「唇がすぼまる」を、頂点の足し算で作る。今日は CPU で足し合わせて頂点バッファを書き換える。

今日いちばん大事な3つ

1つ目は「モーフは差分の足し算」。形を何通りも持つのではなく、元の形からの差分を何本も持ち、重みを掛けて足す。

csharp
// MorphTargets.Blend(Day 69)。元の頂点を写してから、重みが 0 でないターゲットの差分だけを足す
result[i].Position += target.Positions[k] * weight;
result[i].Normal   += target.Normals[k]   * weight;   // 法線も同じ重みで(長さはシェーダが直す)

足し算なので、半分閉じた目(0.5)も、笑いながら「あ」の口(2本を同時に 1)も同じ式で出る。足し算だから壊れ方も足し算になる——happy(目を細めて閉じる)と blink(目を閉じる)を両方 1 にすると、まぶたが2回ぶん下りて目が消える(上の実験台の「happy + blink」)。

2つ目は「表情は名前の約束」。モーフの番号や名前はアバターごとに違うが、VRM の blink はどのアバターでも「両目を閉じる」。表情1つが、モーフ・マテリアルの色・UV のずらしを同じ重みでまとめて動かす。

3つ目は「表情どうしの約束は作者が書く」。上の目が消える問題を防ぐのが overrideBlink(「この表情が出ている間はまばたきを止めよ」)だ。ところが AvatarSample_A は全部 none で書き出されている。アプリ側で勝手に止めず、ファイルの値どおりに評価する(F6 は試しに書き換えて違いを見るだけ)。

新規は Model/ に3本(MorphTargets・VrmExpressions・AutoBlink)。変更は GltfLoader(モーフを読む)、Model(モーフとマテリアルの番号の表)、VrmAvatar(表情を読んで流す)、Mesh(頂点を書き換える口)、MToon と mtoon.vert(UV のずらし)、そして Program.cs。

理論の要点

1. モーフターゲットは「差分」の足し算

glTF のモーフターゲットは、プリミティブの targets に並んだ 位置と法線の差分だ。重みはメッシュ(ノード)に1組だけあり、全プリミティブに同じ重みが効く。

  位置 = 元の位置 + Σ 重み[k] x 位置の差分[k]
  法線 = 元の法線 + Σ 重み[k] x 法線の差分[k]       (シェーダが正規化する)
  • 線形。重み 0.5 は差分のちょうど半分。0.25 秒かけて 0 → 1 へ寄せれば、頂点はまっすぐ動く(F5 の「表情の強さ」で途中を止めて見られる)
  • 1 を超えてよい。仕様は重みを切り詰めない。2つの表情が同じターゲットを動かせば足し合わさる(実験台で 1.5 まで動かせる)
  • 重みはメッシュに1組。Fcl_EYE_Close を 1 にすれば、肌・白目・まつ毛・アイラインの 7 枚が一緒に閉じる。だから重みの並びは MorphTargets に1つだけ置いた
  • 名前は仕様の外。glTF の本体はターゲットを番号でしか呼ばない。mesh.extras.targetNames に名前を入れるのは慣習(Blender・UniVRM・VRoid が書く)

AvatarSample_A のモーフは顔(ノード 91「Face」)だけで、57 本。体と髪は持たない。

ターゲット動かす頂点いちばん大きい差分表情

Fcl_ALL_Surprised2,585 個1.06cmsurprised

2. スキニングの前に足す

glTF は順番を決めている。モーフで形を変えてから、関節行列で曲げる。

  バインドポーズの頂点 ── + Σ 重み x 差分 ──→ 表情の付いた頂点 ── 関節行列 ──→ 画面
                          (CPU。MorphTargets)                   (GPU。mtoon.vert。Day 41 のまま)

差分は「バインドポーズの顔」に対して作られている。まぶたの差分は「顔が正面を向いているとき、下へ 2.36cm」だ。頭を横に倒した後に足すと、差分の向きは倒れずに真下のままなので、まぶたが顔の外へ滑る。先に足せば、まぶたは顔と一緒に関節行列で倒れる。

この順番のおかげで、CPU の合成は描く側を知らなくてよい。書き換えるのはバインドポーズの頂点だけで、関節・アウトラインの押し出し・影パス・速度バッファは、Day 68 と同じ頂点バッファを同じように読む。

3. CPU で合成して、動いたときだけ送る

合成する場所には2通りある。

どこでやり方手が入る所
CPU(今日)頂点を足し合わせ、glBufferSubData で頂点バッファを上書きするMesh に書き換えの口が1つ増えるだけ
GPU差分をテクスチャ(またはバッファ)に詰め、頂点シェーダで重みを掛けて足す頂点シェーダ全部(MToon・影・速度)に同じ足し算が要る。重みの uniform の枠も決める(改造課題3)

CPU でも速く済ませる工夫が3つある。

  1. 差分は疎に持つ。ファイルの差分は頂点の数だけ並んでいて、81% が 0。読むときに 0 でない頂点の番号と差分だけを残す(Target.FromDense)。まばたきは 4,060 頂点のうち 1,066 個しか触らない
  2. 重みが前と同じなら送らない。まばたきの合間(3.5 秒のうち 3.3 秒)は比べるだけで返る。HUD の「頂点を送った」がほとんど「いいえ」になる
  3. 同じ並びの合成は1回。顔の 7 枚のプリミティブは POSITION も 57 本の差分も同じアクセサを指している。ローダーはアクセサの番号を並べた鍵で見分け、差分を1回だけ読んで、できた頂点を 7 本の Mesh へ送る
計った値(Release・RTX 3070)時間・量
合成だけ(GL を通さない。重みが少しだけ立っているとき)0.014 から 0.023ms
合成 + 7 本へ送る0.18 から 0.47ms
1回に送る量4,060 頂点 x 96 バイト x 7 本 = 2.60MB

時間のほとんどは送るほうにかかる。7 本に同じものを送っているのは、ローダーがプリミティブごとに頂点バッファを作っているから(Day 68 の歪み4。改造課題2で直せる)。

4. VRM の表情は「名前の約束」と3種類の割り当て

VRMC_vrm.expressions は preset(名前が決まっている)と custom(作者が足す)の2つの辞書。プリセットは 18 個ある。

種類名前AvatarSample_A のモーフ
感情happy angry sad relaxed surprisedFcl_ALL_Joy / _Angry / _Sorrow / _Fun / _Surprised
口(リップシンク)aa ih ou ee ohFcl_MTH_A / _I / _U / _E / _O

表情1つは3種類の割り当てを持ち、全部が同じ重みで動く。

割り当て中身重み w のとき
morphTargetBindsノード番号・ターゲット番号・重みターゲットの重み += 割り当ての重み x w
materialColorBindsマテリアル番号・種類(6つ)・目標の色色 = 元の色 + (目標 - 元) x w
textureTransformBindsマテリアル番号・拡大・ずらし拡大・ずらし = 元 + (目標 - 元) x w

割り当ては番号でモーフとマテリアルを指す。だから表情は Model を読み終えてからでないと引けない。VrmAvatar.Load は VRMC_vrm を読んだ JSON の文書を閉じる前に、表情の部分だけ JsonElement.Clone() で写しておき、Model ができてから読む。マテリアルの番号は Model.MaterialsByIndex で引き直す(Model.Materials は使われた順に並んでいて、ファイルの番号と一致しないため)。

5. override と isBinary — 表情どうしの約束

happy の目は「細めて閉じた弧」になっている。そこへ自動まばたきが blink を 1 にすると、まぶたがもう一度下りて目が消える(完成条件3の絵)。これを防ぐのが override で、感情の側に「出ている間、まばたき・視線・口をどう抑えるか」を書く。

値抑える量happy 0.3 のとき blink に掛かる倍率
none01
block出ていれば 1(少しでも)0
blendその表情の重み0.7

isBinary は「0 か 1 にしかならない」表情の印。重みが 0.5 を超えたら 1、それ以外は 0。漫符(汗・怒りマーク)のように半分だけ出ると変な絵になるものに付ける。

評価の順番は three-vrm の VRMExpressionManager.update に合わせた(VrmExpressions.Update)。

csharp
// 1. 抑える量を決める(全部の表情を先に見る)
blink -= expression.OverrideAmount(expression.OverrideBlink);   // 視線・口も同じ。最後に 0 で止める
// 2. 元に戻す(割り当てのあるモーフの重みを 0 に、色と UV を読んだときの値に)
// 3. 足す
float weight = expression.OutputWeight * Multiplier(expression.Name);   // isBinary を通し、抑える倍率を掛ける
if (expression.IsBinary && weight < 1.0f) { weight = 0.0f; }             // 抑えられた isBinary は出さない
  • 1 を先に全部済ませる。表情を1つずつ「抑えて足す」と、並び順で結果が変わる(happy の後に blink が来れば抑えられ、前なら抑えられない)
  • 2 で戻してから足す。2つの表情が同じモーフや色を動かすことがある。前のフレームの値に足すと毎フレーム積み上がる
  • 抑えられるのはプリセットのまばたき・視線・口だけ。カスタムの表情(作者が足したウインクなど)は抑えられない

6. 色と UV の表情 — 元から目標へ寄せる

materialColorBinds の目標の色は差ではなく、重み 1 のときの色そのもの(リニア)。だから読んだときの色を覚えておき、「目標 - 元」の差に重みを掛けて足す。6つの種類は MToon の欄に対応する。

type書き換える欄
colorMaterial.BaseColorFactor(MToon の明るい側の色)
emissionColorMaterial.EmissiveFactor
shadeColor / matcapColor / rimColor / outlineColorMToon の ShadeColorFactor / MatcapFactor / ParametricRimColorFactor / OutlineColorFactor

書き換えた値は、Day 68 の MToon.Apply が描くたびに送っている。描く側は何も知らずに新しい色で描く。

textureTransformBinds はマテリアルの全部のテクスチャの UV を拡大・ずらす。今日は MToon に UvScale / UvOffset を足し、mtoon.vert で頂点の UV に1回だけ掛ける。上下の向きに注意がいる。頂点の UV はローダーが v' = 1 - v に裏返してある(Day 32)ので、ファイルの向きの式を書き直して送る。

  ファイルの向き:   v_new  = v  x s + o
  裏返した向き:     v'_new = v' x s + (1 - s - o)          ← MToon.GlUvTransform の w

UV のずらしで動くのは貼る絵だけで、メッシュは動かない。AvatarSample_A の瞳のメッシュは瞳の絵とほぼ同じ大きさなので、絵をずらすとメッシュの縁で欠ける(完成条件5の絵、下の実験台)。UV で目を動かすアバターは、瞳のメッシュを白目いっぱいに作っておく。

7. 自動まばたき — ランダムな間隔と、速く閉じて遅く開く形

人は1分に 15 から 20 回まばたきする。一定の間隔にすると機械に見えるので、待ち時間を毎回 1.5 から 5.5 秒(平均 3.5 秒)から選び直す。形は「閉じる 0.06 秒(一定の速さ)・閉じたまま 0.03 秒・開く 0.12 秒(滑らかに)」で、1回 0.21 秒。まぶたは一気に下りて、ゆっくり上がる。

AutoBlink は表情のことを何も知らない。出すのは blink の重み1つだけで、happy の間に止めるかどうかは表情の overrideBlink が決める。作者の意図(override)とアプリの都合(自動まばたき)を別々の場所に書けるようにしてある。乱数の種は決めてある(new AutoBlink(69))ので、何度起動しても同じ間隔の並びになる。

改造課題

課題1(易): ときどき2回続けてまばたきする

人のまばたきは、ときどき2回続く。AutoBlink に「開き終わったとき、20% の確率で待ち時間を 0.1 秒にする」を足す。自己チェックの間隔の項目(最小 1.5 秒)は落ちるようになるので、何を確かめたいかに合わせて直す——「最小の間隔」ではなく「平均の間隔」で確かめる形にできるか。

課題2(中): 頂点バッファを共有して、送るのを1回にする

今日残した歪みの1つ目(Day 68 の歪み4)。GltfLoader で POSITION のアクセサの番号が同じプリミティブには同じ頂点バッファを使わせ、インデックスバッファだけを別に持たせる。Mesh を「頂点バッファを借りる」形に分けることになる。MorphTargets.Block.Meshes が1本になり、F11 の「1回に送る量」が 2.60MB から 0.37MB に減ることを確かめる。Model.Dispose が同じバッファを2回消さないように。

課題3(難): GPU でモーフを足す

差分を BufferTexture(Day 53)に詰め、mtoon.vert で gl_VertexID とターゲット番号から引いて足す。重みは「0 でないものだけ、番号と重みの組で最大 8 本」を uniform で送る(57 本全部を回すと頂点ごとに 57 回読む)。影パス(depth.vert)と速度バッファ(MotionVectors)にも同じ足し算が要る——描く側がモーフを知ることになる、というのが CPU 版との設計の違い。CPU 版と GPU 版で、まばたき中の1フレームの時間を比べる。

動作確認済み環境

Windows 11 / .NET 10 / NVIDIA GeForce RTX 3070(OpenGL 4.3)、1920x1080、VSync あり

アバター: VRoid Studio 2.14.0 で書き出した AvatarSample_A(VRM 1.0)。Day 68 と同じファイル

確かめたこと: ビルド、dotnet format whitespace --verify-no-changes、自己チェック 12 項目(VRMビューアを出す前と後)、Day 68 の自己チェック 15 項目、Day 48 の割り当て表(311 項目)、床の上で顔に寄った絵(なし・まばたき・感情5つ・happy + まばたき(none / block)・aa・oh・照れ・目そらし・強さ 0.5)

検証の途中で分かったこと

  • happy にまばたきが重なった絵で、目が消えた。最初は合成の誤りを疑ったが、Fcl_ALL_Joy と Fcl_EYE_Close の差分を足すと実際にまぶたが下まぶたを越える。ファイルの override が none なので、仕様どおりの絵だった。F6 の試しを足したのはこのため
  • 目そらしの量は、瞳の絵から決めた。瞳のテクスチャは 1024 x 512 に両目が並び、瞳1つが幅の約 0.2。0.06 で瞳の幅の 1/4 ほど動き、それ以上は縁の欠けが目立つ
  • コンソールに「〜」を出すと化ける(CP932)。表示の文字列では「から」と書いた
