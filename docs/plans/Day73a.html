2つ目は「根の移動を抜き、抜いた傾きを速さとして使う」。Mixamo の歩きは腰が前へ進む。ゲームでは体を運ぶのはカプセル(Day 51)なので、クリップの中の前進は消してその場で足踏みさせる。消すのは「時刻に比例して進んだ分」の直線で、その傾きが「このクリップの足が滑らない速さ」になる。

csharp
// MixamoClip.Load(Day 73a)。腰の移動のキーを世界の m に直してから
d = 腰(終わり) - 腰(始まり)                       // 1 周で進んだ距離(水平だけ)
腰'(t) = 腰(t) - d x (t - 始まり) / 長さ          // 最後のキーが最初のキーに重なり、継ぎ目が消える
ファイルの速さ = |d| / 長さ                        // 歩き 1.211m / 1.1 秒 = 1.10 m/s
アバターの速さ = ファイルの速さ x 腰の高さの比      // 0.895m / 1.02m = 0.878 → 0.97 m/s

3つ目は「しきい値はアバターでの速さ」。Day 42 のブレンド木(BlendTree1D)に、idle 0・walk 0.97・run 2.36 m/s を並べる。歩きの速さちょうどで歩きだけが流れ、その速さで体を運んだときだけ、接地した足が床の上で止まる。速さを 1.5 倍にすると、同じ歩幅のまま 1.5 倍の距離を進むので足が前へ引きずられる(上の実験台の x1.5)。

理論の要点

1. Mixamo のクリップは「ヒューマノイドの名前を持たない骨の木」

Mixamo のクリップの中身は、65 本の骨の木と、その骨のアニメーション。VRMA と違って「どのノードが何か」を書いた拡張は無く、手がかりはノードの名前だけだ。そこで名前の表(MixamoClip.BoneTable。左右合わせて 52 本)を引く。

Mixamo のファイルはリポジトリに入れられない(利用条件)。そこで同じ形を持つ代役を Python で作って入れた(assets/mixamo/make_honya_locomotion.py。CC0)。

2. 表さえあれば Day 71 の道 — cm も正規化が吸収する

表ができたら、VrmAnimation.FromHumanoid に「ノードの木・クリップ・表」を渡す。中身は Day 71 の Load の後半そのもので、骨ごとに「ファイルの祖先の骨の休みの世界の回転 P」と「この骨の休みの世界の回転 C」を測っておき、アバターに当てるときに r = A x q x B の形で写す(Day 71 の要点2〜3)。

休みの回転がばらばらなのは、正規化にとっては何でもない。正規化は「休みの姿勢からどれだけ回ったか」を世界にそろえた向きで測り直すので、ファイルの骨のローカルの軸がどちらを向いていてもよい。自己チェックでは、アバターの骨の回り方とファイルの骨の回り方の差が最大 0.04 度(指の骨の数値の誤差)だった。

cm も何もしなくてよい。腰の移動のキーは「腰の親(Armature)の座標」で書かれていて、Day 71 の腰の写し方は「ファイルの腰の親の休みの世界行列」を通して世界の m に直す。0.01 倍はその行列に入っているので、勝手に掛かる。回転は単位を持たないので、そもそも関係しない。

逆に言うと、単位を直していたのも正規化の道だった。正規化を切る(F9)と、回転のキーがそのまま書かれて手足が全部ねじれるだけでなく、腰の移動の 102(cm)がそのまま m として当たり、アバターは 90m ほど上へ飛んで画面から消える。

3. 根の移動 — 時刻に比例して進んだ分を抜く

Mixamo の歩き(In Place なし)では、腰の移動のキーが 1 周で 1m 以上前へ進む。Day 51 のデモはカプセルが体を運び、モデルは見た目だけという作りなので、このまま当てると、カプセルが進む分とクリップが進む分が2重になる(上の実験台の「残す」)。ループの頭では腰が 1 周ぶん引き戻されるので、アバターは前へ歩いて行っては戻る。

抜くのは直線だ。ループのクリップは最初と最後の姿勢が同じで、腰だけが 1 周ぶん前にいる。その差 d を時刻に比例して引けば、最後のキーが最初のキーに重なり、継ぎ目が消える。

  • 水平だけを抜く。上下(1 歩ごとに沈む)と左右の揺れは残す。それが歩きの絵の一部で、自己チェックでは抜く前と後で上下の幅が同じ 2.99cm だった
  • 世界に直してから測る。Armature は 0.01 倍だけでなく、Blender の向きの直し(Z 上 → Y 上)を持ちうる。キーの座標のまま「Z が前」と決め打ちせず、腰の親の休みの世界行列で世界へ直し、水平の成分を引いてから戻す
  • 読み込みのときに1回だけ。抜いたキーで新しい sampler を作る(AnimationClip.Sampler.MapTimed)。Map(Day 71)はキーの値しか渡さないので、時刻も渡す版を足した

4. 足が滑らない速さ — ファイルの速さ x 腰の高さの比

抜いた直線の傾き |d| / 長さ が、そのクリップの足が滑らない速さになる。モーションキャプチャーの根の移動は、接地した足が床に止まるように体が進んだ記録だからだ。代役は手で決めた速さではなく、脚の動きから同じ関係を満たす速さを求めて書いた(地面を蹴っている半周に、足首が腰に対して後ろへ動く速さの平均。歩き 1.10 m/s・走り 2.69 m/s)。

アバターに当てるときは腰の高さの比を掛ける。Day 71 の腰の縮尺と同じ比で、腰の高さが 0.878 倍のアバターは、同じ角度で脚を振ると歩幅も 0.878 倍になる。

クリップ1 周で進むファイルの速さアバターの速さ(x 0.878)足の滑り(アバターの速さで運んだとき)
honya-walk(1.10 秒)1.211m1.10 m/s0.97 m/s-0.03 m/s
honya-run(0.70 秒)1.882m2.69 m/s2.36 m/s-0.11 m/s

足の滑りは、クリップをアバターに当てて1周回し、左の足首が地面を蹴っている半周の平均の速さを、体を運ぶ速さから引いたもの(Program.MeasureFootSlip)。0 なら止まって見える。0 から少し外れるのは、腰の高さの比が脚の長さの比と同じではないから(AvatarSample_A は代役より脚が少し短い)。走りほど歩幅が大きいので、ずれも大きく出る。

5. 速さで混ぜる — Day 42 の木と位相合わせ

3本は Day 42 の BlendTree1D に、アバターでの速さをしきい値として並べる。速さが 2 本のしきい値の間なら、その2本を距離の比で混ぜる。

位相は合わせる(Day 42 の要点)。歩きの 1.1 秒と走りの 0.7 秒を別々に回すと、混ぜている間に「歩きの左足が前」と「走りの右足が前」が重なり、脚が4本あるように見える。合わせると2本は同じ「1 周のどこか」で読まれ、周期は重みで混ぜた長さ(50:50 なら 0.90 秒)になる。速さを上げるほど歩調が詰まるのは、この1行だけで手に入る。

Day 71 の VRMA の切り替えは位相を合わせない(入ってくるクリップを頭から流したい)。同じ AnimationPlayer を両方に使うので、VrmAvatar.PlayBlend が SyncPhase = true を立て、UpdateAnimation(Day 71)が false に戻す。

速さは寄せる。F4 で選んだ速さへ、1 秒に 4 m/s までの割合で近づける。一気に変えると、重みも1フレームで飛ぶ(Day 51 のキャラクターも加速度を持つ)。

6. 前提: ファイルの休みの姿勢は T ポーズ

正規化の式は「休みの姿勢からどれだけ回ったか」を写す。だからファイルの休みの姿勢とアバターの休みの姿勢が同じ形であることが前提になる。VRM 1.0 のアバターは T ポーズで書き出す決まりで、Mixamo の既定のキャラクター(Y Bot)も T ポーズだ。

休みの姿勢の腕が下がっているファイルでは、腕を下ろす動きが「ほとんど回っていない」と測られ、アバターの腕は T ポーズのまま残る。式は正しく働いていて、前提のほうが崩れている。そこで読み込みのときに、ファイルの休みの姿勢で左の上腕が水平から何度垂れているか(MixamoClip.ArmDroopDegrees)を測り、10 度を超えたら知らせる。

これは作り話ではない。今日、代役を Blender で FBX に書き出して fbx_to_glb.py で戻したところ、Blender の glTF の読み込みが 1 コマ目の姿勢を休みの姿勢にしてしまい、腕が 72 度垂れた休みの姿勢になった。流すと腕が T ポーズのまま歩く(下の設計書「試して分かったこと」)。Mixamo から落とすときに With Skin を選ぶのはこのためで、スキンのバインドポーズ(T ポーズ)が休みの姿勢になる。

試して分かったこと

  • 最初の「足が滑らない速さ」の測り方は間違っていた。代役の速さを「足首がいちばん低いコマ」の速さの平均で求めたら、歩き 0.57 m/s・走り 4.6 m/s という変な値になった。腰が上下するので、振り出しの終わり(足が前へ動いているコマ)まで「接地」に数えて打ち消し合っていた。「足首が腰に対して後ろへ動いている半周」の平均に変えて 1.10 / 2.69 m/s になった。C# の MeasureFootSlip も同じ測り方
  • Blender の glTF の書き出しは、骨1本ずつ別のアニメーションに割ることがある。代役を FBX に書き出して戻したら 13 本に割れていた。アクションごと(ACTIONS)でもシーンの時間軸(SCENE)でも同じだった。読む側で「狙うノードが重ならないならまとめる」(MixamoClip.Merge)を足した。Mixamo の本物の FBX(1ファイル1テイク)なら割れないはずだが、ほかの道具を通したファイルでも読めるようにしておいた
  • Blender の書き出しは 1 コマ目から始まる(時刻が 0 ではなく 1/24 秒など)。そのまま流すと、ループの頭に1コマぶん止まる間ができる。全部のキーを頭のキーの時刻だけ前へずらす(MapTimed の shift)
  • 往復させたファイルは T ポーズでなくなった。Blender の glTF の読み込みが 1 コマ目の姿勢を休みの姿勢にするので、腕が 72 度垂れた。流すと、腕だけ T ポーズのまま歩く(要点6)。読み込みのときの「腕の垂れ」の確かめで、すぐ気づけた
  • 正規化を切るとアバターが消える。Day 71 の VRMA(m で書かれている)では「足が浮く」程度だったが、Mixamo は cm なので腰が 90m 上へ飛ぶ。単位を直していたのも正規化の道(腰の親の休みの世界行列)だった
  • 名前がぶつかった。Day 42 の Fox のブレンド木が _locomotion などの名前をすでに使っていたので、今日のものには Vrm を付けた

改造課題

課題1(易): しきい値を脚の長さの比で決める

今日残した歪みの1つ目。MixamoClip.AvatarSpeed の「腰の高さの比」を、脚の長さの比(leftUpperLeg → leftLowerLeg → leftFoot の休みの世界の位置の距離の和を、ファイルとアバターで比べたもの)に変える。F11 の内訳の「足の滑り」が、走りでも 0 に近づくかを見る。腰の移動の縮尺(Day 71 の HipsScale)は変えないこと——腰の高さは床から測った値なので、そちらは腰の高さの比のままが正しい。

課題2(中): 抜いた直線の向きを「前」にする

今日残した歪みの3つ目。MixamoClip.Drift の水平の向きから角度 atan2(d.x, d.z) を出し、そのクリップの「進む向き」として持つ。円を歩くときの置き場所の向きを、木の重みで混ぜた進む向きだけ戻す(体を進む向きと逆に回す)。確かめるには、make_honya_locomotion.py の歩きの腰の移動を斜め(x にも速さを足す)にした glb を作って walk として置き、直す前は体が円の接線から斜めを向いて歩くこと、直したあとは接線を向くことを見る。

課題3(難): ルートモーションで運ぶ

設計書の2つ目の表の右側。根の移動を抜かずに読み(F5 の「残す」)、毎フレーム「腰の水平の位置の、前のフレームからの差」を取り出して円の上の進みに使い、取り出した分を腰から引いて描く。ループの頭で腰が引き戻される1フレームは、差が 1 周ぶん負になるので捨てる(1 周で進む距離を足す)。足は原理的に滑らなくなるが、F4 で速さを選べなくなる(進む速さはクリップが決める)。Day 73b でカプセルに運ばせるときに、どちらが向いているかを考えてみる。

検証の途中で分かったこと

  • 代役の速さは脚から求めると決まる。手で決めた速さ(最初は歩き 1.35 m/s)だと、アバターに当てたときの足の滑りがクリップの出来に左右される。脚の動きから速さを求めて腰を進めれば、根の移動の傾きと足の動きが必ず釣り合い、自己チェックで「足が止まる」を確かめられる
  • ブレンド木は、点のちょうど上で2本を返す(「歩き 1.0 + 走り 0.0」)。Day 42 の BlendTree1D の作りで、SetBlend が重み 0 の項を捨てるので害は無い。自己チェックは本数ではなく重みで見た
  • 根の移動を残したクリップでは、足の滑りの物差しが使えない(地面を蹴っている半周を「足首が後ろへ動くコマ」で見分けているので、腰ごと前へ進むと見分けられない)。残したときの様子は、腰の継ぎ目(1 周で 1.211m)のほうで確かめた
  • コンソールに「〜」を出すと化ける(CP932)。表示の文字列では使わない(Day 69〜72 と同じ)
