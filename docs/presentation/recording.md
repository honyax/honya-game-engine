# 発表用動画の撮影: ツール化の設計

スライド([slides.html](slides.html))に貼る各 Day の動画(`media/*.mp4`)を、スクリプトで撮るための設計。

## 決まったこと

| 項目 | 決定 |
|---|---|
| 方式 | **B. エンジンの中で撮る**(描いた絵をアプリ自身が読み出して ffmpeg に流す) |
| 画質 | 1280x720・30fps・H.264(MP4)。WebM(VP9)と比べた結果は 4 章 |
| git | 動画はコミットする(発表は会社のノート PC で行うため)。作業用のコピー `.record/` だけを `.gitignore` に入れる |
| 守ること | **`reference/` のファイルは1行も書き換えない**(教材の答えを濁さない) |

## 1. 前提として調べたこと

| 項目 | 状況 | 設計への影響 |
|---|---|---|
| 録画の道具 | ffmpeg 8.0(`D:\opt\ffmpeg`)。`libx264` と `h264_nvenc` が使える | 生の画素を標準入力で受けて MP4 にする役だけを任せる |
| 窓と GL の持ち方(Day 14 以降) | どの Day も `Program` に `_window`(IWindow)・`_gl`(GL)・`_input`(IInputContext)の静的フィールドがあり、`_window.Render += OnRender` で描いている | 外から足したコードがリフレクションで `_window` を拾い、`Render` に後から登録すれば、**アプリの描画が終わった直後・画面に出す直前**の絵を読める |
| 素材の探し方 | `ResolveAssetPath` が、実行ファイルの場所から上へ `assets/` を探す | プロジェクトのコピーをリポジトリの中(`docs/presentation/.record/`)に置けば、素材はそのまま見つかる |
| 窓の大きさ | Day 14〜40 は 960x640、Day 42 以降は 1920x1080。Day 10 は 640x480 の WinForms | 16:9 でない窓は撮影前に 1280x720 へ変え、1920x1080 は ffmpeg で縮める。Day 10 は上下を切って拡大 |
| Day 10 の描画 | `Application.DoEvents()` を回す自前のループで、`Bitmap _backBuffer` に描いて転送している | 別スレッドから `Form.Invoke` で頼めば、フレームの合間(DoEvents の中)に `_backBuffer` を写せる。描きかけを読まない |
| 操作の入口 | Day 48 以降は、切り替えがすべてデバッグメニューにある(F1 でページ送り、F2〜 で各スイッチ)。移動は Day 20 の `InputSystem` がキーのイベントを受けて作る | 窓にキーのメッセージ(`WM_KEYDOWN` / `WM_KEYUP`)を送れば、メニューも移動もふつうに反応する |

試し撮りで分かった注意: 画面を外から撮る方式(A)は、窓が隠れると**後ろにある別のアプリがそのまま録画に入る**(試し撮りで実際に写ったので、ファイルは削除済み)。B は描いた絵を直接読むので、この心配がない。B を選んだ理由の1つ。

## 2. 仕組み

### 2-1. reference に触れずに録画を差し込む

```
reference/Day56/                    ← 触らない
   │ コピー(bin / obj を除く)
   ▼
docs/presentation/.record/Day56/    ← 作業用(.gitignore。撮り終えたら消す)
   ├─ (Day56 のファイル一式)
   ├─ PresentationRecorder.Common.cs   ← tools/Recorder.Common.cs
   └─ PresentationRecorder.Silk.cs     ← tools/Recorder.Silk.cs(Day 10 は Recorder.WinForms.cs)
```

差し込むファイルは `[ModuleInitializer]` を使う。これは **`Main` より前に1回だけ呼ばれる**関数で、元のコードのどこからも呼ばなくても動く。SDK 形式の csproj はフォルダ内の `.cs` を自動で拾うので、**csproj も書き換えずに済む**。環境変数 `HONYA_RECORD` が無ければ何もしないので、ふつうに起動したときは無害。

| ファイル | 役割 |
|---|---|
| `Recorder.Common.cs` | 撮影の表(JSON)を読む / キーの操作を時刻順に並べて窓へ送る / 1/30 秒の升目に合わせて絵を ffmpeg へ流す |
| `Recorder.Silk.cs` | Day 14 以降。`Program._window` が動き出すのを待って `Render` に後から登録し、アプリが描き終わった直後の絵を `glReadPixels` で読む |
| `Recorder.WinForms.cs` | Day 10。裏のスレッドから `Form.Invoke` で頼み、自前ループの `DoEvents` の中(= フレームの合間)で `_backBuffer` を写す |

### 2-2. 1フレームの読み出し(Silk.NET)

```
アプリの OnRender(描き終わる)
  → 差し込んだ処理(同じフレームの中)
       次の撮影時刻(1/30 秒刻み)を過ぎていれば:
         既定のフレームバッファから glReadPixels で RGB を読む
         ffmpeg の標準入力へ書く(別スレッド)
  → 画面に出す(SwapBuffers)
```

- ffmpeg 側: 生の画素を標準入力で受け、`vflip`(GL の原点は左下)と `scale=1280:720` をかけて `libx264` で圧縮する。`-movflags +faststart` を付ける(スライドで読み込みが早い)
- 窓の縦横比が 16:9 でない Day(Day 40 までは 960x640)は、撮影前の準備の間に窓を 1280x720 へ変える。黒い帯も拡大のぼけも出ない
- Day 10(640x480)は上下を切って 16:9 にし、画素が見えるよう最近傍で 2 倍にする
- **限界**: 時間は実時間で進む。アプリが 30fps を割る場面では、同じ絵が続いてカクついて見える(今回の 10 本では起きていない)

### 2-3. 操作の送り方

窓のハンドルに `WM_KEYDOWN` / `WM_KEYUP` を `PostMessage` で送る。

- GLFW(Silk.NET の窓の中身)も WinForms も、このメッセージからキーの状態を作る。なので **メニューの切り替え(押した瞬間)も、移動(押しっぱなし)も効く**
- **修飾キーも送れる**。Ctrl / Shift / Alt の押し下げを先に送ると、GLFW のキーの状態に入り、アプリの `IsKeyPressed(Key.ControlLeft)` などが true になる(Alt を含むときは `WM_SYSKEYDOWN` で送る)
- GLFW はキーをスキャンコードで見分ける。記号のキー(`;` `,` `.` `/`)は配列で仮想キーとの対応が変わるので、英語配列のスキャンコードを直接送る
- **マウスも送れる**(カメラを寄せる・回す)。ホイールは `WM_MOUSEWHEEL`、左ドラッグは `WM_LBUTTONDOWN` → `WM_MOUSEMOVE` を 1/60 秒おき → `WM_LBUTTONUP`。GLFW は**押した瞬間の位置だけを本物のカーソル(`GetCursorPos`)から取る**ので、ドラッグは本物のカーソルの位置を起点にした差で送る(起点がずれると最初の移動で差分が跳ね、カメラが裏返る。1 回目の試し撮りで実際に起きた)
- 窓が最前面でなくても届く。**撮影中に PC を触っても録画は壊れない**(ただしドラッグ中に本物のマウスを窓の上で動かすと、カメラが一緒に動く)

### 2-4. 撮影の表

`docs/presentation/tools/scenes.json` に1本ずつ書く(下は day56 の例)。

```json
{
  "name": "day56",
  "day": "Day56",
  "out": "day56.mp4",
  "warmup": 12,
  "seconds": 12,
  "keys": [
    { "at": -5.0, "tap": "semicolon", "times": 3 },
    { "at": -4.0, "tap": "F1", "mods": ["Shift"] },
    { "at": -3.0, "tap": "F2" },
    { "at": 0.0, "down": "Up" },
    { "at": 2.5, "down": "X" },
    { "at": 11.9, "up": "Up" }
  ]
}
```

| 項目 | 意味 |
|---|---|
| `warmup` | 起動してから撮り始めるまでの秒数(素材の読み込みとシェーダのコンパイルを待つ) |
| `seconds` | 撮る長さ |
| `crf` | 省略可。絵が細かくて重くなる場面だけ画質を少し落とす(既定 20) |
| `keys[].at` | 撮影開始からの秒数。負の値は撮影前の準備(ページの切り替えなど) |
| `keys[].tap` / `times` / `every` | 押して離す。`times` 回、`every` 秒おき |
| `keys[].down` / `up` | 押しっぱなしの開始と終わり |
| `keys[].mods` | 一緒に押す修飾キー(`Ctrl` / `Shift` / `Alt`) |
| `keys[].wheel` | ホイールの目盛り(正で寄る) |
| `keys[].drag` / `duration` | 左ドラッグの移動量 `[dx, dy]`(画素)と、かける秒数。横でカメラが回り、縦で見下ろす角度が変わる |
| `crop` | 省略可。縮める前に切り抜く範囲(ffmpeg の `crop` の引数)。消せない画面上の表示を外すときに使う |

### 2-5. 本体のスクリプト

`docs/presentation/tools/record.ps1`(`.vscode/run.ps1` と同じく PowerShell)。

```
record.ps1 day56                … 1本だけ撮る
record.ps1 -All                 … 表の全部を撮る
record.ps1 day40 -Keep          … 撮影後も作業用コピーを残す(調べたいとき)
record.ps1 day40 -Format vp9    … 形式を変える(h264 / vp9 / lossless)
record.ps1 day40 -OutDir <dir>  … media/ 以外へ出す(比較用)
```

1本ごとに、コピー → 差し込みを置く(csproj の `UseWindowsForms` で WinForms 版かを選ぶ)→ Release でビルド → 起動して撮影 → `ffprobe` で解像度と長さを確かめる → コピーを消す、の順に行う。

## 4. 試して分かったこと

- **形式の比較**(day40 を無劣化で撮り、そこから書き出して SSIM で比べた): 同じ画質での大きさは H.264 と VP9 でほぼ同じ(この映像では H.264 がわずかに小さい)。VP9 は書き出しが数倍遅い。H.264 の特許料を払うのはデコーダを配る側なので、動画を作って使う側には費用が発生しない。再生できる場所の広さで MP4 を選んだ。VS Code のプレビューでは H.264 が再生できない(Electron が独自コーデックを外して配布しているため)が、発表は Chrome / Edge で開くので問題ない
- **day30 の早送り**: End は「止まったまま 30 秒進める」ので、4 回(2 分)飛ばすとプレイヤーが倒される。3 回にした
- **day30 の敵の数**: 1 分 30 秒〜1 分 45 秒の画面に映るのは 50 体前後。数百体になるのはもっと後半
- **同じフレームの連続**: day40 では 360 枚中 34 枚が完全に同じだったが、すべてカメラがショットの区切りで止まりかける区間に固まっている。取りこぼしではない
- **試し撮りの注意**: 画面を外から撮る方式(A)は、窓が隠れると後ろの別のアプリが録画に入る(実際に写ったのでファイルは削除済み)。B を選んだ理由の1つ

## 5. 静止画(機能の ON / OFF を並べるページ)

13 枚目「後処理は、それぞれ何をしているか」と 15 枚目「材質と光は、それぞれ何をしているか」に貼る静止画を撮る仕組み。動画と同じ差し込みを使い、**同じ動画の中で機能を切り替えて**、その前後の1コマを切り出す。構図が揃うので、違いが機能だけになる。

```
stills.ps1 ssao     … stills.json の name が ssao の1つだけ撮る
stills.ps1 -All     … 表の全部を撮る(負荷が高いので、1つずつ撮るのをすすめる)
```

- `record.ps1 -SceneFile stills.json -Format lossless` で短い動画を無劣化で撮り、`shots` に書いた時刻の1コマを JPG(960 幅)にして `media/stills/` に出す。撮り終えた動画は消す
- `shots[].crop` で一部を切り出せる。拡大は既定で最近傍(画素を見せる)、`flags: "lanczos"` で滑らかに
- `record.ps1` はアプリのコンソール出力を作業用コピーの `stdout.log` に残す(`-Keep` のとき、キーが効いたかの確かめに使える。文字コードは CP932)

| ページ | 項目 | 左 / 右 | 場面と撮り方 |
|---|---|---|---|
| 13 | SSAO | 暗がりだけ / 重ねた絵 | デモ v1 の決めの構図。「AO の表示」で遮蔽バッファ → 3 回押して元に戻し、0.7 秒あけて重ねた絵 |
| 13 | ブルーム | OFF / ON | Day 56 の最終デモの「眺める」を最初のショット(街灯とネオン)で一時停止。街灯とネオンのまわりを切り出す |
| 13 | トーンマッピング | なし / ACES | ブルームと同じ場面・同じ撮影 |
| 13 | FXAA | 縁と判定した画素(赤) / 仕上がり | デモ v1。「FXAA の表示」を 2 回で縁の検出、さらに 2 回で元に戻す |
| 15 | ② 影 | OFF / ON | デモ v1 |
| 15 | ③ 法線マップ | OFF / ON | PBR ページの「材質テスト」(レンガの板) |
| 15 | ④ PBR | ランバート(PBR 前) / Cook-Torrance | 材質グリッド(縦が金属度、横が粗さ)。グリッドのまわりを切り出す |
| 15 | ⑤ IBL | OFF / ON | デモ v1 |
| 15 | ⑥ PCF | 半径 0 / 半径 3 | デモ v1。柵の影の縁を 3 倍に拡大 |

### 試して分かったこと

- **Day 56 の場面を無劣化で撮っている最中に、PC が 2 回強制終了した**。重い場面と無劣化の書き出しが重なると厳しい。Day 48 で撮れるものは Day 48 で撮り、1 回に 1 項目ずつ撮るようにした(以降は落ちていない)
- **比べる 2 枚は、間を空けずに続けて撮る**。撮影中に本物のマウス(ホイール・ドラッグ)が窓に届くとカメラが動くことがあり、間が長いと構図がずれる。撮影中はマウスを窓から離しておく
- **PCF の半径の初期値**: デモ v1 の決めの構図は機能を全部 ON にするときに PCF を半径 2 にする(既定値の 1 ではない)。「PCF」は 0 → 1 → 2 → 3 と進むので、2 回で 0、さらに 3 回で 3
- **PBR を切ったときはランバート**: デバッグメニューの説明文は「Cook-Torrance と Blinn-Phong」だが、実際に切り替わるのはランバート(拡散だけ)。スライドのラベルは「ランバート(PBR 前)」にした
- **FXAA は拡大より「縁の検出」で見せる**: OFF / ON を 8 倍に拡大しても分かりにくかった。「赤い画素だけが処理される」表示のほうが、画面全体にかけて縁だけに効くことが一目で伝わる
- **トーンマッピングは露出を上げると逆効果**: 露出を約 2.9 倍にすると、ACES は明るい所を白に寄せるので「なし」より白っぽく見え、狙い(なしは白飛び、ACES は残る)と逆の絵になった。通常の露出の夜の場面(全体の色味と締まりの差)を使う
