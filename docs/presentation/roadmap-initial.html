セットアップ手順(Day 1の冒頭にやること):

  2. VSCodeに C# Dev Kit 拡張とGLSL系拡張を導入
  3. GitHubにリポジトリを作成し、5章の構成で初期化

2. フェーズ別ロードマップ

週末1日×週1回ペース想定。各フェーズに「動くもの」のマイルストーンを置いています。

Phase 0: 環境と土台(1日)

  • .NET 8+ コンソール/WinFormsプロジェクト作成。WriteableBitmap または WinFormsの Bitmap + LockBits で、自前のピクセルバッファを毎フレーム画面に転送するループを作る。
  • マイルストーン: 640x480のバッファに毎フレーム色を書き、60fpsで表示される。

Phase 1: ソフトウェアラスタライザ(6〜8日) — グラフィックス初歩の本丸

学ぶ内容がそのままグラフィックスの教科書になります。順に:

  1. 線分描画(Bresenham)、三角形の塗りつぶし(エッジ関数 or スキャンライン)
  2. バリセントリック座標と頂点属性の補間(色、UV)
  3. 行列変換: モデル→ワールド→ビュー→透視投影→スクリーン。ここで同次座標と透視除算を体で理解する
  4. Zバッファ(深度テスト)
  5. テクスチャマッピング(ニアレスト→バイリニア)
  6. シェーディング: フラット→グーロー→フォン。ランバート拡散+スペキュラ
  7. 背面カリング、簡単なクリッピング
  8. objファイルを読み込んでモデル表示
  9. マイルストーン: 回転するテクスチャ付きモデルがライティング付きで表示される。
  10. 参考: tinyrenderer(C++だが考え方はそのまま移植可)、Scratchapixel

Phase 2: 生OpenGLバインディング体験(2〜3日) — Silk.NETの中身を一度だけ自作

  1. Win32 API(CreateWindowEx、メッセージループ)をP/Invokeでウィンドウ生成
  2. wglCreateContext → モダンコンテキストの取得、wglGetProcAddress で関数ポインタ取得
  3. VBO/VAO/シェーダーコンパイルを生関数で呼び、三角形を1枚出す
  4. マイルストーン: 自作バインディングだけで、シェーダーで色づけした三角形が出る。
  5. ここで「Silk.NETが何を代行しているか」が完全に分かるので、以降は堂々とSilk.NETを使う。

Phase 3: レンダラ層の自作(4〜6日) — Silk.NET上に構築

Phase 1で理解した概念がGPU側でどう対応するかを確認しながら:

  1. シェーダー管理(コンパイル、uniform設定のラッパー)
  2. メッシュ/テクスチャ/マテリアルの抽象化
  3. カメラ(ビュー・プロジェクション行列は Phase 1 の知識そのまま)
  4. 2Dスプライトバッチ(動的頂点バッファ、テクスチャアトラス、描画順ソート)
  5. マイルストーン: スプライトを1万枚、1ドローコール群で描けるSpriteBatch。

Phase 4: エンジンコア(6〜8日)

  1. ゲームループ設計: 固定タイムステップ + 補間(Glenn Fiedler "Fix Your Timestep" 参照)
  2. 入力システム(ポーリング+イベント、キーコンフィグ)
  3. リソース管理(参照カウント or ハンドルベース、非同期ロード)
  4. シーン/エンティティ: まずシンプルなGameObject+Componentで作り、その後ECSに書き換えると両者の設計理由が分かる
  5. 数学ライブラリは System.Numerics を使いつつ、Phase 1で自作した行列と突き合わせる
  6. マイルストーン: シーンをロードし、コンポーネント付きエンティティが動く。

Phase 5: ゲームが作れる状態に(4〜6日)

  1. 2D衝突判定(AABB→円→分離軸)、簡易物理(重力、レスポンス)
  2. オーディオ(Silk.NET.OpenALか、まずは再生だけNAudioでも可)
  3. テキスト描画(stb_truetypeのC#移植 or ビットマップフォント)
  4. 卒業制作: このエンジンでブロック崩しか小さなシューティングを1本完成させる

Phase 6(任意): モダングラフィックスへ

  • ライティングの発展: 法線マップ、シャドウマップ、ディファードレンダリング
  • ここまで来てからUE5を触ると、Nanite/Lumenが「何を解決しているか」が明確に分かり、UE5学習の効率が別物になる。

  3. 写経後の改造課題(理解確認用。例: 「ワイヤーフレーム表示を追加せよ」)

補足A: 前提 — 「どこまで自作できるか」の物理的な下限

ソフトウェアで自作可能な最下層は OSのAPI(ウィンドウ生成・入力)と、GPUドライバが公開するグラフィックスAPI(OpenGL / D3D / Vulkan)を直接呼ぶところまで です。それより下(GPUドライバ、GPUハードウェア)はどうやっても自作できません。

ただし例外が1つあります。GPUを使わず、CPUだけで全ピクセルを計算する「ソフトウェアラスタライザ」 なら、グラフィックスパイプラインそのものを自作できます。これが「グラフィックスの初歩的な技術の理解」に最も効く選択肢です。

補足B: 比較検討 — フルスクラッチ vs Silk.NET vs MonoGame

結論(採用した構成):

  • Silk.NETやMonoGameの「担っている部分の自作」は可能。ただし種類が違う。
    • MonoGameが担う部分(スプライトバッチ、コンテンツパイプライン、描画抽象化)→ 自作する価値が高い。これがまさに「エンジン自作」の本体。
    • Silk.NETが担う部分(OpenGL関数のバインディング、ウィンドウ生成)→ 自作は可能だが、中身は [DllImport("opengl32.dll")] と wglGetProcAddress の書き写し作業が大半で、学びの密度が低い。一度Phase 2で「儀式」として体験し、以降はSilk.NETに任せるのが効率的。
  • したがって A(原理の理解)→ B(儀式を一度だけ体験)→ C(Silk.NET上にエンジン本体を自作) の順を採用。MonoGameは「答え合わせ用の参照実装」として読む。
