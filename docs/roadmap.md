# 自作ゲームエンジン ロードマップ(C# / 低レイヤ重視)

対象: C#メイン・ゲーム開発経験20年のエンジニアが、週末ペースでエンジンとグラフィックスの基礎を「なるべく低いレイヤから」自作して理解するためのロードマップ。

開発環境・ビルド方法・リポジトリの構成は [README](../README.md) を参照。

---

## 1. 進め方: Day制の写経形式(「30日でできる!OS自作入門」方式)

各週末1日=1 Dayとし、**Dayごとに完動するリファレンスコードをAI側が作成し、それを写経→改造する**形式で進めます。各Dayの構成は以下:

1. その日のゴール(動くもの)と、事前に読む特論の回
2. リファレンスコード(依頼を受けてAIがその都度作成。前Dayからの差分が分かる形で)
3. 写経後の改造課題(理解確認用。例: 「ワイヤーフレーム表示を追加せよ」)

使い方: 各Dayを始めるときに「Day nのコードを作成して」と依頼してください。

**状態列の見方**: 「済」= `work/` への写経が完了したDay。空欄は未着手。`reference/DayXX` はPhase単位でまとめて先行作成するため、状態列とreferenceの有無は一致しない(referenceの作成状況は `reference/` を直接見る)。

## 2. フェーズ別ロードマップとDayプラン

週末1日×週1回ペース想定。各フェーズに「動くもの」のマイルストーンを置いています。Day 30までがエンジン本体の構築、Day 31以降がデモとしての作り込みです。

なお、ここまで自作してからUE5を触ると、Nanite/Lumenが「何を解決しているか」が明確に分かり、UE5学習の効率が別物になります。

### 3Dゲーム編(Day 41〜50) — キャラクターが動き回るプレイアブルデモへ

デモ必須編の直後に実施する。ゴールは「AAAクオリティのアセットの中をキャラクターが歩き/走り回れるデモ」。描画はDay 40までの機能で足りるため、ここではキャラクターアニメーション・物理・エフェクトを足す。

物理の対応プリミティブ: Sphere / Box(OBB) / Capsule / Plane / Heightmap。**Cylinderは対象外とし、Capsuleで近似する**(円柱の解析的衝突判定はエッジ・フチの例外処理だらけで工数対効果が悪く、実際のゲームエンジンでもカプセル近似が一般的。厳密に必要になったらconvex hull+GJKを発展課題として)。

## 補足A: 前提 — 「どこまで自作できるか」の物理的な下限

ソフトウェアで自作可能な最下層は **OSのAPI(ウィンドウ生成・入力)と、GPUドライバが公開するグラフィックスAPI(OpenGL / D3D / Vulkan)を直接呼ぶところまで** です。それより下(GPUドライバ、GPUハードウェア)はどうやっても自作できません。

ただし例外が1つあります。**GPUを使わず、CPUだけで全ピクセルを計算する「ソフトウェアラスタライザ」** なら、グラフィックスパイプラインそのものを自作できます。これが「グラフィックスの初歩的な技術の理解」に最も効く選択肢です。

## 補足B: 比較検討 — フルスクラッチ vs Silk.NET vs MonoGame

| 観点 | A. ソフトウェアラスタライザ自作 | B. P/Invokeバインディング自作 | C. Silk.NET | D. MonoGame |
|---|---|---|---|---|
| 自作するもの | 描画パイプライン全部(頂点変換〜ピクセル) | Win32/OpenGL関数のC#バインディング | GPUパイプラインの使い方・エンジン層 | エンジン構造(シーン、ECS等)のみ |
| ライブラリが担う範囲 | ほぼゼロ(画面へのblitのみOS API) | ゼロ(自分でDllImportを書く) | API バインディングとウィンドウ/入力 | 描画・音・入力の抽象化すべて |
| グラフィックス理解 | ◎ 原理を完全に理解できる | ○ APIの生の姿が分かる | ○ GPUの使い方は全部自分で書く | △ 描画の中身はブラックボックス |
| 実用性能 | × (学習専用。GPU不使用) | ○ | ○ | ○ |
| 難易度・罠 | 数学は重いがデバッグしやすい | wglContext生成やGetProcAddressの儀式が煩雑 | ほどよい | 簡単 |
| 週末換算の目安 | 6〜10日 | 2〜4日(儀式部分) | - | - |

**結論(採用した構成):**

- **Silk.NETやMonoGameの「担っている部分の自作」は可能**。ただし種類が違う。
  - MonoGameが担う部分(スプライトバッチ、コンテンツパイプライン、描画抽象化)→ **自作する価値が高い**。これがまさに「エンジン自作」の本体。
  - Silk.NETが担う部分(OpenGL関数のバインディング、ウィンドウ生成)→ 自作は可能だが、中身は `[DllImport("opengl32.dll")]` と `wglGetProcAddress` の書き写し作業が大半で、**学びの密度が低い**。一度Phase 2で「儀式」として体験し、以降はSilk.NETに任せるのが効率的。
- したがって **A(原理の理解)→ B(儀式を一度だけ体験)→ C(Silk.NET上にエンジン本体を自作)** の順を採用。MonoGameは「答え合わせ用の参照実装」として読む。
